9장이 트래픽을 보호하는 단계였다면, 10장은 데이터 플레인이 예상대로 동작하지 않을 때 **원인을 찾아 들어가는** 단계다. 이스티오가 네트워크 통신을 조명해 주는 덕분에, 요청이 어디서 끊기고 느려지는지 프록시·설정·로그를 따라가며 진단할 수 있다.

요청 라우팅에는 네 구성 요소가 참여한다(그림 10.1): ① **istiod** 가 데이터 플레인을 원하는 최신 상태로 동기화하고, ② **인그레스 게이트웨이** 가 트래픽을 클러스터로 들이고, ③ **서비스 프록시(사이드카)** 가 접근 제어·로깅을 하며, ④ **애플리케이션** 이 요청을 처리하고 다시 업스트림을 호출한다. 문제는 이 중 어디에서든 생길 수 있다.

> [!IMPORTANT]
> **버전 확인하기**: 책은 이스티오 **1.13**(엔보이 **1.20.x** 번들) 기준이다. `istioctl proxy-status`·`analyze`·`proxy-config` 같은 진단 명령은 최신에서도 동일하다. 단 두 가지가 달라졌다 — ① `istioctl x describe` 의 experimental 접두사 `x` 가 최신에선 **정식 명령**으로 승격됐고, ② **액세스 로그 활성화 방식**이 바뀌었다(뒤 10.3.3의 버전 노트 참고).

## 10.1 가장 흔한 실수: 잘못 설정된 데이터 플레인

이스티오는 서비스 프록시 설정을 사람이 읽을 수 있는 `VirtualService`·`DestinationRule` 같은 **CRD로 노출**하고, 그 설정으로 데이터 플레인을 바꾸도록 만들어졌다. 그래서 **가장 흔한 실수는 데이터 플레인을 잘못 설정하는 것**이다.

![그림 10.2 — 인그레스 게이트웨이가 catalog를 version-v1(20%)·version-v2(80%) 부분집합으로 라우팅](images/notes/istio-in-action/채영/10-2.catalog-subset-routing.png)

책의 예제(그림 10.2)는 인그레스 게이트웨이가 `catalog` 를 `version-v1`(20%)·`version-v2`(80%) **부분집합(subset)** 으로 나눠 라우팅한다. 그런데 부분집합을 정의하는 `**DestinationRule` 이 없으면**, 해당 부분집합의 클러스터가 존재하지 않아 모든 요청이 **503 Service Unavailable** 로 실패한다.

```bash
# 100번 반복 호출로 증상 확인 → 503이 쏟아진다
for i in {1..100}; do
  curl http://localhost/items -H "Host: catalog.istioinaction.io" \
    -w "\nStatus Code %{http_code}\n"
  sleep .5s
done
```

이 상태를 출발점 삼아, 원인을 좁혀 가는 도구들을 차례로 익힌다.

## 10.2 데이터 플레인 문제 식별하기

문제 식별의 첫 단추는 **컨트롤 플레인과 데이터 플레인이 동기화돼 있는지** 확인하는 것이다. 컨트롤 플레인 문제는 빠르고 넓게 전파되기 때문이다.

### 10.2.1 데이터 플레인이 최신 상태인지 확인하는 방법

데이터 플레인 설정은 **궁극적 일관성(eventually consistent)** 을 갖는다. 서비스·엔드포인트·상태 변화가 즉시 반영되지 않으며, 워크로드·클러스터가 커질수록 동기화에 걸리는 시간도 늘어난다(그림 10.3).

핵심 명령은 `**istioctl proxy-status**` 다. 각 프록시가 istiod가 보낸 xDS 설정(CDS·LDS·EDS·RDS)을 받았는지 상태를 보여준다.


| 상태           | 의미                                                                                |
| ------------ | --------------------------------------------------------------------------------- |
| **SYNCED**   | istiod가 보낸 마지막 설정을 엔보이가 확인함(정상).                                                  |
| **NOT SENT** | istiod가 아무것도 보내지 않음. 보통 **보낼 것이 없어서**이며 정상일 수 있다(예: `istio-egressgateway` 의 RDS). |
| **STALE**    | istiod가 보냈으나 **확인받지 못함**. istiod 과부하 또는 istiod↔엔보이 커넥션 문제를 시사.                    |


이 예제에는 STALE 워크로드가 없으므로, 문제는 컨트롤 플레인이 아니라 **잘못된 데이터 플레인 설정**이다. 다음 단계로 넘어간다.

### 10.2.2 키알리로 잘못된 설정 발견하기

```bash
istioctl dashboard kiali   # http://localhost:20001/kiali
```

- **Overview** 에서 `istioinaction` 네임스페이스의 오류 개수를 보여준다(그림 10.4).
- **Istio Config** 화면에서 문제 있는 `VirtualService` 에 경고 아이콘이 뜨고(그림 10.5), YAML 보기에서 잘못된 부분(subset)이 강조되며 마우스를 올리면 `**KIA1107 Subset not found**` 같은 메시지를 보여준다(그림 10.6).
- 키알리 검증(validation)은 존재하지 않는 부분집합 참조 등을 잡아준다. 워크로드가 예상대로 동작하지 않을 때 취해볼 만한 조치다.

### 10.2.3 istioctl로 잘못된 설정 발견하기

두 명령이 잘못된 설정을 자동으로 짚어준다.

**① `istioctl analyze`** — 이미 생긴 문제를 진단할 뿐 아니라, **클러스터에 적용하기 전** 파일 상태로 미리 검증할 수도 있다.

```bash
istioctl analyze -n istioinaction
# Error [IST0101] (VirtualService catalog-v1-v2) Referenced host+subset
#   in destination rule not found: "...svc.cluster.local+version-v1"
```

오류 코드(`IST0101`)와 온라인 문서 링크까지 안내한다.

**② `istioctl x describe pod`** — 워크로드 하나에 직간접적으로 영향을 주는 이스티오 설정을 요약한다. "이 워크로드가 메시에 속하는가 / 어떤 VirtualService·DestinationRule이 적용되는가 / 상호 인증을 요구하는가?" 에 답한다.

```bash
istioctl x describe pod <pod>
# Warning: Route to subset version-v1 but NO DESTINATION RULE defining subsets!
```

> [!NOTE]
> `istioctl x describe` 의 `x` 는 experimental 표시다. 최신 이스티오에서는 `istioctl describe` 로 **정식 승격**됐다.

## 10.3 엔보이 설정에서 수동으로 잘못된 설정 발견하기

자동 분석으로 부족하면 엔보이 설정 전체를 직접 조사한다. 설정은 **엔보이 관리 인터페이스** 또는 **istioctl** 로 얻는다.

### 10.3.1 엔보이 관리 인터페이스

모든 서비스 프록시는 포트 **15000** 에서 관리 인터페이스를 노출한다(설정 조회 + 일부 값 수정).

```bash
istioctl dashboard envoy deploy/catalog -n istioinaction   # http://localhost:15000
```

- `certs`(인증서), `clusters`(업스트림 클러스터 상태), `config_dump`(현재 설정 전체 덤프), `contention`(뮤텍스 경합) 등을 제공한다(그림 10.7).
- 단, `config_dump` 는 방대하다(예제에서 13,934줄). 그래서 필터링이 편한 **istioctl** 을 주로 쓴다.

### 10.3.2 istioctl로 프록시 설정 쿼리하기

`**istioctl proxy-config**`(약칭 `pc`)는 엔보이 xDS API를 기반으로 프록시 설정을 가져와 필터링한다. 하위 명령은 `cluster` · `endpoint` · `listener` · `route` · `secret` · `log` 다.

요청은 엔보이 안에서 다음 순서로 흐른다(그림 10.8). 이 흐름을 따라가며 어디서 끊겼는지 찾는 것이 수동 디버깅의 핵심이다.

```
다운스트림 → 리스너(IP·포트) → 루트(가상 호스트 매칭) → 클러스터(부분집합) → 엔드포인트(워크로드 IP) → 업스트림
```

- **리스너**: 다운스트림 트래픽을 받는 IP·포트. 허용된 커넥션에 HTTP 필터 체인을 만들고 마지막 필터가 라우터다.
  ```bash
  istioctl pc listeners deploy/istio-ingressgateway -n istio-system
  # 0.0.0.0  8080  ALL  Route: http.8080
  ```

  인그레스 게이트웨이는 **8080** 에서 리슨한다(서비스가 80→8080으로 매핑).
- **루트**: 가상 호스트를 클러스터에 매칭하는 규칙. 이스티오에서는 RDS로 동적 설정된다.
  ```bash
  istioctl pc routes deploy/istio-ingressgateway -n istio-system --name http.8080
  # NAME=http.8080  DOMAINS=catalog.istioinaction.io  MATCH=/*  VIRTUAL SERVICE=catalog...
  ```

  `-o json` 으로 보면 `weightedClusters` 에 `version-v2`(80) / `version-v1`(20) 가중치가 보인다.
- **클러스터**: 라우팅 대상 백엔드. 이름은 `**방향|포트|부분집합|FQDN**` 형식이다(그림 10.9).
  ```bash
  istioctl pc clusters deploy/istio-ingressgateway -n istio-system \
    --fqdn catalog.istioinaction.svc.cluster.local --port 80 --subset version-v1
  # → 결과 없음  ← 이것이 503의 원인 (부분집합 클러스터 미정의)
  ```

  해결은 `DestinationRule` 을 추가하는 것이다. 먼저 검증하고 적용한다.
  ```bash
  istioctl analyze ch10/catalog-destinationrule-v1-v2.yaml -n istioinaction   # 검증 통과
  kubectl apply -f ch10/catalog-destinationrule-v1-v2.yaml
  # 재조회 시 version-v1/v2 클러스터가 TYPE=EDS, DESTINATION RULE=catalog 로 나타남
  ```
- **엔드포인트**: 실제 요청을 처리하는 워크로드 IP.
  ```bash
  istioctl pc endpoints deploy/istio-ingressgateway -n istio-system \
    --cluster "outbound|80|version-v1|catalog.istioinaction.svc.cluster.local"
  # ENDPOINT=10.1.0.60:3000  STATUS=HEALTHY
  ```

> [!TIP]
> **실습으로 익히는 503 추적 흐름 — 요청을 따라 내려가며 "설정이 사라지는 지점" 찾기**
>
> 1. `istioctl proxy-status` → 전부 **SYNCED** (컨트롤 플레인 문제 아님 → **설정 자체**를 의심)
> 2. 키알리 → `**KIA1107 Subset not found**`
> 3. `istioctl analyze` → `**IST0101**` (없는 host+subset 참조)
> 4. `istioctl pc routes` → v1/v2 가중치 라우팅은 **있음** (여기까진 정상)
> 5. `istioctl pc clusters --subset version-v1` → **결과 없음** ← 설정이 끊긴 지점 = 원인
> 6. `DestinationRule` 적용 → 클러스터·엔드포인트 생성 → **해결**
>
> 리스너→루트→클러스터→엔드포인트 순으로 내려가다, **정상적으로 나오던 설정이 처음으로 비는 곳**이 곧 범인이다.

### 10.3.3 애플리케이션 문제 트러블슈팅하기

설정이 맞아도, **간헐적으로 느린 워크로드** 처럼 애플리케이션 쪽 문제가 남을 수 있다. 책은 `catalog` v2에 지연을 주입하고 `VirtualService` 에 **0.5초 타임아웃**을 걸어(그림 10.10), 일부 요청이 **504 Gateway Timeout** 이 나는 상황을 만든다. 이를 액세스 로그로 조사한다.

**엔보이 액세스 로그** — 기본은 TEXT 형식이다.

```bash
kubectl -n istio-system logs deploy/istio-ingressgateway | grep 504
# ... "GET /items HTTP/1.1" 504 UT ...     ← UT = 타임아웃 응답 플래그
```

> [!IMPORTANT]
> **버전 차이 — 액세스 로그 활성화 방식**
>
> - **책(1.13)**: 액세스 로그는 `**demo` 프로파일에서만** 기본 출력된다. 다른 프로파일이면 `istioctl install --set meshConfig.accessLogFile="/dev/stdout"` 로 켜야 한다. 형식은 `--set meshConfig.accessLogEncoding="JSON"` 으로 JSON화해 가독성을 높인다.
> - **최신**: 메시 전체 대신 **Telemetry API**(`kind: Telemetry` 의 `accessLogging`)로 네임스페이스·워크로드 단위로 켜는 방식이 표준이다. 메시 전체에 켜면 로그양이 급증하니 주의.

JSON 로그의 주요 필드: `response_code`, `**response_flags**`(예: `UT`), `upstream_host`(요청을 받은 업스트림), `duration`. **응답 플래그** 는 커넥션이 왜 실패했는지 알려주는 열쇠다.


| 플래그    | 의미                             |
| ------ | ------------------------------ |
| **UT** | 업스트림 요청 타임아웃(upstream timeout) |
| **NR** | 설정된 루트 없음(No Route)            |
| **UC** | 업스트림 커넥션 종료                    |
| **DC** | 다운스트림 커넥션 종료                   |


(책이 소개하는 네 가지다. 전체 목록은 엔보이 공식 문서에 있다.)

**프록시 로그 레벨 높이기** — 더 깊이 봐야 하면 로거별 레벨을 올린다.

```bash
istioctl pc log deploy/istio-ingressgateway -n istio-system   # 현재 로거 목록(기본 warning)
istioctl pc log deploy/istio-ingressgateway -n istio-system \
  --level http:debug,router:debug,connection:debug,pool:debug
```

로거 이름이 곧 엔보이의 기능 영역이다 — `connection`(4계층 TCP), `http`(7계층 HTTP), `router`(요청 라우팅), `pool`(업스트림 커넥션 풀). 레벨은 `none/error/warning/info/debug`. 디버그 로그를 따라가면 느린 업스트림 IP가 액세스 로그의 `upstream_host` 와 일치함을 확인하고, 타임아웃 시 `client disconnected`(클라이언트가 요청을 끊음)까지 짚을 수 있다.

### 10.3.4 ksniff로 네트워크 트래픽 검사

프록시가 정말 커넥션을 끊는지는 파드의 네트워크 트래픽을 직접 봐야 확실하다.

- **ksniff**: `tcpdump` 로 파드 트래픽을 잡아 **와이어샤크** 로 넘겨주는 kubectl 플러그인. 플러그인 관리자 **Krew** 로 설치한다.

```bash
kubectl krew install sniff
kubectl sniff -n istioinaction <slow-pod> -i lo   # -i lo: 로컬호스트 인터페이스
```

- 와이어샤크에서 `http contains "GET /items"` 로 필터링(그림 10.12)하고, 관심 패킷을 우클릭 → **Follow → TCP Stream** 으로 커넥션 시작~종료 흐름 전체를 본다.
- 스트림 색은 방향·상태를 뜻한다(그림 10.13): **회색**=커넥션 성립/종료(SYN·ACK·FIN), **파란색**=서버로 가는 트래픽, **보라색**=클라이언트로 오는 트래픽, **빨간색**=오류·비정상 종료(RST).

> [!NOTE]
> **TCP 제어 플래그**: **SYN**(새 커넥션 시작), **ACK**(수신 확인), **FIN**(정상 종료 요청), **RST**(비정상 강제 종료). 이 네 가지만 알면 스트림에서 "누가 먼저 끊었는지"를 읽을 수 있다.

## 10.4 엔보이 텔레메트리로 자신의 애플리케이션 이해하기

로그·패킷을 뒤지기 전에, 7장에서 프로메테우스에 쌓은 메트릭으로 **실패율을 빠르게 조망**할 수도 있다.

### 10.4.1 그라파나에서 실패한 요청 비율 찾기

`prom-grafana` 를 포트포워딩하고 **Istio Service Dashboard** 에서 `catalog` 서비스를 본다.

- **Client Success Rate = 71.6%**(그림 10.14) — 요청의 약 30%가 실패로 보고된다.
- **Server Success Rate = 100%**(그림 10.15) — 정작 서버는 문제를 모른다.

> [!WARNING]
> **왜 클라이언트와 서버 성공률이 다른가 (7·8장 `reporter` 연결)**
> 엔보이는 업스트림이 끊긴 커넥션을 서버 쪽 지표에는 5xx가 아닌 코드로 기록해, **서버(`reporter=destination`)의 성공률은 100%로 유지된다.** 반면 **게이트웨이/클라이언트(`reporter=source`)** 는 이를 **504 Gateway Timeout**(응답 플래그 **UT**)으로 잡아 실패로 센다. 한편 목적지(catalog) 측은 게이트웨이가 커넥션을 끊은 것을 **응답 플래그 DC**(다운스트림 커넥션 종료)로 기록하는데(그림 10.16), 다음 절의 프로메테우스 쿼리가 바로 이 `reporter="destination"` + `DC` 를 집계해 문제 파드를 찾는다.

### 10.4.2 프로메테우스를 사용해 영향받는 파드 쿼리하기

그라파나로 부족하면 프로메테우스에 직접 질의해 **어느 파드가 범인인지** 좁힌다. `reporter="destination"`, 서비스가 `catalog`, 응답 플래그 `DC` 인 요청을 파드별로 집계한다.

```promql
sort_desc(sum(irate(
  istio_requests_total{
    reporter="destination",
    destination_service=~"catalog.istioinaction.svc.cluster.local",
    response_flags="DC"}[5m]))
by (response_code, kubernetes_pod_name, version))
```

결과를 보면 `version-v2` 인스턴스 두 개 중 **한 파드만** 실패를 보고한다(그림 10.17) — 범인이 특정됐다.

> [!NOTE]
> **파드를 갈라 보려면 `kubernetes_pod_name` 디멘션이 필요하다 (7장 연결)**
> 이 쿼리는 표준 메트릭에 이미 있는 `kubernetes_pod_name`·`version` 라벨로 파드를 나눈다. 만약 내가 나누고 싶은 기준이 표준 메트릭에 **없다면**, 7장에서 다룬 것처럼 **디멘션(라벨)을 커스터마이징**해 추가해야 한다. 관찰 가능성 설계(7장)가 트러블슈팅(10장)에서 이렇게 쓰인다.

> [!TIP]  
> **파드를 삭제하지 않고 레이블을 지우는 이유**  
> 문제가 있는 파드를 찾았을 때는 `kubectl delete pod` 로 삭제하는 대신, 파드의 레이블(예: `app: catalog`)을 제거하는 편이 낫다.
>
> - **삭제는 되돌아온다**: 쿠버네티스는 선언적으로 동작한다. Deployment(ReplicaSet)의 목표는 "지정한 수의 파드를 유지하는 것"이므로, 파드를 삭제해도 컨트롤러가 곧바로 동일한 파드를 다시 생성한다. 문제도 그대로 재현되고, 조사에 필요한 로그·상태도 사라진다.
> - **레이블 제거는 대상에서 제외한다**: 레이블을 지우면 파드가 셀렉터와 더 이상 일치하지 않는다. 컨트롤러는 관리 대상이 아니라고 판단해 그 파드를 그대로 두고, 지정한 수를 채우기 위해 정상 파드를 새로 하나 생성한다.
> - **서비스에서도 함께 빠진다**: 쿠버네티스 서비스도 같은 레이블 셀렉터로 대상을 고른다. 따라서 레이블을 지운 파드는 서비스 Endpoints에서 제외되고, istiod가 이 변경을 데이터 플레인에 전파해 더 이상 트래픽이 전달되지 않는다.
>
> 정리하면 레이블은 **컨트롤러의 관리 대상과 서비스의 트래픽 대상을 동시에 결정하는 기준**이다. 레이블을 제거하면 트래픽은 차단되지만 파드는 살아 있으므로, 격리된 상태에서 원인을 계속 조사할 수 있다.
>
> ```bash
> kubectl label pod <문제-파드> -n istioinaction app-   # app 레이블 제거 → 서비스·컨트롤러 대상에서 이탈
> ```

## 요약

- 진단은 **동기화 확인 → 자동 분석 → 수동 조사** 순서로 좁혀 간다.
- `**istioctl proxy-status**`: 데이터 플레인 동기화 상태 개요(**SYNCED / STALE / NOT SENT**).
- `**istioctl analyze**`: 메시 설정을 분석한다. **클러스터 적용 전** 파일 상태로도 검증할 수 있다.
- `**istioctl x describe pod**`: 워크로드에 적용된 이스티오 설정을 요약·검증한다.
- `**istioctl proxy-config**`(`pc`): `리스너 → 루트 → 클러스터 → 엔드포인트` 흐름을 따라 엔보이 설정을 조회한다. 이 장의 예제에서는 빠진 `DestinationRule` 때문에 부분집합 클러스터가 없어 503이 났다.
- **키알리 검증** 으로 흔한 설정 실수(없는 subset 참조 등)를 잡는다.
- **액세스 로그의 응답 플래그**(UT·UH·NR·UC·DC)로 실패 원인을 구분하고, `istioctl pc log` 로 로그 레벨을 올려 깊이 파고든다.
- 필요하면 **프로메테우스 메트릭** 으로 영향받는 파드를 특정하고, **ksniff+와이어샤크** 로 실제 패킷까지 확인한다.
