지금까지는 **하나의 클러스터** 안에서 이스티오를 다뤘다. 12장은 시야를 넓혀, 서비스 메시를 **여러 클러스터에 걸쳐** 확장한다. 메시의 가치는 워크로드가 많을수록 커지고, 서비스 메시는 특정 클러스터에 종속되지 않는다. 가상의 ACME사가 온프레미스에서 클라우드로 옮겨 가는 시나리오를 따라, 두 클러스터를 하나의 메시로 묶는 과정을 실습한다.

> [!IMPORTANT]
> **버전 확인하기**: 책은 이스티오 **1.13**, 실습은 **Azure(AKS)** 기반이다. 원격 클러스터 시크릿 명령이 책에선 `istioctl x create-remote-secret`(experimental)인데, 최신에선 **`istioctl create-remote-secret`** 으로 정식 승격됐다. 네트워크 지정도 `MeshNetwork` 대신 **`topology.istio.io/network` 네임스페이스 라벨**(1.8+) 방식을 쓴다.

## 12.1 다중 클러스터 서비스 메시의 이점

클러스터 간 통신에서 얻는 이점은 네 가지다.

| 이점 | 설명 |
| --- | --- |
| **가용성(availability)** | 한 클러스터가 사고·급증으로 다운돼도 다른 클러스터로 장애 조치(failover). |
| **격리(isolation)** | 한 팀의 워크로드가 다른 팀 운영에 영향을 주지 않도록 성능·장애를 격리. |
| **규모(scale)** | 단일 클러스터 한계를 넘어, 클러스터 수를 늘려 워크로드를 확장. |
| **규정 준수** | 규제에 따라 특정 워크로드·데이터를 분리해 배치. |

그리고 다중 클러스터에서도 **코드 변경 없이** 이스티오의 기능(세밀한 트래픽 관리, mTLS 상호 인증, 인가 정책)이 클러스터 경계를 넘어 그대로 동작한다.

## 12.2 다중 클러스터 서비스 메시 개요

여러 클러스터를 하나의 메시로 묶으려면 세 가지가 필요하다(그림 12.1). 이 장의 실습은 결국 이 셋을 채우는 과정이다.

1. **클러스터 간 워크로드 디스커버리**: istiod가 프록시를 설정하려면 **상대 클러스터의 워크로드**를 알아야 한다 → 원격 클러스터의 쿠버네티스 API 서버에 접근할 수 있어야 한다.
2. **클러스터 간 워크로드 연결**: 워크로드끼리 실제로 **엔드포인트 IP에 도달**할 수 있어야 한다.
3. **클러스터 간 공통 신뢰(common trust)**: mTLS 상호 인증을 위해 클러스터 간 워크로드가 **같은 신뢰 뿌리**를 공유해야 한다.

> [!NOTE]
> 상용에서 이스티오가 다중 클러스터를 구성하려면 상대 클러스터의 쿠버네티스 API에 접근해야 하는데, 조직 정책상 이를 꺼릴 수 있다. 그럴 때는 **메시 페더레이션**이 대안이며, Gloo Mesh 같은 프로젝트가 자동화·보안을 돕는다.

### 12.2.1 이스티오 다중 클러스터 배포 모델

클러스터 유형은 두 가지다 — **기본 클러스터(primary)**: 컨트롤 플레인이 설치된 클러스터, **원격 클러스터(remote)**: 컨트롤 플레인과 떨어진 클러스터.

| 배포 모델 | 설명 | 특징 |
| --- | --- | --- |
| **기본-원격(primary-remote)** | 단일 컨트롤 플레인이 기본+원격을 관리(공유 컨트롤 플레인) | 리소스 효율적이나 기본 클러스터 중단이 메시 전체에 영향 → 가용성 낮음 |
| **기본-기본(multi-primary)** | 모든 클러스터에 컨트롤 플레인 설치(복제된 컨트롤 플레인) | 가용성 높음, 리소스 더 필요, 중단 범위가 해당 클러스터로 국한 |
| **외부 컨트롤 플레인** | 모든 클러스터가 컨트롤 플레인과 분리 | 클라우드 프로바이더가 관리형으로 제공 가능 |

### 12.2.2 다중 클러스터 배포에서 워크로드를 디스커버리하는 방법은?

istiod가 프록시를 설정하려면 정보가 필요하고, 그 원천은 **쿠버네티스 API 서버**다. 원격 클러스터의 API 서버는 **RBAC**로 보호되므로, 접근하려면 신원과 권한이 필요하다.

- **ServiceAccount**: 기계·서비스용 클라이언트 신원. 생성 시 **토큰(JWT)** 이 자동 발급돼 파드에 주입되고, 이 토큰으로 API 서버에 인증한다.
- **Role / ClusterRole**: 그 신원이 가질 권한 집합.
- istiod는 최소 권한의 **`istio-reader-service-account`** 토큰으로 원격 API 서버를 읽는다(그림 12.5).

### 12.2.3 클러스터 간 워크로드 연결

- 클러스터가 **플랫 네트워크**(같은 VPC 등 단일 네트워크)이거나 네트워크 **피어링**으로 워크로드 IP에 직접 도달 가능하면 조건이 충족된다.
- 서로 **다른 네트워크**에 있으면, 클러스터 간 트래픽을 프록시하는 특수 게이트웨이 = **east-west 게이트웨이**가 필요하다. (외부↔내부의 north-south 트래픽과 대비되는, 클러스터↔클러스터 트래픽)

### 12.2.4 클러스터 간 공통 신뢰

클러스터 간 워크로드가 상호 인증하려면 공통 신뢰가 있어야 하며, 두 가지 방법이 있다.

- **플러그인 CA 인증서(공통 루트 CA)**: istiod의 기본 자체 서명 대신, 사용자가 만든 **중간 CA**를 각 클러스터에 넣되 **같은 루트 CA가 서명**하게 한다(그림 12.8: 루트 CA → 클러스터별 중간 CA → 워크로드 인증서). 중간 CA를 **`cacerts` Secret**(istio-system)으로 제공한다.
  - 단점: 중간 CA가 유출되면 노출 탐지·취소가 어렵다.
- **외부 CA 통합**: 더 안전한 대안. istiod가 등록 기관 역할로 쿠버네티스 CSR을 검증·승인해 외부 CA에 제출한다. **cert-manager(+istio-csr)** 로 붙이거나 커스텀 CA로 구성하며, 발급된 인증서는 **SDS**로 워크로드에 전달된다.

## 12.3 다중 클러스터, 다중 네트워크, 다중 컨트롤 플레인 서비스 메시 개요

실습 인프라(그림 12.9): **west-cluster**(`us-west`, `webapp` 실행)와 **east-cluster**(`us-east`, `catalog` 실행)를 서로 다른 리전·네트워크에 두어 재난 시 상호 보호한다.

### 12.3.1 다중 클러스터 배포 모델 선택하기

ACME는 서비스 중단 비용이 크므로 **고가용성을 최우선**으로 삼는다. 따라서 **다중 클러스터 + 다중 네트워크 + 복제된(다중) 컨트롤 플레인 + east-west 게이트웨이** = **기본-기본(multi-primary)** 모델을 택한다.

### 12.3.2 클라우드 인프라 설정하기

- Azure에 서로 다른 네트워크의 클러스터 2개를 만든다: `sh ch12/scripts/create-clusters-in-azure.sh`.
- 편의 alias: `kwest="kubectl --context=west-cluster"`, `keast="kubectl --context=east-cluster"`.

### 12.3.3 플러그인 CA 인증서 설정하기

두 클러스터가 **같은 루트 CA**를 공유하도록, 클러스터별 중간 CA를 만들어 `cacerts` Secret으로 넣는다. 필요 파일 4개(그림 12.10):

| 파일 | 역할 |
| --- | --- |
| `ca-cert.pem` | 중간 CA의 인증서 |
| `ca-key.pem` | 중간 CA의 개인 키 |
| `root-cert.pem` | 중간 CA를 발급한 **루트 CA 인증서**(클러스터 간 신뢰 검증) |
| `cert-chain.pem` | 중간 CA↔루트 CA를 잇는 신뢰 체인 |

```bash
sh ch12/scripts/generate-certificates.sh      # 루트 CA + 클러스터별 중간 CA 2개 생성
# 각 클러스터에 적용
kubectl create secret generic cacerts -n istio-system \
  --from-file=ca-cert.pem --from-file=ca-key.pem \
  --from-file=root-cert.pem --from-file=cert-chain.pem
```

### 12.3.4 각 클러스터에 이스티오 설치하기

**먼저 네트워크 토폴로지 라벨**을 붙인다(istiod가 이 라벨로 네트워크를 판단).

```bash
kwest label namespace istio-system topology.istio.io/network=west-network
keast label namespace istio-system topology.istio.io/network=east-network
```

**IstioOperator로 컨트롤 플레인 설치** — 두 클러스터는 `meshID` 가 **같고**(같은 메시), `clusterName`·`network` 만 다르다.

```yaml
# west-cluster
spec:
  profile: demo
  values:
    global:
      meshID: usmesh                       # 두 클러스터 동일 → 같은 메시
      multiCluster:
        clusterName: west-cluster          # 클러스터 식별 이름
      network: west-network                # 이 설치가 속한 네트워크
```

```bash
istioctl --context="west-cluster" install -y -f ch12/controlplanes/cluster-west.yaml
istioctl --context="east-cluster" install -y -f ch12/controlplanes/cluster-east.yaml
```

이후 west에 `webapp`, east에 `catalog` 를 배포한다(네임스페이스 `istioinaction` + `istio-injection=enabled`). 아직 클러스터 간 디스커버리·연결은 없다.

> [!NOTE]
> 책 실습에서 west에 `catalog` **스텁 서비스**를 두는 이유: webapp이 catalog FQDN을 IP로 해석해야 트래픽을 라우터로 보내고, east-west 게이트웨이가 실제 라우팅을 처리하기 때문이다. (이스티오 **1.8+ DNS 프록시**로 이 한계가 개선됐다.)

### 12.3.5 클러스터 간 워크로드 디스커버리 활성화하기

istiod가 상대 클러스터를 읽으려면 그 클러스터의 접근 자격(kubeconfig)이 담긴 **원격 시크릿**이 필요하다. 이 시크릿은 `istio-reader-service-account` 토큰을 담고 있으며, 라벨 `istio/multiCluster: "true"` 가 붙어 istiod가 감시한다.

**중요 — 시크릿은 양방향으로 교환**한다.

```bash
# east 접근 자격을 west istiod에 등록
istioctl x create-remote-secret --name="east-cluster" | kwest apply -f -
# west 접근 자격을 east istiod에 등록 (반대 방향도 필수)
istioctl x create-remote-secret --name="west-cluster" | keast apply -f -
```

istiod 로그에 `Adding cluster ... from secret=istio-system/istio-remote-secret-...` 이 뜨면 등록된 것이다.

### 12.3.6 클러스터 간 연결 설정하기

서로 다른 네트워크의 클러스터는 **east-west 게이트웨이**로 잇는다(그림 12.12). 이 게이트웨이는 트래픽을 **암호화된 상태 그대로** 상대 클러스터 워크로드로 프록시하며, 상호 인증 커넥션을 유지한다.

**핵심은 SNI 기반 라우팅**이다. east-west 게이트웨이는 **SNI 클러스터**로 설정된 인그레스 게이트웨이로, 목적지 클러스터 정보를 **SNI 헤더에 인코딩**해 라우팅한다(그림 12.13).

```yaml
# east-west 게이트웨이 (IstioOperator 핵심)
spec:
  profile: empty
  components:
    ingressGateways:
      - name: istio-eastwestgateway
        enabled: true
        label: { istio: eastwestgateway }
        k8s:
          env:
            - name: ISTIO_META_ROUTER_MODE
              value: "sni-dnat"                 # SNI 클러스터 자동 구성
            - name: ISTIO_META_REQUESTED_NETWORK_VIEW
              value: "east-network"             # 프록시할 네트워크
```

설치 후 **SNI 자동 통과(AUTO_PASSTHROUGH)** Gateway로 서비스를 노출한다. VirtualService 없이 SNI 헤더 기반으로 라우팅되는 것이 특징이다(그림 12.14·12.15).

```yaml
kind: Gateway
metadata: { name: cross-network-gateway, namespace: istio-system }
spec:
  selector: { istio: eastwestgateway }
  servers:
    - port: { number: 15443, name: tls, protocol: TLS }   # 멀티클러스터 mTLS 포트
      tls: { mode: AUTO_PASSTHROUGH }
      hosts: ["*.local"]
```

```bash
# 양쪽 클러스터에 east-west 게이트웨이 + expose 적용
keast apply -n istio-system -f ch12/gateways/expose-services.yaml
# ... west 쪽도 동일하게 ...
```

**검증**: `webapp` 프록시의 `catalog` 엔드포인트가 east-west 게이트웨이 주소(포트 **15443**)를 가리키는지 확인하고, 인그레스로 실제 요청을 보내 응답을 확인한다.

```bash
istioctl --context=west-cluster pc endpoints deploy/webapp.istioinaction | grep catalog
curl http://$EXT_IP/api/catalog -H "Host: webapp.istioinaction.io"   # east catalog로 해석돼 응답
```

> [!TIP]
> **다중 클러스터 설정 3단계 요약** — ① 워크로드 디스커버리(원격 시크릿 교환), ② 워크로드 연결(east-west 게이트웨이 + 네트워크 라벨), ③ 공통 신뢰(같은 루트 CA + 중간 CA). 12.2의 세 요소가 그대로 실습으로 채워진 것이다.

### 12.3.7 클러스터 간 로드 밸런싱

6장의 **지역 인식 로드 밸런싱**을 다중 클러스터로 확장한다. 실행 클러스터 이름을 돌려주는 `simple-backend` 를 양쪽에 배포하면, 기본은 라운드 로빈이라 요청이 `Hello from WEST` / `Hello from EAST` 를 오간다.

**지역 인식 라우팅 검증** — 노드의 `topology.kubernetes.io/region`(westus/eastus)·`zone` 라벨에서 위치가 추출된다.

> [!WARNING]
> 지역 인식 라우팅·장애 조치를 쓰려면 **수동(passive) 헬스 체크 = 이상값 감지(outlier detection) DestinationRule 이 반드시** 있어야 한다(6장 리콜). 이게 있어야 정상일 땐 가까운 클러스터로만 보내고, 문제 시 다른 클러스터로 넘긴다.

```bash
kwest apply -f ch12/locality-aware/west/simple-backend-dr.yaml   # 이상값 감지 적용
# 이후 요청은 모두 "Hello from WEST" (가까운 클러스터로 라우팅)
```

**장애 조치 확인** — 엔드포인트는 지역 일치도로 **`priority`**(0=최우선)를 갖는다. west 백엔드에 오류를 주입하면(`ERROR_RATE=1`), 이상값 감지가 이를 걸러 우선순위가 낮은 **east(priority 1)** 로 넘겨 `Hello from EAST` 가 나온다.

**클러스터 간 인가 정책** — 접근 제어도 클러스터 경계를 넘어 그대로 적용된다. 예: 인그레스에서 온 트래픽만 허용하는 `AuthorizationPolicy` 를 east에 걸면, 게이트웨이를 거치지 않은 파드 내부 호출은 `RBAC: access denied` 로 막히고, 게이트웨이 경유 요청만 통과한다.

> [!NOTE]
> 실습 후 클라우드 리소스 정리: `sh ch12/scripts/cleanup-azure-resources.sh`.

## 요약

- 이스티오의 다중 클러스터 배포 모델은 셋 — **기본-원격(단일 컨트롤 플레인), 기본-기본(복제된 컨트롤 플레인), 외부 컨트롤 플레인.** 고가용성이 목표면 기본-기본을 쓴다.
- **공통 신뢰**는 `istio-system` 에 **같은 루트 CA가 서명한 중간 CA(`cacerts`)** 를 넣어 구축한다.
- **워크로드 디스커버리**는 상대 클러스터의 `istio-reader` 토큰이 담긴 **원격 시크릿을 양방향으로 교환**해 활성화한다(`istioctl x create-remote-secret`).
- 다른 네트워크는 **east-west 게이트웨이**로 잇고, **`sni-dnat` 라우터 모드 + SNI 클러스터 + `AUTO_PASSTHROUGH`(포트 15443)** 로 클러스터 간 트래픽을 상호 인증된 상태로 라우팅한다.
- 로드 밸런싱·지역 인식·장애 조치·mTLS·인가 정책 등 **모든 기능이 단일 클러스터와 동일한 방식**으로 클러스터 경계를 넘어 동작한다.
