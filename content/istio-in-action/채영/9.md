8장까지가 트래픽을 관찰하고 다루는 단계였다면, 9장은 그 트래픽을 **보호**하는 단계다. 서비스끼리 서로를 어떻게 신뢰하고(인증), 인증된 주체가 무엇을 할 수 있는지(인가) 정하며, 전송 구간을 암호화(상호 TLS)한다. 이스티오는 이 모든 것을 **애플리케이션 코드 수정 없이** 사이드카 프록시 계층에서 처리한다. 4장에서 트래픽을 메시에 들이는 법을 다뤘다면, 이번 장은 그 트래픽을 보호하는 방법이다.

> [!IMPORTANT]
> **버전 확인하기**: 책은 이스티오 **1.13** 기준이다. 보안 리소스(`PeerAuthentication`, `RequestAuthentication`, `AuthorizationPolicy`)의 개념·필드는 최신(1.20+)에서도 거의 동일하지만, API 그룹이 책의 **`security.istio.io/v1beta1`** → **`security.istio.io/v1`** 로 승격됐다. 실습 경로도 `istio-1.13.0/samples/...` 라 최신 배포판에서는 버전 폴더만 바꾸면 된다.

## 9.1 애플리케이션 네트워크 보안의 필요성

애플리케이션 보안이란 인가받지 않은 사용자의 오·남용이나 접근으로부터 데이터를 지키는 모든 행동이다. 마이크로서비스는 한 프로세스 안의 호출을 **네트워크를 가로지르는 호출**로 쪼개므로, 보안을 위해 다음 두 가지가 필요하다.

- 리소스에 접근을 허가하기 전에 **사용자 인증·인가**를 수행한다.
- 클라이언트–서비스 사이의 여러 네트워크 장치를 지나는 동안 도청·변조를 막도록 **전송 데이터를 암호화**한다.

> [!NOTE]
> **인증 · 인가 한 줄 정의**
> - **인증(authentication)**: 상대가 자신의 정체를 증명하는 절차. "너 **누구**냐"에 답한다.
> - **인가(authorization)**: 인증된 주체가 리소스에 대해 생성·조회·갱신·삭제 같은 작업을 할 수 있는지 허용·거부하는 절차. "너 **뭘 할 수 있냐**"에 답한다.

조금 더 크게 보면, 서비스 통신 보안은 **세 가지 축**으로 나눠 생각하면 이해하기 쉽다.

- **인증(authentication)**: 상대가 **누구인지** 증명한다. 서비스 간 인증(서비스 A가 정말 A가 맞는가)과 최종 사용자 인증(요청을 보낸 사람이 누구인가)으로 나뉜다.
- **인가(authorization)**: 인증된 주체가 **무엇을 할 수 있는지** 정한다.
- **암호화**: 전송 중인 데이터를 **엿보거나 변조하지 못하게** 한다(mTLS).

전통적으로는 이 인증·인가·암호화를 **애플리케이션 라이브러리**로 해결했다. 그러나 언어마다 구현을 다시 만들어야 하고, 버전·정책이 서비스마다 제각각이 되어 일관성을 유지하기 어렵다. 이스티오는 이 공통 관심사를 **사이드카 프록시**로 내려, 개발자가 비즈니스 로직에 집중하면서도 메시 전체에 일관된 보안 정책을 적용할 수 있게 한다.

### 9.1.1 서비스 간 인증

서비스는 서로 상호작용할 때 모두 인증되어야 한다. 상대를 신뢰하려면 **ID 문서(신원 문서)** 를 제시하는데, 이 문서는 보통 신뢰할 수 있는 **제3자(CA)** 가 확인·발급한다. 이스티오는 **SPIFFE**(Secure Production Identity Framework For Everyone) 프레임워크를 사용해 이 서비스 신원 발급을 자동화한다.

> [!NOTE]
> **PKI와 인증서 한 줄 정리**
> mTLS는 공개키 기반구조(PKI) 위에서 동작한다. **인증 기관(CA)** 이 각 워크로드에 인증서를 발급하고, 양쪽이 상대 인증서가 신뢰하는 CA가 서명한 것인지 검증한다. 이스티오에서는 **istiod가 CA 역할**을 맡아 워크로드에 인증서를 자동 발급·교체(rotation)한다.

### 9.1.2 최종 사용자 인증

최종 사용자 인증은 개인 데이터를 저장하는 애플리케이션의 핵심이다. 사용자가 로그인하면 사용자 정보를 담은 **자격 증명**(HTTP 쿠키나 **JWT**)을 발급받고, 이후 요청마다 이를 제시한다. 서비스는 그 자격 증명을 검증해 사용자를 식별한다.

### 9.1.3 인가

인가는 **인증 이후**에 진행된다. 인증된 주체가 리소스에 대해 어떤 작업을 수행할 수 있는지 확인해 허용하거나 거부한다(예: 생성·조회·갱신·삭제). 이스티오는 서비스 인증 ID 모델을 기반으로 **서비스 간** 또는 **최종 사용자↔서비스** 사이에 세분화된 인가를 제공한다.

### 9.1.4 모놀리스와 마이크로서비스의 보안 비교

- **모놀리스**: 최종 사용자만 인증·인가하면 되고, 소수의 정적 서버에서 돌기 때문에 **IP 주소를 신뢰의 근거**로 삼기 좋다(네트워크 방화벽 규칙에 IP를 그대로 쓴다).
- **마이크로서비스**: 수천 개 서비스가 동적으로 스케줄링돼 **IP가 계속 바뀌고**, 여러 클라우드에 걸쳐 실행된다. 그래서 IP는 더 이상 신뢰의 근거가 될 수 없다.

조금 더 풀어 보면 — 모놀리스에서는 대부분의 호출이 한 프로세스 메모리 안에서 일어나므로 네트워크에 노출되는 표면이 작고, 신뢰 경계도 단순하다. 반면 마이크로서비스는 같은 기능이 네트워크로 흩어지면서 **중간자 공격(man-in-the-middle)**, 신원 위조, 권한 과다 같은 위험이 늘어난다. 네트워크 경계(방화벽)만으로는 내부로 침투한 공격자를 막지 못하므로, **서비스 하나하나가 서로를 검증하는 제로 트러스트(zero trust)** 모델이 필요하다.

이 동적·이질적 환경에서 신원을 제공하려고 이스티오가 채택한 것이 **SPIFFE** 다. (그림 9.1은 고정 IP·신뢰 네트워크의 온프레미스, 그림 9.2는 온프레미스+클라우드에 걸친 동적 마이크로서비스를 대비해 보여준다.)

### 9.1.5 이스티오가 SPIFFE를 구현하는 방법

**SPIFFE ID** 는 RFC 3986 URI 형식이다.

```
spiffe://<trust-domain>/<path>
```

- **trust-domain**: 신원 발급자(신뢰 도메인)를 식별한다. 이스티오 기본값은 `cluster.local`.
- **path**: 워크로드를 고유하게 식별한다. 이스티오에서는 워크로드가 실행되는 **쿠버네티스 서비스 어카운트**를 나타낸다.

```
spiffe://cluster.local/ns/<namespace>/sa/<service-account>
```

이 SPIFFE ID를 담은 검증 가능한 문서가 **SVID**(SPIFFE Verifiable Identity Document)이며, 이스티오에서는 **X.509 인증서**로 인코딩된다. 8장 끝에서 본 것처럼 SPIFFE ID는 인증서의 **SAN(Subject Alternative Name)** 에 URI 타입으로 들어가고, 두 워크로드는 이 SVID로 서로를 상호 인증한다. (더 깊은 내용은 부록 C.)

> [!NOTE]
> **SPIFFE ID는 레이블이 아니라 ServiceAccount에서 자동 생성된다**
> SPIFFE ID의 `path` 는 임의의 레이블이 아니라 파드의 **네임스페이스 + ServiceAccount** 로 결정된다. `spiffe://...` 문자열을 직접 하드코딩하지 않고, 파드에 ServiceAccount만 지정하면 **istiod가 자동으로** 그 신원을 만들어 인증서 SAN에 담아 발급한다(미지정 시 그 네임스페이스의 `default` SA 사용). 그래서 신원을 구분하려면 **앱마다 전용 ServiceAccount**를 두는 것이 정석이다. 즉 **레이블 = "어디로 보낼까"(라우팅), ServiceAccount = "누구인가"(신원)** 로 축이 다르다.
>
> **참고 링크**
> - SPIFFE 개념(표준 원문): https://spiffe.io/docs/latest/spiffe-about/overview/
> - Istio 보안 개념(인증·인가 전체 그림): https://istio.io/latest/docs/concepts/security/
> - 보안 리소스 레퍼런스(PeerAuthentication·RequestAuthentication·AuthorizationPolicy): https://istio.io/latest/docs/reference/config/security/
> - 책 실습 소스코드: https://github.com/istioinaction/book-source-code

### 9.1.6 이스티오 보안 요약

세 리소스가 서비스 프록시의 보안을 구성한다(그림 9.3).

| 리소스 | 역할 |
| --- | --- |
| **`PeerAuthentication`** | 서비스 간(peer) 트래픽을 인증한다. 프록시가 상호 인증하며 SVID를 검증하고, 성공 시 프록시 사이 트래픽을 암호화한다. |
| **`RequestAuthentication`** | 요청에 담긴 최종 사용자 자격 증명(JWT)을 검증하고, 검증된 클레임을 필터 메타데이터에 저장한다. |
| **`AuthorizationPolicy`** | 필터 메타데이터(SVID·JWT 클레임)에 기반해 요청을 허용·거부한다. |

이것이 이스티오 보안의 큰 그림이다. 다음 절부터 이 리소스들을 실제로 적용한다.

## 9.2 자동 상호 TLS

사이드카 프록시가 주입된 서비스 사이의 트래픽은 **기본적으로 암호화·상호 인증**된다. 인증서 발급·로테이션 절차를 이스티오가 자동화하므로, 수동 관리에서 오는 오류나 인증서 만료로 인한 서비스 중단을 피할 수 있다.

컨트롤 플레인(**이스티오 CA**)이 발급한 인증서로 서비스가 서로 인증하고 트래픽을 암호화한다(그림 9.4). 책은 이 상태를 "기본적으로 안전(secure by default)"하다고 표현하며, 이후 절에서 `STRICT` 등으로 보안을 더 강화한다.

### 9.2.1 환경 설정하기

백지 상태에서 시작하도록 기존 리소스를 정리하고 세 워크로드를 배치한다(그림 9.5).

```bash
kubectl config set-context $(kubectl config current-context) \
  --namespace=istioinaction
kubectl delete virtualservice,deployment,service,destinationrule,gateway --all
```

- `sleep`: **default** 네임스페이스, **사이드카 없음**(즉 신원/SVID 없음). 여기서 평문으로 요청을 보내는 레거시 워크로드 역할.
- `webapp`, `catalog`: **istioinaction** 네임스페이스, 사이드카 주입.
- 흐름: `sleep` → `webapp`(HTTP) → `catalog`(HTTPS).

### 9.2.2 이스티오의 PeerAuthentication 리소스 이해하기

서비스 간 인증 방식은 **`PeerAuthentication`** 으로 정한다. 적용 범위는 리소스를 어디에 두느냐로 결정된다.

| 범위 | 배치 방법 |
| --- | --- |
| **메시 전체** | `istio-system` 에 이름 `default` 로 배치 |
| **네임스페이스** | 해당 네임스페이스에 이름 `default` 로 배치 |
| **워크로드** | `selector.matchLabels` 로 특정 워크로드만 |

mTLS 모드는 다음과 같다.

- **`STRICT`**: mTLS만 허용. 평문 요청은 거부된다.
- **`PERMISSIVE`**(기본): 암호화 요청과 평문 요청을 **둘 다** 허용. 사이드카가 없는 워크로드도 붙을 수 있어 **점진적 마이그레이션**에 쓴다.
- **`DISABLE`**: 터널링하지 않고 평문 그대로 보낸다.
- **`UNSET`**: 부모(상위 범위)의 정책을 상속한다.

```yaml
apiVersion: security.istio.io/v1   # 책(1.13)은 v1beta1
kind: PeerAuthentication
metadata:
  name: default            # 메시 전체엔 이름을 default 로 두는 것이 관례
  namespace: istio-system
spec:
  mtls:
    mode: STRICT
```

> [!NOTE]
> **메시 전체에 `STRICT` 를 걸면 무슨 일이 일어나나**
> 위 정책을 적용하면 사이드카가 없는 `sleep` 의 평문 요청은 거부된다(`command terminated with exit code 56`). 그래서 실무에서는 먼저 `PERMISSIVE` 로 전체를 운영하며 모든 트래픽이 mTLS로 올라온 것을 확인한 뒤 `STRICT` 로 좁혀 나간다.

범위를 겹쳐 세밀하게 조정할 수도 있다. 예를 들어 메시 전체는 `STRICT` 로 두되, `webapp` 워크로드만 `PERMISSIVE` 로 풀어 레거시 `sleep` 의 평문 요청을 받게 하고, `catalog` 는 여전히 `STRICT` 를 유지한다(그림 9.6).

```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: webapp
  namespace: istioinaction
spec:
  selector:
    matchLabels:
      app: webapp
  mtls:
    mode: PERMISSIVE
```

**검증** — 실제로 암호화·상호 인증이 되는지 두 가지로 확인한다.

- **트래픽 스니핑**: `istioctl install --set values.proxy.privileged=true` 로 재설치 후 파드에서 `tcpdump` 로 평문이 보이지 않는지 확인한다.
  > [!CAUTION]
  > `privileged=true` 는 악의적 공격의 매개가 될 수 있으므로 **운영 클러스터에서는 사용을 지양**한다.
- **신원 확인**: `openssl s_client` 로 `catalog` 인증서의 SAN을 보면 `URI:spiffe://cluster.local/ns/istioinaction/sa/catalog` 가 보인다. SPIFFE ID가 곧 서비스 어카운트임을 확인할 수 있고, `openssl verify` 로 루트 CA(`root-cert.pem`) 서명을 검증하면 `OK` 가 나온다.

## 9.3 서비스 간 트래픽 인가하기

인증으로 신원이 확정되면, **`AuthorizationPolicy`** 로 "그 신원이 무엇을 할 수 있는지"를 정한다. 특정 ID(예: `webapp`)만 `catalog` 에 접근하도록 허용하고 나머지는 막는 식이다(그림 9.9).

### 9.3.1 이스티오에서 인가 이해하기

정책은 컨트롤 플레인이 **모든 프록시에 배포**하고, 각 **서비스 프록시가 로컬에서** 요청 허용·거부를 판단한다(집행 엔진이 분산돼 효율적이다). `spec` 은 세 필드로 이뤄진다.

- **`selector`**: 정책을 적용할 워크로드를 지정한다(없으면 네임스페이스 전체).
- **`action`**: `ALLOW` / `DENY` / `CUSTOM` 중 하나. 규칙에 일치하면 이 액션이 적용된다.
- **`rules`**: 정책을 활성화하는 요청(규칙 목록)을 정의한다.

각 규칙은 출처(`from`)·작업(`to`)·조건(`when`)으로 구성된다.

- **`from` / `source`**: 요청의 출처. `principals`(mTLS 기반 SPIFFE ID), `namespaces`(SVID 출처 네임스페이스, mTLS 필요), `ipBlocks`(출처 IP/CIDR) 등. `notPrincipals` 처럼 부정 매칭도 가능.
- **`to` / `operation`**: 대상 작업. HTTP `hosts`·`methods`·`paths` 등.
- **`when`**: 규칙 부합 후 추가로 충족해야 하는 조건(예: JWT 클레임).

### 9.3.2 작업 공간 설정하기

리소스를 정리하고 다시 배포한다. 메시 전체 `STRICT`(`meshwide-strict-peer-authn.yaml`)와 `webapp` 워크로드 `PERMISSIVE`(`workload-permissive-peer-authn.yaml`)를 적용해, `sleep`(default, 평문) → `webapp`(미인증 요청 수용) → `catalog`(같은 네임스페이스에서 인증된 요청 수용) 상태를 만든다(그림 9.7).

### 9.3.3 워크로드에 정책 적용 시 동작 변화

> [!IMPORTANT]
> **인가의 핵심 규칙**
> - 어떤 워크로드에 **`ALLOW` 정책이 하나라도 생기면**, 그 워크로드는 **기본 거부**로 바뀌고 규칙에 **명시적으로 일치하는 요청만** 허용된다.
> - 워크로드에 걸린 정책이 **하나도 없으면** 모든 요청이 허용된다.

예를 들어 `webapp` 에 `/api/catalog*` 경로만 허용하는 `ALLOW` 정책을 걸면, `/api/catalog` 요청은 통과하지만 `/hello/world` 는 거부된다.

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-catalog-requests-in-web-app
  namespace: istioinaction
spec:
  selector:
    matchLabels:
      app: webapp
  action: ALLOW
  rules:
    - to:
        - operation:
            paths: ["/api/catalog*"]
```

### 9.3.4 전체 정책으로 기본적으로 모든 요청 거부하기

보안을 높이고 사고 과정을 단순화하려면, 먼저 **모든 요청을 막는 catch-all deny** 를 깔고 필요한 것만 열어 나가는 방식이 좋다. `spec` 을 비우면 "아무것도 허용하지 않음 = 전부 거부"가 된다.

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: deny-all
  namespace: istio-system    # 루트 네임스페이스 → 메시 전체
spec: {}                     # 규칙 없음 = 전부 거부
```

적용 후 `sleep` → `catalog` 요청은 `RBAC: access denied` 로 막힌다.

> [!TIP]
> 반대로 **전부 허용**하려면 규칙에 빈 항목을 둔다: `rules: - {}`. (빈 `spec` = 전부 거부 / `rules: [{}]` = 전부 허용, 헷갈리기 쉬운 대칭)

### 9.3.5 특정 네임스페이스에서 온 요청 허용하기

`source.namespaces` 로 특정 네임스페이스에서 온 트래픽만 허용한다.

```yaml
  rules:
    - from:
        - source:
            namespaces: ["default"]
      to:
        - operation:
            methods: ["GET"]
```

> [!WARNING]
> 그런데 `sleep` 은 **사이드카가 없어 SVID가 없다.** 그래서 "default에서 온 요청"으로 식별되지 못해 이 정책으로는 통과하지 못한다. 해결책은 ① `sleep` 에 프록시를 주입하거나 ② `webapp` 이 미인증 요청을 받도록 허용하는 것이다. 책은 ②로 진행한다.

### 9.3.6 미인증 레거시 워크로드에서 온 요청 허용하기

미인증 요청을 허용하려면 규칙에서 **`from` 을 빼면** 된다(출처를 따지지 않음). `webapp` 셀렉터를 달아 `catalog` 는 여전히 상호 인증을 요구하게 둔다.

```yaml
spec:
  selector:
    matchLabels:
      app: webapp
  action: ALLOW
  rules:
    - to:
        - operation:
            methods: ["GET"]
```

적용하면 `sleep` → `webapp` GET은 통과하지만, 그 뒤 `webapp` → `catalog` 호출은 `catalog` 에 아직 ALLOW 정책이 없어 거부된다(`error calling Catalog service`). 다음 절에서 `catalog` 를 연다.

### 9.3.7 특정 서비스 어카운트에서 온 요청 허용하기

트래픽에 실려 오는 서비스 어카운트(SVID로 인코딩된 신원)를 근거로 허용한다. `catalog` 에 `webapp` 의 SPIFFE ID를 `principals` 로 지정한다.

```yaml
spec:
  selector:
    matchLabels:
      app: catalog
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/istioinaction/sa/webapp"]
      to:
        - operation:
            methods: ["GET"]
```

이제 `sleep` → `webapp` → `catalog` 전체 경로가 성공한다.

### 9.3.8 정책의 조건부 적용

`when` 으로 특정 조건을 만족할 때만 정책이 적용되게 한다. 예를 들어 JWT 클레임 `group` 이 `admin` 일 때만 허용한다.

```yaml
  rules:
    - from:
        - source:
            requestPrincipals: ["auth@istioinaction.io/*"]
      when:
        - key: request.auth.claims[group]
          values: ["admin"]
```

`notValues` 로 부정 조건도 쓸 수 있다.

### 9.3.9 값 비교 표현식 이해하기

규칙 값은 여러 개면 **하나만 일치해도**(OR) 매칭된다. 매칭 방식은 네 가지다.

| 방식 | 예 | 의미 |
| --- | --- | --- |
| 정확 일치 | `GET` | 값이 정확히 같음 |
| 접두어 | `/api/catalog*` | `/api/catalog` 로 시작 |
| 접미어 | `*.istioinaction.io` | `.istioinaction.io` 로 끝남 |
| 존재 | `["*"]` | 값이 무엇이든 **존재하기만** 하면 됨 |

한 규칙 안에서 세 속성(`source` · `operation` · `when`)은 **모두 충족(AND)** 해야 하고, `operation` 내부의 `methods`·`paths` 같은 항목도 전부 AND다. 반면 `from` 목록이나 `operation` 목록의 **항목들 사이는 OR**(하나만 맞으면 됨)다.

### 9.3.10 인가 정책이 평가되는 순서 이해하기

이스티오에는 우선순위(priority) 필드가 없다. 대신 액션 종류로 **정해진 순서**를 따른다(그림 9.11).

> [!IMPORTANT]
> **평가 순서: `CUSTOM` → `DENY` → `ALLOW`**
> 1. **CUSTOM** 정책을 먼저 평가한다(외부 인가 서버 연동, 9.5).
> 2. **DENY** 정책을 평가한다.
> 3. **ALLOW** 정책을 평가한다.
>
> 즉 `DENY` 가 `ALLOW` 보다 우선한다. CUSTOM·DENY가 없으면, ALLOW 정책이 없을 땐 허용하고 ALLOW 정책이 있는데 안 맞으면 거부한다.

## 9.4 최종 사용자 인증 및 인가

이스티오는 **JWT** 로 최종 사용자를 인증·인가한다.

### 9.4.1 JSON 웹 토큰이란 무엇인가?

JWT는 클라이언트를 서버에 인증하는 자격 증명으로, 점(`.`)으로 구분된 **세 부분**을 Base64 URL 인코딩한 것이다.

- **헤더(header)**: 토큰 유형·해싱 알고리즘
- **페이로드(payload)**: 사용자 클레임(`iss` 발급자, `sub` 주체, `exp` 만료, `iat` 발행 시각, `group` 등)
- **서명(signature)**: 진위를 확인하는 부분

인증 서버가 **비밀 키로 서명**하고, 대응하는 **공개 키(JWKS)** 를 well-known HTTP 엔드포인트에 노출하면 서비스가 이를 받아 토큰을 검증한다(그림 9.12). 인증 서버는 ① 백엔드에 직접 구현, ② Keycloak 같은 자체 호스팅, ③ Auth0·Okta 같은 IDaaS로 마련할 수 있다.

### 9.4.2 인그레스 게이트웨이에서의 최종 사용자 인증 및 인가

JWT 검증은 보통 **인그레스 게이트웨이**에서 수행한다. 유효하지 않은 요청을 메시 입구에서 조기에 거부하므로 성능에 유리하고, 후속 서비스로의 **재전송 공격(replay attack)** 도 막는다. 실습은 `webapp` 용 게이트웨이·VirtualService를 배치한 뒤 진행한다.

### 9.4.3 RequestAuthentication으로 JWT 검증하기

**`RequestAuthentication`** 은 JWT를 검증하고, 유효한 토큰의 클레임을 필터 메타데이터에 저장해 `AuthorizationPolicy` 가 쓸 수 있게 한다.

```yaml
apiVersion: security.istio.io/v1
kind: RequestAuthentication
metadata:
  name: jwt-token-request-authn
  namespace: istio-system
spec:
  selector:
    matchLabels:
      app: istio-ingressgateway
  jwtRules:
    - issuer: "auth@istioinaction.io"
      jwks: |
        { ...JWKS... }
```

> [!WARNING]
> **헷갈리는 지점 — `RequestAuthentication` 만으로는 못 막는다**
> `RequestAuthentication` 의 검증 결과는 세 가지다.
> - **유효한 토큰**: 통과 + 클레임 저장
> - **잘못된 발급자/만료 토큰**: 거부(`Jwt issuer is not configured` 등)
> - **토큰이 아예 없는 요청**: **그냥 통과한다** (200)
>
> 그래서 "토큰 없는 요청을 막으려면" 반드시 **`AuthorizationPolicy`** 로 `requestPrincipals` 가 있을 것을 요구해야 한다. 아래는 토큰 없는 요청을 거부하는 정책이다(`notRequestPrincipals: ["*"]` = 요청 신원이 하나도 없는 요청 → `DENY`).

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: app-gw-requires-jwt
  namespace: istio-system
spec:
  selector:
    matchLabels:
      app: istio-ingressgateway
  action: DENY
  rules:
    - from:
        - source:
            notRequestPrincipals: ["*"]
      to:
        - operation:
            hosts: ["webapp.istioinaction.io"]
```

- `requestPrincipals` 는 `<iss>/<sub>` 를 결합한 값이다.
- **클레임 기반 차등 접근**: 일반 사용자 토큰(`group: user`)은 GET만, 관리자 토큰(`group: admin`)은 `when` 조건으로 POST(쓰기)까지 허용하는 식으로 나눈다. 일반 사용자의 POST는 `RBAC: access denied` 로 막힌다.

## 9.5 커스텀 외부 인가 서비스와 통합하기

SPIFFE 기반 인증 위의 인가는 기본적으로 RBAC이다. 여기서 표현하기 어려운 정교한 규칙이나 조직의 기존 인가 시스템(**OPA**, Signal Sciences, Gloo Edge Ext Auth 등)을 쓰려면, **외부 인가 서비스**를 프록시 앞에 두고 판단을 위임한다. 요청이 프록시로 들어가기 전에 외부 서버를 호출해 잠시 멈추고, 그 응답(허용/거부)에 따른다(그림 9.13). 외부 서버는 엔보이의 **CheckRequest API** 를 구현해야 한다.

### 9.5.1 외부 인가 실습

기존 정책을 정리하고, 이스티오 배포판이 제공하는 샘플 외부 인가 서비스를 배포한다.

```bash
kubectl delete authorizationpolicy,peerauthentication,requestauthentication --all -n istio-system
kubectl apply -f istio-1.13.0/samples/extauthz/ext-authz.yaml -n istioinaction
```

이 `ext-authz` 는 간단한 검사기로, 요청에 `x-ext-authz: allow` 헤더가 있으면 허용하고 없으면 거부한다(포트 8000 HTTP / 9000 gRPC).

### 9.5.2 이스티오에 외부 인가 설정하기

이스티오가 이 외부 서버를 인식하도록 `istio-system` 의 `istio` configmap(MeshConfig)에 **`extensionProviders`** 를 추가한다.

```yaml
# kubectl edit -n istio-system cm istio → data.mesh 아래
extensionProviders:
  - name: "sample-ext-authz-http"
    envoyExtAuthzHttp:
      service: "ext-authz.istioinaction.svc.cluster.local"
      port: "8000"
      includeHeadersInCheck: ["x-ext-authz"]
```

### 9.5.3 커스텀 AuthorizationPolicy 리소스 사용하기

`action: CUSTOM` 정책으로 어떤 외부 인가 서비스를 쓸지 지정한다. `provider.name` 은 MeshConfig에 등록한 이름과 **정확히 같아야** 한다.

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: ext-authz
  namespace: istioinaction
spec:
  selector:
    matchLabels:
      app: webapp
  action: CUSTOM
  provider:
    name: sample-ext-authz-http
  rules:
    - to:
        - operation:
            paths: ["/"]
```

헤더 없이 `sleep` → `webapp` 을 호출하면 `denied by ext_authz for not found header 'x-ext-authz: allow' in the request` 로 거부되고, `x-ext-authz: allow` 헤더를 넣으면 통과한다.

> [!CAUTION]
> 외부 인가는 요청 경로에 **동기 호출을 하나 더** 얹는다. 외부 서버가 느리거나 죽으면 그 경로 전체의 지연·실패로 이어지므로, 타임아웃과 실패 시 동작을 정의하고 꼭 필요한 경로에만 좁혀 적용한다.

## 요약

- 서비스 통신 보안은 **인증(누구인가) · 인가(무엇을 할 수 있나) · 암호화(전송 보호)** 로 나뉘며, 이스티오는 이를 앱 코드가 아닌 **사이드카 계층**에서 처리한다.
- 워크로드 신원은 **SPIFFE** 표준을 따른다. SPIFFE ID(`spiffe://cluster.local/ns/<ns>/sa/<sa>`)는 X.509 **SVID의 SAN** 에 담기고, **이스티오 CA**(istiod)가 발급·로테이션한다.
- **`PeerAuthentication`** 으로 상호 TLS를 켠다. `STRICT` 는 mTLS만, `PERMISSIVE` 는 평문+mTLS 둘 다 허용하므로 **점진적 마이그레이션**에 쓴다.
- **`AuthorizationPolicy`**: 워크로드에 `ALLOW` 정책이 하나 생기면 나머지는 **기본 거부**, 평가 순서는 **CUSTOM → DENY → ALLOW**. catch-all deny(빈 `spec`) 후 필요한 것만 여는 패턴이 기본이다.
- **`RequestAuthentication`** 으로 JWT를 검증한다. 단, **토큰 없는 요청을 막으려면 반드시 `AuthorizationPolicy` 와 짝**으로 써야 한다(`notRequestPrincipals: ["*"]` + `DENY`).
- 표현하기 어려운 규칙이나 기존 인가 시스템은 **`CUSTOM` 액션 + `extensionProviders`** 로 외부 인가 서버에 위임한다.
