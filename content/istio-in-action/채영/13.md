12장이 여러 쿠버네티스 클러스터를 하나의 메시로 묶는 이야기였다면, 13장은 **쿠버네티스 바깥의 가상 머신(VM)** 을 메시에 편입시킨다. 레거시·물리 워크로드가 VM에 남아 있어도, 사이드카를 설치·설정하면 메시의 일원이 되어 상호 인증·트래픽 관리 등 같은 이점을 누린다. 쿠버네티스에서 자동으로 되던 일들(사이드카 주입·신원 토큰 주입·DNS 해석)을 VM에서는 **직접** 해줘야 한다는 점이 핵심 차이다.

> [!IMPORTANT]
> **버전 확인하기**: 책은 이스티오 **1.13** 기준이고, VM 통합은 **1.9에서 베타로 승격**된 기능이다. 부트스트랩 명령이 책에선 `istioctl x workload ...`(experimental)인데, 최신에선 **`istioctl workload ...`** 로 정식 승격됐다. DNS 프록시는 **1.8+** 에서 도입됐다.

## 13.1 이스티오의 가상 머신 지원

VM이 메시의 일부가 되려면 세 가지가 필요하다 — ① 트래픽을 관리할 **사이드카 설치**, ② 사이드카가 istiod에 붙어 설정을 받도록 **부트스트랩**, ③ istiod 인증에 쓸 **신원 토큰** 제공. 쿠버네티스에선 웹훅·서비스어카운트 토큰으로 자동 처리되지만, 외부 VM은 이 편의가 없어 운영자가 수작업으로 해준다.

이스티오 1.9가 개선한 핵심 3가지: (1) `istioctl` 로 VM 사이드카 설치·설정 단순화, (2) 고가용성용 리소스 **`WorkloadGroup`·`WorkloadEntry`** 도입, (3) VM에서 메시 내부 호스트네임을 풀도록 **로컬 DNS 프록시** 제공.

### 13.1.1 가상 머신에서의 사이드카 프록시 설치 및 설정 단순화하기

- 쿠버네티스는 자신을 신뢰 원천으로 삼아 파드에 서비스어카운트 토큰을 자동 주입하고 istiod가 이를 검증해 **SVID(SPIFFE ID)** 를 발급한다(그림 13.2).
- VM에는 자동 주입이 없으므로, 운영자가 **서비스어카운트를 만들고 그 토큰을 VM에 안전하게 전달**한다. istio-agent가 그 토큰으로 istiod에 인증하면 SVID를 받는다(그림 13.3).

### 13.1.2 가상 머신 고가용성

쿠버네티스의 Deployment/Pod 모델을 VM에 흉내 내어 두 리소스로 대응한다.

| 이스티오 리소스 | 대응 | 역할 |
| --- | --- | --- |
| **`WorkloadGroup`** | Deployment | VM 워크로드 그룹의 **공통 템플릿**(노출 포트, 서비스어카운트=워크로드 신원, 상태 프로브) |
| **`WorkloadEntry`** | Pod | **개별 VM 인스턴스**(주소·상태 등 고유 속성) |

- `WorkloadEntry` 는 수동 생성도 되지만, **권장은 워크로드 자동 등록(auto-registration)** — VM이 부트스트랩 설정으로 istiod에 인증하면, istiod가 그 VM을 나타내는 `WorkloadEntry` 를 **자동 생성**한다(그림 13.4).
- 쿠버네티스 `Service` 의 셀렉터가 **파드와 WorkloadEntry를 함께** 고를 수 있어, 트래픽을 양쪽으로 보내며 **레거시를 무중단·점진적으로 마이그레이션**할 수 있다(그림 13.5).

### 13.1.3 메시 내 서비스의 DNS 해석

- VM은 클러스터 밖이라 `webapp.istioinaction` 같은 **내부 호스트네임을 해석하지 못한다.** 그런데 트래픽이 앱을 떠나 프록시로 리다이렉트돼야 라우팅이 시작되므로, DNS가 안 풀리면 트래픽이 아예 앱을 벗어나지 못한다(그림 13.7).
- **해결: DNS 프록시**(1.8+). istio-agent가 로컬 DNS 프록시를 띄우고, iptables 규칙으로 DNS 쿼리를 그리로 리다이렉트한다. istiod는 새 API인 **NDS(Name Discovery Service)** 로 메시의 서비스·`ServiceEntry` 항목을 DNS 프록시에 계속 동기화한다(그림 13.8).

> [!NOTE]
> **헬스 체크는 readiness만 istio-agent가 담당**
> - **readiness**(트래픽 받을 준비): istio-agent가 `WorkloadGroup` 의 프로브로 검사해 `WorkloadEntry` 상태(healthy/unhealthy)를 istiod에 보고.
> - **liveness**(살아있나, 죽으면 재시작): 서비스 메시 관심사가 아니라 **클라우드 플랫폼**(Azure scale set, AWS ASG, GCP MIG)의 헬스 체크가 담당. istio-agent 프로브는 관대하게, 클라우드 liveness는 보수적으로 두는 게 권장이다.

## 13.2 인프라 준비하기

실습(그림 13.9): `cool-store` 중 `webapp`·`catalog` 는 클러스터(`west-network`)에, **`forum` 서비스는 VM(`vm-network`)** 에 둔다. 서로 다른 네트워크라 VM↔클러스터 트래픽은 **east-west 게이트웨이**로 잇는다.

### 13.2.1 서비스 메시 준비하기

- Azure에 클러스터 생성 → `istio-system` 에 `topology.istio.io/network=west-network` 라벨 → `istioctl install` → `istioinaction` 에 사이드카 주입 라벨 → `webapp`·`catalog` 배포.
- 인그레스로 `/api/catalog/items/1` 호출해 정상 응답을 확인한다.

### 13.2.2 가상 머신 프로비저닝

- VM에 필요한 것: istio-agent 바이너리(데비안/레드햇용), 접속용 IP·SSH, 애플리케이션 포트(8080) 노출.
- `create-vm-in-azure.sh` 로 VM 생성 → SSH 접속 → `nmap -Pn -p 8080 $VM_IP` 하면 아직 **closed**(앱 미실행이라 정상).

## 13.3 가상 머신까지 메시 확장

VM 통합 기능은 기본 비활성이라, `IstioOperator` 로 켠다.

```yaml
spec:
  meshConfig:
    defaultConfig:
      proxyMetadata:
        ISTIO_META_DNS_CAPTURE: "true"              # DNS 쿼리를 DNS 프록시로
  values:
    pilot:
      env:
        PILOT_ENABLE_WORKLOAD_ENTRY_AUTOREGISTRATION: "true"   # 자동 등록
        PILOT_ENABLE_WORKLOAD_ENTRY_HEALTHCHECKS: "true"       # 상태 검사
```

### 13.3.1 istiod와 클러스터 서비스를 가상 머신에 노출하기

- VM이 별개 네트워크에 있으므로 **east-west 게이트웨이**를 설치하고(`cluster-east-west-gw.yaml`), `expose-services.yaml`(mTLS 포트 **15443**)·`expose-istiod.yaml` 로 istiod와 클러스터 서비스를 VM 쪽에 노출한다(그림 13.11).

### 13.3.2 WorkloadGroup으로 워크로드 그룹 나타내기

```yaml
apiVersion: networking.istio.io/v1alpha1
kind: WorkloadGroup
metadata:
  name: forum
  namespace: forum-services
  labels: { app: forum }        # 파드+WorkloadEntry를 함께 선택하는 라벨
spec:
  metadata:
    labels: { app: forum }
  template:
    ports: { http: 8080 }
    serviceAccount: forum-sa     # 워크로드 신원
    network: vm-network          # 같은 네트워크면 직접 IP, 다르면 east-west GW
  probe:
    httpGet: { port: 8080, path: /api/healthz }   # readiness 프로브
```

네임스페이스·서비스어카운트를 만들고 적용하면, 유효 토큰을 제시하는 VM이 이 그룹에 자동 등록된다.

### 13.3.3 가상 머신에 istio-agent 설치 및 설정하기

**① VM용 부트스트랩 설정 생성** (컨트롤 플레인 쪽에서)

```bash
istioctl x workload entry configure \
  --name forum --namespace forum-services \
  --clusterID "west-cluster" --externalIP $VM_IP \
  --autoregister -o ./ch13/workload-files/
```

`WorkloadGroup` 을 읽어 부트스트랩 파일들을 만든다 — `cluster.env`, `mesh`(설정), **`root-cert.pem`**(istiod 검증용), **`istio-token`**(서비스어카운트 토큰), `hosts`(istiod를 east-west GW IP로 해석).

**② VM으로 안전 전송** — 토큰이 들어 있어 `rsync -e "ssh ..."` 로 옮긴다.

**③ VM에서 설치·배치**

```bash
sudo dpkg -i istio-sidecar.deb              # 데비안(.deb) / 레드햇(.rpm)
# 파일들을 정해진 위치로
#   root-cert.pem → /etc/certs/root-cert.pem
#   istio-token   → /var/run/secrets/tokens/istio-token
#   cluster.env   → /var/lib/istio/envoy/cluster.env
#   mesh.yaml     → /etc/istio/config/mesh
#   hosts         → /etc/hosts 에 추가 (istiod를 east-west GW IP로)
sudo systemctl start istio                  # istio-agent 시작
```

`/var/log/istio/istio.log` 에서 `xdsproxy connected to upstream XDS server: istiod...:15012` 가 뜨면 컨트롤 플레인 연결 성공이다.

### 13.3.4 클러스터 서비스로 트래픽 라우팅하기

- `kubectl get workloadentry -n forum-services` — istio-agent가 붙는 순간 `WorkloadEntry` 가 자동 생성돼 있다.
- VM에서 `curl webapp.istioinaction/api/catalog/items/1` → 정상 응답이면 **VM→클러스터** 라우팅이 동작한다. 흐름: 앱 → DNS 프록시로 해석 → iptables가 아웃바운드 프록시로 리다이렉트 → east-west GW → webapp → catalog(그림 13.12).

### 13.3.5 트래픽을 WorkloadEntry로 라우팅하기

반대 방향(클러스터 → VM)은 파드 IP를 직접 쓰지 않고 **`Service`** 로 추상화한다(셀렉터 `app: forum` 이 WorkloadEntry를 엔드포인트로 잡는다).

> [!WARNING]
> **실습에서 겪는 디버깅 흐름**
> `Service` 를 만들고 `/api/users` 를 호출하면 처음엔 **HTTP 500** 이 난다. webapp 액세스 로그에 **`UH`**(no_healthy_upstream), `istioctl pc endpoints ... | grep forum` 은 비어 있다. `WorkloadEntry` 를 `-o yaml` 로 보면 `type: Healthy, status: "False", message: "...connection refused"` — 즉 **VM에서 forum 앱이 아직 안 떠서**(8080 미리슨) readiness 실패다. VM에서 `./forum` 을 실행해 8080을 열면, 헬스 체크 통과 → `WorkloadEntry` 가 `Healthy: True` → 엔드포인트 등록 → 호출이 **200** 이 된다.

### 13.3.6 컨트롤 플레인이 가상 머신에 설정: 상호 인증 강제

- VM도 사이드카가 트래픽을 관리하므로 이스티오 정책이 그대로 적용된다. 예로 `PeerAuthentication`(STRICT)을 걸면, 외부에서 `curl $VM_IP:8080` 같은 **평문 직접 접근은 거부**(Connection reset)되고, 메시 내부 경유(webapp→forum)만 통과한다. mTLS 정책이 VM 프록시에도 배포된 것이다.

## 13.4 DNS 프록시 이해하기

### 13.4.1 DNS 프록시가 클러스터 호스트네임을 해석하는 방법

`webapp.istioinaction` 이 풀리는 순서(그림 13.14):

1. 앱이 DNS 쿼리 → 2. OS가 `/etc/hosts` 먼저 확인 → 3. 없으면 기본 리졸버로 가는데, **iptables가 istio-agent DNS 프록시(포트 15053)로 리다이렉트** → 4. DNS 프록시가 istiod(NDS)가 채운 내부 항목에서 해석 → 5. 클러스터 서비스가 아니면 `resolv.conf` 의 실제 네임서버로 넘겨 외부 도메인 해석.

- 검증: `iptables-save | grep 'to-ports 15053'`, `netstat -ltunp`(pilot-agent가 15053 리슨), `dig +short @localhost -p 15053 webapp.istioinaction`.

### 13.4.2 DNS 프록시가 인식하는 호스트네임은 무엇인가?

- DNS 프록시가 아는 항목 = istiod가 **NDS API** 로 각 사이드카에 설정한 것. `.../debug/ndsz?proxyID=<워크로드>` 로 조회할 수 있다.
- istio-agent는 FQDN 하나에서 **짧은 변형들**(`webapp.istioinaction`, `...svc`, `...svc.cluster` 등)을 만들어 모두 같은 IP로 해석한다(쿠버네티스 내부 경험과 동일).

## 13.5 에이전트 동작 커스터마이징하기

- VM의 `/var/lib/istio/envoy/sidecar.env` 로 에이전트를 조정한다 — 예: `ISTIO_AGENT_FLAGS="--log_output_level=dns:debug"`(DNS 로그 디버그), `SECRET_TTL="12h0m0s"`(인증서 수명). 변경 후 `systemctl restart istio`.

## 13.6 메시에서 WorkloadEntry 제거하기

- VM을 삭제(`az vm delete ...`)하면 잠시 후 `WorkloadEntry` 가 **자동 정리**된다(`No resources found`). 클라우드 인스턴스의 일시성(auto-scaling)을 지원하려면 이 자동 정리가 중요하다.

## 요약

- VM 통합은 쿠버네티스에서 자동이던 일(프록시 설치·신원 부트스트랩·헬스 체크·등록·DNS 해석)을 **수작업/전용 리소스로 대응**하는 것이다(표 13.1).
- **`WorkloadGroup`(=Deployment) · `WorkloadEntry`(=Pod)** 로 VM을 표현하고, **자동 등록**으로 새 VM이 메시에 합류한다.
- **`istioctl x workload entry configure`** 로 부트스트랩 파일을 만들고, VM에 istio-agent를 설치해 **east-west 게이트웨이**를 통해 istiod에 연결한다.
- **DNS 프록시**(+ NDS)가 VM에서 클러스터 내부 호스트네임을 해석한다(`ISTIO_META_DNS_CAPTURE=true`).
- VM 사이드카도 다른 워크로드와 **동일하게** mTLS·트래픽 정책을 따른다.
