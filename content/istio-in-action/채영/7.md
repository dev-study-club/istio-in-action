7장은 관찰 가능성의 **데이터를 만드는 쪽**이다. 엔보이가 요청을 가로챌 때 생기는 메트릭을 이해하고, 이를 프로메테우스로 수집하고, 필요하면 메트릭 자체를 커스터마이징한다. 이렇게 쌓인 데이터를 8장에서 그라파나·예거·키알리로 시각화한다.

> [!IMPORTANT]
> **버전 확인하기**: 책은 이스티오 **1.13**, 최신은 **1.17+**. 큰 흐름은 같지만 세부 리소스·명령이 바뀐 곳이 있어, 달라진 지점마다 버전을 표시해뒀다. 실습 전 `istioctl version` 으로 내 버전을 확인하자.

## 7.1 관찰 가능성이란 무엇인가?

관찰 가능성(observability)은 시스템의 외부 신호(출력)만 보고 내부 상태를 추론할 수 있는 정도를 말한다. 제어이론에서 온 개념으로, 내부를 관찰할 수 있어야 올바른 제어(트래픽 전환·복원력·정책)를 걸 수 있다.

이스티오의 데이터 플레인(엔보이)이 요청 경로 한복판에 있으므로, 제어도 관찰도 이 네트워크 계층에서 이뤄진다. 단, 이스티오는 관찰 가능성의 _일부(앱 수준 네트워크 계측)_ 만 담당한다 — 전부가 아니다.

### 7.1.1 관찰 가능성 vs. 모니터링

- **모니터링**: 미리 정한 "나쁜 상태" 기준과 메트릭을 비교해 경보하는 것. 즉 **알고 있는** 실패를 감시한다. (예: 디스크 사용량이 임계값을 넘으면 경보)
- **관찰 가능성**: 모니터링을 포함하는 상위 개념. 시스템은 예측 불가하다고 전제하고, 카디널리티 높은 데이터(사용자 ID·요청 ID·소스 IP 등)까지 모아 **미처 몰랐던** 문제를 사후에 탐색·질문할 수 있게 한다.

> 예를 들어, 모든 임계값(디스크·대기열·머신 상태)은 정상인데 특정 사용자만 결제에서 10초 지연을 겪는다고 하면, 모니터링은 못 잡지만, 관찰 가능성을 염두에 뒀다면 요청이 거친 정확한 경로를 되짚어 찾아낼 수 있다.

### 7.1.2 이스티오는 어떻게 관찰 가능성을 돕는가?

- 엔보이가 요청 경로에 있어 **초당 요청 수·지연(백분위)·실패 수** 같은 핵심 메트릭을 앱 코드 수정 없이 포착한다. 새 메트릭도 동적으로 추가할 수 있다.
- 분산 트레이싱(요청이 거친 서비스·각 노드 소요 시간)도 지원한다 → 8장.
- **중요한 셋업 변화**: 2장에서 깐 데모용 프로메테우스·그라파나·키알리(`samples/addons/`)는 **삭제**하고, 7·8장은 더 현실적인 도구 셋으로 다시 구성한다.

```bash
cd istio-1.13.0
kubectl delete -f samples/addons/
```

## 7.2 이스티오 메트릭 살펴보기

데이터 플레인(요청 처리)과 컨트롤 플레인(설정 배포) 둘 다 방대한 메트릭을 낸다.

### 7.2.1 데이터 플레인의 메트릭

- 사이드카(엔보이)의 관리자 엔드포인트(`:15000/stats`)에서 커넥션·요청·런타임 통계를 볼 수 있다. distroless 이미지엔 curl이 없어 `pilot-agent request GET stats` 로도 조회한다.
- 핵심 표준 메트릭: **`istio_requests_total`**, `istio_request_bytes`, `istio_response_bytes`, `istio_request_duration(_milliseconds)`.
- 기본적으로 프록시는 통계를 **제한적으로만** 노출한다. 프록시가 아는 통계는 훨씬 많지만, 다 내보내면 시계열이 폭발해 수집 시스템이 과부하되기 때문이다. 더 보려면:
  - 메시 전체: `meshConfig.defaultConfig.proxyStatsMatcher` (수집 시스템 과부하 주의)
  - 워크로드별(권장): `proxy.istio.io/config` 애노테이션의 `proxyStatsMatcher.inclusionPrefixes`

> [!NOTE]
> **카디널리티(cardinality)란?**
> 라벨 값 조합의 가짓수를 말한다. **조합 하나가 시계열 하나**가 되므로, 사용자 ID처럼 값이 수만 가지인 라벨을 디멘션으로 붙이면 시계열이 폭발한다. "엔보이가 통계를 기본적으로 잘라내는 이유"도, "디멘션을 함부로 늘리면 안 되는 이유"(7.4)도 전부 여기서 나온다.
- 업스트림 클러스터 통계로 서킷브레이커 상태(`circuit_breakers.*`), 내부/외부 트래픽 구분(`internal.*`), TLS 세부(`ssl.*`), 커넥션/요청(`upstream_cx_*`, `upstream_rq_*`)을 확인한다. `:15000/clusters` 로는 엔드포인트별(리전/존/활성 요청/health)까지 본다.

### 7.2.2 컨트롤 플레인의 메트릭

- istiod(`:15014/metrics`)는 자기 동작을 노출한다: 인증서 발급·로테이션(`citadel_*`), 빌드 버전(`istio_build`), 연결된 프록시 수(`pilot_xds`), 알려진 서비스·VS 수(`pilot_services`, `pilot_virt_services`), xDS 푸시 횟수 등.
- **가장 중요한 지표**: `pilot_proxy_convergence_time` — 설정 변경을 프록시에 배포·수렴하는 데 걸린 시간(히스토그램). 컨트롤 플레인 성능의 핵심 지표다(11장 심화).
- 각 구성 요소에 일일이 접근하는 건 비현실적이므로, 메트릭 수집 시스템(프로메테우스)이 필요하다.

## 7.3 프로메테우스로 이스티오 메트릭 긁어오기

프로메테우스는 pull(당겨오기) 방식 메트릭 수집 엔진이다. 앱·프록시가 메트릭 엔드포인트를 노출하면 프로메테우스가 주기적으로 수집한다(push 방식과 대비). 같은 대상을 여러 서버가 수집해 고가용성으로 구성할 수 있다.

이스티오 프록시는 **`:15090/stats/prometheus`** 로 프로메테우스 형식 메트릭을 자동 노출한다. 우리가 할 일은 프로메테우스가 이걸 수집하게 설정하는 것뿐이다.

> [!TIP]
> **포트별 역할 — 15000 / 15090 / 15020**
> - **15000**: 엔보이 admin. 사람이 디버깅할 때 쓰는 곳(`/stats`, `/clusters`, `/reset_counters`). localhost 전용이고 프로메테우스가 수집하는 대상은 아니다.
> - **15090**: 엔보이가 내놓는 **원본 exporter**(`/stats/prometheus`). 엔보이 자기 통계만 있다.
> - **15020**: pilot-agent가 15090 + 애플리케이션 메트릭 + 자기 메트릭을 **머지**해 내놓는 곳. **프로메테우스가 실제로 수집하는 대상은 여기**다(사이드카에 `prometheus.io/port: 15020` 애노테이션이 붙어 있다). 뒤에서 PodMonitor가 이 흐름을 잡아준다.

### 7.3.1 프로메테우스와 그라파나 설정하기

- 데모 애드온 대신 **kube-prometheus**(`kube-prometheus-stack` 헬름 차트)를 설치한다. 프로메테우스 오퍼레이터 + 그라파나 + Alertmanager + node exporter 등 프로덕션 레벨 스택을 한 번에 갖춘다.
- 이 장에서는 프로메테우스 연결만 다루고, 그라파나 통합은 8장에서 이어간다.

### 7.3.2 이스티오 컨트롤 플레인과 워크로드를 긁어가도록 프로메테우스 오퍼레이터 설정하기

새로 깐 프로메테우스는 이스티오를 수집하는 법을 모른다. 오퍼레이터의 커스텀 리소스 2개로 알려준다.

| 리소스           | 대상                                                            |
| ---------------- | --------------------------------------------------------------- |
| `ServiceMonitor` | 컨트롤 플레인(istiod)을 수집                                     |
| `PodMonitor`     | `istio-proxy` 컨테이너가 있는 모든 파드의 `/stats/prometheus` 를 수집 |

적용 후 부하를 흘리면 프로메테우스 UI에서 `pilot_xds`(컨트롤 플레인)·`istio_requests_total`(데이터 플레인)이 조회된다. 메트릭 이름이 프로메테우스로 전파되는 데는 몇 분 걸릴 수 있다.

## 7.4 이스티오 표준 메트릭 커스터마이징하기

표준 메트릭은 좋은 출발점이지만 도메인에 맞게 확장할 수 있다. 먼저 세 가지 개념을 이해해야 한다.

- **메트릭(metric)**: 카운터/게이지/히스토그램 값 (예: `istio_requests_total`)
- **디멘션(dimension)**: 메트릭을 쪼개는 기준 (예: `response_code`, 방향(인바운드/아웃바운드)). 디멘션 조합이 다르면 별도 항목으로 집계된다. 같은 것을 **이스티오/엔보이에선 "디멘션", 프로메테우스에선 "라벨(label)"** 이라 부른다.
- **속성(attribute)**: 디멘션의 값을 채우는 런타임 데이터. 엔보이 기본 속성(`request.*`)과 이스티오 peer-metadata 속성(`upstream_peer.*` / `downstream_peer.*`: istio_version, cluster_id 등)이 있다.

> [!WARNING]
> **`reporter`라는 디멘션과 이중집계**
> 이스티오에서 요청 하나는 **사이드카를 두 번** 지난다. 부르는 쪽(source) 프록시에서 한 번, 받는 쪽(destination) 프록시에서 한 번. 그런데 **양쪽 프록시가 같은 요청을 각자 한 번씩** `istio_requests_total` 에 기록한다. 그걸 구분하는 라벨이 `reporter` 다.
>
> - `reporter="source"`: 부른 쪽이 본 것 (클라이언트 관점 — 네트워크 실패·타임아웃까지 포함)
> - `reporter="destination"`: 받은 쪽이 본 것 (서버가 실제로 받은 것)
>
> 그래서 논리적으로 **요청 1건 = 메트릭 2줄**이다. 아무 생각 없이 `sum(istio_requests_total)` 하면 값이 **조용히 2배**가 된다. 보통 `reporter="destination"` 한쪽으로 고정해서 센다.

한 요청 경로의 메트릭을 확인해보면 `reporter` 만 다른 두 줄이 보인다:

```bash
kubectl -n istioinaction exec deploy/webapp -c istio-proxy \
  -- curl -s localhost:15090/stats/prometheus | grep istio_requests_total
# ... reporter="source" ...      } 6
# ... reporter="destination" ... } 6    ← 같은 요청인데 두 줄
```

두 관점을 **굳이 둘 다 세는 이유**는, 그 차이가 곧 **둘 사이 네트워크에서 벌어진 일**이기 때문이다. 서버(destination)는 멀쩡한데 클라이언트(source)만 실패로 잡히면, 중간에서 무언가가 요청을 끊고 있다는 뜻이다. (8.1.3의 그라파나가 Client/Server를 나눠 보여주는 이유가 바로 이것)

> [!NOTE]
> **메타데이터 교환**
> `upstream_peer.istio_version`(업스트림 프록시 버전) 같은 속성이 마법처럼 보이지만 원리는 단순하다. 두 사이드카는 **커넥션을 맺을 때 서로의 워크로드 정보(이름·네임스페이스·버전·클러스터)를 교환**해 둔다. 그래서 내 쪽 프록시가 상대편 값을 자기 메트릭 디멘션으로 쓸 수 있다. 나가는(업스트림) 메트릭이면 `upstream_peer.`, 들어오는(다운스트림) 메트릭이면 `downstream_peer.` 를 붙인다.

### 7.4.1 기존 메트릭 설정하기

- 메트릭은 istiod가 설치하는 **EnvoyFilter(`stats-filter-*`)** = WebAssembly stats 플러그인으로 구성된다(성능을 위해 NULL VM에서 실행).
- 기존 메트릭에 디멘션 추가·제거: `IstioOperator` 의 `telemetry.v2.prometheus.configOverride` 에서 `dimensions:` 로 추가, `tags_to_remove:` 로 제거한 뒤 `istioctl install`. 뒷단에선 `stats-filter` 가 갱신된다.
- **주의**: 새 디멘션을 프록시가 실제로 내보내게 하려면 워크로드에 `sidecar.istio.io/extraStatTags`(= `proxy.istio.io/config` 의 `extraStatTags`) 애노테이션을 **파드 템플릿**에 달아야 한다 — **단, 이건 1.16 이하 얘기다(아래 참고)**.

> [!IMPORTANT]
> **버전 차이 — `extraStatTags`와 stats 확장**
> - **1.16 이하**: 메트릭 통계를 **WebAssembly stats 플러그인**(EnvoyFilter `stats-filter-*`)으로 처리했다. 새 디멘션을 추가하면 프록시가 그 태그를 알도록 `extraStatTags` 애노테이션을 **반드시** 달아야 했다.
> - **1.17+**: 통계가 **네이티브 stats 확장**으로 바뀌어 CPU/메모리 오버헤드가 줄었고, 커스텀 디멘션에 `extraStatTags` 가 **더 이상 필요 없다**(필드는 남아 있지만 Deprecated 표시). 1.17+ 에서 책(1.13)을 따라 하면 이 애노테이션을 붙여도 안 붙여도 결과가 같다.
> - **커스터마이징 방법**: **1.12** 에서 도입된 **Telemetry API** 로 옮겨가(이후 안정화), EnvoyFilter를 직접 만드는 대신 네임스페이스·워크로드 단위까지 선언적으로 설정하는 게 표준이 됐다.
> - **정리**: **1.16 이하** = `EnvoyFilter + Wasm stats + extraStatTags`, **1.17+** = `Telemetry API + 네이티브 stats`.

### 7.4.2 새로운 메트릭 만들기

- stats 플러그인의 `definitions:` 에 새 메트릭을 정의한다. 타입은 COUNTER/GAUGE/HISTOGRAM, 값은 **CEL 표현식**(속성 기반)이다. 예: `(request.method.startsWith('GET') ? 1 : 0)` → `istio_get_calls`.
- `istio_` 접두사는 자동으로 붙는다. 새 메트릭도 프록시가 노출하게 `sidecar.istio.io/statsInclusionPrefixes` 애노테이션이 필요하다.

### 7.4.3 새 속성으로 호출 그룹화하기

- 기존 속성을 조합해 **새 속성**을 만들어 호출을 의미 있게 그룹화한다. **attribute-gen 플러그인**(또 다른 Wasm 확장, stats보다 먼저 실행)을 EnvoyFilter로 구성한다.
- 예: `request.url_path` + `request.method` 를 매칭해 `istio_operationId`(getitems / createitem / deleteitem)를 생성 → 이를 `upstream_operation` 디멘션으로 `istio_requests_total` 에 붙여 "특정 API(`/items`)로의 GET 호출 수"를 추적한다.

## 마무리

- **모니터링은 관찰 가능성의 부분집합**이다. 모니터링은 알려진 나쁜 상태를 감시하고, 관찰 가능성은 예측 못 한 문제까지 사후 탐색한다.
- 이스티오는 사이드카 프록시가 요청을 가로챌 때 7계층(상태 코드·HTTP 메서드·헤더 등)에서 메트릭을 수집한다. 핵심은 **`istio_requests_total`**.
- 기본은 제한적 노출 → `meshConfig.defaultConfig`(메시 전체)나 `proxy.istio.io/config` 애노테이션(워크로드별)으로 확장.
- 컨트롤 플레인의 핵심 지표는 **`pilot_proxy_convergence_time`**(변경을 프록시에 배포하는 시간).
- 프로메테우스는 **pull 방식**으로 프록시의 `:15090/stats/prometheus` 를 수집하고, `ServiceMonitor`/`PodMonitor` 로 컨트롤·데이터 플레인 수집을 켠다.
- `IstioOperator` 로 메트릭/디멘션/속성을 개조할 수 있다. 이스티오는 **황금 신호(지연·처리량·오류·포화도)** 네트워크 메트릭 수집을 쉽게 해줄 뿐, 앱·비즈니스 메트릭을 대체하진 않는다.
