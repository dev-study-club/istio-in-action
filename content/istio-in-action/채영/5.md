# 5 트래픽 컨트롤: 세밀한 트래픽 라우팅

- 배포(release)와 릴리스(출시)를 분리하기
- DestinationRule로 "버전(subset)"을 정의하기
- VirtualService로 요청 라우팅 / 트래픽 시프팅 / 미러링 하기
- ServiceEntry로 클러스터 바깥 서비스를 메시에 등록하기

> 4장까지 = 트래픽을 클러스터 **안으로 들이기**(인그레스).
> 5장 = 들어온 트래픽을 **버전별로 어떻게 흘려보낼지** 세밀하게 제어하기.
> istio 로 어떤 요청을 어떤 버전으로 보낼지 규칙으로 세밀하게 제어한다.

## 5.0 배포(deploy) ≠ 릴리스(release)

- **배포** = 새 버전 코드를 프로덕션에 **띄우는 것** (트래픽은 아직 안 줌)
- **릴리스** = 그 버전에 **실제 사용자 트래픽을 흘리는 것**

이 둘을 분리하면, v2를 띄워만 놓고(배포) 트래픽은 천천히 조금씩 넘기며(릴리스) 안전하게 출시할 수 있다. 이스티오가 이 "트래픽을 언제/얼마나 줄지"를 담당한다.

## 5.1 준비물 2개 (한 쌍): DestinationRule + VirtualService

```bash
┌──────────────────┬──────────────────────────────────────────┐
│  리소스          │                  역할                     │
├──────────────────┼──────────────────────────────────────────┤
│ DestinationRule  │ "버전(subset) 목록 정의" — 여기 v1, v2 있음 │
│ VirtualService   │ "누굴 어디로 보낼지" — 라우팅 규칙         │
└──────────────────┴──────────────────────────────────────────┘
```

> 순서: VirtualService가 `subset: version-v2`라고 쓰려면, DestinationRule에 그 subset이 먼저 정의돼 있어야 한다.

### DestinationRule — 파드 라벨로 버전 그룹 나누기

`ch5/catalog-dest-rule.yaml`:

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: catalog
spec:
  host: catalog.istioinaction.svc.cluster.local
  subsets:
  - name: version-v1        # subset 이름
    labels:
      version: v1           # 파드 라벨 version=v1 인 애들 = 이 그룹
  - name: version-v2
    labels:
      version: v2
```

- catalog 파드에 붙은 라벨 `version: v1` / `version: v2` 로 그룹을 나눈다.
- 이제 VirtualService에서 `subset: version-v1` 처럼 **이름으로** 이 그룹을 가리킬 수 있다.

### 두 버전 배포 + DestinationRule 적용

실습 명령:

```bash
# v2 배포 (절대경로 — 어느 폴더에서든 실행 가능)
kubectl apply -f ~/Desktop/work/book-source-code/services/catalog/kubernetes/catalog-deployment-v2.yaml

# DestinationRule 적용 (subset 정의)
kubectl apply -f ~/Desktop/work/book-source-code/ch5/catalog-dest-rule.yaml

# v1/v2 파드 확인 (-L version = version 라벨을 컬럼으로 표시)
kubectl get pods -l app=catalog -L version
```

![alt text](images/notes/istio-in-action/채영/5-1.catalog-v1-v2-pods.png)

> DestinationRule만 적용하고 VirtualService가 없으면, 트래픽은 v1/v2에 **아무렇게나(라운드로빈)** 섞여 간다. 여기부터 VirtualService로 규칙을 잡는다.

### 추가로 알아보기 — keep-alive 커넥션

**상황.** 전부 v1으로 라우팅하던 VirtualService를 삭제하면 다시 v1/v2로 섞일 것으로 예상했다. 그러나 삭제 후에도 트래픽이 계속 v1으로만 갔다.

```bash
# VS 삭제 (라우팅 규칙 제거)
kubectl delete vs catalog -n istioinaction
kubectl get vs -n istioinaction
# NAME                GATEWAYS                HOSTS                         AGE
# webapp-vs-from-gw   ["coolstore-gateway"]   ["webapp.istioinaction.io"]   8d
#  → catalog VS 없음이 확인됨

# 그런데도 트래픽은 전부 v1
for i in $(seq 1 12); do curl -s -H "Host: webapp.istioinaction.io" http://localhost:8080/api/catalog | grep -q imageUrl && echo "v2" || echo "v1"; done
# v1 v1 v1 v1 v1 v1 v1 v1 v1 v1 v1 v1
```

![alt text](images/notes/istio-in-action/채영/5-keepalive-vs-deleted.png)

**설명.** 원인은 HTTP keep-alive 커넥션 재사용이다.

- webapp은 catalog와 한 번 맺은 HTTP 커넥션을 끊지 않고 이어서 재사용한다(keep-alive). 이미 v1 파드에 연결된 커넥션이 계속 사용되어 트래픽이 v1으로 유지된다.
- 앞 단계에서 v1/v2가 섞였던 것은 v2를 막 배포한 직후여서 커넥션이 새로 맺어지던 시점이었기 때문이다.

**확인.** webapp을 재시작해 기존 커넥션을 끊고 새로 맺게 하면 다시 v1/v2로 분산된다.

```bash
kubectl rollout restart deployment webapp -n istioinaction
# 재시작 후 다시 호출하면 새 커넥션이 v1/v2로 분산됨
for i in $(seq 1 16); do curl -s -H "Host: webapp.istioinaction.io" http://localhost:8080/api/catalog | grep -q imageUrl && echo -n "v2 " || echo -n "v1 "; done; echo
# v1 v1 v2 v1 v2 v1 v1 v2 v2 v2 v2 v1 v1 v2 v2 v1
```

**정리.**

- 라우팅 규칙(VirtualService)은 일반적으로 새로 맺어지는 커넥션과 요청에 적용된다.
- 이미 맺어진 keep-alive 커넥션은 이전 경로를 계속 사용할 수 있다.
- 라우팅 규칙을 바꿨는데 바로 반영되지 않는 것처럼 보일 때는, 커넥션 재사용 여부를 먼저 확인해볼 수 있다.
- weight(트래픽 시프팅)처럼 비율을 명시하면 엔보이가 요청 단위로 분배하므로 이런 현상이 잘 드러나지 않는다.

## 5.2 요청 라우팅 (Request Routing)

특정 **조건(헤더)이면** v2로, 나머지는 v1로 보낸다. = 다크 런치(dark launch). 신버전을 프로덕션에 올려두되 **나(테스터)만** 써보고 일반 사용자는 못 느끼게.

`ch5/catalog-vs-v2-request-mesh.yaml`:

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: catalog
spec:
  hosts:
  - catalog
  gateways:
    - mesh          # ⭐ mesh = 메시 내부(사이드카끼리) 트래픽에 적용 (게이트웨이 아님)
  http:
  - match:
    - headers:
        x-istio-cohort:
          exact: "internal"     # 이 헤더 달고 오면
    route:
    - destination:
        host: catalog
        subset: version-v2      # → v2 로
  - route:                      # 나머지 전부
    - destination:
        host: catalog
        subset: version-v1      # → v1 로
```

```bash
┌───────────────────────────────┬──────────┐
│         요청 조건             │  목적지  │
├───────────────────────────────┼──────────┤
│ x-istio-cohort: internal 있음 │  v2      │
│ 헤더 없음 (일반 사용자)       │  v1      │
└───────────────────────────────┴──────────┘
```

> `gateways: - mesh` = 이 규칙을 **인그레스 게이트웨이가 아니라 메시 내부 트래픽**(webapp → catalog 같은 사이드카끼리)에 적용한다는 뜻. 게이트웨이로 들어오는 트래픽에 걸려면 `gateways`에 게이트웨이 이름을 쓴다.

실습 명령 (port-forward 없이 클러스터 안에서 webapp이 자기 자신을 호출하는 방식):

```bash
# 요청 라우팅 규칙 적용
kubectl apply -f ~/Desktop/work/book-source-code/ch5/catalog-vs-v2-request-mesh.yaml

# 헤더 없이 → 전부 v1 (일반 사용자)
kubectl exec -n istioinaction deploy/webapp -c webapp -- sh -c \
  'for i in 1 2 3 4 5; do wget -qO- http://localhost:8080/api/catalog 2>/dev/null | grep -q imageUrl && echo v2 || echo v1; done'

# 헤더 달고 → 전부 v2 (나 = 테스터)
kubectl exec -n istioinaction deploy/webapp -c webapp -- sh -c \
  'for i in 1 2 3 4 5; do wget -qO- --header="x-istio-cohort: internal" http://localhost:8080/api/catalog 2>/dev/null | grep -q imageUrl && echo v2 || echo v1; done'
```

> 책은 맥에서 `curl -H "Host: webapp.istioinaction.io" -H "x-istio-cohort: internal" http://localhost:8080/api/catalog` 로 응답 본문(v2 엔 `imageUrl` 필드 있음)을 직접 확인한다. 위 방식은 8080 포트가 다른 프로세스에 점유돼 port-forward 가 안 될 때 쓴 대체 방법으로, 결과는 같다.

![alt text](images/notes/istio-in-action/채영/5-2.request-routing-v2.png)

## 5.3 트래픽 시프팅 (Traffic Shifting) — 비율로 나누기 (카나리)

버전을 **퍼센트(weight)로** 나눈다. 신버전을 조금씩 늘려가며 문제 없나 확인하고, 이상하면 즉시 비율을 되돌린다(롤백).

소수의 트래픽만 신버전(v2)으로 먼저 보내 문제를 조기에 감지하는 방식이다. 이상이 없으면 비율을 점차 늘리고, 문제가 있으면 즉시 비율을 되돌린다.

`ch5/catalog-vs-v2-10-90-mesh.yaml`:

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: catalog
spec:
  hosts:
  - catalog
  gateways:
  - mesh
  http:
  - route:
    - destination:
        host: catalog
        subset: version-v1
      weight: 90         # 90% 는 v1
    - destination:
        host: catalog
        subset: version-v2
      weight: 10         # 10% 만 v2 (카나리)
```

```bash
# 10% 만 v2 로
kubectl apply -f ch5/catalog-vs-v2-10-90-mesh.yaml -n istioinaction

# 100번 호출해서 v1/v2 비율 눈으로 확인
for i in $(seq 1 100); do curl -s http://localhost:8080/api/catalog -o /dev/null -w "%{http_code}\n"; done

# 문제 없으면 50:50 으로 상향
kubectl apply -f ch5/catalog-vs-v2-50-50-mesh.yaml -n istioinaction
```

```bash
카나리 진행:  90/10  →  50/50  →  0/100
              조심스레   반반       완전 이전
```

### Kiali로 트래픽 시프팅 눈으로 보기

Kiali 그래프에 트래픽이 흐르려면 두 가지가 동시에 필요하다. 이 둘은 역할이 다르다.

```bash
┌──────────────────┬────────────────────────────────────────────┐
│ ① 트래픽 생성    │ 요청을 계속 만드는 것 (Kiali에 점이 흐르는  │
│                  │ 이유). 이게 없으면 그래프가 비어 있다.      │
│ ② 라우팅 규칙    │ 그 요청을 어떻게 나눌지 (VS apply). 요청을  │
│                  │ 만들지는 않는다.                            │
└──────────────────┴────────────────────────────────────────────┘
```

**① 트래픽 계속 흘리기** — 클러스터 안에서 webapp이 스스로 catalog를 호출하게 하면 port-forward 없이도 트래픽이 발생한다.

```bash
kubectl exec -n istioinaction deploy/webapp -c webapp -- sh -c \
  'for i in $(seq 1 3000); do wget -qO- http://localhost:8080/api/catalog >/dev/null 2>&1; sleep 0.2; done'
```

**② 라우팅 규칙 적용** (위 5.3 의 90/10 apply). 그리고 Kiali에서 확인:

1. 상단 그래프 종류를 `Versioned app graph` 로 → catalog가 `v1` / `v2` 두 노드로 갈린다.
2. `Display ▾` → `Traffic Distribution` 체크 → 화살표에 % 가 표시된다.
3. 우상단 갱신 주기를 `Every 10s` 로 하면 화면이 자주 새로고침된다.

규칙(weight VS)을 적용하기 전에는 catalog가 v1/v2 로 갈리긴 하지만 비율이 통제되지 않는다(라운드로빈).

> VirtualService(또는 weight)가 없으면 Envoy의 기본 로드밸런싱이 v1/v2 엔드포인트에 번갈아가며 요청을 보냄

![alt text](images/notes/istio-in-action/채영/5-2.versioned-graph-roundrobin.png)

90/10 규칙을 적용하면 `catalog → v1` 이 약 90%, `catalog → v2` 가 약 10% 로 갈린다.

실습 명령:

```bash
# 90/10 카나리 규칙 적용
kubectl apply -f ~/Desktop/work/book-source-code/ch5/catalog-vs-v2-10-90-mesh.yaml

# (선택) 반반으로 상향
kubectl apply -f ~/Desktop/work/book-source-code/ch5/catalog-vs-v2-50-50-mesh.yaml
```

![alt text](images/notes/istio-in-action/채영/5-3.traffic-shift-kiali.png)

> 위 화면에서 `catalog → v1` 화살표는 약 89.8%, `catalog → v2` 는 약 10.2% 로 표시됐다. 설정한 90/10 과 거의 일치한다(요청 표본이 늘수록 90/10 에 수렴). weight 를 바꿔 apply 하면 실시간으로 반영된다(엔보이 xDS 무중단 반영).
>
> 여기서 keep-alive 고정 현상이 나타나지 않은 이유: 위 트래픽은 `wget` 이 매 요청 새 커넥션을 맺기 때문에, weight 규칙이 요청 단위로 분배된다.

## 5.4 트래픽 미러링 (Mirroring / Shadowing) — "복사본만 따로"

100% 는 v1(진짜)로 가고, **똑같은 요청의 복사본을 v2에도** 보낸다. 단, **v2의 응답은 버린다.** 사용자는 v2의 존재를 모르고, 나는 v2가 실제 트래픽을 어떻게 처리하는지 로그/메트릭으로만 관찰한다.

실제 사용자에게 v2 응답을 노출하지 않고, v2 가 실제 트래픽을 어떻게 처리하는지 동작만 관찰하는 방식이다. 사용자 영향이 없으므로 카나리보다 위험이 낮다.

`ch5/catalog-vs-v2-mirror.yaml`:

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: catalog
spec:
  hosts:
  - catalog
  gateways:
    - mesh
  http:
  - route:
    - destination:
        host: catalog
        subset: version-v1
      weight: 100        # 실제 응답은 100% v1
    mirror:              # ⭐ 복사본을 v2 로도 보냄 (응답은 무시)
      host: catalog
      subset: version-v2
```

실습 명령:

```bash
# 미러링 규칙 적용
kubectl apply -f ~/Desktop/work/book-source-code/ch5/catalog-vs-v2-mirror.yaml

# 트래픽 넣기 → 응답은 전부 v1 (미러는 v2 응답을 버림)
kubectl exec -n istioinaction deploy/webapp -c webapp -- sh -c \
  'for i in $(seq 1 20); do wget -qO- http://localhost:8080/api/catalog 2>/dev/null | grep -q imageUrl && echo v2 || echo v1; done'

# v2 사이드카 로그에 복사된 요청이 도착해 있다 (응답은 버려짐)
kubectl logs -n istioinaction -l app=catalog,version=v2 -c istio-proxy --tail=15
```

응답은 전부 v1 이다(미러는 v2 응답을 버리기 때문).

![alt text](images/notes/istio-in-action/채영/5-4.mirror-response-all-v1.png)

Kiali(Versioned app graph)에서 미러를 보려면 트래픽을 계속 흘린다.

```bash
kubectl exec -n istioinaction deploy/webapp -c webapp -- sh -c \
  'for i in $(seq 1 2000); do wget -qO- http://localhost:8080/api/catalog >/dev/null 2>&1; sleep 0.2; done'
```

Kiali(Versioned app graph)에서는 v1 과 v2 로 트래픽이 모두 흐르는 것으로 보인다. 카나리(90/10)와 달리 v2 도 v1 과 비슷한 양을 받는다(복사본이므로). 다만 사용자가 받은 응답은 전부 v1 이다.

![alt text](images/notes/istio-in-action/채영/5-4.mirror-kiali.png)

> 카나리와 미러의 Kiali 차이: 카나리는 v2 화살표가 얇다(설정한 비율만큼). 미러는 v2 도 v1 과 비슷하게 굵다(요청을 통째로 복사하므로). 그러나 미러의 v2 응답은 버려져서 사용자에게 가지 않는다.

## 5.5 클러스터 바깥으로의 트래픽 — ServiceEntry

메시는 기본적으로 **클러스터 안** 서비스만 안다. 클러스터 **밖** 서비스(외부 API 등)를 호출할 때, 그 대상을 메시에 **등록**해두면 그 호출에도 타임아웃/관측/정책을 걸 수 있다. 이 등록이 ServiceEntry.

`ch5/forum-serviceentry.yaml`:

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: ServiceEntry
metadata:
  name: jsonplaceholder
spec:
  hosts:
  - jsonplaceholder.typicode.com   # 외부 서비스 주소
  ports:
  - number: 80
    name: http
    protocol: HTTP
  resolution: DNS
  location: MESH_EXTERNAL          # 메시 바깥에 있는 대상이라는 표시
```

```bash
kubectl apply -f ch5/forum-serviceentry.yaml -n istioinaction
```

> ServiceEntry = "메시에 외부 손님을 명단에 올리는 것". 등록해야 메시가 그 외부 호출을 인지하고 제어할 수 있다.

## 요약하자면

- 5장은 **버전(subset)을 정의**하고(DestinationRule), 그 버전으로 **트래픽을 어떻게 흘릴지**(VirtualService) 세밀하게 제어하는 장이다.
- 트래픽 제어 3가지:
  1. **요청 라우팅** = 조건(헤더)이면 v2, 아니면 v1 (다크 런치)
  2. **트래픽 시프팅** = 퍼센트로 조금씩 (90/10 → 50/50 → 0/100), = 카나리
  3. **미러링** = 100% v1 + 복사본을 v2로 (응답 버림), 위험 0 테스트
- **ServiceEntry** = 클러스터 밖 서비스를 메시에 등록.
- 핵심 감각: **배포(띄우기) ≠ 릴리스(트래픽 주기).** 이스티오가 "트래픽을 언제 얼마나 줄지"를 코드 수정 없이 설정만으로 제어한다.
