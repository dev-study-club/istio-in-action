10장이 데이터 플레인 문제를 찾아 들어가는 단계였다면, 11장은 그 문제의 상류에 있는 **컨트롤 플레인(istiod)의 성능**을 다룬다. istiod가 설정을 얼마나 빠르게 데이터 플레인에 밀어 넣느냐가 메시 전체의 반응성을 좌우한다. 이 장에서는 성능에 영향을 주는 요소, 모니터링 방법(네 가지 황금 신호), 그리고 실제 튜닝 레버를 익힌다.

> [!IMPORTANT]
> **버전 확인하기**: 책은 이스티오 **1.13** 기준이다. 여기서 다루는 튜닝 레버(디스커버리 셀렉터, `Sidecar` 리소스, 디바운스/스로틀 env)는 최신에서도 동일하게 유효하다. `Sidecar` 리소스 API가 책의 `networking.istio.io/v1beta1` → 최신 `v1` 로 승격된 정도의 차이가 있다.

## 11.1 컨트롤 플레인의 주요 목표

컨트롤 플레인은 서비스 메시의 **두뇌**다. 운영자가 API(CRD)로 선언한 설정을 받아, 각 워크로드의 사이드카(데이터 플레인)를 **원하는 상태로 동기화**하는 것이 핵심 목표다.

- 동기화가 지연되면 프록시가 낡은 설정을 갖게 된다. 대표 증상이 **유령 워크로드(phantom workload)** — 이미 사라진 엔드포인트로 트래픽을 계속 보내 요청이 실패한다.
- 이스티오 설정은 **궁극적 일관성(eventually consistent)** 모델이라, 잠깐의 지연은 큰 문제가 아니다(실패한 요청은 기본 2회 재시도된다). 다만 지연이 몇 초를 넘어 최종 사용자에게 영향을 주기 시작하면 반드시 피해야 한다.

### 11.1.1 데이터 플레인 동기화 단계 이해하기

변경 이벤트 하나가 프록시에 반영되기까지 **네 단계**를 거친다. 이 중 튜닝 가능한 지점은 **② 디바운스**와 **③ 스로틀링**이다.

1. **이벤트 수신**: 워크로드·설정 변경 이벤트가 동기화를 촉발한다.
2. **디바운스(debounce) — 이벤트 배치화**: istiod가 이벤트를 즉시 처리하지 않고 잠시 모아 병합한다. 지연 시간이 만료되면 병합된 이벤트를 하나의 작업으로 푸시 대기열에 넣는다.
3. **스로틀링(throttling)**: 동시에 처리하는 푸시 개수를 제한해, 처리 중인 작업이 CPU를 충분히 받고 컨텍스트 스위칭 낭비를 줄인다.
4. **프록시로 푸시(수렴)**: 처리된 항목을 엔보이 설정으로 변환해 워크로드에 전송한다 → 프록시 수렴.

### 11.1.2 성능을 결정짓는 요소

| 요소 | 설명 |
| --- | --- |
| **변경 속도(빈도)** | 변경이 잦을수록 동기화 유지에 더 많은 처리가 필요하다. |
| **할당된 리소스** | istiod 리소스를 넘어서면 작업이 대기열로 밀려 푸시가 느려진다. |
| **관리 워크로드 수** | 업데이트 대상 워크로드가 많을수록 배포에 네트워크·처리 능력이 더 든다. |
| **설정 크기** | 설정이 클수록 더 많은 처리 능력·대역폭이 필요하다. |

이 중 **변경 속도**는 기반 환경에서 오는 것이라 제어하기 어렵고, 나머지 셋이 튜닝 대상이다.

## 11.2 컨트롤 플레인 모니터링하기

istiod는 지연·빈도·리소스 사용률·오류 등을 메트릭으로 노출한다. 조회는 istiod의 `:15014/metrics` 에서 한다.

```bash
kubectl exec -it -n istio-system deploy/istiod -- curl localhost:15014/metrics
```

일일이 접근하는 대신 그라파나 **Istio Control Plane Dashboard** 로 본다. 상단은 버전과 **Resource Usage**(Memory·CPU·Goroutines = 포화 신호), 아래로 내려가면 **Push Information**(XDS Pushes·Proxy Push Time·Connections)이 있다.

![Istio Control Plane Dashboard 상단 — Deployed Versions·Resource Usage(Memory/CPU/Goroutines)](images/notes/istio-in-action/채영/11-1.control-plane-dashboard.png)

### 11.2.1 컨트롤 플레인의 네 가지 황금 신호

구글 SRE의 **황금 신호(지연·포화·트래픽·오류)** 를 컨트롤 플레인에 적용한다.

**① 지연 시간(Latency)** — 데이터 플레인 업데이트에 걸리는 시간. **가장 중요한 지표**다.

| 메트릭 | 의미 |
| --- | --- |
| **`pilot_proxy_convergence_time`** | 이벤트가 푸시 대기열에 들어간 순간부터 워크로드 배포 완료까지 전 과정(가장 포괄적). 정상 시 100ms 이하. |
| `pilot_proxy_queue_time` | 푸시 대기열에서 기다린 시간. 여기가 길면 istiod를 **스케일 업**. |
| `pilot_xds_push_time` | 엔보이 설정을 워크로드에 푸시한 시간. 늘면 네트워크 대역폭 포화 → 설정 크기·변경 빈도를 줄인다. |

> [!TIP]
> 그라파나 **Istio Control Plane** 대시보드의 _Push Time_(구버전 _Proxy Push Time_)이 `pilot_proxy_convergence_time` 을 시각화한다. 경보 예: 10초간 지연 1초 초과 → Warning, 2초 초과 → Critical.

![Push Time 히트맵 — 설정 푸시가 일어날 때만 샘플이 찍히며, 여기서는 10ms 이하 구간에 분포(정상)](images/notes/istio-in-action/채영/11-2.proxy-push-time.png)

> [!NOTE]
> 히트맵은 **푸시가 일어난 순간에만** 찍힌다. 변경이 없으면 비어 있는 게 정상이고, 설정·엔드포인트가 바뀔 때(예: 워크로드 스케일, VirtualService apply) 비로소 색 셀이 나타난다.

**② 포화도(Saturation)** — istiod 리소스 사용률. **90% 이상이면 포화**다. istiod는 CPU 집약적이라 CPU가 먼저 포화된다.
- `container_cpu_usage_seconds_total`(컨테이너 보고), `process_cpu_seconds_total`(프로세스 보고).
- 포화 시 리소스(레플리카/CPU·메모리)를 늘린다.

**③ 트래픽(Traffic)** — 시스템 부하. **수신**(설정 변경)과 **발신**(프록시로 푸시)으로 나눈다.
- 수신: `pilot_inbound_updates`(설정 변경 수신 수), `pilot_push_triggers`(푸시를 유발한 이벤트 수), `pilot_services`(인지하는 서비스 수).
- 발신: `pilot_xds_pushes`(모든 유형의 푸시 수), `pilot_xds`(연결된 프록시 커넥션 수), `envoy_cluster_upstream_cx_tx_bytes_total`(전송한 설정 크기).

![XDS Pushes — 워크로드 스케일로 유발한 푸시. 유형별(Clusters/Endpoints/Listeners/Routes/sds)로 쌓여 보인다](images/notes/istio-in-action/채영/11-3.pilot-pushes.png)

![Connections — istiod에 연결된 프록시(엔보이) 커넥션 수(`pilot_xds`). 워크로드가 늘면 함께 오른다](images/notes/istio-in-action/채영/11-5.ads-monitoring.png)

**④ 오류(Errors)** — istiod 실패율.

| 메트릭 | 의미 |
| --- | --- |
| `pilot_total_xds_rejects` | 설정 푸시 거부 횟수 |
| `pilot_xds_cds_reject` / `eds_reject` / `rds_reject` / `lds_reject` | 어떤 xDS API 푸시가 거부됐는지 세분 |
| `pilot_xds_write_timeout` | 푸시 시작 시 오류·타임아웃 합계 |
| `pilot_xds_push_context_errors` | 엔보이 설정 생성 중 오류(주로 istiod 버그) |

## 11.3 성능 튜닝하기

튜닝은 크게 세 갈래다 — ① 이벤트 **배치 처리** 기간을 늘려 푸시 횟수 줄이기, ② **리소스 추가**(스케일 아웃/업), ③ **`Sidecar` 리소스·디스커버리 셀렉터로 설정 범위 줄이기**.

### 11.3.1 작업 공간 준비하기

- `catalog` + 더미 워크로드에 더해, 서비스 **약 600개**·워크로드 규모를 인위로 부풀려(`sleep-dummy-workloads.yaml`, `resources-600.yaml`) 설정을 크게 만든다.
- 다른 애플리케이션·게이트웨이·라우팅 리소스는 정리한 상태에서 시작한다.

### 11.3.2 최적화 전 성능 측정하기

- `bin/performance-test.sh --reps N --delay S` 로 반복 부하를 주고 **지연 P99** 와 **푸시 횟수(Push count)** 를 측정한다.
- **P99**: 요청의 99%가 처리된 최대 지연(예: P99 80ms = 99%가 80ms 이내).
- `--delay 2.5` 로 변경 간격을 벌려 배치 처리에 묻히지 않게 한다.
- **기준선 예시**: 약 **700회 푸시**, P99 ≈ 0.49ms.

> [!NOTE]
> **`Sidecar` 리소스로 설정 크기·푸시 줄이기 (레버 ①·②)**
> 이스티오는 서비스 간 접근 관계를 모르므로 **모든 프록시에 메시 전체 설정**을 보낸다. 그 결과 `catalog` 한 워크로드의 설정이 **약 2MB** 까지 부푼다(`:15000/config_dump` 로 확인). `istio-system` 에 메시 전체 기본 `Sidecar` 를 두면 각 프록시가 **필요한 대상만** 알게 된다.
>
> ```yaml
> apiVersion: networking.istio.io/v1beta1   # 최신은 v1
> kind: Sidecar
> metadata:
>   name: default
>   namespace: istio-system
> spec:
>   egress:
>     - hosts: ["istio-system/*", "prometheus/*"]
>   outboundTrafficPolicy:
>     mode: REGISTRY_ONLY
> ```
>
> 적용 후 설정 크기 **2MB → 644KB**, 워크로드별 `Sidecar` 까지 좁히면 **푸시 700 → 135, 지연도 하락**. `Sidecar` 는 `PeerAuthentication` 처럼 메시/네임스페이스/워크로드 범위로 적용된다. 핵심 필드는 `workloadSelector`, `egress.hosts`, `outboundTrafficPolicy.mode`(`REGISTRY_ONLY` vs `ALLOW_ANY`).

### 11.3.3 이벤트 무시하기: 디스커버리 셀렉터로 범위 좁히기 (레버 ③-a)

기본적으로 컨트롤 플레인은 **모든 네임스페이스**의 이벤트를 감시한다. 메시와 무관한 네임스페이스(다른 팀·배치성 워크로드)의 변경까지 처리하면 불필요한 부하가 생긴다. **디스커버리 셀렉터(discovery selectors)** 로 감시 대상을 좁힌다.

```yaml
# 포함 방식 — 라벨 붙은 네임스페이스만 감시
spec:
  meshConfig:
    discoverySelectors:
      - matchLabels:
          istio-discovery: enabled
```

```yaml
# 제외 방식 — 특정 라벨을 가진 네임스페이스 제외
    discoverySelectors:
      - matchExpressions:
          - key: istio-exclude
            operator: NotIn
            values: ["true"]
```

`istioctl install -f istio-discovery-selector.yaml` 적용 후, 무시할 네임스페이스에 `kubectl label ns <ns> istio-exclude=true` 를 붙인다.

### 11.3.4 이벤트 배치 처리 및 데이터 플레인에 밀어내기 위한 스로틀링 (레버 ③-b)

변경 속도 자체는 제어할 수 없지만, **배치 기간**을 조정해 푸시 횟수를 줄일 수 있다. 트레이드오프가 분명하다 — 배치를 길게 하면 푸시는 줄지만 **설정 반영이 늦어지고**(낡은 설정 위험), 짧게 하면 최신성은 높아지나 푸시가 많아진다.

| 환경 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `PILOT_DEBOUNCE_AFTER` | 100ms | 이벤트를 푸시 대기열에 넣기까지의 디바운스 시간. 이 안에 추가 이벤트가 오면 더 미룬다. |
| `PILOT_DEBOUNCE_MAX` | 10초 | 디바운스를 허용하는 최대 시간. 초과 시 병합 이벤트를 즉시 푸시. |
| `PILOT_ENABLE_EDS_DEBOUNCE` | true | 엔드포인트(EDS) 업데이트도 디바운스를 따를지. false면 엔드포인트는 즉시 반영. |
| `PILOT_PUSH_THROTTLE` | 100 | 동시에 처리하는 푸시 수. CPU 여유가 있으면 높여 업데이트를 빠르게. |

- 포화 상태이고 **수신 트래픽**이 병목이면 → 배치 기간을 늘린다.
- **발신 트래픽**이 병목이면 → 동시 푸시 수를 줄인다.
- 포화가 아니고 빠른 업데이트가 목표면 → 동시 푸시 수를 늘린다.

**예시**: `--set values.pilot.env.PILOT_DEBOUNCE_AFTER="2500ms"` 로 배치 기간을 늘리면 푸시가 **700 → 27** 로 급감한다(CPU·네트워크·메모리 절약). 단 반영이 늦어지므로 조금씩 조정한다.

> [!WARNING]
> 디바운스로 늘어난 대기 시간은 **지연 메트릭(`pilot_proxy_convergence_time` 등)에 잡히지 않는다.** 이 지표는 "푸시 대기열에 들어간 시점"부터 재기 때문이다. 그래서 배치 기간을 늘리면 메트릭상 지연은 좋아 보여도 실제 반영은 느려질 수 있다.

> [!NOTE]
> **리소스 추가 할당 (레버 ②) — 그리고 오토스케일링을 권하지 않는 이유**
> `Sidecar`·디스커버리 셀렉터로도 부족하면 리소스를 늘린다 — **발신 트래픽 병목이면 스케일 아웃(레플리카↑)**, **수신 트래픽 병목이면 스케일 업(CPU/메모리↑)**. 다만 istiod의 연결은 **오래 지속되는(long-lived) ADS 스트림**이라, 오토스케일링으로 레플리카를 늘려도 기존 커넥션이 잘 재분배되지 않는다. 그래서 저자는 istiod **오토스케일링을 권장하지 않고**, 필요하면 최댓값 근처로 고정하는 편을 권한다.

## 11.4 성능 튜닝 가이드라인

튜닝에 앞서 **단일 istiod 인스턴스의 권장 한계**(이스티오 팀 테스트 기준)를 기억한다.

- 쿠버네티스 서비스 최대 **1,000개**, 동기화 워크로드 **2,000개**, 메시 전체 초당 요청 **70,000개**
- 이 규모에서 istiod 인스턴스당 대략 **vCPU 1개 + 메모리 1.5GB** 소요. 대부분 운영 클러스터는 vCPU 2 + 2GB면 충분하다.

**가이드라인(순서대로)**

1. **정말 성능 병목인지 먼저 확인**: 데이터 플레인↔컨트롤 플레인 연결·쿠버네티스 API 서버 상태·`Sidecar` 범위 지정 여부부터 점검.
2. **병목 지점 파악**: 지연·포화·오류·트래픽 메트릭 활용. 포화 낮은데 지연이 오르면 스로틀을 높이고, 포화가 높으면 스케일 아웃/업.
3. **변경은 점진적으로**: 한 번에 하나씩(예: 디바운스 2배), 효과 없으면 원복 후 다른 변수.
4. **안전 최우선**: istiod는 메시 전체 관리자이므로 리소스를 관대하게, **레플리카는 2개 밑으로 내리지 않는다**.
5. **버스터블 VM 지양**: istiod는 CPU를 지속적으로 쓰므로 버스트성 성능은 부적합하다.

## 요약

- 컨트롤 플레인의 주요 목표는 **데이터 플레인을 원하는 상태로 동기화**하는 것이다.
- 성능 영향 요소: **변경 속도·할당 리소스·관리 워크로드 수·설정 크기.** 변경 속도만 제어 불가.
- 모니터링은 **네 가지 황금 신호**로 한다. 핵심 지표는 **`pilot_proxy_convergence_time`**(지연).
- 튜닝 레버 세 가지: **`Sidecar` 리소스로 설정 범위 축소**(가장 먼저), **디스커버리 셀렉터로 무관한 네임스페이스 무시**, **디바운스/스로틀 env로 배치 조정**.
- 부족하면 리소스 추가 — **발신 병목=스케일 아웃, 수신 병목=스케일 업.** istiod 리소스는 관대하게, 오토스케일링은 신중히.
