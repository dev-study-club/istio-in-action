# 6 복원력: 애플리케이션 네트워킹 문제 해결하기

- 클라이언트 측 로드 밸런싱
- 타임아웃(timeout)
- 재시도(retry) 와 그 위험
- 서킷 브레이킹(circuit breaking) = 커넥션 풀 제어 + 이상값 감지

> 2장·3장에서 retry 를 "맛보기"로 봤다면, 6장은 **복원력 본편**이다.
> 핵심 감각: 분산 시스템에서 네트워크와 상대 서비스는 **언젠가 반드시 실패한다.** 복원력 = "의존하는 대상이 실패해도 전체 시스템은 무너지지 않고 버티는 능력." 이를 **앱 코드 수정 없이 Istio 설정(DestinationRule/VirtualService)** 으로 적용한다.

> 6장 예제 앱은 `simple-web` → `simple-backend` 구조다(2~5장의 catalog/webapp 과 별개). simple-web 이 simple-backend 를 호출하고, simple-backend 에 지연/에러를 주입해 복원력 기능을 실험한다.

## 6.1 애플리케이션에 복원력 구축하기

과거에는 타임아웃·재시도·서킷 브레이킹 같은 복원력 로직을 **애플리케이션 라이브러리**(예: Netflix Hystrix/Ribbon)로 각 서비스 코드 안에 직접 넣었다. 언어마다 라이브러리를 새로 만들어야 하고, 설정이 코드 곳곳에 흩어지는 문제가 있었다.

이스티오는 이 복원력 기능을 **사이드카(Envoy)로 옮겨**, 앱 코드 수정 없이 DestinationRule/VirtualService 설정만으로 건다. 언어와 무관하게 동일하게 동작하고, 운영 중에 설정만 바꿔 조정할 수 있다.

이 장에서는 그 도구들(로드 밸런싱·타임아웃·재시도·서킷 브레이킹)을 하나씩 실습한다.

## 실습 준비 — 예제 앱 배포

`simple-web` → `simple-backend` 를 `istioinaction` 네임스페이스에 배포한다. 이 네임스페이스는 이미 `istio-injection=enabled` 라 사이드카가 자동 주입된다. `simple-backend` 는 로드밸런싱/이상값 감지 실습을 위해 파드를 **3개**(`-1` 1개 + `-2` 2개) 띄운다.

## 6.2 클라이언트 측 로드 밸런싱

여러 개의 백엔드 파드가 있을 때, **어느 파드로 보낼지** 고르는 방식. Envoy(클라이언트 쪽 사이드카)가 직접 고른다 → "클라이언트 측" 로드 밸런싱.

DestinationRule 의 `trafficPolicy.loadBalancer` 로 지정한다.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: simple-backend-dr
spec:
  host: simple-backend.istioinaction.svc.cluster.local
  trafficPolicy:
    loadBalancer:
      simple: ROUND_ROBIN     # ← 여기 알고리즘을 바꿈
```

```bash
┌────────────────┬──────────────────────────────────────────────┐
│   알고리즘     │                     뜻                        │
├────────────────┼──────────────────────────────────────────────┤
│ ROUND_ROBIN    │ 차례대로 하나씩 (기본). 균등 분배             │
│ RANDOM         │ 무작위로 하나                                 │
│ LEAST_REQUEST  │ 처리 중 요청이 가장 적은(=한가한) 파드로      │
└────────────────┴──────────────────────────────────────────────┘
```

- ROUND_ROBIN 은 파드를 순서대로 하나씩 선택하고, LEAST_REQUEST 는 처리 중인 요청이 가장 적은 파드를 선택한다. 일반적으로 LEAST_REQUEST 가 응답이 더 안정적이다(부하가 몰린 느린 파드를 자연히 회피하기 때문).

### 실습 — Kiali 로 파드 분산 관찰

DestinationRule 을 아직 안 걸어도 Envoy 는 기본값(ROUND_ROBIN)으로 로드밸런싱한다. 트래픽을 흘리면서 Kiali **Workload graph** 로 보면 `simple-backend` 가 두 워크로드(`simple-backend-1` 1파드 / `simple-backend-2` 2파드)로 갈라지는 게 보인다.

```bash
# 트래픽 계속 흘리기 (port-forward 18080 유지된 상태)
for i in $(seq 1 2000); do curl -s -H "Host: simple-web.istioinaction.io" http://localhost:18080 >/dev/null; sleep 0.3; done

# Kiali 열기
istioctl dashboard kiali
# Namespace=istioinaction, Graph=Workload, Display에 Traffic Distribution/Response Time 체크
```

![Kiali Workload 그래프 — 파드별 트래픽 분산 33.8% / 66.2%](images/notes/istio-in-action/채영/6-2.kiali-workload-graph.png)

게이트웨이 → `simple-web` → `simple-backend` 로 이어지고, `simple-backend` 노드가 오른쪽 두 파드 박스로 갈라진다. Kiali 엣지에서 **33.8% / 66.2% 로 분배되는 걸 확인할 수 있다.**

알고리즘을 바꿔보려면 DestinationRule 을 적용한다(같은 이름 `simple-backend-dr` 이라 apply 만 하면 교체됨):

```bash
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-dr-rr.yaml          # ROUND_ROBIN
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-dr-random.yaml      # RANDOM
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-dr-least-conn.yaml  # LEAST_CONN
```

> 참고: 이 예제는 파드 성능이 비슷해서 육안 차이는 작다. 책에서는 한 파드에 지연을 크게 주고 부하를 걸어 LEAST_CONN 이 ROUND_ROBIN 보다 꼬리 지연(p99)을 낮추는 걸 fortio 로 비교한다. 여기서는 "DestinationRule 하나로 알고리즘이 바뀐다"는 것과 Kiali 분산 관찰까지만 확인한다.

## 6.3 지역 인식 로드 밸런싱 (locality-aware)

- 같은 리전/존(가까운) 파드로 우선 보내면 지연이 줄고 비용도 준다. Istio 는 파드의 지역 정보로 **가까운 곳 우선** 라우팅을 자동 지원한다.
- 가까운 곳이 죽으면 먼 곳으로 넘긴다(failover). (예제: `simple-service-locality.yaml`, `simple-service-locality-failure.yaml`)

## 6.4 투명한 타임아웃과 재시도

타임아웃과 재시도는 둘 다 VirtualService 에 걸며, 앱 코드가 몰라도(투명하게) 사이드카가 처리한다.

### 6.4.1 타임아웃 (Timeout)

무한정 기다리지 않고 **제한 시간 넘으면 끊는다.** 느린 상대가 내 스레드/커넥션을 붙잡아 전체가 느려지는 걸 막는다.

VirtualService 에 `timeout` 을 준다.

```yaml
kind: VirtualService
metadata:
  name: simple-backend-vs
spec:
  hosts:
  - simple-backend
  http:
  - route:
    - destination:
        host: simple-backend
    timeout: 0.5s      # 0.5초 안에 응답 없으면 끊고 실패 처리
```

- 타임아웃이 없으면 느린 응답을 기다리는 동안 호출한 쪽의 리소스(스레드/커넥션)가 계속 묶인다. 제한 시간을 두면 그 시점에 실패로 처리해 리소스를 회수한다.
- (예제: `simple-backend-delayed.yaml` 로 백엔드에 지연을 주입해 타임아웃이 걸리는 걸 확인)

#### 실습 — 지연 주입 후 타임아웃 걸기

`simple-backend-delayed.yaml` 은 `simple-backend-1` 파드의 응답을 ~1초로 느리게 만든다(`TIMING_50_PERCENTILE: 1000ms`). 그 상태에서 VirtualService 에 `timeout: 0.5s` 를 걸면, 느린 backend-1 로 간 요청만 0.5초에 잘려 실패한다.

```bash
# 1) 지연 주입 (backend-1 을 ~1초 응답으로)
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-delayed.yaml
kubectl rollout status deploy/simple-backend-1 -n istioinaction

# 2) 타임아웃 0.5s 적용
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-vs-timeout.yaml
```

트래픽 확인. 주의: **호출은 반드시 `simple-web` 앱을 거쳐야** VS 타임아웃이 적용된다(사이드카 Envoy 가 직접 나가는 트래픽은 iptables 가로채기에서 제외돼 메시 규칙이 안 걸림). port-forward 는 `simple-web` 서비스로 건다.

```bash
kubectl port-forward -n istioinaction svc/simple-web 18090:80    # 이 터미널 점유
# 새 탭에서:
for i in $(seq 1 12); do curl -s -o /dev/null -w "code=%{http_code} time=%{time_total}s\n" http://localhost:18090; done
```

```
# 실제 출력 — 느린 backend-1 로 간 요청이 0.5초에 500 으로 잘림, 빠른 backend-2 는 정상

code=200 time=0.165204s
code=500 time=0.531s
...
```

![Kiali — 느린 backend-1 엣지만 빨강(타임아웃 에러), backend-2 는 초록](images/notes/istio-in-action/채영/6-3.kiali-timeout-error-edge.png)

### 6.4.2 재시도 (Retry) 와 그 위험

실패하면 다시 시도. VirtualService 의 `retries` 로 건다.

```yaml
kind: VirtualService
metadata:
  name: simple-backend-vs
spec:
  hosts:
  - simple-backend
  http:
  - route:
    - destination:
        host: simple-backend
    retries:
      attempts: 2
      retryOn: 5xx,retriable-status-codes    # 어떤 실패에 재시도할지
```

- Istio 는 기본으로 일부 재시도를 자동으로 걸어준다(끄려면 `simple-service-disable-retry.yaml` 처럼 명시적으로 0 으로).

#### ⚠️ 재시도의 위험 — 재시도 폭풍(retry storm)

재시도에는 대가가 따른다. **여러 클라이언트가 동시에 재시도하면 이미 부하가 큰 서비스에 부하가 몇 배로** 몰린다.

```bash
정상:        A → B (1회)
장애 시:     A → B 실패 → 재시도 → 재시도 ... (B 에 몇 배 부하)
게다가 A 도 여러 대면:  전부 동시에 재시도 → B 과부하로 다운 (retry storm / 재시도 폭풍)
```

완화 장치:
```bash
┌────────────────────┬────────────────────────────────────────────┐
│ retry budget       │ 전체 요청의 일정 % 까지만 재시도 허용         │
│ (재시도 예산)      │ → 폭주 방지 (예제: ef-retry-budgets.yaml)    │
├────────────────────┼────────────────────────────────────────────┤
│ retry hedging      │ 느린 요청에 대해 응답 전에 다른 파드로 한 번  │
│ (헤지 재시도)      │ 더 보내 빠른 쪽을 채택 (ef-retry-hedge.yaml) │
└────────────────────┴────────────────────────────────────────────┘
```

- 교훈(2·3장에서 본 것과 연결): **retry 는 간헐적으로 실패하는 상대에는 효과적이지만, 지속적으로 실패하는 상대에는 무력**하며, 오히려 부하를 키울 수 있다. 그래서 서킷 브레이킹이 필요하다.

#### 실습 — 재시도 켜기 전후 실패율 비교

`simple-backend-periodic-failure-500.yaml` 은 `simple-backend-1` 파드가 **75% 확률로 HTTP 500 을 응답으로 돌려주게** 만든다(`ERROR_RATE: 0.75`). backend-1 은 3파드 중 1개라 전체의 약 33% 가 backend-1 로 가고, 그 중 75% 가 실패하므로 재시도가 없으면 전체 약 25% 가 실패한다.

```bash
# 1) backend-1 을 75% 확률로 500 응답하도록
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-periodic-failure-500.yaml
kubectl rollout status deploy/simple-backend-1 -n istioinaction

# 2) 재시도 끄기 (attempts: 0) — 맨바닥 실패율부터 본다
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-service-disable-retry.yaml
```

호출은 반드시 `simple-web` 앱을 거쳐야 VS 규칙이 적용된다(사이드카가 직접 나가는 트래픽은 메시에 안 잡힘). port-forward 는 `simple-web` 서비스로.

```bash
kubectl port-forward -n istioinaction svc/simple-web 18090:80   # 이 터미널 점유

# 새 탭 — 재시도 OFF 상태로 20회
for i in $(seq 1 20); do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18090; done | sort | uniq -c
#   15 200
#    5 500        ← 재시도 없으면 약 25% 실패 (backend-1 로 간 요청들)
```

이제 재시도를 켠다(`attempts: 2`, `retryOn: 5xx,retriable-status-codes`).

```bash
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-vs-retry-on.yaml

# 적용 확인
kubectl get vs simple-backend-vs -n istioinaction -o jsonpath='{.spec.http[0].retries}'
# → {"attempts":2,"retryOn":"5xx,retriable-status-codes"}

# 재시도 ON 상태로 20회
for i in $(seq 1 20); do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18090; done | sort | uniq -c
#   20 200        ← 500 이 사라짐. 실패한 요청을 정상 파드(backend-2)로 재시도해 복구
```

- **재시도가 된 이유:** backend-1 만 고장이고 backend-2 는 정상이라, 재시도가 ROUND_ROBIN 으로 **다른(정상) 파드로 요청을 바꿔 보내** 성공한다.
- **반대로 모든 파드가 고장이면** 재시도는 무력하고 오히려 부하만 늘린다 → 이럴 때 필요한 게 6.5 서킷 브레이킹.

## 6.5 이스티오를 이용한 서킷 브레이킹

"계속 실패하는 상대에겐 아예 그만 보낸다." 두 가지 방식으로 건다. 둘 다 DestinationRule 의 `trafficPolicy`.

### 6.5.1 커넥션 풀 제어로 느린 서비스에 대응하기 (connectionPool)

상대에게 보낼 수 있는 **동시 커넥션/대기 요청 수에 상한**을 둔다. 상한을 넘는 요청은 즉시 실패시켜(빨리 실패, fail-fast) 과부하가 번지는 걸 막는다.

```yaml
kind: DestinationRule
metadata:
  name: simple-backend-dr
spec:
  host: simple-backend.istioinaction.svc.cluster.local
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 1              # 동시 TCP 커넥션 최대 1
      http:
        http1MaxPendingRequests: 1     # 대기 큐 최대 1
        maxRequestsPerConnection: 1
        maxRetries: 1
```

- 동시 처리량에 상한을 두는 것이다. 상한을 넘어선 요청은 대기시키지 않고 즉시 실패로 처리한다. 모든 요청을 받다가 백엔드 전체가 마비되는 것보다, 초과분을 빨리 실패시키는 편이 안전하다.
- 상한 초과로 막히면 Envoy 통계에 `upstream_cx_overflow` / `upstream_rq_pending_overflow` 같은 값이 오르고, 요청 텔레메트리에는 응답 플래그 **`UO`(Upstream Overflow)** 가 붙는다.

#### 실습 — 동시 요청을 몰아 fail-fast 유발

backend 를 정상 상태로 되돌린 뒤(에러/지연 제거), 재시도를 끄고(overflow 503 이 재시도로 가려지지 않게) 커넥션 풀 제한 DR 을 적용한다.

```bash
# 1) backend-1 정상 복구
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend.yaml
kubectl rollout status deploy/simple-backend-1 -n istioinaction
# deployment "simple-backend-1" successfully rolled out

# 2) 재시도 끄기
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-service-disable-retry.yaml
# virtualservice.../simple-backend-vs configured

# 3) 커넥션 풀 제한 DR 적용 (maxConnections:1, http1MaxPendingRequests:1)
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-dr-conn-limit.yaml
# destinationrule.../simple-backend-dr created
```

동시성 20 으로 50 요청을 한꺼번에 몰아넣는다. 커넥션 풀이 동시 1개 + 대기 1개만 허용하므로 나머지는 즉시 실패한다.

```bash
# 동시 20 병렬로 50 요청 (simple-web 경유)
seq 1 50 | xargs -P 20 -I{} curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18090 | sort | uniq -c
#    1 200
#   49 500        ← 동시에 몰린 요청 대부분이 즉시 실패(fail-fast)
```

실패가 정말 서킷브레이킹(커넥션 풀 초과) 때문인지 확인한다. Envoy 요청 텔레메트리에서 응답 플래그 `UO`(Upstream Overflow) 를 센다.

```bash
WEB=$(kubectl get pod -n istioinaction -l app=simple-web -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n istioinaction "$WEB" -c istio-proxy -- pilot-agent request GET stats \
  | grep simple-backend | grep 'response_flags.UO' | grep -oE ': [0-9]+$' | grep -oE '[0-9]+' | paste -sd+ - | bc
# → 49      ← UO(Upstream Overflow) 503 = 49건. 위 실패 개수와 일치
```

- `UO` = **Upstream Overflow**. 커넥션 풀 상한을 넘어 Envoy 가 백엔드로 보내지 않고 즉시 잘라낸 요청이다. "부하가 몰려도 상대를 무너뜨리지 않고, 초과분만 빠르게 실패시킨다"는 걸 수치로 확인한 것.
- 클라이언트에는 `500` 으로 보이는데, 이는 `simple-web` 앱이 사이드카로부터 받은 `503`(overflow)을 자기 응답에서 500 으로 감싸 내보내기 때문이다.

### 6.5.2 이상값 감지로 비정상 서비스에 대응하기 (Outlier Detection)

여러 파드 중 **유독 실패 많은 파드를 자동 감지해서 로드 밸런싱 풀에서 잠깐 뺀다.**

```yaml
kind: DestinationRule
metadata:
  name: simple-backend-dr
spec:
  host: simple-backend.istioinaction.svc.cluster.local
  trafficPolicy:
    outlierDetection:
      consecutive5xxErrors: 1     # 연속 5xx 1번이면
      interval: 5s                # 5초마다 검사
      baseEjectionTime: 30s       # 30초 동안 빼둠
      maxEjectionPercent: 100     # 최대 몇 %까지 뺄 수 있나
```

```bash
동작:  파드3개 중 하나가 5xx 를 응답으로 돌려줌
       → 이상값(outlier) 으로 판정 → 30초간 그 파드로 트래픽 안 보냄
       → 30초 뒤 조금씩 다시 넣어보고 정상이면 복귀
```

- 실패가 반복되는 파드만 일시적으로 로드 밸런싱 풀에서 제외하고, 나머지 정상 파드로만 트래픽을 보낸다.
- **읽는 법**: "아웃라이어 디텍션". outlier = 이상값(무리에서 벗어난 값).

#### 실습 — 불량 파드 자동 격리

`simple-backend-1` 을 다시 75% 실패 상태로 만들고, 이상값 감지 DR 을 적용한다(앞의 커넥션 풀 DR 을 덮어씀).

```bash
# 1) backend-1 다시 75% 500
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-periodic-failure-500.yaml
kubectl rollout status deploy/simple-backend-1 -n istioinaction
# deployment "simple-backend-1" successfully rolled out

# 2) 이상값 감지 DR 적용
kubectl apply -n istioinaction -f ~/Desktop/work/book-source-code/ch6/simple-backend-dr-outlier.yaml
# destinationrule.../simple-backend-dr configured
```

트래픽을 흘리며 실패율을 본다.

```bash
for i in $(seq 1 100); do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18090; done | sort | uniq -c
#   99 200
#    1 500       ← 이상값 감지 없던 맨바닥(~25% 실패)과 비교해 실패가 거의 사라짐
```

Kiali 로 보면 서킷브레이커가 걸렸다는 표시와 격리 효과가 함께 보인다:

![Kiali — 노드에 서킷브레이커 배지(⚡), backend-1 은 20%로 격리](images/notes/istio-in-action/채영/6-4.kiali-circuit-breaker-badge.png)

- 노드에 붙은 **⚡(번개) 배지 = 서킷브레이커(DR 의 outlierDetection/connectionPool)가 설정됐다**는 Kiali 표시. 옆의 🔀 배지는 VirtualService(라우팅) 표시다.
- 분산이 **20% / 80%** 로 나온다. 정상 backend-2 가 80% 를 받고, 고장난 backend-1 은 20% 만 받는다 — 대부분의 시간 동안 풀에서 빠져 있다는 뜻.
- **실패가 0 이 아니라 1% 남는 이유 (= "튀는" 현상):** `baseEjectionTime: 30s` 가 지나면 Envoy 가 backend-1 을 "이제 정상인가?" 확인하려고 잠깐 풀에 다시 넣는다(probe). 그 순간 들어간 요청이 다시 실패하면서 1건이 잡히고, 곧바로 재격리된다. Kiali 의 20% 트래픽이 이 주기적 probe 이고, 1% 실패가 그 결과다.

트래픽을 조금 더 흘려 격리가 완전히 안정되면 분산은 이렇게 굳는다:

![Kiali — 안정 상태. backend-1 은 0.6%(빨강), backend-2 는 99.4%(초록)](images/notes/istio-in-action/채영/6-5.kiali-outlier-steady.png)

엣지에 붙은 두 값의 의미:

- **backend-1 → 0.6% 빨강**: 고장난 파드(75% 500)라 이상값 감지가 반복해서 30초씩 격리한다. 거의 항상 풀에서 빠져 있고, `baseEjectionTime` 이 끝난 직후 "이제 정상인가?" 확인하는 **probe(간보기) 요청 0.6%** 만 여기로 간다. 그 요청도 실패하므로 색이 **빨강**이다. 즉 0.6% = "격리 중인 불량 파드에 가끔 넣어보는 확인용 트래픽".
- **backend-2 → 99.4% 초록**: 정상 파드라 나머지 트래픽 거의 전부(99.4%)를 받고 모두 성공한다. 그래서 **초록**. 즉 99.4% = "격리 덕분에 정상 파드로 몰린 실제 트래픽".
- `simple-web → simple-backend` 진입 엣지가 노랑인 것은 이 0.6% 의 실패가 전체에 소수 섞여 있기 때문이다.
- 앞의 20%/80% 그림은 격리가 자리잡는 초기 단계였고, 이 **0.6%/99.4% 가 충분히 안정된 뒤의 정상 동작**이다. 불량 파드로 가는 probe 비율은 시간이 지날수록 20% → 0.6% 처럼 계속 낮아져 0 에 가까운 값에서 안정된다.

### 서킷 브레이킹 정리

```bash
┌────────────────────┬──────────────────────────────────────────┐
│ connectionPool     │ "너무 많이 몰리면 더 안 받는다" (양 제한)  │
│ outlierDetection   │ "문제 있는 파드는 잠깐 뺀다" (품질 기준 격리) │
└────────────────────┴──────────────────────────────────────────┘
```

## 요약하자면

- 6장 = **복원력 본편.** 분산 시스템의 필연적 실패를 앱 코드 없이 Istio 설정으로 버티는 4가지 도구:
  1. **로드 밸런싱** = 어느 파드로 보낼지 (ROUND_ROBIN / LEAST_REQUEST / 지역 인식)
  2. **타임아웃** = 무한정 안 기다리고 끊기 (`timeout: 0.5s`)
  3. **재시도** = 실패 시 다시 (`retries`), 단 재시도 폭풍 주의 → budget/hedge 로 완화
  4. **서킷 브레이킹** = 계속 실패하는 상대 차단 (connectionPool 로 양 제한 + outlierDetection 으로 불량 파드 격리)
- 핵심 판단(2·3장에서 이어짐): **retry 는 간헐적 실패에는 유효하지만 지속적 실패에는 무력하고 위험**하다 → 그럴 때는 서킷 브레이킹으로 차단해야 한다.
- 어디에 거나: **타임아웃·재시도 = VirtualService**, **로드밸런싱·서킷브레이킹(커넥션풀/이상값 감지) = DestinationRule**.
