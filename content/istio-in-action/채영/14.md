이스티오의 기본 API(VirtualService·DestinationRule·AuthorizationPolicy…)만으로 부족한 요구가 생길 수 있다. 결국 데이터 플레인은 **엔보이 프록시**이므로, 그 엔보이 자체를 확장하면 속도 제한, 헤더 조작, 페이로드 보강, 커스텀 보안 토큰 처리 같은 요구를 메시 안에서 해결할 수 있다. 14장은 엔보이를 재빌드하지 않고 확장하는 네 갈래 — **EnvoyFilter · 외부 속도 제한 · 루아 · 웹어셈블리** 를 다룬다.

> [!IMPORTANT]
> **버전 확인하기**: 책은 이스티오 **1.13** 기준이다. 속도 제한·tap처럼 전용 API가 없던 기능을 당시엔 **`EnvoyFilter`** 로 우회했다. **웹어셈블리(Wasm) 지원은 실험적**으로 기술되며, 도구(`meshctl wasm`/`wasme`)·스펙이 유동적이던 시기다. 최신에선 `WasmPlugin`(`extensions.istio.io/v1alpha1`)이 표준 배포 수단으로 자리 잡았다.

## 14.1 엔보이의 확장 기능

엔보이는 **확장 가능하도록** 설계됐고, 인기 있는 확장 지점을 제공한다. 확장하려면 먼저 그 아키텍처(필터 체인)를 이해해야 한다.

### 14.1.1 엔보이의 필터 체인 이해하기

요청은 다음 순서로 흐르며, 각 단계가 확장 지점이다.

```
리스너 → 네트워크 필터 체인 → HTTP 커넥션 매니저(HCM) → HTTP 필터 체인 → (마지막) 라우터
```

- **리스너**(그림 14.1): 포트를 열고 다운스트림 트래픽(L3/L4)을 받는다.
- **네트워크 필터**(그림 14.2): 바이트 스트림을 순서대로 처리한다. 엔보이 핵심 기능이 여기 구현된다(MongoDB·Redis·Kafka 등, 그리고 가장 많이 쓰는 **HTTP 커넥션 매니저=HCM**).
- **HCM**(그림 14.3): 바이트 스트림을 HTTP 메시지(헤더·바디·트레일러)로 변환하고, 라우팅·액세스 로깅·재시도·헤더 조작을 담당한다. HCM 자체가 **HTTP 필터** 기반이다.
- **HTTP 필터 체인**(그림 14.4): CORS·외부 인증·속도 제한·결함 주입·Gzip·루아·RBAC·Tap·웹어셈블리 등이 순서대로 걸린다.

> [!NOTE]
> **가장 중요한 규칙**: HTTP 필터 체인의 **마지막은 반드시 터미널 필터인 `router`** 다. 라우터가 요청을 적절한 업스트림 클러스터로 보낸다. 그래서 새 필터는 항상 **라우터 앞에**(`INSERT_BEFORE`) 삽입한다.

### 14.1.2 확장용 필터

C++로 필터를 짜 엔보이에 내장할 수도 있지만(커스텀 빌드 유지보수 부담), **바이너리를 바꾸지 않고** 확장하는 세 방법이 있다 — **외부 처리 · 루아 · 웹어셈블리**. (외부 처리 필터는 책 저술 시점엔 아직 정식 배포 전이라, 책은 외부 속도 제한 서비스 호출 방식에 집중한다.)

### 14.1.3 이스티오의 데이터 플레인 커스터마이징하기

이 장에서 쓰는 확장 수단 정리:

- **`EnvoyFilter`** 리소스로 엔보이 HTTP 필터를 직접 설정
- **속도 제한 서버(RLS)** 호출
- **루아** HTTP 필터
- **웹어셈블리** HTTP 필터

## 14.2 EnvoyFilter 리소스로 엔보이 필터 설정하기

원하는 기능이 **기존 엔보이 필터**로 가능하면 `EnvoyFilter` 로 설정한다. 다른 이스티오 API(VirtualService 등)가 결국 엔보이 설정으로 변환되는 것과 달리, `EnvoyFilter` 는 **엔보이의 로우레벨 설정을 거의 그대로** 노출한다.

> [!CAUTION]
> `EnvoyFilter` 는 **가장 낮은 수준**의 API다. 엔보이 명명 규칙을 알아야 하고, **다른 모든 이스티오 리소스가 변환된 뒤 마지막에 적용**된다. 잘못 쓰면 메시를 마비시킬 수 있고, **엔보이 버전과 강하게 결합**돼 업그레이드 시 깨질 수 있다. 최후의 수단으로, `workloadSelector` 로 대상을 좁혀 신중히 쓴다.

**예제 — HTTP tap 필터**(그림 14.5): 데이터 플레인을 지나는 요청/응답을 샘플링해 콘솔로 스트리밍한다.

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata: { name: tap-filter, namespace: istioinaction }
spec:
  workloadSelector:
    labels: { app: webapp }          # ① 대상 워크로드
  configPatches:
    - applyTo: HTTP_FILTER            # ② 어디에
      match:
        context: SIDECAR_INBOUND
        listener:
          portNumber: 8080
          filterChain:
            filter:
              name: "envoy.filters.network.http_connection_manager"
              subFilter: { name: "envoy.filters.http.router" }
      patch:                          # ③ 무엇을
        operation: INSERT_BEFORE      # 라우터 앞에 tap 필터 삽입
        value:
          name: envoy.filters.http.tap
          typed_config: { ... Tap ... }
```

검증은 `istioctl pc listener` 로 필터가 붙었는지 확인하고, `:15000/tap` 에 설정을 올린 뒤 `x-app-tap: true` 헤더 요청을 보내면 그 요청의 헤더·바디가 tap으로 출력된다.

## 14.3 외부 호출로 요청 속도 제한하기

외부 서비스를 호출해 데이터 플레인을 확장하는 예다. 속도 제한은 **로컬**(프록시 단위)과 **글로벌**(공유 백엔드)로 나뉘는데, 여기서는 **글로벌 속도 제한**을 쓴다 — 복제본 수와 무관하게 일관되게 적용되도록, 모든 프록시가 공유 **속도 제한 서버(RLS)** 를 호출한다(그림 14.6·14.7).

- RLS는 엔보이 커뮤니티 구현체(`envoyproxy/ratelimit`)이고, 카운트는 **Redis**(또는 Memcached)에 저장한다.

### 14.3.1 엔보이 속도 제한 이해하기

- 엔보이는 요청 속성(원격 주소·헤더 등)을 묶은 **디스크립터(descriptor)** 를 만들어 RLS로 보낸다. RLS는 이를 미리 정의한 한도와 비교해 카운트를 올리고, 초과하면 **HTTP 429** 로 막는다(그림 14.8).
- **예제**: `x-loyalty` 헤더 등급별 한도(gold 10/분, silver 5/분, bronze 3/분, 없음 1/분).
  - RLS 한도는 **ConfigMap**(`domain` + `descriptors`)으로 정의한다.
  - "어떤 요청에 어떤 디스크립터를 보낼지"(라우트의 `rate_limits` 액션)는 전용 API가 없어 **`EnvoyFilter`**(`applyTo: VIRTUAL_HOST`, `header_value_match` 액션)로 지정한다.
- 배포: RLS+Redis+ConfigMap과 EnvoyFilter 2개를 적용한 뒤, `sleep` 에서 `catalog/items` 를 반복 호출해 한도 초과 시 차단되는지 확인한다.

## 14.4 루아로 이스티오의 데이터 플레인 확장하기

`EnvoyFilter` 는 **기존** 필터를 설정할 뿐이다. **커스텀 로직**을 요청/응답 경로에 넣고 싶으면(엔보이 재빌드 없이), 인라인 **루아(Lua)** 스크립트를 쓴다. `envoy_on_request()`·`envoy_on_response()` 를 구현해 헤더 조작·외부 호출 등을 한다(LuaJIT, 그림 14.9).

- **예제 — A/B 테스트 코호트 부여**: 요청 처리 중 외부 `bucket-tester` 를 **`httpCall()`**(넌블로킹)로 불러 응답값을 `x-test-cohort` 헤더로 추가한다.
- 루아는 `EnvoyFilter` 의 `inlineCode` 로 삽입한다(라우터 앞 `envoy.lua` 필터). 적용 후 요청 헤더에 `X-Test-Cohort: ...` 가 붙는다.

> [!NOTE]
> 요청 **바디**를 검사하려면 스트리밍 대신 전체를 메모리에 적재해야 할 수 있어 성능에 영향을 줄 수 있다.

## 14.5 웹어셈블리로 이스티오의 데이터 플레인 확장하기

마지막 방법. 원하는 언어로 **자체 엔보이 필터**를 만들어 런타임에 동적으로 로드한다.

### 14.5.1 웹어셈블리 소개

- **웹어셈블리(Wasm)** 는 여러 환경에서 이식·실행되도록 만든 바이너리 명령 형식이다(원래 브라우저용, 2019년 W3C 권고). **작은 용량·네이티브에 가까운 속도**, 그리고 **메모리 안전·샌드박스** 실행이 특징이다. 호스트가 모듈에 메모리·기능 접근을 허용한다.

### 14.5.2 왜 엔보이에 웹어셈블리를 사용하는가?

엔보이 필터를 직접 짤 때의 두 단점을 해소한다.

- 반드시 **C++** 여야 함 → Wasm은 **여러 언어** 허용
- 변경을 **엔보이 새 바이너리로 정적 빌드**해야 함 → 엔보이는 **Wasm 실행 엔진을 내장**해(그림 14.11) **재빌드 없이 런타임 동적 로드**

### 14.5.3 웹어셈블리로 새로운 엔보이 필터 만들기

- 엔보이 버전이 지원하는 **ABI**를 알아야 한다. Solo.io의 **`wasme`**(또는 `meshctl wasm`)가 스캐폴딩·빌드를 자동화한다.
- Wasm SDK 지원 언어 4종: **C++ · Rust · AssemblyScript · TinyGo**. 책은 타입스크립트 변형인 **AssemblyScript**를 쓴다.

> [!CAUTION]
> 책 저술 시점 엔보이의 웹어셈블리 지원은 **실험적**이다. 운영 투입 전 철저히 테스트한다.

### 14.5.4 meshctl로 새 엔보이 필터 빌드하기

`meshctl` 은 도커 비슷한 방식으로 Wasm 모듈을 만들고 빌드·배포한다.

```bash
curl -sL https://run.solo.io/meshctl/install | sh
meshctl wasm init ./hello-wasm --language=assemblyscript   # 스캐폴딩(index.ts)
meshctl wasm build assemblyscript ./hello-wasm/ \
  -t webassemblyhub.io/<user>/istioaction-demo:0.1          # OCI 이미지로 패키징
meshctl wasm push webassemblyhub.io/<user>/istioaction-demo:1.0
```

- `index.ts` 는 `onResponseHeaders()` 에서 응답에 헤더를 추가하는 예를 담는다(`onRequestHeaders`·`onRequestBody` 등도 있다).
- 결과는 **OCI(Open Container Initiative) 호환 이미지**라, 기존 컨테이너 레지스트리에 저장할 수 있다. 공개 저장소 **`webassemblyhub.io`** 를 쓸 수 있다.

### 14.5.5 새로운 웹어셈블리 엔보이 필터 배포하기

배포는 **`WasmPlugin`** 리소스로 선언적으로 한다.

```yaml
apiVersion: extensions.istio.io/v1alpha1
kind: WasmPlugin
metadata: { name: httpbin-wasm-filter, namespace: istioinaction }
spec:
  selector:
    matchLabels: { app: httpbin }                            # ① 대상 워크로드
  pluginName: add_header
  url: oci://webassemblyhub.io/<user>/istioaction-demo:1.0    # ② 모듈 URL
```

적용 후 `httpbin` 을 호출하면 응답에 모듈이 넣은 헤더(`hello: world!`)가 보인다. 커스텀 로직을 원하는 언어로 작성해 **런타임에 동적 로드**한 것이다.

## 요약

- 엔보이 아키텍처는 **리스너 + 필터 체인**이 중심이고, HTTP 필터 체인의 **마지막은 항상 `router`** 다.
- **`EnvoyFilter`**: 이스티오 API로 노출되지 않는 엔보이 설정까지 직접 건드린다. 강력하지만 **저수준·버전 결합**이라 신중히.
- **속도 제한·tap** 같은 기능은 (전용 API가 없던 시절) EnvoyFilter로 붙였다. 글로벌 속도 제한은 **RLS + Redis** 를 호출한다.
- **루아**: 인라인 스크립트로 헤더 조작·외부 넌블로킹 호출 등 커스텀 로직을 간단히.
- **웹어셈블리**: 원하는 언어로 새 필터를 만들어 **OCI 이미지로 패키징 → 레지스트리 push → `WasmPlugin` 으로 동적 로드.** 재빌드가 필요 없고 이식성이 가장 높다(단, 당시엔 실험적).
- 우선순위: **기존 엔보이 필터(EnvoyFilter) → 루아(간단) → 웹어셈블리(강력·이식)** 순으로 필요에 맞춰 고른다.
