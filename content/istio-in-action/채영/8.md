7장이 관찰 데이터를 **만드는 쪽**이었다면, 8장은 그 데이터를 **보는 쪽**이다. 프로메테우스에 쌓인 메트릭을 그라파나로 그래프화하고, 요청이 거친 경로를 예거로 추적하고, 서비스 간 트래픽 흐름을 키알리로 지도처럼 본다.

> [!IMPORTANT]
> **버전 확인하기**: 책은 이스티오 **1.13**, 최신은 **1.17+**. 화면 구성은 거의 같지만, 트레이싱·텔레메트리는 **Telemetry API**가 표준이 됐고(8.2.3) 키알리 차트 버전도 다르다(8.3.1). 달라진 지점마다 버전을 표시해뒀다.

## 8.1 그라파나를 사용해 이스티오 서비스와 컨트롤 플레인 메트릭 시각화하기

kube-prometheus에 딸려온 그라파나(`prom-grafana`)를 사용한다. 기본 로그인은 `admin` / `prom-operator`.

### 8.1.1 이스티오의 그라파나 대시보드 설정하기

- 이스티오 대시보드는 공식 배포판에서 빠졌으므로 GitHub 소스(`ch8/dashboards/*.json`)에서 직접 가져온다.
- 방식: 대시보드 JSON들을 **ConfigMap**으로 만들고 `grafana_dashboard=1` **라벨**을 붙이면 그라파나가 자동 인식한다(사이드카 로더). 컨트롤 플레인·워크로드·서비스·메시·성능·확장 대시보드가 생긴다.

### 8.1.2 컨트롤 플레인 메트릭 보기

- **Istio Control Plane Dashboard** → CPU/메모리/고루틴, 컨트롤 플레인 오류, 설정 동기화 문제, 활성 데이터 플레인 커넥션 수 등.
- 각 그래프의 **Explore** 로 원본 PromQL을 볼 수 있다. 예: _Pilot Push Time_ = `pilot_proxy_convergence_time`(7장의 그 지표).

### 8.1.3 데이터 플레인 메트릭 보기

- **Istio Service Dashboard** 에서 서비스를 선택(예: `webapp.istioinaction`)하면 클라이언트/서버 요청량·지연·성공률(non-5xx)·TCP 바이트 등이 보인다.
- 이 그래프들은 표준 메트릭으로 채워지며, 7장 방식으로 커스텀·특정 엔보이 메트릭을 추가해 확장할 수 있다.

> [!NOTE]
> **대시보드가 Client / Server를 나눠 보여주는 이유 — `reporter`(7장 이중집계)**
> 7장에서 본 `reporter` 가 여기서 실제로 쓰인다. 같은 호출이 부른 쪽(`reporter="source"` = Client)과 받은 쪽(`reporter="destination"` = Server) 양쪽에서 기록되므로, 대시보드도 둘을 갈라 보여준다. **나눠 보면 정보, 합치면 거짓말**이다 — 예컨대 Server 성공률은 100%인데 Client 성공률만 떨어지면, 둘 사이(네트워크·타임아웃·재시도·서킷브레이커)에서 요청이 끊기고 있다는 신호다.

## 8.2 분산 트레이싱

마이크로서비스는 요청 하나가 여러 홉을 거친다. 어디서 느려지고 실패하는지 알려면 홉 전체를 꿰는 도구가 필요한데, 그것이 **분산 트레이싱**(구글 Dapper 논문 기원)이다.

이스티오 데이터 플레인이 요청에 상관관계 메타데이터를 붙여, 개발자가 언어별 라이브러리를 직접 붙이는 부담을 크게 덜어준다. 단, 완전 자동은 아니다(아래 8.2.1의 함정 참고).

### 8.2.1 분산 트레이싱은 어떻게 작동하는가?

- **스팬(span)**: 한 서비스·구성 요소 내 작업 단위(시작·종료 시각, 이름, 태그, 로그). 스팬에는 **스팬 ID·트레이스 ID** 가 있다.
- **트레이스(trace)**: 여러 스팬을 인과관계로 엮은 것(요청이 거친 전체 그래프).
- 프록시가 요청을 통과시킬 때 진행 중인 트레이스가 없으면 새로 시작하고 **B3 집킨 헤더**를 붙인다. 이미 헤더가 있으면 기존 트레이스로 이어붙인다. (B3는 집킨의 옛 이름 **B**ig **B**rother **B**ird 에서 온 말로, 집킨이 정한 트레이스 전파 형식을 가리킨다.)

한 요청의 추적 정보(트레이스 컨텍스트)를 다음 홉으로 넘기는 헤더 묶음이다:

| 헤더 | 역할 |
| --- | --- |
| `x-b3-traceid` | **요청 전체**를 식별하는 ID (홉이 여럿이어도 하나) |
| `x-b3-spanid` | **지금 이 구간**(스팬)의 ID |
| `x-b3-parentspanid` | 부모 스팬 ID (누가 나를 불렀나 = 인과관계) |
| `x-b3-sampled` | 이 요청을 수집(샘플링)할지 여부 (1/0) |
| `x-b3-flags` | 디버그 등 플래그 |
| `x-request-id` | 엔보이의 요청 상관관계 ID (엄밀히는 B3는 아니지만 함께 씀) |
| `x-ot-span-context` | 오픈트레이싱 스팬 컨텍스트 |

> [!WARNING]
> **가장 중요한 함정**: 이스티오는 "들어온 요청"과 "그 결과 나가는 호출"을 자동으로 연결하지 못한다. 그래서 **애플리케이션이 이 헤더들을 모든 하위 호출에 직접 전파해야** 트레이스가 끊기지 않는다. (대개 RPC 프레임워크가 자동 전파해 준다)

- 오픈트레이싱 구현체(실제 트레이싱 백엔드): **예거**, **집킨**, 라이트스텝, 인스타나. (오픈텔레메트리는 이들을 아우르는 상위 프레임워크)
  - **집킨(Zipkin)**: 트위터가 만든 원조 오픈소스 분산 트레이싱 시스템. 앞서 나온 **B3 헤더 형식을 정의**했다. 예거가 집킨 형식과 호환되므로, 이스티오는 예거를 쓰면서도 트레이싱 설정은 `zipkin` 으로 붙는다(8.2.2).

### 8.2.2 분산 트레이싱 시스템 설치하기

- 예거는 DB가 필요해 복잡하므로, 학습용으로 예거 샘플(`samples/addons/jaeger.yaml`)을 그대로 사용한다.
- 이 샘플이 이스티오 기본값에 맞는 **`zipkin` 쿠버네티스 서비스**를 만들어 줘서 바로 연결된다(예거는 집킨 형식과 호환).

> [!IMPORTANT]
> **버전 차이 — 예거 v1 → v2**
> 책의 예거는 **v1(all-in-one·인메모리)** 이다. 이스티오 **1.30 애드온은 예거 v2(`jaeger:2.14.0`)** 로 바뀌었는데, OpenTelemetry Collector 기반에 Badger 파일 저장소를 쓴다(v1은 2025년 12월 31일 EOL — [jaeger #6321](https://github.com/jaegertracing/jaeger/issues/6321)). 트레이스 수집도 **OTLP(4317/4318)** 가 기본이고, `zipkin`(9411) 서비스는 B3 호환용으로 함께 남아 있다. (이 랩에도 v2가 떠 있다)

### 8.2.3 분산 트레이싱을 수행하도록 이스티오 설정하기

- 트레이싱은 **메시 전체 / 네임스페이스 / 워크로드** 3단계로 설정할 수 있다.
- 백엔드 지정 방법:
  - 설치 시: `IstioOperator` 의 `meshConfig.defaultConfig.tracing.zipkin.address: zipkin.istio-system:9411`
  - 설치 후: `istio-system` 의 `istio` configmap(MeshConfig) 수정
  - 워크로드별: `proxy.istio.io/config` 애노테이션
- 지원 백엔드: 집킨 / 데이터독 / 예거(집킨 호환) / 스택드라이버 등.
- 검증: 인그레스로 외부 httpbin `/headers` 를 호출하면 응답에 `x-b3-*` 집킨 헤더가 자동으로 붙어 있음을 확인할 수 있다.

> [!IMPORTANT]
> **버전에 따른 트레이싱 설정 방법**
> - **~1.13 (책 기준)**: `meshConfig.defaultConfig.tracing.zipkin.address` 로 백엔드를 직접 박고 B3(집킨) 형식으로 스팬을 밀어 보냈다.
> - **1.30 (지금)**: `zipkin.address` 는 legacy(동작은 함). 표준은 **`meshConfig.extensionProviders` 로 백엔드(예: OTLP)를 등록하고 `kind: Telemetry` 로 켜는** 방식이다(Telemetry API는 1.22부터 stable). 실제로 이 랩의 istiod도 `otel-tracing` extensionProvider로 예거 v2에 OTLP로 연결돼 있다.

### 8.2.4 분산 트레이싱 데이터 보기

- 예거 UI(`istioctl dashboard jaeger`, `:16686`)에서 Service = `istio-ingressgateway` 를 선택하고 Find Traces. 트레이스가 없으면 트래픽을 조금 보낸다.
- 트레이스를 클릭하면 스팬 타임라인·세부 정보가 보인다. 데모 프로파일은 샘플링이 100%라 기본적으로 다 잡힌다.

### 8.2.5 트레이스 샘플링, 강제 트레이스, 커스텀 태그

- **샘플링**: 트레이싱은 성능 비용이 크므로 수집 비율을 조절한다. MeshConfig의 `tracing.sampling`(예: `10` = 10%)으로 전역 설정. 운영에선 낮게 두는 게 정석이다.

> [!WARNING]
> **책의 "애노테이션 워크로드별 샘플링"은 깨지기 쉽다**
> 책은 `proxy.istio.io/config` 애노테이션의 `tracing.sampling` 으로 워크로드별 샘플링을 건다. 그런데 이 애노테이션은 mesh 설정을 **필드 단위로 "덮어쓰기"(deep merge 아님)** 한다. `sampling` 만 적으면 **트레이싱 백엔드 주소까지 통째로 날아가 트레이스가 아예 안 잡히고**, "전역값이 이긴 것처럼" 보인다.
> 관련 istio/istio 이슈 (시간 순, 모두 종료됨):
> - [#30141](https://github.com/istio/istio/issues/30141) (2021): 애노테이션으로 sampling을 덮어써도 무시돼 트레이스가 안 들어온다.
> - [#32114](https://github.com/istio/istio/issues/32114) (2021): `sampling` 만 바꾸면 트레이싱 설정 전체가 지워진다 — 이 현상의 대표 이슈.
> - [#34161](https://github.com/istio/istio/issues/34161) (2021): 애노테이션 sampling이 적용되지 않는다.
> - [#49560](https://github.com/istio/istio/issues/49560) (2024): 같은 원인의 일반화 — 애노테이션이 `meshConfig.defaultConfig` 를 필드 단위로 지운다.
>
> 이 동작은 버그가 아니라 의도된 것이라 코드로 고쳐지진 않았고, **2024년 이스티오 1.22에서 Telemetry API가 stable 되면서 "애노테이션 대신 이걸 써라"로 정리됐다**(아래 참고).
>
> 또 샘플링 결정은 요청 경로의 **첫 프록시(보통 인그레스 게이트웨이)에서 내려지고**, 하위 프록시는 B3 헤더로 전파된 그 결정을 따른다. 그래서 중간 워크로드만 올려도 소용없고, 게이트웨이를 올린 뒤 재배포해야 한다.

> [!IMPORTANT]
> **버전 차이 — 지금은 Telemetry API로 샘플링 (1.22+ 안정)**
> 이스티오 **1.22+** 에선 애노테이션 대신 `kind: Telemetry` 의 `randomSamplingPercentage` 로 건다. 네임스페이스(셀렉터 없이 그 ns에 배치)·워크로드(`selector.matchLabels`) 단위로 스코프가 잡히고, 우선순위는 **Telemetry API > 애노테이션 > meshConfig** 다.

```yaml
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: sampling
  namespace: istioinaction
spec:
  tracing:
    - randomSamplingPercentage: 10
```
- **강제 트레이스**: 샘플링을 낮게 두고, 진단이 필요한 특정 요청에만 **`x-envoy-force-trace: true`** 헤더를 넣어 그 요청과 하위 호출 그래프 전체를 강제로 추적한다.
- **커스텀 태그**: 스팬에 키-값 메타데이터를 추가해 보고·필터·탐색에 활용한다. 세 가지 소스가 있다 — ① 리터럴 값, ② 환경 변수, ③ 요청 헤더. `proxy.istio.io/config` 의 `tracing.customTags` 로 설정한다.
- **(심화) 백엔드 엔진 커스터마이징**: 호스트·포트만이 아니라 수집 엔드포인트 등을 바꾸려면 **커스텀 부트스트랩**(`sidecar.istio.io/bootstrapOverride` + configmap)을 쓴다.

> [!CAUTION]
> 커스텀 부트스트랩은 내부 엔보이 버전에 강하게 결합돼 이전 버전과의 호환성을 보장하지 않는다. 잘못하면 서비스가 중단되는 고급 시나리오이므로, 라이브 적용 전 철저히 테스트한다.

## 8.3 키알리를 이용한 시각화

**키알리** 는 프로메테우스 메트릭 + 예거 트레이스를 읽어 **실시간 방향 그래프(directed graph)** 로 메시를 그리는 대시보드다. 게이지·차트에 강한 그라파나와 달리, 키알리는 **서비스 간 연결·트래픽 흐름의 상호작용형 지도**에 특화돼 있다.

### 8.3.1 키알리 설치하기

- 데모 샘플 대신 **키알리 오퍼레이터**(헬름)를 권장한다. **선행 조건: 프로메테우스가 먼저 있어야 한다**(키알리가 거기서 메트릭을 읽는다).
- `Kiali` 커스텀 리소스에서 프로메테우스 URL·예거 URL·인증 전략(예제는 `anonymous`)을 지정하면 오퍼레이터가 키알리 인스턴스를 배포한다. `:20001` 로 접근.
- 화면 흐름:
  - **Overview**: 네임스페이스별 앱 수·건강 상태 개요
  - **Graph**: 트래픽 이동·바이트/요청 수·버전별 흐름(카나리 등)·초당 요청 수·health·HTTP/TCP·네트워크 실패를 한눈에
  - **워크로드 상세 탭**: Overview / Traffic(인·아웃 성공률) / Logs(앱·엔보이·연관 스팬) / **Inbound·Outbound Metrics(스팬↔메트릭 상관관계)** / Traces / Envoy(적용된 CDS·LDS·RDS)
- **텔레메트리 연관(correlation)**: 메트릭·트레이스·로그를 한 화면에서 이어봐서 "지연 급증 → 관련 트레이스 → 원인(새 버전 / 성능 저하 서비스)"을 창 여러 개 안 열고 추적할 수 있다.
- **워크로드 vs 애플리케이션**: 워크로드는 동일 복제본으로 뜨는 실행 바이너리(쿠버네티스에선 디플로이먼트의 파드). 애플리케이션은 워크로드들 + 서비스·설정을 묶은 상위 개념이다.
- 운영 보너스(10장 예고): 키알리는 잘못된 이스티오 설정도 검증한다 — 없는 Gateway를 가리키는 VirtualService, 없는 목적지 라우팅, 같은 호스트에 VS 중복, 못 찾는 subset 등.

### 8.3.2 결론

그라파나(메트릭 대시보드) → 예거(다중 홉 지연 추적, 단 앱의 헤더 전파 필요) → 키알리(트래픽 흐름 그래프)로 이어지는 **관찰 가능성 시각화 3종 세트**를 갖췄다. 다음(9장)은 이 트래픽을 _보호_ 하는 단계다.

## 마무리

- **그라파나**: 이스티오 컨트롤·데이터 플레인용 기본 대시보드로 메트릭을 시각화한다. 대시보드는 ConfigMap + `grafana_dashboard=1` 라벨로 주입한다.
- **분산 트레이싱**: 요청 처리에 관여한 구성 요소를 꿰뚫어 본다. 프록시가 요청에 트레이스 헤더를 붙이지만, 전체 시야를 얻으려면 **애플리케이션이 헤더를 전파해야** 한다.
- **트레이스 = 스팬의 모음.** 다중 홉에서 지연·실패 위치를 찾는 데 쓴다. 샘플링·강제 트레이스·커스텀 태그로 수집을 조절한다.
- 트레이싱 백엔드는 설치 시 `defaultConfig`(메시 전체)로 걸거나 `proxy.istio.io/config` 애노테이션(워크로드별)으로 건다.
- **키알리**: 오퍼레이터로 프로메테우스 메트릭 + 예거 트레이스를 읽어, 네트워크 그래프·메트릭 상관관계 등 이스티오 전용 디버깅 대시보드를 제공한다.
