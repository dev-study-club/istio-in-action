# 4 이스티오 게이트웨이: 클러스터로 트래픽 들이기

- 클러스터 **바깥**에서 안으로 트래픽을 넣는 인그레스 게이트웨이
- `Gateway` + `VirtualService` 두 리소스의 역할 나누기
- 호스트 기반 라우팅 (올바른 Host면 200, 아니면 404) 직접 확인
- TLS(HTTPS) 게이트웨이 세우고 인증서 검증까지

> 2장에서 게이트웨이를 "맛보기"로 썼다면, 4장은 게이트웨이를 **제대로** 다룬다. 특히 HTTPS/TLS.
> 핵심 분업: **Gateway = L4/L5(포트·호스트·TLS 열기), VirtualService = L7(어느 앱으로 라우팅)**

## 4.1 인그레스 개념

- **인그레스(ingress)** = 클러스터 바깥 → 안으로 들어오는 트래픽. 이 트래픽의 관문이 `istio-ingressgateway`(엔보이).
- 인그레스 게이트웨이도 결국 **엔보이**다. 파드 안에서 실제 엔보이 프로세스가 도는 걸 확인할 수 있음:

```bash
kubectl -n istio-system exec deploy/istio-ingressgateway -- ps aux | grep envoy
istio-p+  18  /usr/local/bin/envoy -c etc/istio/proxy/envoy-rev.json --drain-time-s 45 ...
```

> 즉 3장에서 도커로 띄운 엔보이와 **동일한 엔보이**가 클러스터 입구에 서 있는 것. (에지 프록시 역할)

### 4.1.1 Gateway 리소스 — 문을 연다

`ch4/coolstore-gw.yaml` : "ingressgateway에서 80 포트를, `webapp.istioinaction.io` 호스트에 대해 열어라"

```yaml
kind: Gateway
metadata:
  name: coolstore-gateway
spec:
  selector:
    istio: ingressgateway          # 어느 게이트웨이 파드에 적용할지
  servers:
  - port: { number: 80, name: http, protocol: HTTP }
    hosts:
    - "webapp.istioinaction.io"    # 이 호스트만 받음 (2장의 "*"와 다름!)
```

```bash
kubectl apply -n istioinaction -f ch4/coolstore-gw.yaml
gateway.networking.istio.io/coolstore-gateway created

# 게이트웨이가 진짜 8080 리스너를 열었는지 istioctl로 확인
# (기본 istio-ingressgateway는 권한 없이 뜨려고 80이 아닌 8080을 listen)
istioctl proxy-config listener deploy/istio-ingressgateway -n istio-system
ADDRESSES PORT  MATCH DESTINATION
0.0.0.0   8080  ALL   Route: http.8080          # ← 우리가 연 문
0.0.0.0   15021 ALL   Inline Route: /healthz/ready*
0.0.0.0   15090 ALL   Inline Route: /stats/prometheus*
```

> 문(Gateway)만 열면 아직 "어디로 보낼지" 규칙이 없음 → 호출하면 **404**.

```bash
# VirtualService 없이 호출 → 404 (문은 열렸지만 길 안내가 없음)
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8081/api/catalog -H "Host: webapp.istioinaction.io"
404
```

### 4.1.2 VirtualService 리소스 — 길을 안내한다

`ch4/coolstore-vs.yaml` : "coolstore-gateway로 들어온 `webapp.istioinaction.io` 트래픽을 webapp 서비스로 보내라"

```yaml
kind: VirtualService
metadata:
  name: webapp-vs-from-gw
spec:
  hosts:
  - "webapp.istioinaction.io"
  gateways:
  - coolstore-gateway          # ← coolstore-gateway로 들어온 것만
  http:
  - route:
    - destination: { host: webapp, port: { number: 80 } }
```

```bash
kubectl apply -n istioinaction -f ch4/coolstore-vs.yaml
virtualservice.networking.istio.io/webapp-vs-from-gw created

# 이제 라우트가 생김
istioctl proxy-config route deploy/istio-ingressgateway -n istio-system
NAME       VHOST NAME                     DOMAINS                     VIRTUAL SERVICE
http.8080  webapp.istioinaction.io:80     webapp.istioinaction.io     webapp-vs-from-gw.istioinaction
```

### 호스트 기반 라우팅 확인 (핵심)

```bash
# 올바른 Host → 200 + 실제 응답
curl -s -o /dev/null -w "Host: webapp.istioinaction.io → %{http_code}\n" \
  http://localhost:8081/api/catalog -H "Host: webapp.istioinaction.io"
Host: webapp.istioinaction.io → 200

curl -s http://localhost:8081/api/catalog -H "Host: webapp.istioinaction.io"
[{"id":1,"color":"amber","department":"Eyewear","name":"Elinor Glasses","price":"282.00"}, ...]

# Host 없음 / 틀린 Host → 404 (게이트웨이가 거부)
curl -s -o /dev/null -w "Host 헤더 없음          → %{http_code}\n" http://localhost:8081/api/catalog
Host 헤더 없음          → 404
curl -s -o /dev/null -w "Host: wrong.example.com → %{http_code}\n" \
  http://localhost:8081/api/catalog -H "Host: wrong.example.com"
Host: wrong.example.com → 404
```

> **핵심:** Gateway가 `webapp.istioinaction.io`만 받도록 열려있어서, 요청 Host가 `webapp.istioinaction.io`가 아니면 **문 앞에서 404로 거부**. 같은 IP·포트라도 Host 헤더로 갈라 보내는 게 L7 라우팅.

> 💡 kind 로컬 참고: `EXTERNAL-IP`가 없어서 `kubectl port-forward svc/istio-ingressgateway 8081:80`으로 연결해서 테스트함. 실제 클라우드면 게이트웨이의 LoadBalancer IP로 바로 호출.

## 4.2 게이트웨이 트래픽 보안 (TLS/HTTPS)

지금까진 평문 HTTP. 이제 HTTPS로 암호화하자.

```bash
Gateway가 처리하는 계층
   L4/L5 : 포트 열기, TLS 종료(암호 풀기), SNI로 어느 인증서 쓸지 결정
VirtualService가 처리하는 계층
   L7    : 복호화된 HTTP를 보고 어느 서비스로 라우팅
```

### TLS 인증서를 시크릿으로 등록

```bash
# webapp 인증서 + 키를 istio-system에 시크릿으로 생성
kubectl create -n istio-system secret tls webapp-credential \
  --key  ch4/certs/3_application/private/webapp.istioinaction.io.key.pem \
  --cert ch4/certs/3_application/certs/webapp.istioinaction.io.cert.pem
secret/webapp-credential created
```

### HTTPS(443) 게이트웨이 적용

`ch4/coolstore-gw-tls.yaml` : 80(HTTP)에 더해 443(HTTPS)을 열고, 위 시크릿을 인증서로 지정

```yaml
  - port: { number: 443, name: https, protocol: HTTPS }
    tls:
      mode: SIMPLE                     # 서버 TLS (표준 https)
      credentialName: webapp-credential # ← 위에서 만든 시크릿
    hosts:
    - "webapp.istioinaction.io"
```

```bash
kubectl apply -n istioinaction -f ch4/coolstore-gw-tls.yaml
gateway.networking.istio.io/coolstore-gateway configured
```

### HTTPS 호출 + 인증서 검증

```bash
# port-forward 8443 → 443, CA 체인으로 서버 인증서 검증
curl -s -o /dev/null -w "https 응답코드: %{http_code}\n" \
  https://webapp.istioinaction.io:8443/api/catalog \
  --cacert ch4/certs/2_intermediate/certs/ca-chain.cert.pem \
  --resolve webapp.istioinaction.io:8443:127.0.0.1
https 응답코드: 200

# 인증서 정보 (누가 발급했나 + TLS 버전)
curl -sv https://webapp.istioinaction.io:8443/api/catalog --cacert ... --resolve ... 2>&1 | grep -iE "subject:|issuer:|SSL connection"
* SSL connection using TLSv1.3 / AEAD-CHACHA20-POLY1305-SHA256
*  subject: CN=webapp.istioinaction.io
*  issuer:  CN=webapp.istioinaction.io

# CA 검증 없이(신뢰 안 함) 호출 → 연결 거부 (000)
curl -s -o /dev/null -w "%{http_code}\n" https://webapp.istioinaction.io:8443/api/catalog \
  --resolve webapp.istioinaction.io:8443:127.0.0.1
000   # ← 인증서를 신뢰 못 해 TLS 핸드셰이크 실패 (정상 보안 동작)
```

> **정리:** 게이트웨이가 TLS를 **종료(termination)** 한다 = 바깥과는 HTTPS로 암호화해 주고받고, 클러스터 안으로는 복호화된 트래픽을 넘김. 앱은 TLS를 몰라도 됨.

### 그 외 (개념만)

```bash
┌──────────────────────┬────────────────────────────────────────────┐
│      TLS 모드/기능    │                    설명                    │
├──────────────────────┼────────────────────────────────────────────┤
│ SIMPLE               │ 서버 인증서만 (일반 https)                 │
│ MUTUAL (mTLS)        │ 서버+클라이언트 양쪽 인증서 (상호 인증)    │
│ PASSTHROUGH (SNI)    │ 게이트웨이가 복호화 안 하고, SNI(호스트명) │
│                      │ 만 보고 뒤로 그대로 넘김                   │
├──────────────────────┼────────────────────────────────────────────┤
│ HTTP→HTTPS redirect  │ 80으로 오면 443으로 강제 리다이렉트        │
│ TCP 게이트웨이       │ HTTP 아닌 raw TCP도 게이트웨이로 통과 가능 │
└──────────────────────┴────────────────────────────────────────────┘
```

- **SNI(Server Name Indication)** : TLS 핸드셰이크 때 "나 `webapp.istioinaction.io` 갈래"라고 **암호화 전에** 알려주는 필드. 게이트웨이가 이걸 보고 어느 인증서/백엔드를 쓸지 결정. (PASSTHROUGH 모드의 핵심)
- **게이트웨이 액세스 로그** : `ingress-gw-access-logging.yaml`로 켜면 게이트웨이 통과 요청을 로그로 남김.
- **쿠버네티스 Gateway API** : 표준 인그레스를 대체하는 새 API. 이스티오의 Gateway/VirtualService가 여기에 영감을 줬음(이스티오 게 먼저 나옴). 둘은 별개 리소스.

## 요약하자면
- [Gateway] 문 열기 = 포트/호스트/TLS 지정 (L4/L5). "webapp.istioinaction.io의 80·443을 연다"
- [VirtualService] 길 안내 = 들어온 트래픽을 어느 서비스로 (L7). Gateway와 `gateways` 필드로 묶임
- [분업] Gateway 없이 VS만 → 안 됨 / VS 없이 Gateway만 → 404. 둘이 짝
- [호스트 라우팅] 같은 IP·포트라도 Host 헤더로 갈라 보냄. 안 맞으면 404로 거부
- [TLS] 시크릿(cert+key) → Gateway가 credentialName으로 참조 → 게이트웨이에서 TLS 종료. 앱은 몰라도 됨
- [ingressgateway] 결국 엔보이(에지 프록시). 3장에서 다룬 엔보이가 클러스터 입구에 선 것
