## 기본 기능으로 부족할 때, 엔보이를 직접 확장합니다

- **엔보이 필터**가 무엇이고 어떻게 동작하는지 이해하기
- **EnvoyFilter** 리소스로 엔보이를 직접 설정하기
- **외부 호출**(속도 제한 서버)로 요청 처리 결정하기
- **루아(Lua)** 스크립트로 데이터 플레인 확장하기
- **웹어셈블리(Wasm)** 모듈로 데이터 플레인 확장하기

이스티오는 트래픽 분산·보안·가시성 같은 기능을 기본으로 많이 제공하지만, 현실의 요구사항은 그보다 복잡합니다. 조직마다 이런 것들이 필요해집니다.

- 사내 **외부 인가 서비스** 연동, **HMAC 서명 검증** 같은 비표준 프로토콜 처리
- 헤더 조작, 페이로드 보강을 위한 **추가 서비스 호출**
- 조직별 **보안 토큰 처리** 로직

이럴 때 이스티오 코어를 바꾸지 않고, 그 아래의 **엔보이를 확장**해서 해결합니다.

## 14.1 엔보이의 확장 기능

이스티오 서비스 메시의 기능 대부분은 **엔보이**가 제공합니다. 어디를 확장해야 할지 알려면 먼저 엔보이 아키텍처를 알아야 합니다.

### 14.1.1 엔보이의 필터 체인 이해하기

![엔보이 요청의 일생 — 리스너가 소켓을 열고, 리스너 필터 체인 → TLS 전송 소켓 → 네트워크 필터 체인(HCM)을 차례로 거친다 (envoyproxy.io — Life of a Request)](images/notes/istio-in-action/14-1.avif)

```plain text
[클라이언트]
  ↓ TCP 연결
[Listener — 포트 오픈]
  ↓
[Listener 필터 체인 — TLS inspector 등 초기 필터]
  ↓
[네트워크 필터 체인 — HttpConnectionManager 포함]
  ↓
[HTTP 디코딩 → HTTP 필터 체인]
  ↓
[Router 필터 → 업스트림으로 전송]
  ↓
[업스트림 응답 → 필터 체인을 역방향으로 통과 → 클라이언트]
```

![그림 14.2 네트워크에서 들어온 바이트는 리스너로 들어오고, 리스너는 네트워크 필터를 거쳐 바이트를 처리한다](images/notes/istio-in-action/14-2.avif)

| 구성 요소 | 역할 |
| --- | --- |
| **리스너 (Listener)** | 트래픽의 **입구**. 포트를 열고 네트워크 스트림에서 바이트를 읽어 필터로 넘김 |
| **네트워크 필터** | 가장 기본적인 필터. **바이트 스트림을 인코딩/디코딩** — MongoDB, Redis, Thrift, Kafka, **HTTP Connection Manager(HCM)** 등 |
| **HCM** (네트워크 필터) | 바이트를 **HTTP로 해석**하고, 헤더·경로 기반 **라우팅, 액세스 로깅, 헤더 조작**까지 처리. 안에 **HTTP 필터 체인**을 가짐 |
| **HTTP 필터** | HTTP 요청/응답에 순서대로(연쇄로) 동작. 체인의 **마지막은 항상 Router 필터** — 실제로 업스트림 클러스터에 요청을 보냄 |

![엔보이 필터 체인 전체 — 리스너 필터 체인, TLS 전송 소켓, 네트워크 필터 체인, 그리고 HCM 안의 HTTP 필터 체인(마지막이 Router)](images/notes/istio-in-action/14-3.avif)

> **핵심 구조** — 리스너 → **네트워크 필터 체인** → (그중 HCM) → **HTTP 필터 체인** → Router. 우리가 확장하는 지점은 대부분 **HCM 안의 HTTP 필터 체인**, 그것도 **Router 바로 앞**입니다.

### 14.1.2 확장용 필터

엔보이에는 이미 많은 HTTP 필터가 내장돼 있고, 이스티오도 그중 상당수를 기본 기능에 씁니다.

| 분류 | 대표 HTTP 필터 |
| --- | --- |
| **보안·인증** | CORS, CSRF, JWT 인증, RBAC, **외부 인가(ext_authz)** |
| **트래픽 제어** | 장애 주입(fault), **속도 제한(ratelimit)**, 로컬 속도 제한, Router |
| **프로토콜 변환** | gRPC-Web, gRPC-JSON 트랜스코더, gzip/compressor |
| **디버깅** | **Tap** — 요청/응답을 복사해 스트리밍 |
| **직접 로직 작성** | **Lua**, **Wasm** — 필터 자체를 스크립트/모듈로 작성 |

이 중 확장 관점에서 중요한 건 세 갈래입니다.

1. **내장 필터를 설정만으로 켜기** — Tap 같은 필터를 EnvoyFilter로 삽입 (14.2)
2. **외부 서비스를 호출하는 필터** — ext_authz, 글로벌 rate limit처럼 **외부 서버에 물어보고** 계속 진행할지 결정 (14.3)
3. **필터 로직을 직접 작성** — Lua(14.4), Wasm(14.5)

### 14.1.3 이스티오의 데이터 플레인 커스터마이징하기

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| **EnvoyFilter로 필터 설정** | 엔보이의 모든 설정에 접근 가능 | 버전 간 **호환성 보장 없음**, 잘못 쓰면 메시 전체 장애 |
| **Lua 필터** | 간단한 헤더 조작·경로 변경에 **빠르고 유연** | 복잡한 로직엔 한계, 무거운 연산은 성능 저하 |
| **Wasm 필터** | 성능 좋고 **여러 언어**로 복잡한 요구사항 처리, 샌드박스로 격리 | 빌드·배포·디버깅 **진입 장벽이 높음** |
| **엔보이를 C++로 직접 확장** | 최고 성능 — 이스티오도 일부 필터를 이렇게 탑재 | **커스텀 엔보이 빌드**를 계속 유지보수해야 함 → 일반적으로 비권장 |

## 14.2 EnvoyFilter 리소스로 엔보이 필터 설정하기

이스티오의 VirtualService, DestinationRule 같은 API는 엔보이 설정을 **추상화**한 것입니다. 이 API로 표현할 수 없는 설정이 필요할 때 **EnvoyFilter**로 리스너·라우트·클러스터·필터를 **직접** 패치합니다.

> **주의** — EnvoyFilter는 이스티오 추상화를 **우회**합니다.
> - 엔보이 API는 이스티오 릴리즈마다 바뀔 수 있어 **하위 호환성이 보장되지 않음**
> - 잘못된 설정은 **데이터 플레인 전체 장애**로 이어질 수 있음 → 반드시 테스트 환경에서 검증
> - 이스티오의 다른 리소스(VirtualService, DestinationRule 등)로 설정이 생성된 **뒤에** 적용됨
> - 표준 API로 안 될 때만 쓰는 **비상 수단**

**예제 — webapp에 Tap 필터 삽입하기**

Tap 필터는 요청/응답이 지나갈 때마다 그 내용을 **수정 없이 복사해 스트리밍**합니다. 클라이언트나 업스트림에 영향 없이 데이터 플레인을 들여다볼 수 있는 디버깅 도구입니다.

![그림 14.5 엔보이 HTTP tap 필터로 요청과 응답을 수정 없이, 클라이언트·업스트림에 영향 없이 스트리밍해 데이터 플레인을 디버깅할 수 있다](images/notes/istio-in-action/14-4.avif)

```yaml
# ch14/tap-envoy-filter.yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: tap-filter
  namespace: istioinaction
spec:
  workloadSelector:                 # ① 적용 대상 워크로드
    labels:
      app: webapp
  configPatches:
  - applyTo: HTTP_FILTER            # ② 패치할 위치
    match:
      context: SIDECAR_INBOUND      #    인바운드 리스너
      listener:
        portNumber: 8080            #    8080 리스너의
        filterChain:
          filter:
            name: "envoy.filters.network.http_connection_manager"   # HCM 안의
            subFilter:
              name: "envoy.filters.http.router"                     # router 필터를 기준으로
    patch:                          # ③ 어떻게 패치할지
      operation: INSERT_BEFORE      #    router 바로 앞에 삽입
      value:
       name: envoy.filters.http.tap
       typed_config:
          "@type": "type.googleapis.com/envoy.extensions.filters.http.tap.v3.Tap"
          commonConfig:
            adminConfig:
              configId: tap_config  # admin API(/tap)로 켜고 끔
```

| 필드 | 의미 |
| --- | --- |
| `workloadSelector` | 이 설정을 적용할 워크로드. 생략하면 **네임스페이스 전체**(istio-system이면 메시 전체) |
| `applyTo` | 패치 대상 종류 — `LISTENER`, `FILTER_CHAIN`, `NETWORK_FILTER`, `HTTP_FILTER`, `ROUTE_CONFIGURATION`, `VIRTUAL_HOST`, `HTTP_ROUTE`, `CLUSTER` 등 |
| `match.context` | `SIDECAR_INBOUND`, `SIDECAR_OUTBOUND`, `GATEWAY`, `ANY` |
| `patch.operation` | `MERGE`, `ADD`, `REMOVE`, `INSERT_BEFORE`, `INSERT_AFTER`, `INSERT_FIRST`, `REPLACE` |

```bash
kubectl apply -f ch14/tap-envoy-filter.yaml
kubectl get envoyfilter -n istioinaction
# NAME         AGE
# tap-filter   8s

# 인바운드 리스너(15006)에 tap 필터가 router 앞에 들어갔는지 확인
istioctl proxy-config listener deploy/webapp.istioinaction --port 15006 -o json
#   { "name": "envoy.filters.http.tap", ... "configId": "tap_config" },
#   { "name": "envoy.filters.http.router", ... }
```

**tap 동작 확인** — 터미널 3개

```bash
# 터미널 1: admin 포트 포워딩 후 tap 시작 (x-app-tap: true 헤더가 있는 요청만 매칭)
kubectl port-forward -n istioinaction deploy/webapp 15000 &
curl -X POST -d @./ch14/tap-config.json localhost:15000/tap

# 터미널 2: 헤더를 붙여 반복 호출
while true; do
  curl -s -H "x-app-tap: true" -H "Host: webapp.istioinaction.io" http://$EXT_IP/api/catalog
  sleep 1
done

# 터미널 3: 디버그 로그
istioctl proxy-config log deploy/webapp -n istioinaction --level http:debug
istioctl proxy-config log deploy/webapp -n istioinaction --level tap:debug
kubectl logs -n istioinaction -l app=webapp -c istio-proxy -f
# ':path', '/api/catalog'
# 'x-app-tap', 'true'
# debug envoy tap ... submitting buffered trace sink
```

터미널 1에는 매칭된 요청·응답의 **헤더와 바디가 JSON으로 스트리밍**됩니다.

## 14.3 외부 호출로 요청 속도 제한하기

Tap은 엔보이 **안에서** 끝나는 필터였습니다. 이번엔 **외부 서비스를 호출해서** 요청을 계속 진행할지 결정하는 필터 — **글로벌 속도 제한**입니다.

### 14.3.1 엔보이 속도 제한 이해하기

엔보이의 속도 제한 방법은 여러 가지(네트워크 필터, **로컬** 속도 제한, **글로벌** 속도 제한)지만 여기선 글로벌을 다룹니다.

![그림 14.6 같은 서비스의 여러 복제본이 동일한 속도 제한 서비스를 호출해 서비스 전체에 대한 글로벌 속도 제한을 받는다](images/notes/istio-in-action/14-5.avif)

- 워크로드의 **모든 엔보이가 같은 속도 제한 서버**를 호출
- 속도 제한 서버는 **Redis 같은 글로벌 키-값 저장소**로 카운터 관리
- → **복제본 수와 무관하게** 일관된 제한 적용 (로컬 제한은 복제본마다 따로 셈)

![그림 14.7 글로벌 속도 제한 — 요청 속성을 속도 제한 서버에 보내 이 요청을 제한할지 판단받는다](images/notes/istio-in-action/14-6.avif)

구성 요소는 세 가지입니다.

| 구성 요소 | 역할 | 예제 파일 |
| --- | --- | --- |
| **속도 제한 서버 + 규칙** | descriptor(키-값)별 한도를 보유하고 판단 | `rlsconfig.yaml`, `rls.yaml` |
| **rate limit 필터** | 엔보이 HTTP 필터 체인에서 서버를 **호출** | `catalog-ratelimit.yaml` |
| **rate limit action** | 요청의 **어떤 속성**을 descriptor로 만들어 보낼지 정의 | `catalog-ratelimit-actions.yaml` |

**① 속도 제한 서버 규칙** — `x-loyalty` 헤더 등급별 분당 한도

```yaml
# ch14/rate-limit/rlsconfig.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: catalog-ratelimit-config
  namespace: istioinaction
data:
  config.yaml: |
    domain: catalog-ratelimit
    descriptors:
      - key: header_match
        value: no_loyalty        # 헤더 없음 → 1/분
        rate_limit:
          unit: MINUTE
          requests_per_unit: 1
      - key: header_match
        value: gold_request      # gold → 10/분
        rate_limit:
          unit: MINUTE
          requests_per_unit: 10
      - key: header_match
        value: silver_request    # silver → 5/분
        rate_limit:
          unit: MINUTE
          requests_per_unit: 5
      - key: header_match
        value: bronze_request    # bronze → 3/분
        rate_limit:
          unit: MINUTE
          requests_per_unit: 3
```

```bash
# 규칙(ConfigMap) + 속도 제한 서버(envoyproxy/ratelimit) + Redis 배포
kubectl apply -f ch14/rate-limit/rlsconfig.yaml -n istioinaction
kubectl apply -f ch14/rate-limit/rls.yaml -n istioinaction

kubectl get pod -n istioinaction
# ratelimit-99d5d9c5-q4zcm   1/1   Running
# redis-6cf4ff9768-x97m8     1/1   Running
```

> `rls.yaml`의 ratelimit·redis 파드에는 `sidecar.istio.io/inject: "false"`가 붙어 있습니다. ConfigMap을 `/data/ratelimit/config/config.yaml`로 마운트하고, gRPC **8081** 포트로 엔보이 요청을 받습니다.

**② rate limit 필터** — catalog의 HTTP 필터 체인에서 router 앞에 삽입

```yaml
# ch14/rate-limit/catalog-ratelimit.yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: catalog-ratelimit-filter
  namespace: istioinaction
spec:
  workloadSelector:
    labels:
      app: catalog
  configPatches:
  - applyTo: HTTP_FILTER
    match:
      context: SIDECAR_INBOUND
      listener:
        portNumber: 3000
        filterChain:
          filter:
            name: "envoy.filters.network.http_connection_manager"
            subFilter:
              name: "envoy.filters.http.router"
    patch:
      operation: INSERT_BEFORE
      value:
        name: envoy.filters.http.ratelimit
        typed_config:
          "@type": type.googleapis.com/envoy.extensions.filters.http.ratelimit.v3.RateLimit
          domain: catalog-ratelimit           # 서버 규칙의 domain과 일치
          failure_mode_deny: true             # 서버 장애 시 요청 거부
          rate_limit_service:
            grpc_service:
              envoy_grpc:
                cluster_name: outbound|8081||ratelimit.istioinaction.svc.cluster.local
              timeout: 10s
            transport_api_version: V3
```

**③ rate limit action** — 어떤 요청 속성을 보낼지

```yaml
# ch14/rate-limit/catalog-ratelimit-actions.yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: catalog-ratelimit-actions
  namespace: istioinaction
spec:
  workloadSelector:
    labels:
      app: catalog
  configPatches:
    - applyTo: VIRTUAL_HOST           # 라우트 쪽 설정이므로 VIRTUAL_HOST에 MERGE
      match:
        context: SIDECAR_INBOUND
        routeConfiguration:
          vhost:
            route:
              action: ANY
      patch:
        operation: MERGE
        value:
          rate_limits:
            - actions:
              - header_value_match:
                  descriptor_value: no_loyalty
                  expect_match: false      # x-loyalty 헤더가 "없으면" 매칭
                  headers:
                  - name: "x-loyalty"
            - actions:
              - header_value_match:
                  descriptor_value: bronze_request
                  headers:
                  - name: "x-loyalty"
                    exact_match: bronze
            - actions:
              - header_value_match:
                  descriptor_value: silver_request
                  headers:
                  - name: "x-loyalty"
                    exact_match: silver
            - actions:
              - header_value_match:
                  descriptor_value: gold_request
                  headers:
                  - name: "x-loyalty"
                    exact_match: gold
```

`header_value_match`의 결과는 `header_match: <descriptor_value>` 형태의 descriptor가 되어 서버로 전송되고, 서버는 ①의 규칙과 맞춰 봅니다.

```bash
kubectl apply -f ch14/rate-limit/catalog-ratelimit.yaml -n istioinaction
kubectl apply -f ch14/rate-limit/catalog-ratelimit-actions.yaml -n istioinaction

kubectl get envoyfilter -n istioinaction
# catalog-ratelimit-actions   27s
# catalog-ratelimit-filter    28s

# 라우트에 rateLimits가 병합됐는지 확인
istioctl proxy-config route deploy/catalog.istioinaction --name 'inbound|3000||' -o json | grep -A6 rateLimits
```

**동작 확인** — sleep 앱에서 catalog 호출

```bash
# 헤더 없음: 1/분 → 두 번째 호출부터 429
kubectl exec -it deploy/sleep -n istioinaction -c sleep -- curl http://catalog/items -v
# < HTTP/1.1 200 OK
kubectl exec -it deploy/sleep -n istioinaction -c sleep -- curl http://catalog/items -v
# < HTTP/1.1 429 Too Many Requests
# < x-envoy-ratelimited: true

# silver: 5/분 → 6번째 호출에서 429
kubectl exec -it deploy/sleep -n istioinaction -c sleep -- curl -H "x-loyalty: silver" http://catalog/items -v
```

> 응답의 `x-envoy-ratelimited: true`는 **엔보이가 속도 제한으로 거부했다**는 표시입니다. 애플리케이션까지 요청이 가지 않았습니다.

## 14.4 루아로 이스티오의 데이터 플레인 확장하기

Lua 스크립트를 엔보이 필터 체인에 넣으면 **요청/응답 헤더 조작, 바디 검사, 외부 호출**을 커스텀 로직으로 구현할 수 있습니다.

- `envoy_on_request(request_handle)` — 요청 경로에서 실행
- `envoy_on_response(response_handle)` — 응답 경로에서 실행
- `httpCall()` — 다른 클러스터를 **논블로킹**으로 호출

> **주의** — 바디 전체를 메모리에 올리는 식의 **무거운 작업은 성능 저하**를 부릅니다. (ssadh 블로그 작성자도 운영 중 "데이터가 안 들어온다"는 문의를 추적하려고 바디 전체를 로깅하는 Lua를 넣었다가 프록시가 뻗은 경험을 적어 두었습니다.)

**예제 — A/B 테스트 그룹 헤더 붙이기**

요청이 httpbin에 도달하기 전에 **bucket-tester 서비스를 호출**해 테스트 그룹을 받고, 그 값을 `x-test-cohort` 헤더로 붙입니다. 응답에는 `istioinaction: it works!` 헤더를 추가합니다.

```bash
kubectl apply -f ch14/httpbin.yaml -n istioinaction
kubectl apply -f ch14/bucket-tester-service.yaml -n istioinaction   # http-echo가 "dark-launch-7"을 응답
```

```yaml
# ch14/lua-filter.yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: httpbin-lua-extension
  namespace: istioinaction
spec:
  workloadSelector:
    labels:
      app: httpbin
  configPatches:
  - applyTo: HTTP_FILTER                  # ① Lua 필터를 router 앞에 삽입
    match:
      context: SIDECAR_INBOUND
      listener:
        portNumber: 80
        filterChain:
          filter:
            name: "envoy.filters.network.http_connection_manager"
            subFilter:
              name: "envoy.filters.http.router"
    patch:
      operation: INSERT_BEFORE
      value:
       name: envoy.lua
       typed_config:
          "@type": "type.googleapis.com/envoy.extensions.filters.http.lua.v3.Lua"
          inlineCode: |
            function envoy_on_request(request_handle)
              local headers, test_bucket = request_handle:httpCall(
              "bucket_tester",
              {
                [":method"] = "GET",
                [":path"] = "/",
                [":scheme"] = "http",
                [":authority"] = "bucket-tester.istioinaction.svc.cluster.local",
                ["accept"] = "*/*"
              }, "", 5000)
              request_handle:headers():add("x-test-cohort", test_bucket)
            end
            function envoy_on_response(response_handle)
              response_handle:headers():add("istioinaction", "it works!")
            end
  - applyTo: CLUSTER                      # ② httpCall이 호출할 클러스터를 직접 추가
    match:
      context: SIDECAR_OUTBOUND
    patch:
      operation: ADD
      value:
        name: bucket_tester
        type: STRICT_DNS
        connect_timeout: 0.5s
        lb_policy: ROUND_ROBIN
        load_assignment:
          cluster_name: bucket_tester
          endpoints:
          - lb_endpoints:
            - endpoint:
                address:
                  socket_address:
                    protocol: TCP
                    address: bucket-tester.istioinaction.svc.cluster.local
                    port_value: 80
```

> `httpCall()`의 첫 인자 `"bucket_tester"`는 **엔보이 클러스터 이름**입니다. 그래서 두 번째 패치로 그 이름의 클러스터를 `ADD`해 줘야 합니다.

```bash
kubectl apply -f ch14/lua-filter.yaml

kubectl exec -it deploy/sleep -n istioinaction -c sleep -- curl http://httpbin.istioinaction:8000/headers
# 정상 결과
# {
#   "headers": {
#     "Host": "httpbin.istioinaction:8000",
#     ...
#     "X-Test-Cohort": "dark-launch-7"      ← Lua가 외부 호출 결과로 붙인 헤더
#   }
# }
```

> **트러블슈팅 메모** — ssadh 블로그 실습에서는 `hashicorp/http-echo:1.0` 이미지로 바꾼 뒤 `503` + `invalid header value for: x-test-cohort`가 났습니다. 응답 헤더 `istioinaction: it works!`는 붙어서 **Lua 필터 자체는 동작**했습니다. 원인은 bucket-tester 응답 바디(끝의 개행 등)를 **헤더 값으로 그대로 쓸 수 없어서**로 보입니다(추정). 필요하면 Lua에서 `test_bucket:gsub("%s+$", "")`처럼 공백을 잘라낸 뒤 붙이세요.

## 14.5 웹어셈블리로 이스티오의 데이터 플레인 확장하기

### 14.5.1 웹어셈블리 소개

**웹어셈블리(Wasm)는** 원래 브라우저에서 네이티브에 가까운 속도로 코드를 돌리기 위한 **이식성 있는 바이너리 포맷**입니다.

- **이식성** — 한 번 빌드한 모듈을 어떤 호스트에서도 실행
- **고성능** — 네이티브에 가까운 실행 속도
- **안전성** — **샌드박스** 안에서 실행되어 호스트 메모리에 직접 접근 불가
- **다양한 언어** — C/C++, Rust, Go(TinyGo), AssemblyScript 등으로 작성 가능

엔보이는 Wasm 런타임을 내장하고 있어, Wasm 모듈을 **필터로 로드**할 수 있습니다.

### 14.5.2 왜 엔보이에 웹어셈블리를 사용하는가?

| 기존 방식(C++ 필터)의 문제 | Wasm이 해결하는 방식 |
| --- | --- |
| **C++로만** 작성 가능 | **여러 언어**로 작성 |
| 엔보이 바이너리에 **정적으로 빌드**해야 함 → 커스텀 엔보이 유지보수 | 런타임에 **동적 로드** — 엔보이 재빌드 불필요 |
| 필터 버그가 **프록시 전체를 죽일** 수 있음 | **샌드박스**에서 실행 — 메모리·CPU 제한, 장애 격리 |
| 배포 경로가 엔보이 릴리즈와 묶임 | **OCI 레지스트리**에 이미지처럼 올려 배포·버전 관리 |

> Lua보다 무겁지만 **복잡한 로직, 성능, 격리**가 필요할 때 선택지입니다. 책 기준으로는 **실험적 기능**이니 운영 전 충분히 테스트해야 합니다.

### 14.5.3 웹어셈블리로 새로운 엔보이 필터 만들기

Wasm 필터는 **Proxy-Wasm ABI**에 맞춰 작성합니다. 엔보이가 호출하는 콜백을 구현하는 방식으로, Lua의 `envoy_on_request`/`envoy_on_response`와 비슷한 역할입니다.

| 콜백 (개념) | 시점 |
| --- | --- |
| `onRequestHeaders` | 요청 헤더 수신 시 — 헤더 검사·추가·거부 |
| `onRequestBody` | 요청 바디 수신 시 |
| `onResponseHeaders` | 응답 헤더 수신 시 — 예: 응답 헤더 추가 |
| `onResponseBody` | 응답 바디 수신 시 |

각 언어별 **Proxy-Wasm SDK**(Rust, Go, C++, AssemblyScript)가 이 콜백 구조를 제공합니다. 책 예제는 **AssemblyScript**로 응답에 헤더를 추가하는 간단한 필터를 만듭니다.

### 14.5.4 meshctl로 새 엔보이 필터 빌드하기

책은 [Solo.io](http://Solo.io)의 CLI(**wasme**, 이후 **meshctl**에 통합)로 **프로젝트 생성 → 빌드 → OCI 이미지로 푸시**하는 흐름을 보여줍니다.

1. **init** — 언어(AssemblyScript 등)를 골라 필터 프로젝트 템플릿 생성
2. **build** — Wasm 모듈을 컴파일하고 **OCI 이미지**로 패키징
3. **push** — 레지스트리(책에서는 WebAssembly Hub)에 업로드

> 두 블로그 모두 이 단계는 실습하지 않았습니다. 정확한 명령어·옵션은 원서의 14.5.4를 확인하세요. 현재 이스티오에서는 빌드 도구가 무엇이든 **OCI 이미지로 레지스트리에 올리고 WasmPlugin으로 가져오는** 방식이 표준입니다.

### 14.5.5 새로운 웹어셈블리 엔보이 필터 배포하기

이스티오 **1.12+에서는** **WasmPlugin** CRD로 배포합니다. WasmPlugin에 모듈 위치(OCI URL), 필터 **단계(phase)**, 설정을 적으면 **istio-agent가 모듈을 내려받아 엔보이에 주입**합니다. EnvoyFilter로 직접 패치할 필요가 없습니다.

```bash
kubectl explain wasmplugins.extensions.istio.io
```

**예제 1 — Basic Auth 필터를 인그레스 게이트웨이에 적용**

```yaml
apiVersion: extensions.istio.io/v1alpha1
kind: WasmPlugin
metadata:
  name: basic-auth
  namespace: istio-system
spec:
  selector:
    matchLabels:
      istio: ingressgateway         # 인그레스 게이트웨이에만 적용
  url: oci://ghcr.io/istio-ecosystem/wasm-extensions/basic_auth:1.12.0
  phase: AUTHN                      # 인증 단계 — 이스티오 인증 필터 앞
  pluginConfig:
    basic_auth_rules:
      - prefix: "/api"
        request_methods:
          - "GET"
          - "POST"
        credentials:
          - "ok:test"
          - "YWRtaW4zOmFkbWluMw=="   # admin3:admin3
```

```bash
kubectl get wasmplugin -A
# istio-system   basic-auth   21s

# 자격 증명 없이 → 401
curl -s -H "Host: webapp.istioinaction.io" http://$EXT_IP/api/catalog -v

# 자격 증명과 함께 → 200
curl -s -H "Authorization: Basic YWRtaW4zOmFkbWluMw==" \
     -H "Host: webapp.istioinaction.io" http://$EXT_IP/api/catalog -v
```

| phase | 삽입 위치 |
| --- | --- |
| `AUTHN` | 이스티오 **인증** 필터 앞 |
| `AUTHZ` | 이스티오 **인가** 필터 앞 |
| `STATS` | 이스티오 **통계** 필터 앞 |
| (미지정) | router 바로 앞 |

**예제 2 — Coraza WAF를 Wasm으로 적용** (ssadh 블로그의 추가 실습)

**Coraza**는 Go로 작성된 오픈소스 **웹 애플리케이션 방화벽(WAF)으로**, **OWASP CRS(Core Rule Set)** 및 ModSecurity SecLang 규칙과 호환됩니다. Wasm 빌드를 제공해 인그레스 게이트웨이에 바로 붙일 수 있습니다.

![Coraza 요청 처리 단계 — Phase 1(요청 헤더) ~ Phase 5(로깅). 파란 단계는 요청을 중단(차단)할 수 있는 단계](images/notes/istio-in-action/14-7.avif)

```yaml
apiVersion: extensions.istio.io/v1alpha1
kind: WasmPlugin
metadata:
  name: coraza-ingressgateway
  namespace: istio-system
spec:
  selector:
    matchLabels:
      istio: ingressgateway
  url: oci://ghcr.io/corazawaf/coraza-proxy-wasm
  phase: AUTHN
  pluginConfig:
    default_directives: default
    directives_map:
      default:
      - Include @demo-conf
      - SecDebugLogLevel 9
      - SecRuleEngine On
      - Include @crs-setup-conf
      - Include @owasp_crs/*.conf
```

```bash
# 게이트웨이가 레지스트리에서 모듈을 받아옴
kubectl logs -n istio-system -l app=istio-ingressgateway | grep -i wasm
# info wasm fetching image corazawaf/coraza-proxy-wasm from registry ghcr.io with tag latest

# 정상 요청 → 200
curl -s http://webapp.istioinaction.io:30000/api/catalog

# XSS 시도 → 403 (Phase 1에서 차단)
curl -s 'http://webapp.istioinaction.io:30000/api/catalog?arg=<script>alert(0)</script>' -I
# HTTP/1.1 403 Forbidden

# SQL Injection 시도 (바디) → 403 (Phase 2에서 차단)
curl -i -X POST 'http://webapp.istioinaction.io:30000/api/catalog' --data "1%27%20ORDER%20BY%203--%2B"
# HTTP/1.1 403 Forbidden

kubectl logs -n istio-system -l app=istio-ingressgateway -f
# critical envoy wasm ... Coraza: Access denied (phase 1). Inbound Anomaly Score Exceeded ...
#   [file "@owasp_crs/REQUEST-949-BLOCKING-EVALUATION.conf"] [id "949111"] [uri "/api/catalog?arg=<script>alert(0)</script>"]
```

> Wasm 하나로 **애플리케이션 수정 없이** 게이트웨이 수준 WAF가 적용됐습니다. 이게 Wasm 확장의 실전 가치입니다.
