## 메시는 쿠버네티스 밖으로도 뻗어 나갑니다

- **레거시 워크로드**(가상머신·물리 머신)를 이스티오 메시에 통합하기
- 가상머신에 **istio-agent 설치·설정**하기
- 가상머신에 **ID 프로비저닝**하기
- 클러스터 서비스 ↔ 가상머신 서비스를 **서로 노출**하기
- **로컬 DNS 프록시**로 클러스터 서비스의 FQDN 해석하기

![가상머신의 envoy가 east-west 게이트웨이를 거쳐 클러스터의 istiod·애플리케이션과 mTLS로 통신하는 구조 (istio.io blog — simple-vms)](images/notes/istio-in-action/13-1.avif)

지금까지는 메시를 **컨테이너·쿠버네티스 관점**에서만 다뤘습니다. 하지만 현실의 워크로드는 여전히 **가상머신**에서 많이 돕니다. "그냥 컨테이너로 옮기면 되지 않나?" 싶지만, 현실적으로 안 되는 경우가 있습니다.

| 현대화가 어려운 이유 | 예시 |
| --- | --- |
| **규제·조직 역량** | 규제 때문에 **온프레미스**에서 돌려야 하는데, 쿠버네티스를 운영할 전문성이 없음 |
| **컨테이너화 난이도** | 재설계가 필요하거나, 의존성끼리 충돌하는 **의존성 지옥** |
| **머신 고유 의존성** | 실행 중인 **가상머신 자체에 묶인** 의존성이 있음 |

이 장은 **사이드카 프록시를 설치·설정해서 어떤 워크로드든 메시의 일부로 만드는 방법**을 보여줍니다. 레거시를 그대로 두면서도 **복원력·보안·고가용성**을 메시 수준에서 얻는 것이 목표입니다.

## 13.1 이스티오의 가상머신 지원

가상머신 통합은 이스티오 초창기부터 가능했지만, **컨트롤 플레인 바깥의 우회책과 자동화**가 잔뜩 필요했습니다. **1.9.0**에서 핵심 기능이 구현되고 API 방향이 정해지면서 **베타**로 승격됐고, 그 핵심 기능은 세 가지입니다.

| 핵심 기능 | 어떻게 해결했나 |
| --- | --- |
| **사이드카 설치·설정 단순화** | `istioctl`로 설정 파일 생성 |
| **가상머신 고가용성** | 새 리소스 **WorkloadGroup / WorkloadEntry** 도입 |
| **메시 내 서비스의 DNS 해석** | 사이드카와 함께 뜨는 **로컬 DNS 프록시** |

### 13.1.1 가상머신에서의 사이드카 프록시 설치 및 설정 단순화하기

어떤 워크로드든 메시의 일부가 되려면 **세 가지**가 필요합니다.

1. 네트워크 트래픽을 관리할 **사이드카 프록시 설치**
2. 프록시가 **istiod에 연결**해 메시 설정을 받도록 설정
3. istiod에 인증할 **ID 토큰** 제공

![그림 13.1 워크로드가 메시의 일부가 되기 위해 필요한 것 — 사이드카, istiod 연결 설정, 검증 가능한 ID 클레임](images/notes/istio-in-action/13-2.avif)

쿠버네티스 파드도 똑같은 조건이 필요하지만, **웹훅(또는 istioctl)이 사이드카를 주입**하고 **쿠버네티스가 토큰을 파드에 넣어주기** 때문에 신경 쓸 일이 없었습니다. 이 편의성은 **쿠버네티스 밖으로 확장되지 않습니다.** 그래서 가상머신 쪽은 운영자가 직접 **프록시 설치 + 설정 + 부트스트랩 토큰 제공**을 해줘야 합니다.

**네트워크 구성에 따라 연결 방식이 달라집니다.**

![단일 네트워크 — 클러스터와 VM이 같은 L3 네트워크를 공유해 istiod·파드에 IP로 직접 접근 (Tetrate Academy)](images/notes/istio-in-action/13-3.avif)

![다중 네트워크 — VM이 다른 네트워크에 있어 east-west 게이트웨이가 두 네트워크를 이어줌 (Tetrate Academy)](images/notes/istio-in-action/13-4.avif)

- **단일 네트워크**: VM이 istiod와 파드에 **IP로 직접** 도달 가능. 게이트웨이를 거쳐도 되지만 필수는 아님
- **다중 네트워크**: 파드가 VM IP에 직접 못 감 → **컨트롤 플레인 트래픽, 데이터 플레인 트래픽 모두 east-west 게이트웨이를 경유**. VM에는 게이트웨이 주소를 알려줘야 함

> 이 장의 실습은 **다중 네트워크**(west-network ↔ vm-network) 구성을 가정합니다.

**가상머신의 ID 프로비저닝 자세히 보기**

이스티오는 가상머신 ID의 **신뢰의 원천으로 쿠버네티스**를 씁니다. 쿠버네티스에서 토큰을 만들어 머신에 넘기면, 머신의 istio-agent가 그 토큰으로 istiod에 인증하고 **SVID**를 받습니다.

![그림 13.2 클러스터 워크로드 — (1) 서비스 어카운트 토큰이 파드에 자동 주입되고 (2) 그 토큰으로 인증해 SVID를 받음](images/notes/istio-in-action/13-5.avif)

![그림 13.3 가상머신 — (1) 서비스 어카운트 생성 (2) 토큰을 VM으로 수동 전달 (3) 그 토큰으로 인증해 SVID를 받음](images/notes/istio-in-action/13-6.avif)

접근법은 같고, 차이는 **"토큰을 누가 넣어주냐"** 하나입니다. VM에서는 운영자가 **토큰 생성과 안전한 전송을 자동화**해야 하고, 멀티 클라우드라면 이 부담이 빠르게 커집니다.

> **플랫폼이 할당한 ID (Platform-assigned identity)** — 커뮤니티가 개발 중인 대안으로, **클라우드가 VM에 부여한 ID**를 신뢰의 원천으로 씁니다. istiod가 그 클레임을 클라우드 프로바이더에 검증하는 방식이라 토큰 수동 전달이 필요 없어집니다. (책 기준 아직 미구현)

![플랫폼이 부여한 ID로 워크로드를 인증하는 방식 — istiod가 클라우드 프로바이더에 토큰 진위를 검증](images/notes/istio-in-action/13-7.avif)

실습에서는 쿠버네티스를 신뢰의 원천으로 쓰고, 간결함을 위해 **토큰을 수작업으로** 옮깁니다.

### 13.1.2 가상머신 고가용성

이스티오는 쿠버네티스가 컨테이너 고가용성을 달성하는 방식을 **거의 그대로 흉내** 냅니다.

| 쿠버네티스 | 이스티오(VM) | 역할 |
| --- | --- | --- |
| **Deployment** | **WorkloadGroup** | 복제본을 어떻게 만들지 정의하는 **템플릿** — 노출 포트, 레이블, 서비스 어카운트(ID), 헬스 프로브 방법 등 **공통 속성** |
| **Pod** | **WorkloadEntry** | 실제 트래픽을 처리하는 **개별 VM 하나**. 공통 속성 + 상태·주소 같은 **고유 속성** |

WorkloadEntry는 수동으로 만들 수도 있지만, 권장 방식은 새로 뜬 워크로드가 알아서 메시에 참가하는 **워크로드 자동 등록**입니다.

**워크로드 자동 등록 이해하기**

![그림 13.4 워크로드 자동 등록 과정 — (1) VM이 초기 설정과 토큰으로 WorkloadGroup에 등록 요청 (2) istiod가 토큰이 해당 서비스 어카운트 것인지 검증 (3) 성공하면 VM을 나타내는 WorkloadEntry 생성](images/notes/istio-in-action/13-8.avif)

VM을 WorkloadEntry로 표현하는 게 중요한 이유는, **쿠버네티스 Service나 이스티오 ServiceEntry가 레이블 셀렉터로 선택**할 수 있기 때문입니다. 실제 주소가 아니라 **서비스 FQDN**으로 워크로드를 고르니, 클라이언트 모르게 비정상 VM을 버리고 새 VM을 띄울 수 있습니다.

![그림 13.5 WorkloadGroup/WorkloadEntry와 Deployment/Pod의 관계 — 하나의 Service가 레이블(app=forum)로 파드와 WorkloadEntry를 동시에 선택](images/notes/istio-in-action/13-9.avif)

> **마이그레이션 활용** — 같은 Service 뒤에 VM과 파드를 **병렬로** 두고, 5장의 **트래픽 전환**으로 VM → 파드로 조금씩 옮깁니다. 오류가 늘면 다시 VM으로 되돌리면 됩니다.

**이스티오가 수행하는 헬스 체크 이해하기**

| 프로브 | 확인 내용 | 누구 책임? |
| --- | --- | --- |
| **Readiness** | 시작 후 **트래픽 받을 준비**가 됐는가 | **이스티오** — WorkloadGroup에 정의, istio-agent가 수행 |
| **Liveness** | 실행 중 **정상인가** (아니면 재시작) | **플랫폼** — 메시의 관심사가 아님. 클라우드의 자동 복구 기능 사용 |

- Azure: VM Scale Set 자동 인스턴스 복구
- AWS: Auto Scaling Group 헬스 체크
- GCP: Managed Instance Group 헬스 체크·자동 복구

![그림 13.6 사이드카 프록시가 애플리케이션 헬스 상태를 istiod에 업데이트](images/notes/istio-in-action/13-10.avif)

istio-agent가 WorkloadGroup 명세대로 앱을 주기적으로 프로브하고, 상태가 **정상↔비정상으로 바뀔 때 istiod에 보고**합니다. 컨트롤 플레인은 이를 보고 정상이면 **데이터 플레인에 VM 엔드포인트를 설정**하고, 비정상이면 **제거**합니다.

> **프로브 설정 팁**
> - istio-agent의 **readiness는 공격적**으로 — 오류를 내는 인스턴스로 트래픽이 가지 않게
> - 클라우드의 **liveness는 보수적**으로 — VM에 회복할 시간을 줘야 함. 성급히 죽이면 진행 중 요청이 유예 없이 끊겨 사용자에게 실패가 보임
> - 경험칙: **readiness가 liveness보다 항상 먼저 실패**하도록

### 13.1.3 메시 내 서비스의 DNS 해석

VM은 클러스터 밖에 있으니 **쿠버네티스 내부 DNS에 접근할 수 없고**, 따라서 클러스터 서비스 호스트네임을 해석하지 못합니다.

![DNS 프록시가 없을 때 — VM의 앱이 사내 DNS에 클러스터 서비스 이름을 물어도 'no such host' (istio.io blog — dns-proxy)](images/notes/istio-in-action/13-11.avif)

"프록시가 라우팅 설정을 다 갖고 있는데 DNS가 왜 필요하지?" — 프록시에 설정은 있습니다. 문제는 **트래픽을 앱에서 꺼내 프록시까지 보내는 것**입니다. 그 전제 조건이 **호스트네임 해석**이고, 해석에 실패하면 트래픽은 **앱을 떠나지도 못해** 엔보이로 리다이렉트될 기회조차 없습니다. (part12에서 west에 **스텁 서비스**를 만들었던 것과 같은 문제)

![그림 13.7 DNS 해석이 실패하므로 아웃바운드 트래픽이 엔보이 프록시에 도달하지 못함](images/notes/istio-in-action/13-12.avif)

예전에는 **모든 쿠버네티스 서비스를 등록한 프라이빗 DNS 서버**를 두고 VM이 그걸 네임서버로 쓰게 했습니다. 워크로드가 동적이라 **external-dns** 같은 컨트롤러로 동기화를 자동화해야 했죠. 이스티오는 이걸 **DNS 프록시**로 해결합니다.

![그림 13.8 DNS 쿼리가 iptables 규칙으로 DNS 프록시에 리다이렉트되고, DNS 프록시에는 istiod가 클러스터 내 서비스를 설정해 둠](images/notes/istio-in-action/13-13.avif)

- DNS 프록시는 **엔보이와 함께 사이드카 안에서** 동작 (istio-cni를 쓰면 방식이 약간 다름)
- 앱의 DNS 쿼리는 이스티오의 전형적인 트래픽 캡처 방식인 **iptables 규칙**으로 DNS 프록시에 리다이렉트
- DNS 프록시를 계속 최신으로 유지하려고 **NDS(Name Discovery Service)** 라는 새 xDS API 도입 — Service나 ServiceEntry가 추가될 때마다 컨트롤 플레인이 DNS 항목을 동기화

![DNS 프록시가 켜진 상태 — 클러스터 서비스는 사이드카가 직접 응답(캐시), 나머지만 업스트림 네임서버로 (istio.io blog — dns-proxy)](images/notes/istio-in-action/13-14.avif)

> DNS 프록시는 VM 전용이 아닙니다. 파드에서도 켜면 **kube-dns 부하 감소, 해석 지연 개선**, ServiceEntry 호스트 해석 같은 이점이 있습니다.

## 13.2 인프라 준비하기

![그림 13.9 실습 구성 — webapp·catalog는 west-network의 클러스터, forum은 vm-network의 가상머신](images/notes/istio-in-action/13-15.avif)

- **webapp, catalog** → 쿠버네티스 클러스터 (west-network)
- **forum** → 가상머신 (vm-network)
- 클러스터와 VM이 **다른 네트워크**라는 게 핵심 → VM에서 클러스터로 가는 트래픽을 리버스 프록시할 **east-west 게이트웨이가 필요**

> 스터디 실습은 AWS CloudFormation으로 VPC 1개에 **k3s-s(t3.xlarge, 192.168.10.10)** + **forum-vm(t3.small, 192.168.10.200)** 을 띄웠습니다. 책처럼 네트워크를 물리적으로 나누면 east-west 게이트웨이 LoadBalancer에 공인 IP가 필요해 복잡해지므로, **같은 VPC에 두고 이스티오 설정상 네트워크만 다르게** 선언했습니다.

### 13.2.1 서비스 메시 준비하기

클러스터와 VM이 다른 네트워크이므로 **istio-system 네임스페이스에 네트워크 레이블**부터 붙입니다.

```bash
# 네트워크 토폴로지 레이블 — 이 클러스터는 west-network
kubectl create namespace istio-system
kubectl label namespace istio-system topology.istio.io/network=west-network

# demo 프로파일로 컨트롤 플레인 설치 (1.17.8)
istioctl install -f ch13/controlplane/cluster-in-west-network.yaml \
  --set values.global.proxy.privileged=true -y
```

```yaml
# ch13/controlplane/cluster-in-west-network.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  name: istio-controlplane
  namespace: istio-system
spec:
  profile: demo
  components:
    egressGateways:
    - name: istio-egressgateway
      enabled: false
  values:
    global:
      meshID: usmesh
      multiCluster:
        clusterName: west-cluster
      network: west-network
```

```bash
# 앱 배포 (part12의 webapp/catalog 재사용)
kubectl create ns istioinaction
kubectl label namespace istioinaction istio-injection=enabled
kubectl -n istioinaction apply -f ch12/webapp-deployment-svc.yaml
kubectl -n istioinaction apply -f ch12/webapp-gw-vs.yaml
kubectl -n istioinaction apply -f ch12/catalog.yaml

# 동작 확인
curl -s -H "Host: webapp.istioinaction.io" http://192.168.10.10:30000/api/catalog/items/1
```

### 13.2.2 가상머신 프로비저닝

forum-vm의 요구사항은 단순합니다.

- **Ubuntu** (istio-sidecar.deb를 쓰기 위해 데비안 계열)
- **SSH 접근** 가능 (설정 파일·토큰 전달용)
- 애플리케이션 포트 **8080 노출**

```bash
# forum-vm: 기본 DNS 상태 — systemd-resolved가 127.0.0.53:53에서 수신
cat /etc/resolv.conf
# nameserver 127.0.0.53
ss -unlp | grep :53
# UNCONN 0 0 127.0.0.53%lo:53 ... users:(("systemd-resolve",...))
```

> 이 **127.0.0.53**을 기억해 두세요. 13.4에서 iptables가 이 주소로 가는 DNS 쿼리를 가로챕니다.

## 13.3 가상머신까지 메시 확장

가상머신 통합 기능은 **베타이고 기본 비활성화**입니다. IstioOperator로 설치를 업데이트해 세 기능을 켭니다.

```yaml
# ch13/controlplane/cluster-in-west-network-with-vm-features.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  name: istio-controlplane
  namespace: istio-system
spec:
  profile: demo
  components:
    egressGateways:
    - name: istio-egressgateway
      enabled: false
  meshConfig:
    defaultConfig:
      proxyMetadata:
        ISTIO_META_DNS_CAPTURE: "true"                       # DNS 쿼리를 캡처해 DNS 프록시로 리다이렉트
  values:
    pilot:
      env:
        PILOT_ENABLE_WORKLOAD_ENTRY_AUTOREGISTRATION: true   # 워크로드 자동 등록
        PILOT_ENABLE_WORKLOAD_ENTRY_HEALTHCHECKS: true       # VM 워크로드 헬스 체크
    global:
      meshID: usmesh
      multiCluster:
        clusterName: west-cluster
      network: west-network
```

```bash
istioctl install -f ch13/controlplane/cluster-in-west-network-with-vm-features.yaml \
  --set values.global.proxy.privileged=true -y
```

이제 프록시들이 DNS 쿼리를 로컬 DNS 프록시로 보내고, 워크로드가 **자동 등록 + 헬스 상태 보고**를 할 수 있습니다. 단, 전제 조건이 하나 더 있습니다 — **VM이 istiod에 연결해 설정과 ID를 받아올 수 있어야** 합니다.

### 13.3.1 istiod와 클러스터 서비스들을 가상머신에 노출하기

같은 네트워크면 그냥 되지만, 다른 네트워크이므로 **east-west 게이트웨이**가 컨트롤 플레인·워크로드로 트래픽을 프록시해줘야 합니다.

**Step 1. east-west 게이트웨이 설치**

```yaml
# ch13/gateways/cluster-east-west-gw.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  name: istio-eastwestgateway
  namespace: istio-system
spec:
  profile: empty
  components:
    ingressGateways:
    - name: istio-eastwestgateway
      label:
        istio: eastwestgateway
        app: istio-eastwestgateway
        topology.istio.io/network: west-network
      enabled: true
      k8s:
        env:
        - name: ISTIO_META_ROUTER_MODE
          value: "sni-dnat"               # part12와 같은 SNI 기반 라우팅
        - name: ISTIO_META_REQUESTED_NETWORK_VIEW
          value: west-network
        service:
          ports:
          - name: status-port
            port: 15021
            targetPort: 15021
          - name: mtls                    # 클러스터 서비스용 다중 클러스터 mTLS
            port: 15443
            targetPort: 15443
          - name: tcp-istiod              # xDS + CA
            port: 15012
            targetPort: 15012
          - name: tcp-webhook             # 사이드카 주입·검증 웹훅
            port: 15017
            targetPort: 15017
  values:
    global:
      meshID: usmesh
      multiCluster:
        clusterName: west-cluster
      network: west-network
```

```bash
istioctl install -f ch13/gateways/cluster-east-west-gw.yaml -y

kubectl get svc -n istio-system -l istio.io/rev=default
# istio-eastwestgateway  LoadBalancer  10.10.200.192  192.168.10.10  15021,15443,15012,15017
# istiod                 ClusterIP     10.10.200.197  <none>         15010,15012,443,15014
```

> istiod 서비스를 보면 **15017은 443 포트로 노출**돼 있습니다(`https-webhook: 443 → 15017`). 그래서 뒤의 VirtualService에서 15017 → istiod **443**으로 라우팅합니다.

![그림 13.11 istiod와 클러스터 서비스를 VM에 노출하는 포트 — 15012(xDS·CA), 15017(웹훅), 15443(다중 클러스터 mTLS)](images/notes/istio-in-action/13-16.avif)

**Step 2. 다중 클러스터 mTLS 포트(15443) 노출** — VM → 메시 내 서비스 요청을 리버스 프록시

```yaml
# ch13/expose-services.yaml
apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: cross-network-gateway
  namespace: istio-system
spec:
  selector:
    istio: eastwestgateway
  servers:
    - port:
        number: 15443
        name: tls
        protocol: TLS
      tls:
        mode: AUTO_PASSTHROUGH    # SNI만 보고 종료 없이 통과 (part12와 동일)
      hosts:
        - "*.local"
```

**Step 3. istiod 포트(15012, 15017) 노출** — Gateway + VirtualService로 istiod까지 라우팅

```yaml
# ch13/expose-istiod.yaml
apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: istiod-gateway
spec:
  selector:
    istio: eastwestgateway
  servers:
    - port:
        name: tls-istiod
        number: 15012
        protocol: tls
      tls:
        mode: PASSTHROUGH
      hosts:
        - "*"
    - port:
        name: tls-istiodwebhook
        number: 15017
        protocol: tls
      tls:
        mode: PASSTHROUGH
      hosts:
        - "*"
---
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: istiod-vs
spec:
  hosts:
  - "*"
  gateways:
  - istiod-gateway
  tls:
  - match:
    - port: 15012
      sniHosts:
      - "*"
    route:
    - destination:
        host: istiod.istio-system.svc.cluster.local
        port:
          number: 15012
  - match:
    - port: 15017
      sniHosts:
      - "*"
    route:
    - destination:
        host: istiod.istio-system.svc.cluster.local
        port:
          number: 443
```

```bash
kubectl apply -f ch13/expose-services.yaml
kubectl apply -f ch13/expose-istiod.yaml -n istio-system

kubectl get gw,vs -A
# istio-system  gateway/cross-network-gateway
# istio-system  gateway/istiod-gateway
# istio-system  virtualservice/istiod-vs   ["istiod-gateway"]  ["*"]
```

### 13.3.2 WorkloadGroup으로 워크로드 그룹 나타내기

남은 건 VM이 속할 **WorkloadGroup**을 만드는 것뿐입니다.

```yaml
# ch13/workloadgroup.yaml
apiVersion: networking.istio.io/v1alpha3
kind: WorkloadGroup
metadata:
  name: forum
  namespace: forum-services
spec:
  metadata:
    annotations: {}
    labels:
      app: forum                # Service가 이 레이블로 그룹의 워크로드를 선택
  template:
    serviceAccount: forum-sa    # 이 그룹에 등록하려면 forum-sa 토큰이 있어야 함
    network: vm-network         # 같은 네트워크면 직접, 다르면 east-west 게이트웨이 경유
  probe:                        # istio-agent가 8080/api/healthz로 readiness 확인
    periodSeconds: 5
    initialDelaySeconds: 1
    httpGet:
      port: 8080
      path: /api/healthz
```

| 속성 | 의미 |
| --- | --- |
| `labels` | 쿠버네티스 Service가 이 그룹으로 등록된 **WorkloadEntry를 선택**할 수 있게 함 |
| `network` | 컨트롤 플레인이 VM으로 가는 라우팅을 설정할 때 사용 — **같은 네트워크면 IP**, 다르면 **그 네트워크의 east-west 게이트웨이** |
| `serviceAccount` | 워크로드의 **ID**. 그룹 멤버로 등록하려면 이 서비스 어카운트의 **클레임을 제시**해야 함 |

```bash
kubectl create namespace forum-services
kubectl create serviceaccount forum-sa -n forum-services
kubectl apply -f ch13/workloadgroup.yaml

kubectl get workloadgroup -n forum-services
# NAME    AGE
# forum   40s
```

이제 클러스터는 **forum-sa의 유효한 토큰을 제시하는 워크로드를 자동 등록**하도록 설정됐습니다.

**가상머신 사이드카용 설정 생성하기**

WorkloadGroup은 자동 등록뿐 아니라 **그룹 VM들의 공통 설정을 생성**하는 데도 쓰입니다. `istioctl`이 WorkloadGroup 정보에 **클러스터 쿼리 결과**를 더해 설정 파일을 만들어 줍니다.

```bash
istioctl x workload entry configure \
  -f ch13/workloadgroup.yaml \
  -o /tmp/my-workload-files/ \
  --clusterID "west-cluster" \    # 설치 시 지정한 클러스터 이름과 반드시 일치
  --autoregister                  # 자동 등록 활성화
# (다른 네트워크라면 --externalIP $VM_IP 로 워크로드 IP 지정)

tree /tmp/my-workload-files/
# ├── cluster.env
# ├── hosts            ← 192.168.10.10 istiod.istio-system.svc
# ├── istio-token
# ├── mesh.yaml
# └── root-cert.pem
```

| 파일 | 내용 |
| --- | --- |
| `hosts` | istiod를 노출하는 **east-west 게이트웨이 IP** |
| `root-cert.pem` | istiod가 제시한 인증서를 검증할 **루트 인증서** — 보안 커넥션의 선행 조건 |
| `istio-token` | forum WorkloadGroup의 멤버임을 istiod에 인증할 **서비스 어카운트 토큰** |
| `mesh.yaml` / `cluster.env` | 메시·네트워크·공통 속성 설정 (WorkloadGroup에 정의한 대로) |

```bash
# 토큰 디코드 — audience가 istio-ca, 주체가 forum-sa
jwt decode $(cat ./my-workload-files/istio-token)
# "aud": ["istio-ca"],
# "sub": "system:serviceaccount:forum-services:forum-sa"

cat ./my-workload-files/mesh.yaml
# defaultConfig:
#   discoveryAddress: istiod.istio-system.svc:15012
#   meshId: usmesh
#   proxyMetadata:
#     ISTIO_META_AUTO_REGISTER_GROUP: forum
#     ISTIO_META_CLUSTER_ID: west-cluster
#     ISTIO_META_DNS_CAPTURE: "true"
#     ISTIO_META_NETWORK: vm-network
#     SERVICE_ACCOUNT: forum-sa
#     TRUST_DOMAIN: cluster.local
#   readinessProbe:
#     httpGet: { path: /api/healthz, port: 8080 }
```

이 설정이 있으면 사이드카는 **컨트롤 플레인에 보안 커넥션 → SVID 발급 → xDS로 엔보이 설정 수신**을 거쳐 메시 구성원이 됩니다.

**생성된 파일을 가상머신으로 전송하기**

토큰이라는 **민감 정보**가 들어 있으므로 안전하게 옮겨야 합니다. 실습에서는 SSH(scp)로 복사하지만, **운영에서는 반드시 자동화**해야 합니다.

```bash
# k3s-s → 로컬 → forum-vm
scp ubuntu@$APP_IP:/tmp/my-workload-files/\* ./my-workload-files
scp ./my-workload-files/{cluster.env,istio-token,mesh.yaml,root-cert.pem} ubuntu@$FORUM:/tmp/
```

### 13.3.3 가상머신에 istio-agent 설치 및 설정하기

**Step 1. istio-agent 설치** — 데비안 패키지로 제공

```bash
# forum-vm
curl -LO https://storage.googleapis.com/istio-release/releases/1.17.8/deb/istio-sidecar.deb
dpkg -i istio-sidecar.deb

which pilot-agent envoy
# /usr/local/bin/pilot-agent
# /usr/local/bin/envoy
```

**Step 2. 설정 파일을 에이전트가 읽는 위치로 옮기기**

```bash
mkdir -p /etc/certs /var/run/secrets/tokens
cp /tmp/root-cert.pem /etc/certs/root-cert.pem
cp /tmp/istio-token   /var/run/secrets/tokens/istio-token
cp /tmp/cluster.env   /var/lib/istio/envoy/cluster.env
cp /tmp/mesh.yaml     /etc/istio/config/mesh

# istiod 호스트네임 → east-west 게이트웨이 IP로 정적 해석
echo "192.168.10.10 istiod.istio-system.svc" | sudo sh -c 'cat >> /etc/hosts'
# 에이전트가 자기 호스트네임 해석을 방해하지 않도록 하드코딩
echo "$(hostname --all-ip-addresses | cut -d ' ' -f 1) $(hostname)" | sudo sh -c 'cat >> /etc/hosts'
```

> **"DNS 프록시가 클러스터 호스트네임을 해석해주는 거 아니었나?"** — 맞지만, **에이전트가 아직 istiod에 연결 전**이면 DNS 프록시에 아무 항목도 없습니다. 닭과 달걀 문제라 istiod 주소만큼은 `/etc/hosts`에 정적으로 넣습니다. 환경에 맞지 않으면 east-west 게이트웨이 앞에 **네트워크 로드 밸런서**를 두는 방법도 있습니다.

**Step 3. 권한 부여 후 에이전트 시작**

```bash
# 패키지가 만든 istio-proxy 사용자에게 소유권 부여
chown -R istio-proxy /var/lib/istio /etc/certs /etc/istio/proxy /etc/istio/config /var/run/secrets

systemctl start istio
systemctl enable istio

# 시작 시 iptables 규칙이 설치되는 것을 볼 수 있다
journalctl -u istio -f
# -A ISTIO_OUTPUT -d 127.0.0.53/32 -p tcp -m tcp --dport 53 -j REDIRECT --to-ports 15053  ← DNS 캡처
# -A ISTIO_REDIRECT -p tcp -j REDIRECT --to-ports 15001                                  ← 아웃바운드 캡처

# 인증서가 발급됐는지 확인
tree /etc/certs/
# ├── cert-chain.pem   ← istiod가 발급한 SVID
# ├── key.pem
# └── root-cert.pem
```

**Step 4. 에이전트 로그 확인**

- 표준 출력 → `/var/log/istio/istio.log`
- 표준 오류 → `/var/log/istio/istio.err.log`

```bash
grep xdsproxy /var/log/istio/istio.log
# info xdsproxy Initializing with upstream address "istiod.istio-system.svc:15012" and cluster "west-cluster"
# info xdsproxy connected to upstream XDS server: istiod.istio-system.svc:15012

# 로그 파일이 안 생겼다면 서비스 시작 실패 → systemd 로그 확인
journalctl -u istio -f
```

**Step 5. 워크로드가 메시에 등록됐는지 확인**

자동 등록이 켜져 있으면 에이전트가 istiod에 연결되자마자 **WorkloadEntry가 생성**됩니다.

```bash
kubectl get workloadentries -n forum-services
# NAME                              AGE     ADDRESS
# forum-192.168.10.200-vm-network   2m13s   192.168.10.200

istioctl proxy-status
# forum-vm.forum-services   west-cluster   SYNCED  SYNCED  SYNCED  SYNCED  ...  1.17.0
# webapp-...istioinaction   west-cluster   SYNCED  SYNCED  SYNCED  SYNCED  ...  1.17.8
```

WorkloadEntry의 **주소(192.168.10.200)** 는 이 VM만의 고유 속성입니다.


### 13.3.5 트래픽을 WorkloadEntry로 라우팅하기

이번엔 반대로 **클러스터 → VM**입니다. WorkloadEntry의 IP를 직접 쓸까요? **아닙니다.** 파드 IP를 직접 안 쓰는 것과 같은 이유 — 인스턴스를 교체 가능하게 유지하려면 **쿠버네티스 Service**로 레이블 선택해야 합니다.

**Step 1. WorkloadEntry를 선택하는 Service 생성**

```yaml
# services/forum/kubernetes/forum-svc.yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    app: forum
  name: forum
spec:
  ports:
  - name: http
    port: 80
    protocol: TCP
    targetPort: 8080
  selector:
    app: forum        # WorkloadGroup이 부여한 레이블
```

```bash
kubectl apply -f services/forum/kubernetes/forum-svc.yaml -n forum-services

kubectl get svc,ep -n forum-services
# service/forum    ClusterIP  10.10.200.152  80/TCP
# endpoints/forum  <none>          ← 쿠버네티스 Endpoints에는 안 잡힘 (파드가 아니니까)

# 라우트·클러스터는 생겼다
istioctl proxy-config cluster deploy/webapp.istioinaction --fqdn forum.forum-services.svc.cluster.local
# forum.forum-services.svc.cluster.local  80  -  outbound  EDS

# 그런데 엔드포인트가 없다!
istioctl proxy-config endpoint deploy/webapp.istioinaction | grep forum
# (없음)
```

**Step 2. 요청해 보면 실패**

```bash
curl -s -H "Host: webapp.istioinaction.io" http://$APP_IP:30000/api/users
# error calling Forum service

kubectl logs -n istioinaction deploy/webapp -c istio-proxy
# "GET /api/users HTTP/1.1" 503 UH no_healthy_upstream ... outbound|80||forum.forum-services.svc.cluster.local
```

![그림 13.13 webapp의 엔보이 액세스 로그 — forum으로의 연결이 UH(no healthy upstream)로 끝나 webapp이 500을 반환](images/notes/istio-in-action/13-19.avif)

**UH** = 클러스터에 트래픽을 보낼 **정상 엔드포인트가 없음**. 즉 webapp에 forum 엔드포인트가 설정되지 않은 겁니다.

**Step 3. 원인 — forum 워크로드의 readiness 실패**

```bash
kubectl get workloadentries -n forum-services -o yaml
#   status:
#     conditions:
#     - message: 'Get "http://192.168.10.200:8080/api/healthz": ... connect: connection refused'
#       status: "False"
#       type: Healthy
```

당연합니다 — VM에 **forum 앱을 아직 안 띄웠습니다.**

**Step 4. VM에서 forum 앱 시작**

```bash
# forum-vm
wget -O forum https://git.io/J3QrT
chmod +x forum
./forum

curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/api/healthz
# 200

# k3s-s — 이제 엔드포인트가 HEALTHY로 등장
istioctl proxy-config endpoint deploy/webapp.istioinaction \
  --cluster 'outbound|80||forum.forum-services.svc.cluster.local'
# ENDPOINT              STATUS    OUTLIER CHECK  CLUSTER
# 192.168.10.200:8080   HEALTHY   OK             outbound|80||forum.forum-services.svc.cluster.local

kubectl get workloadentries -n forum-services -o yaml | grep -A2 'status: "True"'
#       status: "True"
#       type: Healthy

# 다시 요청 — 성공
kubectl logs -n istioinaction deploy/webapp -c istio-proxy
# "GET /api/users HTTP/1.1" 200 - via_upstream ... "192.168.10.200:8080" outbound|80||forum.forum-services.svc.cluster.local
```

![Kiali — webapp에서 forum(VM)으로 가는 트래픽이 나타남](images/notes/istio-in-action/13-20.avif)

> **핵심** — 이스티오는 **준비 안 된 워크로드로 트래픽을 보내지 않습니다.** 방법은 단순히 **데이터 플레인에 그 엔드포인트를 설정하지 않는 것**. 운영 환경에서는 이게 오류 인스턴스로의 라우팅을 막고 정상 인스턴스로만 보내주는 역할을 합니다.

### 13.3.6 컨트롤 플레인이 가상머신 설정: 상호 인증 강제

VM도 이제 사이드카가 트래픽을 관리하니 **이스티오의 모든 기능**을 적용할 수 있습니다. 예로 **mTLS 강제**를 걸어봅니다.

현재는 VM의 8080이 열려 있어 **메시 밖의 아무나** 요청할 수 있습니다.

```bash
# 메시에 속하지 않은 내 PC에서
curl -is $FORUM:8080/api/users | grep HTTP
# HTTP/1.1 200 OK       ← 인증 없이도 통과
```

```yaml
# ch13/strict-peer-auth.yaml — 메시 전체 STRICT
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT
```

```bash
kubectl apply -f ch13/strict-peer-auth.yaml

# 정책이 전파된 뒤 — 메시 밖 요청은 거부
curl -is $FORUM:8080/api/users
# curl: (56) Recv failure: Connection reset by peer

# 인그레스 → webapp → forum 경로는 mTLS라 정상
curl -s -H "Host: webapp.istioinaction.io" http://$APP_IP:30000/api/users
# 200
```

VM이 **컨트롤 플레인이 내려준 설정을 그대로 준수**한다는 증거입니다. PeerAuthentication은 한 예일 뿐, VirtualService·DestinationRule·AuthorizationPolicy 등 **모든 이스티오 API**로 VM 프록시를 설정할 수 있습니다.

## 13.4 DNS 프록시 이해하기

DNS 프록시는 이스티오 사이드카의 **새 구성 요소**입니다. 이 절의 목표는 DNS 프록시가 클러스터 서비스 호스트네임을 **어떻게 해석하는지** 이해하는 것입니다.

### 13.4.1 DNS 프록시가 클러스터 호스트네임을 해석하는 방법

![그림 13.14 클러스터 서비스 호스트네임 해석의 흐름](images/notes/istio-in-action/13-21.avif)

1. 클라이언트가 `webapp.istioinaction`을 해석하려고 **DNS 쿼리** 생성
2. OS가 먼저 **`/etc/hosts`** 확인 → 일치 항목 없으면 기본 해석기로 전달
3. 우분투 기본 해석기는 **systemd-resolved** (`127.0.0.53:53`)
4. 하지만 요청은 거기 **도달하지 않음** — istio-agent가 설치한 **iptables 규칙이 DNS 프록시로 리다이렉트**
5. DNS 프록시에는 메시에 알려진 서비스 항목이 있음(컨트롤 플레인이 **NDS**로 설정) → 일치하면 바로 응답
6. 클러스터 서비스가 아니면 DNS 프록시가 물러나 **`resolv.conf`의 네임서버**로 넘김 → 여기서 해석되거나 실패

**Step 1. iptables 규칙 확인** — `ISTIO_META_DNS_CAPTURE="true"`일 때만 추가됨

```bash
# forum-vm
iptables-save | grep 'to-ports 15053'
# -A OUTPUT       -d 127.0.0.53/32 -p udp -m udp --dport 53 -j REDIRECT --to-ports 15053
# -A ISTIO_OUTPUT -d 127.0.0.53/32 -p tcp -m tcp --dport 53 -j REDIRECT --to-ports 15053
```

**Step 2. 15053을 누가 듣고 있나** — pilot-agent(istio-agent)

```bash
netstat -ltunp | egrep 'PID|15053'
# tcp  127.0.0.1:15053  LISTEN  3909/pilot-agent
# udp  127.0.0.1:15053          3909/pilot-agent

# DNS 프록시에 직접 물어보기
dig +short @localhost -p 15053 webapp.istioinaction    # 10.10.200.104
dig +short @localhost -p 15053 catalog.istioinaction   # 10.10.200.121
dig +short @localhost -p 15053 forum.forum-services    # 10.10.200.152
dig +short @localhost -p 15053 www.daum.net            # 모르는 이름 → 업스트림으로 넘겨 해석
```

> 실습에서는 DNS 서버를 `@localhost -p 15053`으로 직접 지정했지만, 실제로는 **iptables가 자동으로** 이 포트로 보내므로 앱은 아무것도 몰라도 됩니다.

### 13.4.2 DNS 프록시가 인식하는 호스트네임은 무엇인가?

DNS 프록시의 전체 항목은 **istiod 디버그 엔드포인트**로 워크로드별 NDS 설정을 조회해 확인합니다.

```bash
istioctl proxy-status | awk '{print $1}'
# forum-vm.forum-services   ← proxyID로 사용

kubectl -n istio-system exec deploy/istiod -- \
  curl -Ls "localhost:8080/debug/ndsz?proxyID=forum-vm.forum-services" | jq
```

```json
{
  "resource": {
    "@type": "type.googleapis.com/istio.networking.nds.v1.NameTable",
    "table": {
      "webapp.istioinaction.svc.cluster.local": {
        "ips": ["10.10.200.104"],
        "registry": "Kubernetes",
        "shortname": "webapp",
        "namespace": "istioinaction"
      },
      "forum.forum-services.svc.cluster.local": {
        "ips": ["10.10.200.152"],
        "registry": "Kubernetes",
        "shortname": "forum",
        "namespace": "forum-services"
      }
    }
  }
}
```

테이블엔 **FQDN만** 있고 `webapp.istioinaction` 같은 짧은 이름은 없습니다. 그런데 어떻게 해석됐을까요? **istio-agent가 NDS를 받을 때 쿠버네티스에서 쓰일 모든 변형을 스스로 생성**하기 때문입니다.

- `webapp.istioinaction`
- `webapp.istioinaction.svc`
- `webapp.istioinaction.svc.cluster`

모두 같은 IP(10.10.200.104)로 해석됩니다.

> **정리**
> - DNS 프록시는 **istiod가 아는 서비스들**로 설정된다
> - istio-agent가 **짧은 변형**을 생성한다 (쿠버네티스에서의 경험과 맞추기 위해)
> - 이 레코드들로 **클러스터 서비스 호스트네임**을 해석한다
> - 퍼블릭 도메인 같은 **나머지 쿼리는 머신의 원래 네임서버**로 넘어간다

## 13.5 에이전트 동작 커스터마이징하기

에이전트는 로그 내용·형식, 요청할 **인증서 수명** 등 다양한 옵션이 있습니다. 예를 들어 다음 두 가지를 바꿔봅니다.

- DNS 프록시 **로깅 수준을 debug**로
- 인증서 수명을 **12시간**으로 단축

사이드카 설정 파일 **`/var/lib/istio/envoy/sidecar.env`** 를 수정합니다.

```bash
# forum-vm
echo 'ISTIO_AGENT_FLAGS="--log_output_level=dns:debug"' >> /var/lib/istio/envoy/sidecar.env
echo 'SECRET_TTL="12h0m0s"' >> /var/lib/istio/envoy/sidecar.env

grep "^[^#]" /var/lib/istio/envoy/sidecar.env
# ISTIO_AGENT_FLAGS="--log_output_level=dns:debug"
# SECRET_TTL="12h0m0s"

systemctl restart istio

# DNS 프록시가 모르는 이름을 업스트림으로 넘기는 과정이 보인다
dig +short @localhost -p 15053 www.daum.net
tail -f /var/log/istio/istio.log
# debug dns response for hostname "www.daum.net." not found in dns proxy, querying upstream
# debug dns upstream response for hostname "www.daum.net." : ... status: NOERROR
```

인증서가 로테이션되면 `/etc/certs/cert-chain.pem`의 만료 시각으로 TTL 변경도 확인할 수 있습니다. 전체 옵션은 이스티오 **pilot-agent** 문서를 참고하세요.

## 13.6 메시에서 WorkloadEntry 제거하기

자동 등록된 것처럼, VM이 **사라지면 자동으로 정리**됩니다. forum-vm(EC2)을 종료하고 잠시 기다리면:

```bash
watch kubectl get workloadentries -A
# No resources found
```

클라우드 네이티브 워크로드의 **일시성**을 지원하려면, 자동 **정리**도 자동 등록만큼 중요합니다.

**쿠버네티스 vs 가상머신 — 이 장의 요약**

| 기능 | 쿠버네티스 구현 | 가상머신 구현 |
| --- | --- | --- |
| **프록시 설치** | istioctl 수동 주입 또는 웹훅 자동 주입 | 직접 다운로드해 설치 (`istio-sidecar.deb`) |
| **프록시 설정** | 사이드카 주입 중에 완료 | istioctl로 WorkloadGroup에서 설정 생성 → VM으로 전송 |
| **워크로드 ID 부트스트랩** | 쿠버네티스가 SA 토큰 주입 | SA 토큰을 VM으로 **수작업 전송** |
| **헬스 체크** | 쿠버네티스가 readiness/liveness 수행 | WorkloadGroup에 readiness 설정 (liveness는 클라우드) |
| **등록** | 쿠버네티스가 처리 | WorkloadGroup 멤버로 **자동 등록** |
| **DNS 해석** | 클러스터 DNS 사용 (DNS 프록시는 선택) | istiod가 설정한 **DNS 프록시**로 FQDN 해석 |

> **실전에서는 반드시 자동화** — 이 장에서는 전 과정을 보여주려고 수작업으로 했지만, VM을 손으로 메시에 붙이면 메시가 아주 취약해집니다(새벽 3시에 VM을 손으로 재구성하는 상황). 대부분 조직은 이미 **Packer·Ansible·Terraform**으로 VM 구축을 자동화하고 있으니, 그 스크립트에 **사이드카 설치 + 설정·토큰 제공**만 추가하면 됩니다.
