## 들어가며 — 복원력(Resilience)이란

![복원력 패턴 지도](images/notes/istio-in-action/6-1.png)

**시스템이 장애나 오류로부터 빠르게 복구되어 계속 기능하는 능력**을 의미합니다. 마이크로서비스는 네트워크로 통신하는 만큼 장애 지점이 늘어나고, 한 서비스의 지연이 호출 체인을 타고 번져 **연쇄 장애(cascading failure)** 로 이어집니다. "장애가 나지 않게 만들면 된다"는 전제는 현실이 아니므로, **장애를 전제로 자동 복구·우회하도록 설계**해야 합니다.

이스티오는 애플리케이션 코드를 수정하지 않고도 네트워크 계층에서 복원력 패턴을 투명하게 처리해 줍니다.

이번 장에서 다루는 핵심 메커니즘은 다음과 같습니다.

- **클라이언트 측 로드밸런싱:** 중앙 병목을 제거하고 홉을 줄입니다.
- **지역 인식 로드밸런싱:** 같은 region/zone을 우선해 지연과 비용을 줄입니다.
- **타임아웃:** 무한 대기를 방지합니다. 외부에서 내부로 갈수록 짧게 설정합니다.
- **재시도:** 간헐적인 실패를 자동으로 복구합니다. 다만 연쇄 장애에 주의해야 합니다.
- **서킷 브레이킹:** 불건전한 서비스로의 트래픽을 차단해 회복할 기회를 줍니다.

## 6.1 애플리케이션에 복원력 구축하기

서비스 A가 서비스 B를 호출하는데 B의 특정 엔드포인트에서 지연이 발생했다면, A가 이를 **사전에 식별해** 다른 엔드포인트·다른 가용 영역·다른 리전으로 라우팅하길 바랍니다. B가 간헐적으로 실패하면 재시도하고, B가 회복할 때까지 물러나야 할 수도 있습니다.

계속 부하를 가하면(재시도로 부하가 오히려 증폭되기도 합니다) B는 과부하 상태가 되고, 이 과부하는 A와 A에 의존하는 모든 서비스로 파급됩니다. **해결책은 애플리케이션이 장애를 예상하고 자동으로 복원하거나 대체 경로로 돌아가도록 구축하는 것**입니다.

### 6.1.1 애플리케이션 라이브러리에 복원력 구축하기

서비스 메시 이전에는 이런 패턴을 **애플리케이션 코드**에 직접 작성했습니다.

- **Twitter Finagle** (2011 오픈소스, Scala/Java/JVM) — 타임아웃·재시도·서킷 브레이킹 등 RPC 복원력 패턴
- **Netflix Hystrix / Ribbon** — 각각 서킷 브레이커와 클라이언트 측 로드밸런싱. Spring Cloud Netflix로 흡수되며 자바 커뮤니티에서 크게 유행

라이브러리 방식의 문제는 세 가지입니다.

1. **언어·프레임워크마다 구현이 다르다.** Finagle과 NetflixOSS는 자바 개발자에게는 훌륭하지만 Node.js·Go·Python 개발자는 각자 변형을 찾거나 직접 만들어야 했습니다.
2. **비즈니스 로직을 침범한다.** 네트워킹 코드가 여기저기 흩어져 실제 도메인 로직을 가려버립니다.
3. **운영 부담이 크다.** 여러 언어·프레임워크 조합을 **동시에 패치하고 기능 동등성(feature parity)** 을 유지해야 합니다.

### 6.1.2 이스티오로 이런 문제 해결하기

이스티오의 서비스 프록시는 애플리케이션 옆에 위치하며 드나드는 모든 네트워크 트래픽을 처리합니다. 프록시가 **HTTP 같은 애플리케이션 수준 요청을 이해**하므로, 복원력 기능을 프록시 안에서 구현할 수 있습니다.

예를 들어 "HTTP 503이면 세 번까지 재시도"를 설정할 수 있고, **무엇을 재시도할지·몇 번 할지·시도별 타임아웃은 얼마인지**를 정확히 지정할 수 있습니다. 프록시가 **서비스 인스턴스마다 배포**되므로 애플리케이션별로 다르게 세밀하게 제어할 수 있습니다.

이스티오 서비스 프록시가 구현하는 복원력 패턴:

- 클라이언트 측 로드 밸런싱 (Client-side load balancing)
- 지역 인식 로드 밸런싱 (Locality-aware load balancing)
- 타임아웃 및 재시도 (Timeouts and retries)
- 서킷 브레이킹 (Circuit breaking)

### 6.1.3 분산형 복원력 구현

이스티오에서는 요청이 통과하는 데이터 플레인 프록시가 **애플리케이션 인스턴스와 같은 위치**에 있고, 중앙집중식 게이트웨이가 필요 없습니다. 복원력 로직을 코드에 함께 두는 라이브러리 방식과 **동일한 아키텍처**를 코드 침범 없이 얻는 셈입니다.

> **왜 중앙집중식이 아닌가:** 과거에는 하드웨어 로드 밸런서, 메시징 시스템, ESB, API 관리 같은 **비싸고 바꾸기 어려운 중앙 장치**를 요청 경로에 두었습니다. 이 구현들은 **더 정적인 환경**을 전제로 만들어져서, 고도로 동적이고 탄력적인 클라우드 아키텍처에 맞게 확장되지 못합니다. 그래서 복원력 패턴은 **분산 구현**을 선택해야 합니다.

### 실습 환경 준비

예제는 Nic Jackson의 [Fake Service](https://github.com/nicholasjackson/fake-service)를 사용합니다. `simple-web` → `simple-backend` 호출 구조이며, `simple-backend`는 복제본이 여러 개(backend-1 × 1, backend-2 × 2)라 **런타임에 일부 엔드포인트만 망가뜨려 보기** 좋습니다.

```bash
# 리소스 초기화
kubectl delete gw,vs,deploy,svc,destinationrule,envoyfilter --all -n istioinaction

# 기본 서비스 배포
kubectl apply -f ch6/simple-backend.yaml -n istioinaction
kubectl apply -f ch6/simple-web.yaml -n istioinaction
kubectl apply -f ch6/simple-web-gateway.yaml -n istioinaction

# 확인
kubectl get deploy,pod,svc,ep -n istioinaction -o wide
docker exec -it myk8s-control-plane istioctl proxy-status

# 도메인 질의를 위한 임시 설정 (실습 후 삭제할 것)
echo "127.0.0.1       simple-web.istioinaction.io" | sudo tee -a /etc/hosts

# 호출 테스트
curl -s http://simple-web.istioinaction.io:30000
curl -H "Host: simple-web.istioinaction.io" localhost   # 포트포워딩 환경

# 신규 터미널 : 반복 접속 걸어두기
while true; do curl -s http://simple-web.istioinaction.io:30000 | jq ".upstream_calls[0].body"; date "+%H:%M:%S"; sleep 1; echo; done
```

에러·지연 주입은 Fake Service의 환경변수로 제어합니다.

| 환경변수                             | 의미                             | 예시                        |
| ------------------------------------ | -------------------------------- | --------------------------- |
| TIMING_50_PERCENTILE                 | 응답 지연 중앙값                  | 1000ms (1초 지연 시뮬레이션) |
| TIMING_VARIANCE                      | 지연 편차                        | 10ms                        |
| ERROR_TYPE / ERROR_RATE / ERROR_CODE | 에러 주입 방식 / 확률 / 상태 코드 | http_error / 0.75 / 503     |

> **실습 팁:** `kubectl apply`로 env를 바꿔도 반영되지 않는 경우가 있습니다(이미지 버전 차이 등). 그럴 때는 파드에 직접 들어가 `export`로 덮어쓰거나 `kubectl rollout restart`를 함께 실행하세요.

```bash
kubectl exec -it deploy/simple-backend-1 -n istioinaction -- sh
export TIMING_50_PERCENTILE=1000ms
exit

# 반영 확인
kubectl describe pod -n istioinaction -l app=simple-backend | grep TIMING_50_PERCENTILE:
```

## 6.2 클라이언트 측 로드 밸런싱

![로드밸런싱 알고리즘과 꼬리 지연](images/notes/istio-in-action/6-2.png)

클라이언트(사이드카 프록시)에게 **가용 엔드포인트 목록을 알려주고**, 클라이언트가 스스로 알고리즘을 골라 요청을 보내는 방식입니다. 중앙 LB라는 **병목·단일 장애점이 사라지고 불필요한 홉이 제거**되어, 클라이언트와 서비스가 변화하는 토폴로지에 더 잘 대응합니다.

이스티오는 서비스/엔드포인트 디스커버리(EDS)로 프록시에 최신 엔드포인트를 계속 밀어 넣고, 운영자는 `DestinationRule`로 알고리즘만 지정합니다. 기반이 엔보이이므로 엔보이의 알고리즘을 그대로 지원합니다 — **라운드 로빈(기본값), 랜덤, 가중치를 적용한 최소 요청**.

### 6.2.1 클라이언트 측 로드 밸런싱 시작하기

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: simple-backend-dr
spec:
  host: simple-backend.istioinaction.svc.cluster.local
  trafficPolicy:
    loadBalancer:
      simple: ROUND_ROBIN # 엔드포인트 결정을 '순서대로 돌아가며'
```

**DestinationRule은 "이 목적지를 호출하는 메시 내 모든 클라이언트"에 정책을 지정한다**는 점이 핵심입니다. 특정 워크로드가 아니라 **목적지 기준**입니다.

설정이 실제 Envoy에 반영됐는지는 항상 `istioctl proxy-config`로 확인합니다.

```bash
# 클러스터 설정 : lbPolicy 확인
docker exec -it myk8s-control-plane istioctl proxy-config cluster \
  deploy/simple-web.istioinaction \
  --fqdn simple-backend.istioinaction.svc.cluster.local -o json | grep lbPolicy
# "lbPolicy": "LEAST_REQUEST"

# 엔드포인트 목록과 상태
docker exec -it myk8s-control-plane istioctl proxy-config endpoint \
  deploy/simple-web.istioinaction \
  --cluster 'outbound|80||simple-backend.istioinaction.svc.cluster.local'
# ENDPOINT            STATUS      OUTLIER CHECK     CLUSTER
# 10.10.0.14:8080     HEALTHY     OK                outbound|80||simple-backend...
# 10.10.0.15:8080     HEALTHY     OK                outbound|80||simple-backend...
# 10.10.0.16:8080     HEALTHY     OK                outbound|80||simple-backend...

# 로드밸런싱 분포 육안 확인
for i in {1..50}; do curl -s http://simple-web.istioinaction.io:30000 | jq -r ".upstream_calls[0].body"; done | sort | uniq -c | sort -nr
```

> 사실 **이스티오 서비스 프록시의 기본 설정도 ROUND_ROBIN** 입니다. DestinationRule을 적용하지 않아도 이미 클라이언트 측 로드밸런싱이 동작하고 있습니다.

### 6.2.2 시나리오 설정하기

`simple-backend-1`에 `TIMING_50_PERCENTILE=1000ms`를 넣어 **긴 GC나 리소스 경합으로 한 엔드포인트만 느려진 상황**을 시뮬레이션합니다. 로드밸런싱은 이렇게 **주기적으로 혹은 예기치 못하게 지연이 급증하는 엔드포인트의 영향을 줄이는** 효과적인 전략입니다.

부하 생성은 **Fortio** CLI를 사용합니다.

```bash
# 설치 (macOS)
brew install fortio
fortio server
open http://127.0.0.1:8080/fortio

# Windows: fortio_win_*.zip 다운로드 → 압축 해제 → .\fortio server
# (WSL2 혼용 시 윈도우 쪽에서 실행하면 정상 동작)

# 동작 확인
fortio curl http://simple-web.istioinaction.io:30000

# CLI로 부하 생성 (30초, 2 커넥션, 2 qps)
fortio load -quiet -jitter -t 30s -c 2 -qps 2 --allow-initial-errors \
  http://simple-web.istioinaction.io:30000

# 클러스터 내부에서 실행하는 경우
kubectl -n default run fortio --image=fortio/fortio:1.6.8 --restart='Never' \
  -- load -H "Host: simple-web.istioinaction.io" \
  -jitter -t 60s -c 10 -qps 1000 \
  http://istio-ingressgateway.istio-system/
```

**웹 대시보드 테스트 파라미터** — 60초 동안 10개 커넥션으로 초당 1000개 요청

| 항목                     | 값                                        |
| ------------------------ | ----------------------------------------- |
| URL                      | http://simple-web.istioinaction.io:30000  |
| QPS / Duration / Threads | 1000 / 60s / 10                           |
| Jitter                   | Check                                     |
| No Catch-up              | Uncheck                                   |
| Timeout                  | 2000ms                                    |

> **참고:** Timeout은 반드시 2000ms로 늘려야 합니다. 기본값 750ms로는 1초 지연 요청이 **전부 실패**해서 알고리즘 차이가 보이지 않습니다.

### 6.2.3 다양한 클라이언트 측 로드 밸런싱 전략 테스트하기

로드밸런싱 전략을 라운드 로빈 → 랜덤 → 최소 커넥션으로 바꿔가며 같은 부하를 겁니다.

| 알고리즘              | 50분위  | 75분위  | 90분위  | 99분위  |
| --------------------- | ------- | ------- | ------- | ------- |
| ROUND_ROBIN (기본값)  | 0.190초 | 1.031초 | 1.103초 | 1.147초 |
| RANDOM                | 0.193초 | 1.023초 | 1.059초 | 1.081초 |
| LEAST_CONN (권장)     | 0.184초 | 0.196초 | 1.008초 | 1.029초 |

세 알고리즘의 **50분위는 거의 같습니다(0.18~0.19초).** 차이는 **꼬리 지연(tail latency)** 에서 드러납니다. 라운드 로빈·랜덤은 75분위부터 이미 1초를 넘지만, 최소 커넥션은 75분위까지 0.2초 이내를 유지합니다.

```bash
# RANDOM 으로 변경
kubectl apply -f ch6/simple-backend-dr-random.yaml -n istioinaction

# LEAST_CONN 으로 변경
kubectl apply -f ch6/simple-backend-dr-least-conn.yaml -n istioinaction

# 반영 확인
kubectl get destinationrule simple-backend-dr -n istioinaction \
  -o jsonpath='{.spec.trafficPolicy.loadBalancer.simple}{"\n"}'
```

### 6.2.4 다양한 로드 밸런싱 알고리듬 이해하기

로드 테스트를 종합하면 세 가지를 알 수 있습니다. 첫째, **현실적인 지연 분포에서는 알고리즘마다 결과가 크게 다릅니다.** 둘째, 히스토그램과 백분위수가 모두 다릅니다. 셋째, **최소 커넥션이 랜덤·라운드 로빈보다 확실히 낫습니다.**

- **라운드 로빈 / 랜덤:** 구현과 이해가 쉽지만 **런타임 동작을 전혀 고려하지 않습니다.** 리소스가 동일해도 GC·경합 때문에 엔드포인트는 결코 균일하지 않은데, 이 둘은 느린 엔드포인트에도 똑같이 요청을 밀어 넣습니다.
- **최소 커넥션:** 엔드포인트의 **대기열 깊이(queue depth)** 를 보고 활성 요청이 가장 적은 쪽을 고릅니다. 형편없이 동작하는 엔드포인트를 자연스럽게 피하고 빠르게 응답하는 쪽을 선호합니다.

> **엔보이 최소 요청 로드 밸런싱**
>
> - 이스티오는 `LEAST_CONN`이라고 부르지만, 엔보이가 추적하는 것은 **커넥션이 아니라 요청 깊이**입니다. Envoy 설정에는 `LEAST_REQUEST`로 나타납니다.
> - 전체를 스캔하지 않고 **무작위로 엔드포인트 2개를 뽑아 그중 활성 요청이 적은 쪽을 선택**합니다. 연속된 로드밸런싱 시도에서도 동일하게 동작합니다.
> - 이를 **"두 가지 선택의 힘(the power of two choices)"** 이라고 합니다. 전수 조사 대비 비용은 훨씬 싸면서 결과는 거의 비슷한, 잘 알려진 타협점입니다.

## 6.3 지역 인식 로드 밸런싱

컨트롤 플레인이 **서비스 토폴로지 전체를 이해한다**는 점을 활용해, 워크로드의 위치에 따라 루트에 가중치를 부여하는 방식입니다. 모든 엔드포인트를 동등하게 취급하면 리전·영역을 넘나들며 **지연이 길어지고 클라우드 데이터 전송 비용도 발생**합니다.

### 6.3.1 지역 인식 로드 밸런싱 실습

이스티오는 노드 레이블에서 지역 정보를 가져와 엔보이 로드밸런싱 엔드포인트에 지역 정보로 보강합니다.

- `topology.kubernetes.io/region` / `topology.kubernetes.io/zone` (구: `failure-domain.beta.kubernetes.io/*`)
- 구글 클라우드·AWS 같은 프로바이더가 자동으로 붙여주는 경우가 많습니다.

단일 노드 실습 환경에서는 노드 레이블 대신 **파드 레이블로 지역을 명시**할 수 있습니다.

- **라벨 형식:** `istio-locality: region.zone` (예: `us-west1.us-west1-a`)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: simple-web
spec:
  template:
    metadata:
      labels:
        app: simple-web
        istio-locality: us-west1.us-west1-a # 호출자
---
# simple-backend-1 : us-west1.us-west1-a  (simple-web과 같은 영역)
# simple-backend-2 : us-west1.us-west1-b  (리전은 같고 영역이 다름)
```

**지역 인식 로드밸런싱은 기본적으로 활성화**되어 있습니다. 끄려면 `meshConfig.localityLbSetting.enabled: false`로 설정합니다. 리전·영역뿐 아니라 더 세밀한 **하위 영역(subzone)** 까지 구분할 수 있습니다.

> **주의 — 반드시 이상값 감지와 함께:** 헬스 체크가 없으면 이스티오는 **로드밸런싱 풀의 어느 엔드포인트가 비정상인지, 어떤 기준으로 다음 지역에 흘려보낼지 알 수 없습니다.** 이상값 감지는 엔드포인트가 오류를 반환하는지 **수동적으로(passively) 관찰**해 비정상으로 표시하며, 이것이 페일오버의 트리거가 됩니다.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: simple-backend-dr
spec:
  host: simple-backend.istioinaction.svc.cluster.local
  trafficPolicy:
    outlierDetection:
      consecutive5xxErrors: 1
      interval: 5s
      baseEjectionTime: 30s
      maxEjectionPercent: 100
```

**호출 테스트 1 — 이상값 감지 적용 전후**

```bash
# 적용 전 : 지역 무시하고 3개 엔드포인트에 고르게 분산
for i in {1..50}; do curl -s http://simple-web.istioinaction.io:30000 | jq -r ".upstream_calls[0].body"; done | sort | uniq -c

kubectl apply -f ch6/simple-backend-dr-outlier.yaml -n istioinaction

# 적용 후 : simple-backend-1(같은 zone)로만 100% 라우팅

# 엔드포인트에 지역 정보가 실렸는지 확인
docker exec -it myk8s-control-plane istioctl proxy-config endpoint \
  deploy/simple-web.istioinaction \
  --cluster 'outbound|80||simple-backend.istioinaction.svc.cluster.local' -o json
```

```text
"locality": { "region": "us-west1", "zone": "us-west1-b" },
"weight": 1,
"priority": 1          # 다른 zone은 priority가 낮게(1) 부여됨
```

**호출 테스트 2 — 오동작 주입 후 페일오버 확인**

같은 영역의 `simple-backend-1`이 **항상 HTTP 500을 반환**하도록 만듭니다.

```bash
kubectl apply -f ch6/simple-service-locality-failure.yaml -n istioinaction
# ERROR_TYPE=http_error / ERROR_RATE=1 / ERROR_CODE=500

docker exec -it myk8s-control-plane istioctl proxy-config endpoint \
  deploy/simple-web.istioinaction \
  --cluster 'outbound|80||simple-backend.istioinaction.svc.cluster.local'
# ENDPOINT            STATUS      OUTLIER CHECK     CLUSTER
# 10.10.0.23:8080     HEALTHY     OK                outbound|80||simple-backend...
# 10.10.0.24:8080     HEALTHY     OK                outbound|80||simple-backend...
# 10.10.0.25:8080     HEALTHY     FAILED            outbound|80||simple-backend...  ← 제거됨
```

JSON으로 보면 `edsHealthStatus`는 여전히 `HEALTHY`인데 `failedOutlierCheck: true`가 붙습니다. **쿠버네티스 관점에서는 정상이지만 엔보이 관점에서는 퇴출된 상태**라는 뜻입니다.

**동작 확인 결과 정리:**

- 이상값 감지를 추가하면 같은 zone으로만 라우팅됩니다.
- 같은 zone의 엔드포인트가 비정상이면 자동으로 다른 zone으로 페일오버합니다.
- 이 지역 인식 로드밸런싱은 **단일 클러스터 내부**에서 이뤄지는 동작입니다.

> **튜닝 관점:** 기본 지역 인식 LB가 항상 바람직하지는 않습니다. 특정 지역에서 **호출하는 서비스 인스턴스보다 목표 서비스 인스턴스가 적으면** 그 지역만 과부하가 걸리고 시스템 전체 부하가 의도치 않게 불균형해집니다. 결국 부하 특성과 토폴로지에 맞춘 튜닝이 필요합니다.

### 6.3.2 가중치 분포로 지역 인식 로드 밸런싱 제어 강화

기본 동작은 "같은 지역으로 전부 보내고, 장애나 비정상 엔드포인트가 있을 때만 다른 지역으로 넘김"입니다. 하지만 피크 시간이나 계절성 트래픽으로 **특정 지역이 과부하될 것으로 예상되면** 미리 나눠 보낼 수 있습니다. 이를 **지역 가중 분포(locality weighted distribution)** 라고 합니다.

```yaml
trafficPolicy:
  loadBalancer:
    localityLbSetting:
      distribute:
        - from: us-west1/us-west1-a/* # 출발지 영역
          to:
            "us-west1/us-west1-a/*": 70 # 최인접 지역
            "us-west1/us-west1-b/*": 30 # 인접 지역
  connectionPool:
    http:
      http2MaxRequests: 10
      maxRequestsPerConnection: 10
  outlierDetection:
    consecutive5xxErrors: 1
    interval: 5s
    baseEjectionTime: 30s
    maxEjectionPercent: 100
```

> **5장의 트래픽 분할과 다른 점:** 5장의 가중치는 **서비스 부분집합(subset, 버전)** 간 비중이었습니다. 여기서는 **배포 토폴로지(지역)** 기준이며 부분집합과 무관합니다. 둘은 배타적이지 않고 **중첩해서 함께 사용**할 수 있습니다 — 지역 인식 로드밸런서 **위에** 5장의 세밀한 트래픽 제어를 얹는 식입니다.

## 6.4 투명한 타임아웃과 재시도

네트워크에 분산된 시스템을 구축할 때 가장 큰 문제는 **지연과 실패**입니다. 앞 절에서는 로드밸런싱과 지역으로 완화했다면, 여기서는 타임아웃과 재시도로 네트워크에 내재된 신뢰성 문제를 정면으로 다룹니다.

### 6.4.1 타임아웃

![중첩된 타임아웃](images/notes/istio-in-action/6-3.png)

분산 환경에서 가장 까다로운 시나리오는 **실패가 아니라 지연**입니다. 처리가 느려지면 리소스를 오래 붙들고, 서비스에 작업이 적체되며, 결국 연쇄 장애로 번집니다.

`VirtualService`에서 요청별로 지정하며, 시간을 초과하면 500 응답을 반환합니다.

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: simple-backend-vs
spec:
  hosts:
    - simple-backend
  http:
    - route:
        - destination:
            host: simple-backend
      timeout: 0.5s
```

- **아키텍처 원칙:** 트래픽이 들어오는 **가장자리(edge)에 가까울수록 길게**, 호출 그래프가 **깊어질수록 짧게(제한적으로)** 설정합니다.
- **가장 제한적인 타임아웃이 먼저 발동합니다.** A→B가 1초, B→C가 2초라면 B→C 타임아웃은 영원히 발동하지 않습니다. 즉 **바깥쪽 타임아웃이 안쪽보다 짧으면 안쪽 설정은 무의미**해집니다.

```bash
# 환경 재설정
kubectl apply -f ch6/simple-web.yaml -n istioinaction
kubectl apply -f ch6/simple-backend.yaml -n istioinaction
kubectl delete destinationrule simple-backend-dr -n istioinaction

# 평상시 : 10~20ms
for i in {1..10}; do time curl -s http://simple-web.istioinaction.io:30000 | jq .code; done

# 1초 지연 서비스 배포 후 0.5초 타임아웃 적용
kubectl apply -f ch6/simple-backend-delayed.yaml -n istioinaction
kubectl apply -f ch6/simple-backend-vs-timeout.yaml -n istioinaction

# 0.5초 초과 시 500 응답 확인
for i in {1..10}; do time curl -s http://simple-web.istioinaction.io:30000 | jq .code; done
# curl ... 2% cpu 0.537 total
# 500
```

### 6.4.2 재시도

![Thundering Herd — 계층마다 재시도하면 요청이 증폭된다](images/notes/istio-in-action/6-4.png)

간헐적 네트워크 실패에 재시도하지 않으면 서비스가 **흔하고 예견 가능한 실패**에 취약해집니다. 반대로 무분별한 재시도는 연쇄 장애를 부릅니다 — **서비스가 실제로 과부하된 상태라면 재시도는 문제를 악화시킬 뿐입니다.**

이스티오는 **기본적으로 재시도가 켜져 있고, 2회까지 재시도**합니다. 동작을 정확히 관찰하려면 먼저 기본값을 끄고 시작합니다.

```bash
# 메시 전역 기본 재시도 끄기
docker exec -it myk8s-control-plane bash
istioctl install --set profile=default --set meshConfig.defaultHttpRetryPolicy.attempts=0
exit

# 확인
kubectl get istiooperators -n istio-system -o yaml | grep -A2 defaultHttpRetryPolicy
```

**기본 재시도가 적용되는 조건** — 모두 "요청이 실제로 전송되지 못했음"을 뜻하므로 재시도해도 안전한 상황입니다.

- 커넥션 수립 실패 `connect-failure`
- 스트림 거부됨 `refused-stream`
- 사용 불가 (gRPC 상태 코드 14) `unavailable`
- 취소됨 (gRPC 상태 코드 1) `cancelled`
- 재시도 가능 상태 코드 — **이스티오 기본값은 HTTP 503뿐**

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: simple-backend-vs
spec:
  hosts:
    - simple-backend
  http:
    - route:
        - destination:
            host: simple-backend
      retries:
        attempts: 2 # 최대 재시도 횟수 (원 요청 포함 총 3회 전송)
        retryOn: 5xx # 다시 시도할 오류
        perTryTimeout: 300ms # 시도별 타임아웃
        retryRemoteLocalities: true # 재시도 시 다른 지역 엔드포인트 허용 여부
```

**실습 1 — 503은 기본으로 재시도된다**

```bash
# 75% 확률로 503을 반환하는 simple-backend-1 배포
kubectl apply -f ch6/simple-backend-periodic-failure-503.yaml -n istioinaction

# 재시도 없음 : simple-backend-1 --(503)--> simple-web --(500)--> curl
for i in {1..10}; do curl -s http://simple-web.istioinaction.io:30000 | jq .code; done
# 500 과 200 이 섞여서 반환

# attempts: 2 만 지정해서 적용
kubectl apply -f ch6/simple-backend-enable-retry.yaml -n istioinaction

# 모두 200 반환 — 실패는 있지만 호출자에게는 드러나지 않는다
for i in {1..10}; do curl -s http://simple-web.istioinaction.io:30000 | jq .code; done
```

Envoy 라우트에 실제로 어떻게 반영됐는지 확인합니다.

```bash
docker exec -it myk8s-control-plane istioctl proxy-config routes \
  deploy/simple-web.istioinaction --name 80 -o json
```

```text
"retryPolicy": {
    "retryOn": "connect-failure,refused-stream,unavailable,cancelled,retriable-status-codes",
    "numRetries": 2,
    "retryHostPredicate": [{ "name": "envoy.retry_host_predicates.previous_hosts" }],
    "hostSelectionRetryMaxAttempts": "5",
    "retriableStatusCodes": [ 503 ]
}
```

`previous_hosts` 프레디케이트는 **직전에 실패한 호스트를 피해서** 다른 엔드포인트를 고르게 하고, 최대 5번까지 호스트 선택을 다시 시도합니다.

**실습 2 — 500은 기본으로 재시도되지 않는다**

```bash
# 75% 확률로 500 반환
kubectl apply -f ch6/simple-backend-periodic-failure-500.yaml -n istioinaction

# 재시도 동작 안 함 : retriableStatusCodes 에 503 만 있기 때문
for i in {1..10}; do curl -s http://simple-web.istioinaction.io:30000 | jq .code; done
# 200 / 500 섞여서 반환

# retryOn: 5xx 로 명시하면 모두 성공
kubectl apply -f ch6/simple-backend-vs-retry-500.yaml -n istioinaction
```

가능한 `retryOn` 값은 [엔보이 문서](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/router_filter#x-envoy-retry-on)를 참고합니다.

**타임아웃에 따른 재시도**

각 재시도에는 자체 제한 시간(`perTryTimeout`)이 있고, 재시도 사이에는 **백오프 지연**이 있습니다. 이스티오의 **백오프 베이스는 25ms**이며 연속 재시도마다 `25ms × 재시도 횟수`까지 기다립니다. `attempts: 2`면 실제로는 **원 요청 1회 + 재시도 2회 = 총 3회** 전달됩니다.

```text
perTryTimeout × attempts + backoffTime × (attempts-1) < 전체 타임아웃
```

전체 타임아웃 1초에 `perTryTimeout: 500ms` × 3회 재시도 정책은 **의도대로 동작하지 않습니다.** 재시도를 다 하기 전에 전체 타임아웃이 먼저 터집니다.

**Thundering Herd 문제**

호출 깊이(call depth)가 깊은 구조에서 각 계층마다 재시도하면 내부 서비스로 요청이 기하급수적으로 증폭됩니다. **5개 계층에서 각 2회 재시도하면 들어온 요청 하나가 최대 2⁵ = 32회의 요청**이 됩니다. 체인 끝의 리소스가 이미 과부하 상태라면, 이 추가 부하가 그 리소스를 완전히 쓰러뜨립니다.

대응 방안:

- Edge에서는 재시도 1회 또는 0회, **중간 계층은 0회**, 호출 스택 깊숙한 곳에서만 재시도합니다. (다만 이 방법도 완벽하지는 않습니다.)
- 전체 재시도 횟수에 상한을 두는 **재시도 예산(retry budget)** 이 근본 해법이지만, **이스티오 API에는 아직 노출되지 않았습니다.**
- 재시도는 기본적으로 **자기 지역의 엔드포인트**에 시도합니다. `retryRemoteLocalities: true`로 다른 지역까지 확장할 수 있으며, **이상값 감지가 같은 지역의 오작동을 알아채기 전 구간**을 메우는 데 유용합니다.

### 6.4.3 고급 재시도

백오프 시간(25ms)과 재시도 가능 상태 코드(503)는 이스티오 API로 바꿀 수 없습니다. **확장 API인 EnvoyFilter로 엔보이 설정을 직접 수정**해야 합니다.

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: simple-backend-retry-status-codes
  namespace: istioinaction
spec:
  workloadSelector:
    labels:
      app: simple-web
  configPatches:
    - applyTo: HTTP_ROUTE
      match:
        context: SIDECAR_OUTBOUND
        routeConfiguration:
          vhost:
            name: "simple-backend.istioinaction.svc.cluster.local:80"
      patch:
        operation: MERGE
        value:
          route:
            retry_policy:
              retry_back_off:
                base_interval: 50ms # 백오프 기본 간격 상향
              retriable_status_codes: # 재시도할 수 있는 코드를 추가
                - 408
                - 400
```

VirtualService의 `retryOn`에도 `retriable-status-codes`를 추가해야 위 코드 목록이 실제로 쓰입니다.

```yaml
retries:
  attempts: 2
  retryOn: 5xx,retriable-status-codes
```

```bash
# 408 에러 주입
kubectl apply -f ch6/simple-backend-periodic-failure-408.yaml -n istioinaction
# EnvoyFilter 적용 전 : 408은 5xx가 아니므로 재시도 안 됨 → 500 리턴
# EnvoyFilter + retryOn 적용 후 : 모두 성공

kubectl apply -f ch6/simple-backend-ef-retry-status-codes.yaml -n istioinaction
kubectl apply -f ch6/simple-backend-vs-retry-on.yaml -n istioinaction

docker exec -it myk8s-control-plane istioctl proxy-config route \
  deploy/simple-web.istioinaction --name 80 -o json
```

```text
"retryPolicy": {
    "retryOn": "5xx,retriable-status-codes",
    "numRetries": 2,
    "retriableStatusCodes": [ 408, 400 ],
    "retryBackOff": { "baseInterval": "0.050s" }
}
```

> **EnvoyFilter는 '비상용(break glass)' 수단입니다.** 이스티오 API는 기저 데이터 플레인에 대한 추상화인데, EnvoyFilter는 그 추상화를 우회합니다. **엔보이 API는 이스티오 릴리즈마다 바뀔 수 있으므로 하위 호환성을 전제하면 안 되고**, 운영에 넣은 필터가 업그레이드 후에도 유효한지 반드시 확인해야 합니다. (자세한 내용은 14장)

> **요청 헤징 (Request Hedging):** 요청이 `perTryTimeout`에 걸리면 동일 요청을 **다른 호스트로도 보내 원래 요청과 경쟁(race)** 시키고, 먼저 성공한 응답을 다운스트림 호출자에게 반환하는 기법입니다. 원본이 먼저 돌아오면 원본을 씁니다. 테일 레이턴시는 개선되지만 요청 부하가 늘어나는 트레이드오프가 있습니다. 역시 EnvoyFilter로만 설정할 수 있습니다.

```yaml
- applyTo: VIRTUAL_HOST
  patch:
    operation: MERGE
    value:
      hedge_policy:
        hedge_on_per_try_timeout: true
```

## 6.5 이스티오를 이용한 서킷 브레이킹

![서킷 브레이킹 — 커넥션 풀 제어와 이상값 감지](images/notes/istio-in-action/6-5.png)

복원력 아키텍처의 마지막 퍼즐 조각은 **재시도를 아예 건너뛰고 빠르게 실패하는 것**입니다. 부하를 더 얹는 대신 잠시 트래픽을 제한해 **업스트림이 회복할 시간을 벌어줍니다.** 가정의 회로 차단기가 단락이 반복되면 회로를 열어 나머지 시스템을 보호하는 것과 같은 발상입니다.

이스티오에는 '서킷 브레이커'라는 명시적 설정이 없고, 두 가지 방법으로 이를 구현합니다.

1. **커넥션 풀 제어:** 특정 서비스로 허용할 커넥션·미해결 요청 개수를 관리합니다 (Fail Fast). → **느려지는 서비스**에 대응
2. **이상값 감지:** 오동작하는 특정 호스트를 풀에서 잠시 퇴출시킵니다 (Eviction). → **모든 호스트가 소진되면 사실상 회로가 '개방'된 상태**가 됩니다.

### 6.5.1 커넥션 풀 제어로 느린 서비스에 대응하기

어떤 서비스에 진행 중인 요청이 10개이고 계속 늘어나는 중이라면, **요청을 더 보내는 것은 의미가 없습니다.** 업스트림을 압도할 뿐입니다. 요청이 너무 쌓이면 **단락시켜(fail fast) 클라이언트에 즉시 반환**하는 편이 낫습니다.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: simple-backend-dr
spec:
  host: simple-backend.istioinaction.svc.cluster.local
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 1 # 커넥션 총 개수
      http:
        http1MaxPendingRequests: 1 # 큐 대기 요청 수
        maxRequestsPerConnection: 1 # 커넥션당 요청 수
        http2MaxRequests: 1 # 동시(병렬) 요청 수
        maxRetries: 1
```

| 파라미터                 | 설명                                                            | Envoy 명칭                  | 기본값  |
| ------------------------ | --------------------------------------------------------------- | --------------------------- | ------- |
| maxConnections           | 커넥션 총 개수이자 오버플로 보고 임계값. 실제 상한은 "엔드포인트 개수 + 설정값" | max_connections             | 2^32-1  |
| http1MaxPendingRequests  | 사용할 커넥션이 없어 큐에서 대기 중인 요청 수                     | max_pending_requests        | 1024    |
| maxRequestsPerConnection | 커넥션 하나당 처리할 HTTP 요청 수                                 | max_requests_per_connection | -       |
| http2MaxRequests         | 클러스터 내 모든 엔드포인트에 대한 최대 병렬 요청 수               | max_requests                | 1024    |
| maxRetries               | 동시에 미해결 상태일 수 있는 재시도 수                            | max_retries                 | -       |

> **이름 함정 — `http2MaxRequests`:** 이름과 달리 **HTTP/2 전용이 아닙니다.** 내부적으로 HTTP1.1/HTTP2 상관없이 클러스터 내 모든 엔드포인트에 걸친 **병렬 요청 최대 개수**를 제어합니다. 이스티오가 이름을 잘못 붙인 케이스입니다. ([istio#27473](https://github.com/istio/istio/issues/27473))

**통계 수집 활성화 (필수 준비)**

기본적으로 이스티오는 수집 에이전트가 **카디널리티에 압도되지 않도록** 엔보이 통계를 잘라냅니다. 서킷 브레이킹이 원인인지 업스트림 장애가 원인인지 구별하려면 대상 클러스터의 통계를 명시적으로 켜야 합니다.

```bash
# simple-web 디플로이먼트에 애너테이션 추가
# sidecar.istio.io/statsInclusionPrefixes: "cluster.outbound|80||simple-backend.istioinaction.svc.cluster.local"
kubectl apply -f ch6/simple-web-stats-incl.yaml -n istioinaction

# 정확한 관찰을 위해 카운터 초기화
kubectl exec -it deploy/simple-web -c istio-proxy -n istioinaction \
  -- curl -X POST localhost:15000/reset_counters
```

**단계별 실습 — 임계값을 하나씩 풀어보기**

응답에 1초가 걸리는 `simple-backend-1` 하나만 남긴 상태(`simple-backend-2`는 replicas=0)에서 진행합니다.

**① 기준선: 커넥션 1, 초당 1요청 → 100% 성공**

```bash
fortio load -quiet -jitter -t 30s -c 1 -qps 1 http://simple-web.istioinaction.io:30000
# Code 200 : 30 (100.0 %)
# All done 30 calls  1023.868 ms avg, 1.0 qps
```

**② 커넥션 2, 초당 2요청 → 서킷 브레이커 발동**

```bash
fortio load -quiet -jitter -t 30s -c 2 -qps 2 --allow-initial-errors \
  http://simple-web.istioinaction.io:30000
# Sockets used: 19 (for perfect keepalive, would be 2)
# Code 200 : 30 (63.8 %)
# Code 500 : 17 (36.2 %)
```

```bash
kubectl exec -it deploy/simple-web -c istio-proxy -n istioinaction \
  -- curl -s localhost:15000/stats | grep simple-backend | grep overflow
```

```text
upstream_cx_overflow: 45            # maxConnections 초과
upstream_cx_pool_overflow: 0
upstream_rq_pending_overflow: 18    # http1MaxPendingRequests 초과  ← 실패 17건과 일치
upstream_rq_retry_overflow: 0
```

`Sockets used: 19`가 결정적 단서입니다. 완벽한 keepalive라면 2여야 하는데 19개를 썼다는 건 **커넥션이 계속 끊기고 다시 열렸다**는 뜻입니다.

**③ `http2MaxRequests` 1 → 2 (동시 요청 허용량 증가)**

```bash
kubectl patch destinationrule simple-backend-dr -n istioinaction --type merge --patch \
  '{"spec": {"trafficPolicy": {"connectionPool": {"http": {"http2MaxRequests": 2}}}}}'

fortio load -quiet -jitter -t 30s -c 2 -qps 2 --allow-initial-errors http://simple-web.istioinaction.io:30000
# Sockets used: 3
# Code 200 : 33 (97.1 %)
# Code 500 : 1 (2.9 %)
```

```text
upstream_cx_overflow: 40
upstream_rq_pending_overflow: 1     # 18 → 1 로 급감
```

남은 1건은 **보류 대기열(pending queue) 서킷 브레이커**가 걸린 것입니다.

**④ `http1MaxPendingRequests` 1 → 2 (큐 깊이 증가) → 100% 성공**

```bash
kubectl patch destinationrule simple-backend-dr -n istioinaction --type merge --patch \
  '{"spec": {"trafficPolicy": {"connectionPool": {"http": {"http1MaxPendingRequests": 2}}}}}'

fortio load -quiet -jitter -t 30s -c 2 -qps 2 --allow-initial-errors http://simple-web.istioinaction.io:30000
# Sockets used: 2 (for perfect keepalive, would be 2)   ← 큐 덕분에 소켓 2개만 사용
# Code 200 : 33 (100.0 %)
```

```text
upstream_cx_overflow: 45
upstream_rq_pending_overflow: 0     # 0 !
```

> **읽는 법:** `upstream_cx_overflow`는 45로 여전히 높지만 실패는 0입니다. **커넥션 상한을 넘는 것 자체는 실패가 아니고**, 넘친 요청이 **큐에도 들어가지 못할 때(`rq_pending_overflow`) 비로소 요청이 실패**합니다. 두 메트릭을 함께 봐야 원인을 특정할 수 있습니다.

**런타임에 서킷 브레이킹을 식별하는 법**

애플리케이션 입장에서 "서킷 브레이킹 때문에 실패한 것"과 "업스트림이 진짜 죽어서 실패한 것"을 구별해야 합니다. 이스티오는 임계값 초과로 실패시킨 응답에 **`x-envoy-overloaded: true` 헤더**를 붙입니다. 임계값을 다시 가장 엄격하게(커넥션·보류 요청·최대 요청 모두 1) 되돌리고, 부하 테스트 도중에 단발 curl을 실행하면 재현됩니다.

```text
"upstream_calls": [{
  "uri": "http://simple-backend:80/",
  "headers": {
    "Server": "envoy",
    "X-Envoy-Overloaded": "true"      # ← 서킷 브레이킹 지표
  },
  "code": 503,
  "error": "Error processing upstream request: expected code 200, got 503"
}],
"code": 500
```

프록시 액세스 로그에서는 **503 + `UO` 플래그**로 나타납니다.

```text
# simple-web istio-proxy : 서킷 브레이킹으로 업스트림 전달 실패
"GET // HTTP/1.1" 503 UO upstream_reset_before_response_started{overflow} ...

# simple-web 애플리케이션 : backend 응답을 못 받아 사용자에게 500 반환
"GET / HTTP/1.1" 500 - via_upstream ...
```

- **`UO` = Upstream Overflow** — 엔보이의 커넥션 풀·요청 큐가 가득 차 업스트림으로 요청을 전달할 수 없는 상태
- **`via_upstream`** — 오류가 엔보이가 아니라 업스트림 애플리케이션에서 발생했음을 의미

> **관찰 포인트:** 503을 만든 주체는 **simple-web 쪽 사이드카**입니다. 그래서 Kiali/Jaeger에서 simple-backend 쪽에는 503 기록이 없는데 simple-web에는 500이 찍히는, 언뜻 모순처럼 보이는 그림이 나옵니다. 요청이 **애초에 백엔드에 도달하지 않았기** 때문입니다. Jaeger에서는 `error=true` 태그나 `guid:x-request-id`로 필터링해 추적할 수 있습니다.

**프로메테우스 메트릭:** `envoy_cluster_upstream_cx_overflow`, `envoy_cluster_upstream_rq_pending_overflow`

일반적으로 **네트워크는 실패할 수 있다는 전제**로 애플리케이션 코드를 작성해야 합니다. 이 헤더를 확인하면 캐시된 값을 반환하거나 축약된 응답을 주는 등 **폴백(fallback) 전략**을 선택할 수 있습니다.

### 6.5.2 이상값 감지로 비정상 서비스에 대응하기

앞 절이 "느려지는 서비스"였다면, 이번에는 **오동작(misbehaving)하는 특정 호스트를 서비스에서 제거**하는 접근입니다. 이스티오는 엔보이의 이상값 감지 기능을 사용합니다.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: simple-backend-dr
spec:
  host: simple-backend.istioinaction.svc.cluster.local
  trafficPolicy:
    outlierDetection:
      consecutive5xxErrors: 1 # 연속 5xx N회 시 제거
      interval: 5s # 판단(sweep) 주기
      baseEjectionTime: 5s # 제거 지속 시간
      maxEjectionPercent: 100 # 최대 제거 비율
```

| 파라미터             | 의미                                                                        | 기본값 |
| -------------------- | --------------------------------------------------------------------------- | ------ |
| consecutive5xxErrors | 연속 에러 임계값. 1이면 한 번만 실패해도 발동                                 | 5      |
| interval             | 서비스 프록시의 퇴출 판단 주기                                               | 10초   |
| baseEjectionTime     | 퇴출 지속 시간. 실제 시간 = 퇴출 횟수(n) × baseEjectionTime → 반복 퇴출될수록 길어짐 | 30초   |
| maxEjectionPercent   | 풀에서 제거 가능한 호스트 비율. 100%면 전부 오동작 시 어떤 요청도 통과 못 함(= 회로 개방) | 10%    |

**실습 결과** (75% 확률로 500을 반환하는 엔드포인트 1개 포함)

이상값 감지를 고립시켜 관찰하기 위해 **기본 재시도는 꺼둔 상태**로 시작하고, 마지막에 재시도를 더해 둘이 어떻게 보완되는지 봅니다.

| 설정                 | 성공률            | 실패율            |
| -------------------- | ----------------- | ----------------- |
| 이상값 감지 없음      | Code 200 : 71.7%  | Code 500 : 28.3%  |
| 이상값 감지 적용      | Code 200 : 96.7%  | Code 500 : 3.3%   |
| 이상값 감지 + 재시도  | Code 200 : 100%   | -                 |

**해석이 중요합니다.** 이상값 감지만으로는 3.3%가 남습니다. 이 실패는 **엔드포인트가 비정상으로 판정되기까지 필요한 초기 실패**(아래 통계의 `ejections_consecutive_5xx: 3`)입니다. 여기에 재시도를 얹으면 그 초기 실패까지 가려져 **100%가 됩니다.**

- **이상값 감지**: 문제 있는 엔드포인트를 **구조적으로 격리**
- **재시도**: 격리 전/후에 남는 **간헐적 실패를 흡수**

두 기능은 경쟁 관계가 아니라 보완 관계입니다.

```bash
# 엔드포인트 상태를 실시간 모니터링 (신규 터미널)
while true; do docker exec -it myk8s-control-plane istioctl proxy-config endpoint \
  deploy/simple-web.istioinaction \
  --cluster 'outbound|80||simple-backend.istioinaction.svc.cluster.local'; date; sleep 1; echo; done
```

```text
ENDPOINT            STATUS      OUTLIER CHECK     CLUSTER
10.10.0.27:8080     HEALTHY     OK                outbound|80||simple-backend...
10.10.0.29:8080     HEALTHY     OK                outbound|80||simple-backend...
10.10.0.30:8080     HEALTHY     FAILED            outbound|80||simple-backend...   # 퇴출
# baseEjectionTime(5s) 경과 후 자동으로 OK 로 복귀
```

```bash
# 이상값 감지 메트릭
kubectl exec -it deploy/simple-web -c istio-proxy -n istioinaction \
  -- curl -s localhost:15000/stats | grep simple-backend | grep outlier
```

```text
outlier_detection.ejections_active: 0                    # 현재 퇴출 중인 수
outlier_detection.ejections_consecutive_5xx: 3           # 연속 5xx로 감지된 횟수
outlier_detection.ejections_detected_consecutive_5xx: 3
outlier_detection.ejections_enforced_consecutive_5xx: 3  # 실제로 강제 적용된 횟수
outlier_detection.ejections_enforced_total: 3
outlier_detection.ejections_overflow: 0                  # maxEjectionPercent 상한에 걸린 수
outlier_detection.ejections_total: 3
```

```bash
# 재시도 메트릭 — 재시도를 함께 켰을 때
kubectl exec -it deploy/simple-web -c istio-proxy -n istioinaction \
  -- curl -s localhost:15000/stats | grep simple-backend | grep retry
```

```text
upstream_rq_retry: 4                      # 재시도 발생 횟수
upstream_rq_retry_backoff_exponential: 4
upstream_rq_retry_success: 4              # 재시도로 성공 전환된 수
upstream_rq_retry_limit_exceeded: 0
upstream_rq_retry_overflow: 0             # maxRetries 상한 초과
```

> **`detected` vs `enforced` 구분:** `detected`는 감지된 횟수, `enforced`는 실제 퇴출이 집행된 횟수입니다. `enforcingConsecutive5xx`(기본 100)가 100 미만이면 감지돼도 확률적으로만 집행되므로 두 값이 벌어집니다. 이상값 감지가 "설정은 했는데 동작 안 하는 것 같을 때" 먼저 볼 지표입니다.

| ----------------------- | -------------------------------- | ---------------------------------------------------------- |
| 로드밸런싱 (6.2)        | DestinationRule                  | LEAST_CONN이 가장 우수 (power of two choices). 차이는 꼬리 지연에서 드러남 |
| 지역 인식 로드밸런싱 (6.3) | Deployment 라벨 + DestinationRule | 이상값 감지 필수. 기본 활성화. 단일 클러스터 내 동작         |
| 타임아웃 (6.4.1)        | VirtualService                   | 외부는 길게, 내부는 짧게. 가장 제한적인 값이 먼저 발동       |
| 재시도 (6.4.2)          | VirtualService                   | 기본 2회 / 503만 대상. call depth 고려, thundering herd 주의 |
| 고급 재시도 (6.4.3)     | EnvoyFilter                      | 백오프·상태코드 재정의, 헤징. 비상용이며 버전마다 검증 필요   |
| 커넥션 풀 제어 (6.5.1)  | DestinationRule                  | Fail Fast. cx_overflow와 rq_pending_overflow를 함께 판독     |
| 이상값 감지 (6.5.2)     | DestinationRule                  | 비정상 엔드포인트 격리. 재시도와 조합 시 효과 극대화          |

### 트러블슈팅 치트시트

```bash
# 1. 설정이 Envoy에 반영됐는가
istioctl proxy-config cluster  deploy/<app>.<ns> --fqdn <svc-fqdn> -o json   # LB/서킷브레이커/이상값감지
istioctl proxy-config route    deploy/<app>.<ns> --name 80 -o json           # 타임아웃/재시도
istioctl proxy-config endpoint deploy/<app>.<ns> --cluster '<cluster-name>'  # 엔드포인트 상태

# 2. 통계 켜고 초기화
#    Deployment에 sidecar.istio.io/statsInclusionPrefixes 애너테이션 추가
kubectl exec -it deploy/<app> -c istio-proxy -n <ns> -- curl -X POST localhost:15000/reset_counters

# 3. 어떤 임계값에 걸렸는가
kubectl exec -it deploy/<app> -c istio-proxy -n <ns> -- curl -s localhost:15000/stats \
  | grep <target> | grep -E 'overflow|outlier|retry'

# 4. 액세스 로그 응답 플래그
#    UO  = 서킷 브레이킹(Upstream Overflow)
#    UF  = 업스트림 커넥션 실패
#    UT  = 업스트림 타임아웃
#    NR  = 라우트 설정 없음
```

### 마무리

- 모든 복원력 패턴은 애플리케이션 수정 없이 **네트워크 계층에서 투명하게** 처리됩니다.
- 각 기법에는 트레이드오프가 있습니다 — **재시도 → 요청 증폭**, **헤징 → 부하 증가**, **커넥션 풀 제한 → 정상 요청까지 차단**. 시스템 특성에 맞게 균형 있게 튜닝해야 합니다.
- 끊임없이 변화하는 대규모 시스템에서 예상치 못한 네트워크 오류에 **사람이 수동으로 개입해 대응하는 것은 불가능**합니다. 이스티오의 클라이언트 측 복원력 기능은 서비스가 간헐적 네트워크 문제와 토폴로지 변화로부터 **투명하게 스스로 복구**하도록 만듭니다.
