서비스 프록시는 애플리케이션과 함께 배치돼 프로세스 외부에서 실행되며, 애플리케이션은 다른 서비스와 통신할 때 서비스 프록시를 거칩니다.
이스티오에서 엔보이 프록시는 서비스 메시에 참여하는 모든 애플리케이션 인스턴스와 함께 배치돼 서비스 메시의 데이터 플레인을 형성합니다.

## 엔보이 프록시란 무엇인가?

- **개발 배경**: 분산 시스템을 구축할 때 발생하는 어려운 애플리케이션 네트워킹 문제를 해결하고자 리프트(Lyft)가 개발했습니다.
- **오픈소스 공개**: 2016년 9월 오픈소스로 공개됐으며, 1년 후 CNCF에 합류했습니다.
- **구현 언어와 목표**: C++로 작성됐으며, 그 목표는 성능을 높이는 것, 특히 높은 부하에서도 더 안정적이고 결정론적으로 동작하도록 만드는 것이었습니다.

> 애플리케이션에게 네트워크는 투명해야 한다. 네트워크 및 애플리케이션 문제가 발생할 때는 문제의 원인을 파악하기 쉬워야 한다.

엔보이는 프록시입니다. 프록시란 클라이언트와 서버 간 통신의 중간에 위치한 네트워크 아키텍처의 중개 구성 요소라고 앞서 언급한 바 있습니다. 프록시는 중간에 위치함으로써 보안, 프라이버시, 정책 같은 기능을 추가할 수 있습니다.

### 프록시의 기능 정의

1. **중개 지점 제공**: 프록시는 단일 식별자 혹은 IP 주소를 갖고 중간에 위치할 수 있으며, 클라이언트는 서비스 인스턴스들과 통신하는 데 이 프록시를 사용합니다.
2. **로드 밸런싱**: 프록시가 서비스 인스턴스 간의 로드 밸런싱을 처리합니다.
3. **헬스 체크와 우회**: 클러스터의 인스턴스 상태를 검사하고, 실패하거나 오동작하는 백엔드 인스턴스를 우회하도록 트래픽을 라우팅합니다.

> **참고**: 프록시는 클라이언트가 어느 백엔드가 과부하돼 있거나 장애가 발생했는지 파악할 필요가 없도록 보호할 수 있습니다.

### 애플리케이션 수준 프록시로서의 엔보이

- **애플리케이션 수준 프록시**: 서비스 디스커버리, 로드 밸런싱, 헬스 체크 같은 기능을 제공하기 위해 애플리케이션 요청 경로 중간에 삽입할 수 있지만, 엔보이는 그 이상을 할 수 있습니다.
- **7계층 프로토콜 이해**: 애플리케이션이 다른 서비스와 통신할 때 사용하는 7계층 프로토콜을 이해할 수 있습니다.
- **프로토콜 확장**: 기본 제공 프로토콜 외에도 다양한 프로토콜을 이해하도록 확장할 수 있습니다. MongoDB, DynamoDB, AMQP 같은 프로토콜 필터도 작성돼 있습니다.
- **관찰 가능성의 중요성**: 애플리케이션에 투명하게 보이고 신뢰성을 갖추는 것도 중요하지만, 분산 아키텍처에서 일어나고 있는 일을 빠르게 이해할 수 있는 능력도 그만큼 중요합니다.
- **배포 유연성**: 클러스터 에지 프록시로, 여러 서비스의 공유 프록시로, 심지어 이스티오처럼 서비스별 프록시로도 사용할 수 있습니다. 이스티오에서는 엔보이 프록시를 서비스 인스턴스당 하나씩 배포해 유연성, 성능, 제어 능력을 높입니다. 이런 패턴 중 하나(사이드카 서비스 프록시)를 사용한다고 해서 다른 패턴을 사용할 수 없는 것은 아닙니다.
- **메시의 진입점**: 엔보이는 서비스 메시의 진입점으로 사용돼 클러스터에 들어오는 트래픽을 완벽히 제어하고 관찰할 수 있습니다.

## 엔보이 핵심 기능

| 개념              | 설명                                            |
| ----------------- | ----------------------------------------------- |
| 리스너(Listener)  | 애플리케이션이 연결할 수 있도록 외부 세계로 포트를 노출한다 |
| 루트(Route)       | 리스너로 들어오는 트래픽을 처리하는 라우팅 규칙  |
| 클러스터(Cluster) | 엔보이가 트래픽을 라우팅할 수 있는 특정 업스트림 서비스 |

엔보이는 트래픽 방향성을 나타낼 때 다른 프록시와 비슷한 용어를 사용합니다. 이 트래픽은 엔보이의 클러스터 중 하나로 라우팅되며, 클러스터는 트래픽을 업스트림 시스템으로 보내는 역할을 합니다.

### 1. 서비스 디스커버리

- **디스커버리 API 위임**: 엔보이가 간단한 디스커버리 API에서 서비스 엔드포인트를 찾도록 설정하기만 하면, 애플리케이션은 서비스 엔드포인트를 찾는 방법을 몰라도 됩니다.
- **궁극적 일관성 전제**: 엔보이는 서비스 디스커버리 카탈로그의 업데이트가 궁극적으로 일관성을 가질 것이라는 가정에 기반해 설계됐습니다. 이는 분산 시스템에서는 통신할 모든 서비스의 정확한 상태와 사용 가능 여부를 실시간으로 파악할 수 없다는 것을 의미합니다.

### 2. 로드 밸런싱

- **고급 알고리즘 제공**: 엔보이는 애플리케이션이 활용할 수 있는 고급 로드 밸런싱 알고리즘을 여러 가지 구현하고 있습니다.
- **지역 인식 로드 밸런싱**: 엔보이의 로드 밸런싱 알고리즘에서 흥미로운 기능 중 하나입니다. 특정 기준을 충족하지 않으면 트래픽이 지역 경계를 넘지 않게 해 트래픽을 더 잘 분산시킬 수 있습니다.

지원하는 알고리즘은 다음과 같습니다.

- 랜덤
- 라운드 로빈
- 가중치를 적용한 최소 요청
- 일관된 해싱(sticky)

### 3. 트래픽 및 요청 라우팅

엔보이는 HTTP 1.1과 HTTP/2 같은 애플리케이션 프로토콜을 이해할 수 있으므로 정교한 라우팅 규칙을 사용해 트래픽을 특정 백엔드 클러스터로 보낼 수 있습니다.

- **기본 리버스 프록시 라우팅**: 가상 호스트 매핑과 콘텍스트 경로 라우팅을 처리할 수 있습니다.
- **고급 라우팅**: 헤더 및 우선순위 기반 라우팅, 라우팅 재시도 및 타임아웃, 오류 주입까지도 수행할 수 있습니다.

### 4. 트래픽 전환 및 섀도잉 기능

- **비율 기반 트래픽 분할/전환**: 이 기능을 활용해 CD(지속적 배포) 기술을 사용할 수 있습니다.
- **트래픽 섀도잉**: 라이브 운영 환경 트래픽에 영향을 주지 않고, 섀도잉한 트래픽을 서비스의 새 버전으로 라우팅할 수 있습니다.

### 5. 네트워크 복원력

> **참고**: 엔보이에게 특정 종류의 복원력 문제를 맡길 수는 있지만, 그 파라미터를 설정하고 잘 조정하는 것은 애플리케이션의 책임이라는 점을 유의해야 합니다.

- **타임아웃과 재시도**: 요청 타임아웃과 요청 수준 재시도를 자동으로 수행할 수 있습니다. 이런 재시도 동작은 네트워크 불안정이 간간이 요청에 영향을 줄 때 매우 유용합니다. 반면에 재시도 증폭은 연쇄 장애로 이어질 수 있어, 엔보이에서는 재시도 동작을 제한할 수 있습니다.
- **커넥션/요청 제한**: 업스트림 클러스터를 호출할 때 진행 중인 커넥션 혹은 요청의 개수를 제한하고, 그 임계값을 넘어서는 것은 빠르게 실패시키도록 설정할 수 있습니다.
- **이상값 감지(outlier detection)**: 서킷 브레이커처럼 동작해 오동작하는 엔드포인트를 로드 밸런싱 풀에서 제거할 수 있습니다.

### 6. HTTP/2와 gRPC

- **HTTP/2**: 단일 커넥션에서 여러 요청을 처리하고 서버 푸시, 스트리밍, 요청 백프레셔를 지원하도록 프로토콜을 개선한 버전입니다.
- **양방향 프록시**: 엔보이는 처음부터 HTTP/1.1과 HTTP/2 프록시로 개발돼 다운스트림과 업스트림 모두에게 각 프로토콜을 프록시할 수 있습니다.
- **gRPC**: HTTP/2 위에서 구글 프로토콜 버퍼를 사용하는 RPC 프로토콜로, 역시 엔보이가 기본적으로 지원합니다.

### 7. 메트릭 수집을 통한 관찰 가능성

엔보이의 목표 중 하나는 네트워크를 이해할 수 있게 만드는 것입니다. 수집하는 메트릭의 예는 다음과 같습니다.

- 총 커넥션 개수
- 총 활성 HTTP/1.1 커넥션 개수
- 총 HTTP/2 요청 개수
- 클러스터의 커넥션 서킷 브레이커가 임계값을 넘겨 발동한 횟수
- 총 요청 재시도 횟수
- 5xx 오류가 계속돼 퇴출된 횟수

### 8. 분산 트레이싱을 통한 관찰 가능성

- **트레이스 스팬 보고**: 엔보이는 트레이스 스팬을 오픈트레이싱 엔진에 보고해 호출 그래프 내 트래픽 흐름, 홉, 지연 시간을 시각화할 수 있습니다. 즉, 별도의 오픈트레이싱 라이브러리를 설치할 필요가 없습니다.
- **헤더 생성**: 서비스 간 호출을 연관시킬 목적으로 `x-request-id` 헤더를 생성하며, 트레이싱이 시작될 때 첫 `x-b3-*` 헤더를 만들 수도 있습니다. 다만 이 헤더들을 이후 홉으로 전파하는 것은 애플리케이션의 책임입니다.

### 9. 자동 TLS 종료 및 시작

- **TLS 종료**: 엔보이는 특정 서비스로 향하는 TLS 트래픽을 종료시킬 수 있습니다.
- **운영 부담 감소**: 엔터프라이즈 개발자와 운영자가 언어별 설정과 키스토어 또는 트러스트 스토어를 만지작거리지 않아도 됩니다. 요청 경로에 엔보이가 있으면 TLS, 심지어 상호 TLS까지도 자동으로 얻을 수 있습니다.

### 10. 속도 제한

복원력의 중요한 측면은 보호받는 리소스로의 접근을 차단하거나 제한할 수 있는 기능입니다. 다음과 같은 경우에 필요합니다.

- 호출 비용이 비쌉니다.
- 지연 시간이 길거나 예측하기 어렵습니다.
- 기아를 방지하기 위해 공정성 알고리즘이 필요합니다.

엔보이는 네트워크 수준과 HTTP 수준 모두에서 속도 제한 서비스와 통합할 수 있습니다.

### 11. 엔보이 확장

- **바이트 처리 엔진**: 엔보이의 핵심은 프로토콜 코덱을 구축할 수 있는 바이트 처리 엔진입니다. 엔보이에서는 추가 필터를 구축하는 것을 주요 사용 사례로 삼고 있습니다.
- **덜 침습적인 확장**: 루아 스크립트와 웹어셈블리를 지원하므로 덜 침습적인 방법으로도 엔보이 기능을 확장할 수 있습니다.

## 엔보이 설정

- **설정 형식**: 엔보이는 JSON/YAML 형식 설정 파일로 구성됩니다.
- **설정 범위**: 리스너, 루트, 클러스터뿐 아니라 Admin API 활성화 여부, 액세스 로그 저장 위치, 트레이싱 엔진 설정 등 서버별 설정도 지정합니다.
- **v3 설정 API**: 호출 시 스트리밍 기능을 사용해, 프록시가 올바른 설정으로 수렴하는 데 걸리는 시간을 줄일 수 있습니다. 프록시가 주기적으로 폴링하는 대신 서버가 업데이트를 엔보이에 푸시할 수 있어 API를 폴링할 필요가 없어집니다.

### 정적 설정

```yaml
static_resources:
  listeners:
    - name: httpbin-demo
      address:
        socket_address:
          address: 0.0.0.0
          port_value: 15001
      filter_chains:
        - filters:
            - name: envoy.http_connection_manager
              config:
                stat_prefix: egress_http
                route_config:
                  name: httpbin_local_route
                  virtual_hosts:
                    - name: httpbin_local_service
                      domains: ["*"]
                      routes:
                        - match: { prefix: "/" }
                          route:
                            auto_host_rewrite: true
                            cluster: httpbin_service
                http_filters:
                  - name: envoy.router
  clusters:
    - name: httpbin_service
      connect_timeout: 5s
      type: LOGICAL_DNS
      dns_lookup_family: V4_ONLY
      lb_policy: ROUND_ROBIN
      hosts:
        - socket_address:
            address: httpbin
            port_value: 8000
```

### 동적 설정

엔보이는 특정 API군을 사용해 다운타임이나 재시작 없이 실시간으로 업데이트할 수 있습니다.

| API     | 하는 일                                                     |
| ------- | ----------------------------------------------------------- |
| **LDS** | 엔보이가 자신이 어떤 리스너를 노출해야 하는지 쿼리할 수 있는 API |
| **RDS** | 리스너 설정의 일부로 사용할 루트를 지정                       |
| **CDS** | 엔보이가 클러스터 목록과 각 클러스터용 설정을 찾을 수 있는 API  |
| **EDS** | 클러스터 설정의 일부로, 특정 클러스터에 어떤 엔드포인트를 사용해야 하는지 지정 |
| **SDS** | 인증서를 배부하는 데 사용하는 API                             |
| **ADS** | 나머지 API에 대한 모든 변경 사항을 직렬화된 스트림으로 제공     |

이 API들을 통틀어 xDS 서비스라고 부릅니다.

> **참고**: 엔보이의 xDS API는 궁극적 일관성을 전제로 구축됐으며, 궁극적으로는 올바른 구성으로 수렴합니다. 예를 들어 엔보이가 트래픽을 클러스터 `foo`로 라우팅하는 새 루트가 RDS로 업데이트되었는데, 이 클러스터 `foo`를 포함한 CDS 업데이트는 아직 수행되지 않았을 수 있습니다. 이 경우 CDS가 업데이트될 때까지 라우팅 오류가 발생할 수 있습니다.

이스티오는 서비스 프록시용 부트스트랩을 다음과 같이 설정할 수 있습니다.

```yaml
bootstrap:
  dynamicResources:
    ldsConfig:
      ads: {}
    cdsConfig:
      ads: {}
    adsConfig:
      apiType: GRPC
      grpcServices:
        - envoyGrpc:
            clusterName: xds-grpc
      refreshDelay: 1.00s
  staticResources:
    clusters:
      - name: xds-grpc
        type: STRICT_DNS
        connectTimeout: 10.000s
        hosts:
          - socketAddress:
              address: istio-pilot.istio-system
              portValue: 15010
        circuitBreakers:
          thresholds:
            - maxConnections: 1000000
              maxPendingRequests: 1000000
              maxRequests: 1000000
            - priority: HIGH
              maxConnections: 1000000
              maxPendingRequests: 1000000
              maxRequests: 1000000
        http2ProtocolOptions: {}
```

>

> - 아래 `typed_config` 추가
> - httpbin 엔드포인트 포트를 8000 → 8080으로 변경

```yaml
typed_config:
  "@type": type.googleapis.com/envoy.extensions.filters.http.router.v3.Router

    "Host": ["httpbin"],

  }
}
```

새로운 헤더들이 추가됐습니다.

- **`X-Request-Id`**: 클러스터 내 다양한 요청 사이의 관계를 파악하고, 요청이 여러 서비스를 거치는 과정을 추적하는 데 사용합니다.
- **`X-Envoy-Expected-Rq-Timeout-Ms`**: 업스트림 서비스에 대한 힌트로, 요청이 15,000ms 후에 타임아웃될 것으로 기대한다는 의미입니다.

## 엔보이는 어떻게 이스티오에 맞는가?

- **컨트롤 플레인의 필요성**: 엔보이는 프록시로서 서비스 메시에 매우 적합합니다. 다만 엔보이를 최대한 활용하려면 보조 인프라나 구성 요소가 필요합니다. 이스티오가 제공하는 사용자 설정, 보안 정책, 런타임 설정을 지원하는 구성 요소들이 컨트롤 플레인을 형성합니다.
- **istiod의 역할**: istiod는 이 API를 구현하기도 하지만, 엔보이에게 서비스 저장소의 구현을 추상화해주기도 합니다. 이스티오를 쿠버네티스에 배포하면 서비스 디스커버리에 쿠버네티스의 서비스 저장소를 사용합니다.
- **텔레메트리 수집**: 엔보이는 많은 메트릭과 텔레메트리를 내보낼 수 있습니다. 이 텔레메트리는 어딘가로 보내져야 하며, 엔보이는 이를 보내도록 설정돼야 합니다. 프로메테우스 같은 시계열 시스템과 연동되도록 데이터 플레인을 설정합니다.
- **TLS 종료와 시작**: 엔보이는 메시 내의 서비스로 향하는 TLS 트래픽을 종료하고 시작할 수 있습니다.
