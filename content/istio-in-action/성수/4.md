서비스가 서로 통신하기 전에 무언가 상호작용을 시작해야 합니다. 이를테면 물건을 구매하는 최종 사용자, API를 쿼리하는 클라이언트 등이 있습니다. 이런 시작의 공통점은 클러스터 외부에서 시작한다는 것입니다.
그렇다면 클러스터의 외부 트래픽을 어떻게 클러스터 내부로 유입시킬 수 있을까요?

## 트래픽 인그레스 개념

![가상 IP와 가상 호스팅](images/notes/istio-in-action/4-1.png)

- **인그레스(Ingress)란**: 네트워크 외부에서 발원해 네트워크 내부 엔드포인트를 향하는 트래픽을 말합니다.
- **인그레스 포인트의 역할**: 트래픽은 먼저 네트워크 내부로 향하는 트래픽에 문지기 역할을 하는 인그레스 포인트로 라우팅됩니다. 인그레스 포인트는 어떤 트래픽을 로컬 네트워크로 허용할지에 대한 규칙과 정책을 집행합니다.

### 가상 IP: 서비스 접근 단순화

외부 시스템을 가져오는 엔드포인트를 `api.istioinaction.io/v1/products`에 노출하고 싶은 서비스가 있다고 해봅시다.

- **DNS 해석**: 클라이언트가 그 엔드포인트를 쿼리하려고 할 때, 클라이언트의 네트워킹 스택은 `api.istioinaction.io` 도메인 이름을 IP 주소로 해석하려고 합니다. 이는 DNS 서버로 수행합니다.
- **첫 단계는 DNS 매핑**: 네트워킹 스택은 DNS 서버에 특정 호스트네임의 IP 주소를 물어봅니다. 따라서 네트워크로 들여오는 작업의 첫 단계는 서비스 IP를 DNS 호스트네임에 대응시키는 것입니다. 공개 주소의 경우 Amazon Route 53이나 구글 클라우드 DNS를 사용할 수 있습니다.
- **DNS만으로는 부족한 이유**: 동작하는 엔드포인트의 IP 주소로 DNS 매핑이 변경될 때까지 클라이언트는 많은 오류를 보게 됩니다. 서비스가 다운될 때마다 그렇게 하는 것은 느리고, 오류가 발생하기 쉬우며, 가용성이 낮습니다.
- **가상 IP의 이점**: 가상 IP 주소가 실제 서비스 인스턴스로 트래픽을 전달하므로 가용성과 유연성을 높일 수 있습니다.
- **리버스 프록시와의 관계**: 가상 IP는 리버스 프록시라는 인그레스 포인트 유형에 바인딩됩니다. 리버스 프록시는 요청을 백엔드 서비스들에 분산시키는 역할을 하는 중간 구성 요소로, 특정 서비스에 해당하지 않습니다. 로드 밸런싱 같은 기능도 있어 특정 백엔드 하나가 요청 때문에 과부하되지 않도록 할 수 있습니다.

### 가상 호스팅: 단일 접근 지점의 여러 서비스

- **클라이언트가 보는 것**: 서비스는 자체 IP를 지닌 서비스 인스턴스 여럿으로 구성될 수 있지만, 클라이언트는 오직 가상 IP만을 사용합니다.
- **가상 IP 하나에 호스트네임 여럿**: 두 호스트네임에 대한 요청 모두 동일한 가상 IP로 흐르게 되고, 그에 따라 동일한 인그레스 리버스 프록시가 그 요청을 라우팅하게 됩니다. 리버스 프록시가 충분히 똑똑하다면, `Host` HTTP 헤더를 사용해 어느 요청이 어느 서비스 그룹으로 가야 하는지 기술할 수 있습니다.
- **가상 호스팅의 정의**: 서로 다른 서비스 여러 개를 진입점 하나로 호스팅하는 것을 가상 호스팅이라고 합니다.
- **분기 기준**: HTTP/1.1에서는 `Host` 헤더를, HTTP/2에서는 `:authority` 헤더를 사용할 수 있습니다. 또한 TCP 커넥션에서는 TLS의 SNI에 의존할 수 있습니다.

> **참고**: 이스티오의 에지 인그레스 기능도 서비스 트래픽을 클러스터 안으로 라우팅하는 데 가상 IP 라우팅과 가상 호스팅을 사용합니다.

## 이스티오 인그레스 게이트웨이

![Gateway와 VirtualService](images/notes/istio-in-action/4-2.png)

- **인그레스 게이트웨이란**: 이스티오에는 네트워크 인그레스 포인트 역할을 하는 인그레스 게이트웨이라는 개념이 있는데, 이것은 클러스터 외부에서 시작한 트래픽이 클러스터에 접근하는 것을 방어하고 제어합니다.
- **리버스 프록시 기능**: 인그레스 게이트웨이는 클러스터로 트래픽을 허용하면서 리버스 프록시 기능도 수행합니다.
- **구현체**: 이스티오는 인그레스 게이트웨이로 단일 엔보이 프록시를 사용합니다.

이스티오 서비스 프록시가 이스티오 인그레스 게이트웨이에서 실제 작동 중인지 확인할 수 있습니다.

```bash
kubectl -n istio-system exec \
  deploy/istio-ingressgateway -- ps
```

실행 결과, 이스티오 서비스 프록시에서 동작 중인 프로세스로 pilot-agent와 envoy가 보여야 합니다.

인그레스 게이트웨이가 트래픽을 클러스터 내부로 허용하도록 설정하려면, 우선 이스티오의 리소스인 Gateway와 VirtualService를 이해해야 합니다. 이 두 리소스는 이스티오에서 트래픽의 흐름을 조절하는 데 핵심적인 역할을 합니다.

### Gateway 리소스 설정하기

이스티오에서 인그레스 게이트웨이를 설정하려면, Gateway 리소스를 사용해 개방하고 싶은 포트와 그 포트에서 허용할 가상 호스트를 지정합니다.

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: coolstore-gateway
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "webapp.istioinaction.io"
```

이 Gateway 리소스는 80 포트를 리스닝하고 HTTP 트래픽을 기대하도록 엔보이를 설정합니다.

```bash
kubectl -n istioinaction apply -f ch4/coolstore-gw.yaml

istioctl -n istio-system proxy-config \
  listener deploy/istio-ingressgateway
```

HTTP 포트를 올바르게 노출합니다. VirtualService의 루트를 살펴보면, 아직 게이트웨이에 아무것도 없음을 알 수 있습니다.

```bash
istioctl proxy-config route deploy/istio-ingressgateway \
  -o json --name http.8080 -n istio-system
```

리스너는 모든 것을 HTTP 404로 라우팅하는 기본 블랙홀 루트로 바인딩돼 있습니다. 다음 절에서는 트래픽을 80 포트에서 서비스 메시 내의 서비스로 라우팅하도록 가상 호스트를 설정할 것입니다.

**게이트웨이 파드의 노출 조건**

- **외부 노출 필요**: 게이트웨이를 실행하는 파드는 기본 istio-ingressgateway든 커스텀 게이트웨이든, 클러스터 외부에 노출된 포트나 IP에서 리스닝할 수 있어야 합니다.
- **로컬 환경**: 예제에서 사용 중인 로컬 도커 데스크톱에서는 인그레스 게이트웨이가 80 포트에서 리스닝 중입니다.
- **클라우드 환경**: GKE 같은 클라우드 서비스에 배포했다면, 외부에서 라우팅할 수 있는 IP 주소를 갖고 있는 LoadBalancer 타입 서비스를 사용해야 합니다.
- **권한**: istio-ingressgateway는 권한 있는 접근이 필요하지 않습니다. 시스템 포트를 리스닝하지 않기 때문입니다. 기본적으로 8080 포트에서 리스닝하며, 실제 포트는 서비스든 로드 밸런서든 게이트웨이를 노출하는 데 사용하는 포트입니다.

### VirtualService로 게이트웨이 라우팅

- **역할**: 트래픽이 게이트웨이로 들어오면 그 트래픽을 서비스 메시 내 특정 서비스로 가져올 방법이 필요한데, 이때 사용하는 것이 VirtualService 리소스입니다.
- **정의하는 것**: 클라이언트가 특정 서비스와 통신하는 방법을 정의하며, 구체적으로 FQDN, 사용 가능한 서비스 리전, 기타 라우팅 속성이 있습니다.

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: webapp-vs-from-gw
spec:
  hosts:
    - "webapp.istioinaction.io"
  gateways:
    - coolstore-gateway
  http:
    - route:
        - destination:
            host: webapp
            port:
              number: 8080
```

게이트웨이로 들어오는 트래픽에 수행할 작업을 이 VirtualService 리소스로 정의합니다. coolstore-gateway 게이트웨이 정의를 통해 들어온 트래픽에만 적용됩니다. 예를 들어 클라이언트가 이스티오 게이트웨이가 리스닝하고 있는 IP로 해석되는 `http://webapp.istioinaction.io`로 쿼리하는 경우 이 규칙에 부합합니다. 클라이언트는 HTTP 요청의 `Host` 헤더를 `webapp.istioinaction.io`로 명시적으로 설정할 수도 있습니다.

```bash
❯ kubectl apply -n istioinaction -f ch4/coolstore-vs.yaml

❯ istioctl proxy-config route deploy/istio-ingressgateway \
  -o json --name http.8080 -n istio-system
```

VirtualService를 정의하면 이스티오 게이트웨이에 엔보이 루트가 어떻게 생성되는지 확인할 수 있습니다. 도메인이 `webapp.istioinaction.io`와 일치하는 트래픽을 서비스 메시 내 webapp으로 라우팅하는 엔보이 루트입니다.

서비스를 배포하는 방법은 다음과 같습니다.

```bash
❯ kubectl config set-context $(kubectl config current-context) \
  --namespace=istioinaction

❯ kubectl apply -f services/catalog/kubernetes/catalog.yaml
❯ kubectl apply -f services/webapp/kubernetes/webapi.yaml

# 파드 확인
❯ kubectl get pod

❯ kubectl get gateway

❯ kubectl get virtualservice
```

이제 게이트웨이를 호출해 트래픽이 클러스터 내부로 허용되는지 확인합니다. 이스티오 인그레스 게이트웨이를 로컬호스트 80 포트에서 사용할 수 있는 도커 데스크톱 방식을 사용하고 있음을 기억하세요.

공개 로드 밸런서에 노출된 인그레스 게이트웨이의 올바른 호스트를 얻는 방법 중 한 가지를 다음과 같이 소개합니다.

```bash
URL=$(kubectl -n istio-system get svc istio-ingressgateway \
  -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
```

```bash
❯ curl -v http://localhost/api/catalog
```

이스티오 게이트웨이도 VirtualService에서 선언한 라우팅 규칙도 `localhost:80`이라는 호스트는 알지 못하며, 아는 것은 가상 호스트 `webapp.istioinaction.io`입니다. 명령줄에 `Host` 헤더를 재정의하면 호출이 동작합니다.

```bash
curl http://localhost/api/catalog -H "Host: webapp.istioinaction.io"
```

> **정리**: Gateway 리소스는 서비스 메시 클러스터의 에지에서 리스닝하고자 하는 포트, 프로토콜, 가상 호스트를 정의합니다.

### 이스티오 인그레스 게이트웨이 vs 쿠버네티스 인그레스

이스티오는 쿠버네티스 인그레스 v1 리소스를 지원하지만, 쿠버네티스 인그레스 v1 사양에는 상당한 한계가 있습니다.

- **첫 번째, HTTP에만 맞춰진 단순함**: 쿠버네티스 인그레스 구현체에는 nginx, Traefik 등이 있지만, 어느 것이든 HTTP 트래픽에 맞춰져 있습니다. 실제 인그레스 사양은 80 포트와 443 포트만 인그레스 포인트로 간주합니다. 이는 클러스터 운영자가 서비스 메시로 허용할 수 있는 트래픽 유형을 심각하게 제한합니다.
- **두 번째, 사양의 부족**: 복잡한 트래픽 라우팅 규칙, 트래픽 분할, 트래픽 섀도잉 같은 것들을 지정하는 일반적인 방법이 없습니다. 이런 영역에서 사양이 부족한 까닭에 각 벤더는 인그레스 구현체에서 설정의 최적 구현법을 재창조해야 했습니다.
- **세 번째, 벤더별 애노테이션 난립**: 벤더 대부분이 설정을 디플로이먼트의 맞춤형 애노테이션으로 노출하는 방식을 택했습니다. 이 애노테이션은 벤더마다 상이하고 호환되지 않으므로, 이스티오가 이런 추세를 따랐다면 에지 게이트웨이로서 엔보이의 모든 기능을 반영하기 위해 애노테이션이 더 많이 필요했을 것입니다.
- **이스티오의 선택**: 결국 이스티오 인그레스 패턴을 백지 상태에서 구축하기로 결정했고, 4계층과 5계층 속성을 7계층 라우팅 문제로부터 명확하게 분리해냈습니다. 이스티오 Gateway는 L4, L5 문제를 처리하고 VirtualService는 L7 문제를 처리합니다. 많은 메시 및 게이트웨이 공급자들도 인그레스용으로 자체 API를 구축했고, 쿠버네티스 커뮤니티는 인그레스 API 개정을 준비하고 있습니다.

> **쿠버네티스 Gateway API**: 인그레스 v1 API를 대체하고자 Gateway API를 열심히 준비하고 있으며, 이스티오의 구현체와 리소스는 Gateway API보다 먼저 등장했고 여러 면에서 Gateway API에 영감을 줬습니다.

### 이스티오 인그레스 게이트웨이 vs API 게이트웨이

- **API 게이트웨이의 역할**: 조직이 네트워크나 아키텍처 경계의 서비스를 사용하는 클라이언트에게 서비스 구현의 세부 사항을 추상화할 수 있게 해줍니다.
- **기대되는 기능**: 클라이언트는 잘 문서화된 API들을 호출하게 되고, 이 API들은 앞뒤 호환성을 지니면서 발전하며, 셀프 서비스와 기타 사용 메커니즘을 제공할 수 있습니다. 또한 여러 보안 기술을 사용해 클라이언트를 식별할 수 있어야 하고, 메시지를 변형할 수 있어야 하며, 비즈니스 수준으로 정교하게 속도를 제한할 수 있어야 하고, 자체 가입 기능이나 개발자 포털을 제공할 수 있어야 합니다.

## 게이트웨이 트래픽 보안

- **왜 필요한가**: 클러스터 외부의 서비스를 클러스터 내부에서 실행 중인 서비스에 연결할 때, 인그레스 게이트웨이의 기본 기능 중 하나는 트래픽을 보호해 시스템의 신뢰 구축을 돕는 것입니다.
- **서버 진위 확인**: 트래픽 보호는 클라이언트가 통신하려는 서버의 진위를 가리는 것에서 시작할 수 있습니다. 자신이 그 서비스라고 주장하는 서버가 정말 통신하려는 서비스가 맞는지 검증하는 것입니다.
- **암호화**: 누군가 도청하는 일을 막고 싶으므로 트래픽을 암호화해야 합니다.
- **이스티오가 제공하는 것**: 들어오는 TLS/SSL 트래픽을 종료하고, 백엔드 서비스로 전달하고, TLS가 아닌 트래픽을 적절한 TLS 포트로 리다이렉트하고, 상호 TLS를 구현할 수 있습니다.

![게이트웨이 TLS 모드](images/notes/istio-in-action/4-3.png)

### TLS를 사용한 HTTP 트래픽

- **목적**: 중간자(Man-In-The-Middle) 공격을 방지하고 서비스 메시로 들어오는 모든 트래픽을 암호화하기 위해 이스티오 게이트웨이에 TLS를 설정할 수 있습니다. 들어오는 트래픽 모두가 HTTPS로 제공되도록 하는 것입니다.
- **중간자 공격이란**: 클라이언트가 어떤 서비스에 연결하려고 하지만, 그 서비스가 아닌 사칭 서비스에 연결할 때를 말합니다. 사칭 서비스는 통신에 접근할 수 있게 되며, 여기에는 민감정보도 포함됩니다. TLS는 이 공격을 완화하는 데 도움을 줍니다.

**인증서가 동작하는 방식**

- **인증서란**: 서버가 제시하는 인증서는 서버가 클라이언트에게 자신의 정체를 알리는 방법입니다. 기본적으로 서버의 공개 키이며, 신뢰할 수 있는 기관인 인증 기관(CA)에서 서명한 것입니다.
- **클라이언트 측 준비**: 먼저 클라이언트에 CA 발급자의 인증서가 설치돼 있어야 합니다. 이는 이 발급자가 신뢰할 수 있는 CA이며 발급한 인증서 역시 신뢰할 수 있다는 의미입니다.
- **검증과 암호화**: 클라이언트는 인증서가 신뢰할 수 있는 CA가 서명한 것인지 검증할 수 있습니다. 그런 다음 인증서 내 공개 키를 사용해 서버로 보내는 트래픽을 암호화하고, 서버는 비밀키로 트래픽을 복호화합니다.

> TLS 핸드셰이크에는 더 정교한 프로토콜이 포함되는데, 최초 통신에는 공개/비공개 키를 조합하고 TLS 세션에서 트래픽 암호화/복호화에 사용할 세션 키(대칭)를 생성합니다.

istio-ingressgateway가 인증서와 키를 사용하도록 설정하려면 먼저 인증서/키를 쿠버네티스 시크릿으로 만들어야 합니다.

```bash
kubectl create -n istio-system secret tls webapp-credential \
  --key ch4/certs/3_application/private/webapp.istioinaction.io.key.pem \
  --cert ch4/certs/3_application/certs/webapp.istioinaction.io.cert.pem
```

> **참고**: istio-system 네임스페이스에 시크릿을 만듭니다. 기본 게이트웨이가 istio-system 네임스페이스에서 실행되고 있으므로 시크릿도 여기에 넣어야 합니다. 인그레스 게이트웨이를 다른 네임스페이스에서 실행해도 되지만, 그때는 시크릿도 그 네임스페이스에 있어야 합니다.

```yaml
- port:
    number: 443
    name: https
    protocol: HTTPS
  tls:
    mode: SIMPLE
    credentialName: webapp-credential
  hosts:
    - "webapp.istioinaction.io"
```

Gateway 리소스에서 인그레스 게이트웨이의 443 포트를 열고 이를 HTTPS로 지정합니다. `tls` 부분을 추가해 인증서와 키의 위치를 지정합니다.

```bash
kubectl apply -f ch4/coolstore-gw-tls.yaml
```

> 클라우드를 사용하고 있다면, 로드 밸런서 퍼블릭 IP로 호스트 IP를 사용할 수 있습니다 — `kubectl get svc -n istio-system`

```bash
curl -v -H "Host: webapp.istioinaction.io" https://localhost/api/catalog
```

이는 서버에서 제공하는 인증서는 기본 CA 인증서 체인을 사용해 확인할 수 없다는 의미입니다. curl 클라이언트에 적절한 CA 인증서 체인을 전달해봅시다.

```bash
curl -v -H "Host: webapp.istioinaction.io" https://localhost/api/catalog \
  --cacert ch4/certs/2_intermediate/certs/ca-chain.cert.pem
```

아직도 검증을 하지 못합니다. 도커 데스크톱 호스트 때문입니다. curl 파라미터 `--resolve`를 사용해 실제로 localhost를 호출하면서 `webapp.istioinaction.io`를 호출하는 것처럼 시뮬레이션할 수 있습니다.

```bash
curl -H "Host: webapp.istioinaction.io" \
  https://webapp.istioinaction.io:443/api/catalog \
  --cacert ch4/certs/2_intermediate/certs/ca-chain.cert.pem \
  --resolve webapp.istioinaction.io:443:127.0.0.1
```

> **참고**: `--resolve` 플래그를 사용해 인증서 내 호스트네임과 포트를 실제 사용 중인 IP로 대응시키고 있음을 유념하세요. 도커 데스크톱에서는 인그레스가 로컬호스트에서 실행됩니다. 클라우드에서 제공하는 로드 밸런서를 사용하고 있다면 127.0.0.1을 적절한 IP로 바꾸면 됩니다.

> 최신 curl 버전은 적절한 SSL 라이브러리가 포함돼 잘 동작해야 합니다. 하지만 사용자는 `curl --version | grep -i SSL`을 입력했을 때 출력되는 SSL 라이브러리(OpenSSL, LibreSSL 등) 정보를 확인할 필요가 있습니다.

이스티오 인그레스 게이트웨이는 TLS 커넥션을 종료하고, 트래픽을 서비스 메시 내에서 실행 중인 뒷단의 webapp 서비스로 보냅니다.

### HTTPS로 HTTP 리다이렉트

모든 트래픽이 항상 TLS를 쓰도록 강제하려면 어떻게 해야 할까요?

```yaml
tls:
  httpsRedirect: true
```

```bash
kubectl apply -f ch4/coolstore-gw-tls-redirect.yaml
```

이제 HTTP 포트로 인그레스 게이트웨이를 호출하면 이렇게 보여야 합니다.

```bash
curl -v http://localhost/api/catalog \
  -H "Host: webapp.istioinaction.io"
```

이제 인그레스 게이트웨이로 들어오는 모든 트래픽은 항상 암호화될 것이라고 기대할 수 있습니다.

### 상호 TLS를 사용한 HTTP 트래픽

- **목표**: 클라이언트가 자신의 공개 인증서를 보내게 하고 서버가 그 인증서를 신뢰하는지 검증하게 하고 싶습니다.
- **준비물**: 기본 istio-ingressgateway가 상호 TLS 커넥션에 참여하도록 구성하려면, 클라이언트의 인증서를 검증하는 데 사용할 수 있도록 CA 인증서 집합을 제공해야 합니다.

```bash
kubectl create -n istio-system secret \
  generic webapp-credential-mtls \
  --from-file=tls.key=ch4/certs/3_application/private/webapp.istioinaction.io.key.pem \
  --from-file=tls.crt=ch4/certs/3_application/certs/webapp.istioinaction.io.cert.pem \
  --from-file=ca.crt=ch4/certs/2_intermediate/certs/ca-chain.cert.pem
```

Gateway 리소스를 업데이트하고, 예상 프로토콜을 상호 TLS로 구성합니다.

```yaml
tls:
  mode: MUTUAL
  credentialName: webapp-credential-mtls
```

```bash
kubectl apply -f ch4/coolstore-gw-mtls.yaml
```

```bash
curl -H "Host: webapp.istioinaction.io" \
  https://webapp.istioinaction.io:443/api/catalog \
  --cacert ch4/certs/2_intermediate/certs/ca-chain.cert.pem \
  --resolve webapp.istioinaction.io:443:127.0.0.1
```

> **이스티오 게이트웨이 SDS**: istio-agent 프로세스에 내장된 SDS에서 인증서를 가져옵니다. SDS는 업데이트를 자동으로 전파하는 동적 API입니다.
>
> ```bash
> istioctl pc secret -n istio-system deploy/istio-ingressgateway
>
> # 새 인증서 구성이 적용되지 않는 경우에는 istio-ingressgateway 파드를 내쫓아본다
> kubectl delete po -n istio-system -l app=istio-ingressgateway
> ```

SSL 핸드셰이크가 성공하지 못했기 때문에 이 호출은 거부됩니다. curl 명령어에 CA 인증서만 전달했는데, 클라이언트의 인증서와 비밀키도 전달해야 합니다.

```bash
curl -H "Host: webapp.istioinaction.io" \
  https://webapp.istioinaction.io:443/api/catalog \
  --cacert ch4/certs/2_intermediate/certs/ca-chain.cert.pem \
  --resolve webapp.istioinaction.io:443:127.0.0.1 \
  --cert ch4/certs/4_client/certs/webapp.istioinaction.io.cert.pem \
  --key ch4/certs/4_client/private/webapp.istioinaction.io.key.pem
```

이제 적절한 HTTP/1.1 200 응답과 상품 목록 JSON 페이로드가 보여야 합니다. 클라이언트는 상호 TLS를 이루고자 서버의 인증서를 검증하고 자신의 인증서를 보내고 있습니다.

### 여러 가상 호스트를 TLS로 서빙하기

이스티오의 인그레스 게이트웨이는 동일한 HTTPS 포트에서 자체 인증서와 비밀키가 있는 여러 가상 호스트를 서빙할 수 있습니다. 자체 인증서와 키 쌍이 있는 `webapp.istioinaction.io`와 `catalog.istioinaction.io` 서비스를 둘 다 추가할 수 있습니다.

```yaml
servers:
  - port:
      number: 443
      name: https-webapp
      protocol: HTTPS
    tls:
      mode: SIMPLE
      # ...

  - port:
      number: 443
      name: https-catalog
      protocol: HTTPS
```

인증서와 키 쌍이 각각 다르므로 시크릿을 따로 만듭니다.

```bash
kubectl create -n istio-system secret tls catalog-credential \
  --key ch4/certs2/3_application/private/catalog.istioinaction.io.key.pem \
  --cert ch4/certs2/3_application/certs/catalog.istioinaction.io.cert.pem
```

```bash
kubectl apply -f ch4/coolstore-gw-multi-tls.yaml
```

istio-ingressgateway를 업데이트했으니, `webapp.istioinaction.io`를 호출하면 단순 TLS 때처럼 작동합니다.

```bash
curl -H "Host: webapp.istioinaction.io" \
  https://webapp.istioinaction.io:443/api/catalog \
  --cacert ch4/certs/2_intermediate/certs/ca-chain.cert.pem \
  --resolve webapp.istioinaction.io:443:127.0.0.1
```

이스티오 게이트웨이로 catalog 서비스를 호출할 때는 catalog용 인증서를 씁니다.

```bash
curl -H "Host: catalog.istioinaction.io" \
  https://catalog.istioinaction.io:443/items \
  --cacert ch4/certs/2_intermediate/certs/ca-chain.cert.pem \
  --resolve catalog.istioinaction.io:443:127.0.0.1
```

> **동작 원리**: 이것이 가능한 이유는 SNI라는 TLS 확장에 있습니다. HTTPS 커넥션이 만들어지면 클라이언트는 먼저 TLS 핸드셰이크의 ClientHello 부분에서 어느 서비스에 접근해야 하는지부터 전달합니다. 이스티오의 게이트웨이가 TLS의 SNI를 구현하는 덕분에 올바른 인증서를 제시할 수 있고 올바른 서비스로 라우팅할 수 있는 것입니다.

## TCP 트래픽

- **처리 범위**: 이스티오는 TCP로 접근하는 모든 트래픽을 처리할 수 있습니다.
- **한계**: 이스티오가 트래픽을 단순 TCP로 다루면 재시도, 요청 수준 서킷 브레이킹, 복잡한 라우팅 등과 같은 유용한 기능을 사용할 수 없습니다. 단순히 이스티오가 어떤 프로토콜을 사용하는지 분간할 수 없기 때문입니다.

### 이스티오 게이트웨이에서 TCP 포트 노출하기

![TCP 게이트웨이](images/notes/istio-in-action/4-4.png)

```bash
kubectl config set-context $(kubectl config current-context) \
  --namespace=istioinaction

kubectl apply -f ch4/echo.yaml
```

기본적으로 31400 포트를 노출합니다.

```yaml
servers:
  - port:
      number: 31400
      name: tcp-echo
      protocol: TCP
    hosts:
      - "*"
```

리스닝 포트를 찾습니다.

```bash
kubectl get svc -n istio-system istio-ingressgateway \
  -o jsonpath='{.spec.ports[?(@.name=="tcp")]}'
```

게이트웨이를 구성합니다.

```bash
kubectl apply -f ch4/gateway-tcp.yaml
```

인그레스 게이트웨이에 포트를 노출했으니 트래픽을 에코 서비스로 라우팅해야 합니다.

```yaml
gateways:
  - echo-tcp-gateway
tcp:
  - match:
      - port: 31400
    route:
      - destination:
          host: tcp-echo-service
          port:
            number: 2701
```

VirtualService를 만듭니다.

```bash
kubectl apply -f ch4/echo-vs.yaml
```

이제 인그레스 게이트웨이에 포트를 노출하고 라우팅을 설정했으므로, telnet 명령어로 커넥션을 맺을 수 있습니다.

```bash
telnet localhost 31400
```

## SNI 통과를 사용한 트래픽 라우팅

- **다루는 내용**: 이스티오 인그레스 게이트웨이에서 트래픽을 종료하지 않고 SNI 호스트네임에 따라 TCP 트래픽을 라우팅하는 방법입니다.
- **게이트웨이의 역할**: SNI 헤더를 살펴보고 트래픽을 특정 백엔드로 라우팅하는 것뿐입니다. TLS 커넥션 종료는 그 후 백엔드에서 처리합니다. 커넥션은 게이트웨이를 통과하고 처리는 게이트웨이가 아닌 실제 서비스가 담당하게 됩니다.

![SNI 통과](images/notes/istio-in-action/4-5.png)

라우팅 메커니즘에 PASSTHROUGH를 사용하도록 설정된 Gateway 정의를 살펴봅시다.

```yaml
servers:
  - port:
      number: 31400
      name: tcp-sni
      protocol: TLS
    hosts:
      - "simple-sni-1.istioinaction.io"
    tls:
      mode: PASSTHROUGH
```

TLS를 종료하는 예제 애플리케이션을 배포하는 것부터 시작합니다.

```bash
kubectl apply -f ch4/sni/simple-tls-service-1.yaml
```

다음으로 31400 포트를 여는 Gateway 리소스를 배포합니다.

```bash
kubectl delete gateway echo-tcp-gateway -n istioinaction
```

이제 통과 게이트웨이를 적용합니다.

```bash
kubectl apply -f ch4/sni/passthrough-sni-gateway.yaml
```

게이트웨이에서 서비스로 트래픽을 흘리도록 VirtualService 리소스로 라우팅 규칙도 지정해야 합니다.

```yaml
tls:
  - match:
      - port: 31400
        sniHosts:
          - simple-sni-1.istioinaction.io
    route:
      - destination:
          host: simple-tls-service-1
          port:
            number: 80
```

VirtualService를 만듭니다.

```bash
kubectl apply -f ch4/sni/passthrough-sni-vs-1.yaml
```

인그레스 게이트웨이의 31400 포트를 호출해봅시다.

```bash
curl -H "Host: simple-sni-1.istioinaction.io" \
  https://simple-sni-1.istioinaction.io:31400 \
  --cacert ch4/sni/simple-sni-1/2_intermediate/certs/ca-chain.cert.pem \
  --resolve simple-sni-1.istioinaction.io:31400:127.0.0.1
```

curl의 호출은 이스티오 게이트웨이로 갔다가 종료 없이 예제 서비스 simple-tls-service-1로 도달합니다. 라우팅을 더 명확하게 하기 위해 인증서가 다르고 SNI 호스트에 기반해 라우팅을 하는 두 번째 서비스를 배포해봅시다.

```bash
kubectl apply -f ch4/sni/simple-tls-service-2.yaml
```

```bash
kubectl apply -f ch4/sni/passthrough-sni-gateway-both.yaml
kubectl apply -f ch4/sni/passthrough-sni-vs-2.yaml
```

다음으로 동일한 인그레스 게이트웨이 포트를 다른 호스트네임으로 다시 호출해보고, 요청이 어떻게 올바른 서비스로 라우팅되는지 살펴봅시다.

```bash
curl -H "Host: simple-sni-2.istioinaction.io" \
  https://simple-sni-2.istioinaction.io:31400/ \
  --cacert ch4/sni/simple-sni-2/2_intermediate/certs/ca-chain.cert.pem \
  --resolve simple-sni-2.istioinaction.io:31400:127.0.0.1
```

## 운영 팁

### 게이트웨이 책임 나누기

- **게이트웨이의 정체**: 이스티오 게이트웨이는 단순히 사이드카로 배포되지 않는 엔보이 프록시에 불과합니다. 즉, 게이트웨이를 인그레스, 이그레스, 공유 게이트웨이 기능, 멀티 클러스터 프록시 등 다양한 용도로 사용할 수 있습니다.

```bash
istioctl install -y -n istioinaction -f ch4/my-user-gateway.yaml
```

이렇게 하면 istioinaction 네임스페이스 전용 새 게이트웨이가 설치됩니다.

> **비용 주의**: 새 인그레스 게이트웨이를 만들 때는 로드 밸런서나 기타 네트워킹 설정으로 클러스터 외부에 노출해야 할 가능성이 높습니다. LoadBalancer 타입 쿠버네티스 서비스를 사용하면 로드 밸런서마다 비용이 발생합니다.

### 게이트웨이 주입

- **목적**: 사용자에게 IstioOperator 리소스에 대한 전체 접근 권한을 부여하지 않고도 자체 게이트웨이를 만들 수 있게 허용하는 방법입니다.
- **동작 방식**: 미완성 게이트웨이 디플로이먼트를 배포하고 이스티오가 나머지를 채우는 방식이 됩니다. 팀에게 미완성 게이트웨이 Deployment 리소스를 주고 이스티오가 나머지를 자동 설정하게 할 수 있습니다.

```yaml
template:
  metadata:
    annotations:
      sidecar.istio.io/inject: "true"
      inject.istio.io/templates: gateway
    labels:
      ingress: my-user-gateway-injected
  spec:
    containers:
      - name: istio-proxy
        image: auto
```

istio-sidecar-injector configmap에서 사용할 수 있는 템플릿을 볼 수 있습니다.

```bash
kubectl apply -f ch4/my-user-gw-injection.yaml
```

### 인그레스 게이트웨이 액세스 로그

이스티오의 프록시도 액세스 로그를 만들 수 있습니다. 데모 설치 프로필에서는 인그레스 게이트웨이와 서비스 프록시가 액세스 로그를 표준 출력 스트림에 출력하도록 설정됩니다.

```bash
kubectl -n istio-system logs deploy/istio-ingressgateway
```

인그레스 게이트웨이의 액세스 로그를 출력합니다. 운영 환경 이스티오에서는 액세스 로깅이 비활성화돼 있으며, 표준 출력 스트림으로 출력하도록 `accessLogFile` 속성을 설정해 이를 변경할 수 있습니다.

```bash
istioctl install --set meshConfig.accessLogFile=/dev/stdout
```

> **주의**: 각 요청은 한 서비스에서 다른 서비스로 여러 홉을 이동하기 때문에 생성되는 액세스 로그량은 어떤 로깅 시스템에든 부담을 줄 수 있습니다. 더 나은 접근 방식은 관심 있는 워크로드에 대해서만 액세스 로그를 켜는 것이며, 이는 텔레메트리 API를 사용해 가능합니다.

```yaml
spec:
  selector:
    matchLabels:
      app: istio-ingressgateway
  accessLogging:
    - providers:
        - name: envoy
      disabled: false
```

파드에 액세스 로그를 활성화합니다. 이스티오 설치에서 액세스 로그를 표준 출력하도록 설정했다면 굳이 설정할 필요 없습니다. 모든 워크로드가 이미 콘솔에 출력 중일 것이기 때문입니다. 그러나 테스트 목적으로 `disabled` 속성을 `true`로 설정하고 인그레스 게이트웨이가 액세스 로그를 쓰지 않는 것을 관찰할 수는 있습니다.

### 게이트웨이 설정 줄이기

- **문제**: 메시에 서비스가 많다면 데이터 플레인 프록시의 설정이 매우 커질 수 있습니다. 설정이 크면 리소스 폭증, 성능 문제, 확장성 문제로 이어질 수 있습니다. Sidecar 리소스를 사용해 줄일 수 있는 방법은 다른 장에서 적용합니다.
- **게이트웨이는 예외**: Sidecar 리소스는 게이트웨이에는 적용되지 않습니다. 새 게이트웨이를 배포하면 프록시에는 메시 내 라우팅할 수 있는 서비스가 모두 설정됩니다. 상술했듯이, 이렇게 하면 설정이 아주 커져 게이트웨이에 부담이 될 수 있습니다.
- **해결 요령**: 프록시에서 필요 이상의 설정은 제거하고 게이트웨이 관련 설정만 포함되도록 하는 것입니다. 최근까지 이 기능은 기본적으로 꺼져 있었는데, 최신 버전에서는 활성화 여부를 확인할 수 있습니다.

```yaml
spec:
  profile: minimal
  components:
    pilot:
      k8s:
        env:
          - name: PILOT_FILTER_GATEWAY_CLUSTER_CONFIG
            value: "true"
```

`PILOT_FILTER_GATEWAY_CLUSTER_CONFIG` 플래그는 게이트웨이 프록시 설정 내에 있는 클러스터를, 해당 게이트웨이에 적용한 VirtualService에서 실제로 참조하는 클러스터로만 좁힙니다.
