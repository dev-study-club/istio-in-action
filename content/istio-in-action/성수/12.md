## 메시는 클러스터 하나에 갇혀 있지 않습니다

- 여러 클러스터에서 서비스 메시 스케일링하기
- 두 클러스터를 합치기 위한 **전제 조건** 해결하기
- 여러 클러스터의 워크로드 간 **공통 신뢰(common trust)** 설정하기
- 클러스터 간 **워크로드 찾기**
- east-west 트래픽을 위한 **인그레스 게이트웨이** 설정하기

## 12.1 다중 클러스터 서비스 메시의 이점

책은 가상의 **ACME사**로 시작합니다. 클라우드로 이전하며 **단일 클러스터**로 출발했지만, 곧 **작은 클러스터 여러 개**로 방향을 바꿨습니다. 이유는 다섯 가지입니다.

| 이점 | 의미 |
| --- | --- |
| **격리성 강화** (Improved isolation) | 한 팀의 사고가 **다른 팀에 영향을 주지 않음** |
| **장애 경계** (Failure boundary) | 클러스터 전체에 영향을 주는 설정·운영에 **경계선**을 그어, 한 클러스터가 죽어도 **나머지 아키텍처에 미치는 영향을 줄임** |
| **규정 준수** (Regulatory and compliance) | 민감 데이터에 접근하는 서비스를 **아키텍처의 다른 부분과 분리** |
| **가용성·성능 향상** | **여러 리전**에서 운영해 가용성을 높이고, **가장 가까운 클러스터**로 라우팅해 지연을 줄임 |
| **멀티·하이브리드 클라우드** | 서로 다른 클라우드 프로바이더, 온프레미스 등 **다양한 환경**에서 워크로드 실행 |

ACME가 서비스 메시를 도입한 주된 동기도 **여러 클러스터에 걸쳐 메시를 확장**하고, **클러스터 간에도 트래픽 관리·관찰 가능성·보안**을 쓰기 위해서였습니다. 이를 위한 접근법은 두 가지입니다.

**① 다중 클러스터 서비스 메시 (Multi-cluster service mesh)**

![다중 클러스터 서비스 메시 — 여러 클러스터가 하나의 메시와 하나의 컨트롤 플레인 관점을 공유 (istio.io Deployment Models)](images/notes/istio-in-action/12-1.avif)

- 여러 클러스터에 걸쳐 있고, 워크로드가 **클러스터 간에 트래픽을 라우팅**하도록 설정된 **하나의** 메시
- VirtualService, DestinationRule, Sidecar 등 **이스티오 설정이 그대로** 적용됨

**② 메시 연합 (Mesh federation, 다중 메시)**

![메시 연합 — 신뢰 도메인이 다른 두 메시(foo.com / bar.com) 사이에서 명시적으로 허용한 통신만 연결 (istio.io Deployment Models)](images/notes/istio-in-action/12-2.avif)

- **독립된 메시 2개**의 워크로드 간 통신을 노출·활성화
- **자동화가 덜 돼 있어** 양쪽 메시 모두에 수동 설정이 필요
- 하지만 **서로 다른 팀**이 메시를 운영하거나 **보안 격리 요구가 엄격**할 때 좋은 선택지

> **이 장은 ①만 다룹니다.** 메시 연합은 이스티오 공식 문서를 참고하세요.

## 12.2 다중 클러스터 서비스 메시 개요

다중 클러스터 서비스 메시는 **앱에는 완전히 투명하게** 클러스터 간에 서비스를 연결하면서, 메시 기능은 **클러스터 간 통신에도 전부 유지**합니다. 이스티오의 구현 방식은 단순합니다 — **모든 클러스터의 서비스를 쿼리**하고, 그 정보로 **프록시가 클러스터 사이에서 라우팅하도록 설정**합니다.

![그림 12.1 다중 클러스터 서비스 메시에는 클러스터 간 디스커버리, 연결성, 공통 신뢰가 필요하다](images/notes/istio-in-action/12-3.avif)

**클러스터들을 하나의 메시로 합치는 세 가지 전제 조건** — 이 장 전체가 이 셋을 하나씩 해결하는 구조입니다.

| 전제 조건 | 의미 | 해결하는 절 |
| --- | --- | --- |
| **① 클러스터 간 워크로드 디스커버리** | 컨트롤 플레인이 **상대 클러스터의 워크로드를 찾을 수** 있어야 함 (= 상대 쿠버네티스 API 서버에 접근 가능해야 함) | 12.2.2 → 12.3.5 |
| **② 클러스터 간 워크로드 연결성** | 워크로드끼리 **실제로 커넥션을 맺을 수** 있어야 함. 엔드포인트를 알아도 연결이 안 되면 쓸모없음 | 12.2.3 → 12.3.6 |
| **③ 클러스터 간 공통 신뢰** | 클러스터를 넘어 **서로 인증**할 수 있어야 이스티오 보안 기능이 동작 | 12.2.4 → 12.3.3 |

> ⚠️ **다중 클러스터 연결성과 보안.** 이스티오가 클러스터 간 워크로드를 찾는 방법은 **상대 클러스터의 쿠버네티스 API에 접근하는 것뿐**입니다. 즉 **각 클러스터가 다른 클러스터의 API에 접근할 수 있게** 되는데, 조직에 따라서는 받아들이기 어려운 보안 태세입니다. 그런 경우에는 **메시 연합**이 더 낫습니다.

### 12.2.1 이스티오 다중 클러스터 배포 모델

다중 클러스터 메시에서 클러스터는 두 종류로 나뉩니다.

- **기본 클러스터 (primary cluster)** — 이스티오 **컨트롤 플레인이 설치된** 클러스터
- **원격 클러스터 (remote cluster)** — 컨트롤 플레인과 **떨어져 있는** 클러스터

이 조합에 따라 **배포 모델 세 가지**가 나오고, 고르는 기준은 **원하는 가용성 수준**입니다.

**기본-원격 (primary-remote, 컨트롤 플레인 공유)**

![그림 12.2 기본-원격 배포 모델 — 기본 클러스터의 컨트롤 플레인이 원격 클러스터의 API 서버까지 디스커버리](images/notes/istio-in-action/12-4.avif)

**기본-기본 (primary-primary, 복제된 컨트롤 플레인)**

![그림 12.3 기본-기본 배포 모델 — 클러스터마다 컨트롤 플레인이 있고 서로의 API 서버를 디스커버리](images/notes/istio-in-action/12-5.avif)

- 컨트롤 플레인이 여럿이라 **가용성이 높습니다.** 중단이 나도 **그 클러스터로 국한**되기 때문입니다.
- 트레이드오프로 **리소스가 더 필요**합니다.

**외부 컨트롤 플레인 (external control plane)**

![그림 12.4 외부 컨트롤 플레인 배포 모델 — 모든 클러스터가 원격이고 컨트롤 플레인은 밖에 있다](images/notes/istio-in-action/12-6.avif)

- **모든 클러스터가 컨트롤 플레인과 떨어져** 있습니다.
- 클라우드 프로바이더가 이스티오를 **관리형 서비스**로 제공할 때 쓰는 모델입니다.

| 모델 | 컨트롤 플레인 위치 | 장점 | 단점 |
| --- | --- | --- | --- |
| **기본-원격** | 기본 클러스터 1곳 | 리소스 적음 | 기본 클러스터 장애 시 **원격도 설정 갱신 불가** |
| **기본-기본** | **모든 클러스터** | **가용성 최고** (장애가 해당 클러스터로 국한) | 리소스 많이 필요 |
| **외부 컨트롤 플레인** | 메시 **밖** | 운영 부담을 외부(관리형)로 넘김 | 외부 컨트롤 플레인에 의존 |

### 12.2.2 다중 클러스터 배포에서 워크로드는 어떻게 찾는가?

컨트롤 플레인은 **쿠버네티스 API 서버와 통신**해 서비스·엔드포인트 같은 프록시 설정용 정보를 모읍니다. 그런데 API 서버 접근은 **막강한 권한**입니다 — 리소스 세부 정보와 민감 정보를 조회할 수 있고, 클러스터를 **되돌릴 수 없는 상태로 망가뜨릴 만큼** 업데이트·삭제도 할 수 있습니다. 그래서 쿠버네티스는 **RBAC**으로 API 서버 접근을 보호합니다.

클러스터 간 디스커버리에 쓰이는 RBAC 개념만 짚고 갑니다.

| 개념 | 역할 |
| --- | --- |
| **서비스 어카운트** (ServiceAccount) | 기계·서비스 등 **사람이 아닌 클라이언트에 ID** 부여 |
| **서비스 어카운트 토큰** | 서비스 어카운트마다 생성되는 **ID 클레임(JWT)**. 쿠버네티스가 파드에 주입하고, 파드는 이 토큰으로 **API 서버에 인증** |
| **Role / ClusterRole** | 서비스 어카운트나 사용자 같은 ID에 대한 **권한 집합** |

![그림 12.5 istiod의 ID와 접근을 설정하는 리소스 — 서비스 어카운트, 롤, 토큰](images/notes/istio-in-action/12-7.avif)

클러스터 **안**에서 istiod가 자기 서비스 어카운트 토큰으로 API 서버에 붙는 것과 **기술적으로 똑같습니다.** 차이는 **원격 클러스터의 서비스 어카운트 토큰**(과 API 서버와 보안 통신을 시작할 인증서)을 istiod에게 **넘겨줘야 한다**는 것뿐입니다.

![그림 12.6 istiod는 상대 클러스터의 서비스 어카운트 자격 증명으로 두 번째 클러스터의 워크로드 정보를 조회한다 — 토큰은 반대편 클러스터로 옮겨져야 한다](images/notes/istio-in-action/12-8.avif)

> **이 과정은 `istioctl`이 자동화합니다.** 12.3.5의 `create-remote-secret` 이 바로 "토큰 + CA 인증서를 kubeconfig 형태로 묶어 상대 클러스터에 시크릿으로 넣는" 명령입니다.

### 12.2.3 클러스터 간 워크로드 연결

두 번째 전제 조건은 **워크로드가 클러스터를 건너 연결**할 수 있어야 한다는 것입니다.

| 네트워크 형태 | 예시 | 필요한 것 |
| --- | --- | --- |
| **플랫 네트워크** (flat network) | 단일 네트워크 공유(Amazon VPC 등), 또는 **네트워크 피어링**으로 연결 | **없음** — 워크로드가 **IP로 바로 연결**되니 조건이 이미 충족 |
| **서로 다른 네트워크** | 다른 클라우드, 온프레미스, 피어링 불가 | 네트워크 **에지**에서 클러스터 간 트래픽을 프록시하는 특수 인그레스 게이트웨이 = **east-west 게이트웨이** |

![그림 12.7 east-west 게이트웨이는 각 클러스터의 워크로드로 요청을 리버스 프록시한다](images/notes/istio-in-action/12-9.avif)

공식 문서가 꼽는 **다중 네트워크(multiple networks)** 를 쓰는 이유는 다음과 같습니다.

![다중 네트워크 메시 — 네트워크마다 게이트웨이를 두고 그 게이트웨이를 통해 넘어간다 (istio.io Deployment Models)](images/notes/istio-in-action/12-10.avif)

- 서비스 엔드포인트의 **IP 또는 VIP 대역 중복** (Overlapping IP)
- **관리 경계** 교차
- **내결함성**
- 네트워크 주소 **확장**
- **네트워크 분할**을 요구하는 표준 준수

> **east-west 게이트웨이가 필수는 아닙니다.** 멀티 클러스터·멀티 프라이머리라도 네트워크 장비에서 **L3 라우팅**(예: BGP)으로 파드 대역끼리 통신이 되면, 즉 **플랫 네트워크로 만들어주면** 게이트웨이 없이 통신합니다. 맨 뒤 **추가 실습 1**에서 직접 해봅니다.

![IstioCon 발표 — Cilium BGP로 두 kind 클러스터의 파드 대역을 플랫 네트워크로 묶은 멀티 프라이머리 데모](images/notes/istio-in-action/12-11.avif)

### 12.2.4 클러스터 간 공통 신뢰

마지막 전제 조건은 **클러스터들이 공통된 신뢰**를 갖는 것입니다. 그래야 반대편 클러스터의 워크로드끼리 **상호 인증(mTLS)** 할 수 있습니다. 방법은 두 가지입니다.

#### 방법 ① 플러그인 CA 인증서 (PLUG-IN CA CERTIFICATES)

![그림 12.8 같은 루트가 서명한 중간 CA 인증서를 각 클러스터에서 사용하기](images/notes/istio-in-action/12-12.avif)

![루트 인증서 → 클러스터별 중간 인증서 → 워크로드 인증서로 이어지는 서명 체인 (중간 CA를 이스티오 플러그인 CA로 사용)](images/notes/istio-in-action/12-13.avif)

- 이스티오가 중간 CA를 **스스로 만들게 두지 않고**, **사용할 인증서를 지정**합니다. 인증서는 이스티오 설치 네임스페이스에 **시크릿**으로 넣습니다.
- 두 클러스터 모두 **같은 루트 CA가 서명한 중간 CA**를 쓰게 하면 공통 신뢰가 생깁니다.
- **간단**하다는 게 장점입니다.

> ⚠️ **위험.** 중간 CA가 **노출**되면, 노출을 감지해 인증서를 폐기할 때까지 공격자가 **신뢰받는 인증서를 마음대로 서명**할 수 있습니다. 그래서 조직들은 중간 CA를 넘겨주길 꺼립니다. 중간 CA를 **메모리에만 올리고 etcd(쿠버네티스 시크릿 저장소)에 두지 않으면** 위험을 줄일 수 있지만, 더 안전한 대안은 ②입니다.

#### 방법 ② 외부 인증 기관 통합 (EXTERNAL CERTIFICATE AUTHORITY INTEGRATION)

- **istiod**가 쿠버네티스 **CSR(인증서 서명 요청)** 리소스를 검증·승인하는 **등록 기관(RA)** 역할을 합니다.
- 승인된 CSR은 다음 중 하나로 **외부 CA에 제출**됩니다.

| 방식 | 설명 |
| --- | --- |
| **cert-manager** | cert-manager가 **우리 외부 CA를 지원할 때만** 가능. 지원하면 cert-manager의 **istio-csr**이 쿠버네티스 CSR을 지켜보다가 외부 CA에 서명을 요청 |
| **맞춤 개발** | 승인된 CSR을 지켜보고 외부 CA에 제출하는 **쿠버네티스 컨트롤러를 직접 구현** |

![cert-manager 연동 흐름 — 사이드카가 istiod에 CSR 요청 → istiod 승인 → cert-manager가 설정된 외부 CA(Let's Encrypt, Vault, Venafi 등)로 서명 → 서명된 인증서 반환](images/notes/istio-in-action/12-14.avif)

외부 CA가 서명한 인증서는 쿠버네티스 CSR에 저장되고, istiod가 **SDS**로 워크로드에 전달합니다(part9의 SDS와 같은 경로).

> **(참고) 시크릿은 암호화되지 않습니다.** 시크릿 데이터는 **etcd에 평문(base64)** 으로 저장되고, 파드에 볼륨 마운트하면 노드 디스크가 아닌 **tmpfs(메모리)** 에 올라갑니다. 그래서 **etcd 접근 통제와 저장 시 암호화**가 권장되고, 버전 관리 시스템에 넣으면 안 됩니다(Sealed Secrets, Vault 등 활용). 플러그인 CA 방식의 `cacerts` 시크릿에 **중간 CA 개인 키**가 들어간다는 점을 떠올리면 왜 중요한지 보입니다.

## 12.3 다중 클러스터, 다중 네트워크, 다중 컨트롤 플레인 서비스 메시 개요

실제 엔터프라이즈를 흉내 내 **여러 클러스터 · 여러 리전 · 서로 다른 네트워크**로 구성합니다.

- **west-cluster** — us-west 리전의 사설 네트워크. **webapp** 실행
- **east-cluster** — us-east 리전의 사설 네트워크. **catalog** 실행

![그림 12.9 다중 클러스터 서비스 메시 다이어그램 — west-network의 webapp이 east-network의 catalog를 호출](images/notes/istio-in-action/12-15.avif)

- 두 리전에 두면 한쪽에 재난이 나도 **서비스 중단을 막을** 수 있습니다.
- webapp과 catalog가 **다른 클러스터에 있어야 할 기술적 이유는 없습니다** — 시연용일 뿐입니다. 실제로는 **"수다스러운" 워크로드는 지연을 줄이려고 가까이** 두는 게 좋습니다.

### 12.3.1 다중 클러스터 배포 모델 선택하기

- **다중 네트워크**이므로 **east-west 게이트웨이**는 필수입니다.
- 컨트롤 플레인을 **복제할지, 하나만 둘지**는 **비즈니스 요구 사항**에 달렸습니다.
- ACME의 온라인 상점은 **1분 중단에 수백만 달러**가 날아갑니다 → **고가용성 최우선** → **기본-기본 모델**

> **결론: east-west 게이트웨이로 네트워크를 잇는 "다중 클러스터 · 다중 네트워크 · 다중 컨트롤 플레인" 메시를 기본-기본 모델로 구축합니다.**

### 12.3.3 플러그인 CA 인증서 설정하기

part9에서 워크로드 ID 부트스트래핑을 다룰 때 생략한 사실이 있습니다 — **이스티오는 설치 시 인증서에 서명할 CA를 직접 만듭니다.** 이 CA는 `istio-system` 에 **`istio-ca-secret`** 시크릿으로 저장되고 **istiod 복제본들이 공유**합니다.

이 기본 동작을 바꿔 **우리 CA를 쓰게** 하려면, `istio-system` 에 **`cacerts`** 라는 시크릿을 넣으면 됩니다.

![그림 12.10 cacerts 시크릿은 루트 CA의 공개 키와 중간 CA의 공개 키·개인 키로 구성된다. 루트 CA의 개인 키는 클러스터 밖에 안전하게 보관한다](images/notes/istio-in-action/12-16.avif)

| 파일 | 내용 |
| --- | --- |
| `ca-cert.pem` | **중간 CA**의 인증서 |
| `ca-key.pem` | **중간 CA**의 개인 키 |
| `root-cert.pem` | 중간 CA를 발급한 **루트 CA**의 인증서. 루트 CA가 중간 CA들을 검증하며, 이것이 **클러스터 간 상호 신뢰의 핵심** |
| `cert-chain.pem` | **중간 CA 인증서 + 루트 인증서**를 이어 붙인 신뢰 체인 |

> **인증서 계층 구조.** **루트 CA** = 모든 클러스터가 신뢰하는 최상위 / **중간 CA** = 클러스터별로 발급되어 워크로드 인증서 서명에 사용 / **인증서 체인** = 클라이언트가 검증할 수 있도록 이어 붙인 것.

#### 플러그인 CA 인증서 적용하기

책의 `./ch12/scripts/generate-certificates.sh` 는 [smallstep CLI](https://github.com/smallstep/cli)(`brew install step`)로 **루트 CA 1개 → 중간 CA 2개**를 만듭니다.

```bash
#!/bin/bash
set -ex

cert_dir=`dirname "$BASH_SOURCE"`/../certs

echo "Clean up contents of dir './chapter12/certs'"
rm -rf ${cert_dir}

echo "Generating new certificates"
mkdir -p ${cert_dir}/west-cluster
mkdir -p ${cert_dir}/east-cluster

if ! [ -x "$(command -v step)" ]; then
  echo 'Error: Install the smallstep cli (https://github.com/smallstep/cli)'
  exit 1
fi

# 루트 CA
step certificate create root.istio.in.action ${cert_dir}/root-cert.pem ${cert_dir}/root-ca.key \
  --profile root-ca --no-password --insecure --san root.istio.in.action \
  --not-after 87600h --kty RSA

# 같은 루트로 서명한 중간 CA 2개
step certificate create west.intermediate.istio.in.action ${cert_dir}/west-cluster/ca-cert.pem ${cert_dir}/west-cluster/ca-key.pem --ca ${cert_dir}/root-cert.pem --ca-key ${cert_dir}/root-ca.key --profile intermediate-ca --not-after 87600h --no-password --insecure --san west.intermediate.istio.in.action --kty RSA
step certificate create east.intermediate.istio.in.action ${cert_dir}/east-cluster/ca-cert.pem ${cert_dir}/east-cluster/ca-key.pem --ca ${cert_dir}/root-cert.pem --ca-key ${cert_dir}/root-ca.key --profile intermediate-ca --not-after 87600h --no-password --insecure --san east.intermediate.istio.in.action --kty RSA

# 인증서 체인 = 중간 CA + 루트
cat ${cert_dir}/west-cluster/ca-cert.pem ${cert_dir}/root-cert.pem > ${cert_dir}/west-cluster/cert-chain.pem
cat ${cert_dir}/east-cluster/ca-cert.pem ${cert_dir}/root-cert.pem > ${cert_dir}/east-cluster/cert-chain.pem
```

```plain text
ch12/certs
├── east-cluster
│   ├── ca-cert.pem    # 중간 CA 인증서
│   ├── ca-key.pem     # 중간 CA 개인 키
│   └── cert-chain.pem # 인증서 체인
├── root-ca.key        # 루트 개인 키  ← 클러스터에 넣지 않음
├── root-cert.pem      # 루트 인증서
└── west-cluster
    ├── ca-cert.pem
    ├── ca-key.pem
    └── cert-chain.pem
```

```bash
openssl x509 -in ch12/certs/root-cert.pem -noout -text
#   Issuer: CN=root.istio.in.action / Subject: CN=root.istio.in.action
#   X509v3 Basic Constraints: critical  CA:TRUE, pathlen:1   # 하위 CA 1단계 생성 가능

openssl x509 -in ch12/certs/east-cluster/ca-cert.pem -noout -text
#   Issuer: CN=root.istio.in.action / Subject: CN=east.intermediate.istio.in.action
#   X509v3 Basic Constraints: critical  CA:TRUE, pathlen:0   # 이 중간 CA는 더 이상 하위 CA를 만들 수 없음
```

> **`pathlen` 이 계층을 강제합니다.** 루트는 `pathlen:1`(중간 CA까지만), 중간 CA는 `pathlen:0`(워크로드 인증서만 서명). 중간 CA 키가 새더라도 **또 다른 CA를 만들어낼 수는 없게** 막는 장치입니다.

**istio-system 네임스페이스를 먼저 만들고 cacerts 시크릿 배포**

```bash
# west-cluster
kwest create namespace istio-system
kwest create secret generic cacerts -n istio-system \
--from-file=ch12/certs/west-cluster/ca-cert.pem \
--from-file=ch12/certs/west-cluster/ca-key.pem \
--from-file=ch12/certs/root-cert.pem \
--from-file=ch12/certs/west-cluster/cert-chain.pem

# east-cluster
keast create namespace istio-system
keast create secret generic cacerts -n istio-system \
--from-file=ch12/certs/east-cluster/ca-cert.pem \
--from-file=ch12/certs/east-cluster/ca-key.pem \
--from-file=ch12/certs/root-cert.pem \
--from-file=ch12/certs/east-cluster/cert-chain.pem

# 확인
for i in west east; do echo ">> k8s cluster : $i <<"; kubectl get secret cacerts -n istio-system --kubeconfig=./$i-kubeconfig; echo; done
```

> **순서가 중요합니다.** `cacerts` 는 **컨트롤 플레인 설치 전에** 있어야 합니다. istiod가 뜸 때 이 시크릿이 있으면 자체 CA를 만드는 대신 이걸로 워크로드 인증서에 서명합니다.

### 12.3.4 각 클러스터에 컨트롤 플레인 설치하기

설치 전에 **각 클러스터에 네트워크 메타데이터**를 붙입니다. 이스티오는 이 **토폴로지 정보**로 두 가지를 합니다.

- **지역 정보**로 라우팅할 때 **가까운 워크로드를 우선** (12.3.7)
- **다른 네트워크**에 있는 원격 워크로드로 갈 때 **east-west 게이트웨이를 경유**하도록 설정 (12.3.6)

#### 클러스터 간 연결을 위해 네트워크에 레이블 붙이기

설치 시 **MeshNetworks** 설정으로도 할 수 있지만, 이제는 드문 고급 사례에서나 쓰는 **레거시**입니다. 더 간단한 방법은 **이스티오 설치 네임스페이스에 레이블**을 붙이는 것입니다.

```bash
kwest label namespace istio-system topology.istio.io/network=west-network
keast label namespace istio-system topology.istio.io/network=east-network

for i in west east; do echo ">> k8s cluster : $i <<"; kubectl get ns istio-system --show-labels --kubeconfig=./$i-kubeconfig; echo; done
```

#### IstioOperator 리소스를 사용해 컨트롤 플레인 설치하기

```yaml
# ch12/controlplanes/cluster-west.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  name: istio-controlplane
  namespace: istio-system
spec:
  profile: demo
  components:
    egressGateways:            # 이그레스 게이트웨이 비활성화
    - name: istio-egressgateway
      enabled: false
  values:
    global:
      meshID: usmesh           # 메시 이름 — 두 클러스터가 반드시 같아야 함
      multiCluster:
        clusterName: west-cluster   # 멀티 클러스터 메시 안에서 이 클러스터의 식별자
      network: west-network         # 이 설치가 속한 네트워크
```

```yaml
# ch12/controlplanes/cluster-east.yaml — clusterName, network만 다르다
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  name: istio-controlplane
  namespace: istio-system
spec:
  profile: demo
  components:
    egressGateways:
    - name: istio-egressgateway
      enabled: false
  values:
    global:
      meshID: usmesh
      multiCluster:
        clusterName: east-cluster
      network: east-network
```

| 필드 | west | east | 규칙 |
| --- | --- | --- | --- |
| `meshID` | usmesh | usmesh | **같아야** 하나의 메시 |
| `clusterName` | west-cluster | east-cluster | **달라야** 함. 12.3.5 원격 시크릿의 **식별자**로 쓰임 |
| `network` | west-network | east-network | 12.3.4의 **네임스페이스 레이블과 일치**해야 함 |

#### 두 클러스터 모두에 워크로드 실행하기

지금 상태는 **메시가 2개**입니다. 클러스터마다 **자기 서비스만 아는 istiod 1개**와 **인그레스 게이트웨이 1개**가 있을 뿐, 클러스터 간 디스커버리도 연결도 없습니다.

![그림 12.11 현재 메시 설정 — 각 클러스터의 istiod는 자기 API 서버의 엔드포인트만 디스커버리한다](images/notes/istio-in-action/12-17.avif)

**west에는 webapp을 배포합니다.**

```bash
kwest create ns istioinaction
kwest label namespace istioinaction istio-injection=enabled
kwest -n istioinaction apply -f ch12/webapp-deployment-svc.yaml
kwest -n istioinaction apply -f ch12/webapp-gw-vs.yaml
kwest -n istioinaction apply -f ch12/catalog-svc.yaml   # ← webapp이 호출할 catalog의 '스텁' 서비스
```

```yaml
# ch12/catalog-svc.yaml — 셀렉터에 맞는 파드가 west에는 없다
apiVersion: v1
kind: Service
metadata:
  labels:
    app: catalog
  name: catalog
spec:
  ports:
  - name: http
    port: 80
    protocol: TCP
    targetPort: 3000
  selector:
    app: catalog
```

```bash
kwest get svc,ep catalog -n istioinaction
# service/catalog   ClusterIP   10.100.2.43   <none>   80/TCP
# endpoints/catalog   <none>          ← 엔드포인트 없음
```

> **catalog는 east에서만 도는데 왜 west에 서비스를 만들까?** 이 서비스가 없으면 webapp 컨테이너가 **FQDN을 IP로 해석조차 못 합니다.** 그러면 트래픽이 앱을 떠나 **프록시로 리다이렉트되는 지점까지 가지도 못하고** 실패합니다. **스텁 서비스**를 두면 FQDN이 클러스터 IP로 해석되고, 앱이 요청을 시작하면 iptables가 사이드카로 보내고, **실제 라우팅은 엔보이가 클러스터 간 설정으로 처리**합니다.
> 이는 이스티오 커뮤니티가 **DNS 프록시**를 개선하며 해결하려던 에지 케이스이고, 13장(가상머신)에서 DNS 프록시를 다룹니다.

**east에는 catalog를 배포합니다.**

```bash
keast create ns istioinaction
keast label namespace istioinaction istio-injection=enabled
keast -n istioinaction apply -f ch12/catalog.yaml

ieast proxy-config endpoint deploy/istio-ingressgateway.istio-system | grep catalog
# 10.20.0.15:3000   HEALTHY   OK   outbound|80||catalog.istioinaction.svc.cluster.local
```

이제 **서로를 연결해야 하는 워크로드**가 준비됐습니다. 하지만 클러스터 간 디스커버리 없이는 **사이드카에 반대 클러스터 워크로드가 설정되지 않습니다.**
