part1\~9에서는 설정하는 법을 배웠습니다. 이번 장은 **그 설정이 생각대로 동작하지 않을 때 무엇을 어떤 순서로 보는가**에 대한 이야기입니다.

| 유형 | 증상 | 도구 |
| --- | --- | --- |

> ⚠️ **버전 주의.** 이 페이지는 두 자료를 합쳤는데 환경이 다릅니다 — 하나는 **istio 1.16 계열 / minikube**, 다른 하나는 **istio 1.27 / kind, k8s 1.33** 입니다. 개념과 명령어는 동일하지만 **출력 컬럼이 조금씩 다릅니다**(아래에서 그때그때 표시). part1\~9에서 쓰던 `myk8s` kind 환경(1.17.8)과도 다르므로 `docker exec -it myk8s-control-plane` 접두사가 필요할 수 있습니다.

## 10.1 가장 흔한 실수: 잘못 설정한 데이터 플레인

이스티오의 서비스 프록시 설정은 **VirtualService, DestinationRule 같은 리소스로 노출**되고, 이것이 **엔보이 설정으로 변환되어 데이터 플레인에 적용**됩니다. 그래서 실수는 대부분 이 변환 어딘가에서 어긋납니다.

실습을 위해 **설정 오류가 포함된 환경**을 일부러 배포합니다.

```bash

kubectl create ns istioinaction &&
kubectl label ns istioinaction istio-injection=enabled

# 9장 Securing 실습 설정 제거
kubectl delete authorizationpolicy,peerauthentication,requestauthentication -n istio-system
kubectl delete deploy/sleep -n default
kubectl delete svc/sleep -n default
```

## 10.2 데이터 플레인 문제 식별하기

### 10.2.1 데이터 플레인이 최신 상태인지 확인하는 방법

설정 내용을 들여다보기 전에 **애초에 설정이 프록시까지 갔는지**부터 확인합니다.

- 데이터 플레인 설정은 **궁극적 일관성(eventual consistency)** 입니다. 컨트롤 플레인과 동기화되기 전까지 즉시 반영되지 않습니다.
- 컨트롤 플레인은 **특정 서비스의 개별 엔드포인트 IP 주소**를 데이터 플레인으로 보냅니다.
- 엔드포인트 중 하나가 비정상이 되면, **쿠버네티스가 파드를 비정상으로 표시하는 데 시간이 걸리고**, 컨트롤 플레인이 문제를 인지해 데이터 플레인에서 엔드포인트를 제거하는 데 또 시간이 걸립니다.
- **대규모 클러스터에서는 동기화에 필요한 시간이 더 늘어납니다.**

```bash
istioctl proxy-status
```

```plain text

catalog-primary-658c756d7f-kv52g.istioinaction         Kubernetes     istiod-85798b5866-8ptm6     1.27.0      4 (CDS,LDS,EDS,RDS)
```

**모든 워크로드와 모든 xDS API별로 동기화 상태가 나열됩니다.** 상태값의 의미는 셋입니다.

| 상태 | 의미 |
| --- | --- |
| **SYNCED** | istiod가 보낸 마지막 설정을 **엔보이가 확인함** |
| **NOT SENT** | istiod가 아무것도 보내지 않음. **보통은 보낼 것이 없어서** — 문제가 아닌 경우가 많음 |
| **STALE** | istiod가 업데이트를 보냈지만 **확인받지 못함.** istiod 과부하, 엔보이↔istiod 커넥션 부족·끊김, 혹은 이스티오 버그 |

> **여기서 STALE이 보이면 설정 내용을 볼 필요가 없습니다.** 전달 경로부터 고쳐야 합니다. 반대로 전부 SYNCED인데 동작이 이상하면 **설정 내용 자체가 틀린 것**이므로 10.2.2로 넘어갑니다. 이번 실습은 후자입니다.

> **버전 차이:** `SUBSCRIBED TYPES` 컬럼은 비교적 최근 버전에서 추가됐습니다. 구버전에서는 `CDS / LDS / EDS / RDS` 가 각각 개별 컬럼으로 나오고 그 자리에 SYNCED·STALE·NOT SENT가 찍힙니다. 보는 법은 같습니다.

## 10.3 엔보이 설정에서 수동으로 잘못된 설정 발견하기

워크로드에 적용된 엔보이 설정은 **엔보이 관리 인터페이스**나 **istioctl**로 가져올 수 있습니다.

### 10.3.1 엔보이 관리 인터페이스

엔보이 관리 인터페이스는 **프록시의 특정 부분 수정 기능과 엔보이 설정을 노출**하며, **모든 서비스 프록시에서 15000 포트**로 접근할 수 있습니다.

```bash
istioctl dashboard envoy deploy/catalog -n istioinaction
# http://localhost:15000
```

브라우저가 열리면서 관리 대시보드가 노출한 옵션들이 나열됩니다. **`config_dump`** 로 프록시가 현재 적재한 엔보이 설정을 전부 출력할 수 있는데 — **데이터양에 주의해야 합니다.**

```bash
curl -s localhost:15000/config_dump | wc -l
14633
```

> **1만 4천 줄입니다.** 사람이 눈으로 읽을 물건이 아닙니다. 그래서 `istioctl proxy-config` 로 **필터링해서 보는 것**이 실전 방식입니다. part7에서 `/stats` 를 grep 없이 돌리지 말라고 한 것과 같은 이유입니다.

### 10.3.2 istioctl로 프록시 설정 쿼리하기

`istioctl proxy-config`(줄여서 `istioctl pc`) 는 **엔보이 xDS API를 기준으로** 워크로드의 프록시 설정을 가져오고 필터링합니다.

| 서브커맨드 | xDS | 가져오는 것 |
| --- | --- | --- |
| `listener` | **LDS** | 리스너 설정 |
| `route` | **RDS** | 루트 설정 |
| `cluster` | **CDS** | 클러스터 설정 |
| `endpoint` | **EDS** | 엔드포인트 설정 |
| `secret` | **SDS** | 시크릿 설정 |

#### 요청을 라우팅하기 위한 엔보이 API의 상호작용

엔보이 프록시의 핵심 기능은 **Discovery**(트래픽을 전달할 타겟을 식별)입니다. 요청 하나가 앱까지 가는 길을 API 단위로 끊어보면 이렇습니다.

1. **엔보이 리스너**는 **네트워크 설정**(다운스트림 트래픽을 프록시로 허용하는 IP 주소 및 포트 등)을 정의합니다. 허용된 커넥션에 **HTTP 필터 체인**이 만들어지고, 체인에서 가장 중요한 필터가 **라우터 필터**로 고급 라우팅 작업을 수행합니다. → 이스티오에서는 **Gateway 리소스**로 설정
2. **엔보이 루트**는 **가상 호스트를 클러스터에 일치시키는 규칙 집합**입니다. **루트는 순서대로 처리**되며, **일치하는 첫 번째 항목**이 트래픽을 워크로드 클러스터로 라우팅하는 데 사용됩니다. 정적으로 설정할 수도 있지만 **이스티오에서는 RDS로 동적 설정**합니다. → **VirtualService**
3. **엔보이 클러스터**에서, 각 클러스터에는 **유사한 워크로드에 대한 엔드포인트 그룹**이 있습니다. **부분집합(subset)** 은 클러스터 내에서 워크로드를 더 분할해 정밀한 트래픽 관리를 가능하게 합니다. → 디스커버리로 자동 설정되거나 **DestinationRule**
4. **엔보이 엔드포인트**는 **요청을 처리하는 워크로드의 IP 주소**입니다.

> **ADS(Aggregated Discovery Service)** 는 xDS 설정 중앙 관리 서버와의 통신 API입니다. 엔보이가 개별적으로는 다른 엔보이와의 관련 설정 처리 및 **순서 문제**를 해결하기 어렵기 때문에 중앙 서버를 두고 처리하는 방식을 제공합니다. **이스티오에서는 pilot이 그 역할이었고, 현재는 istiod로 통합**되었습니다. (part1에서 본 그 통합입니다)

#### [LDS] 엔보이 리스너 설정 쿼리하기

인그레스 게이트웨이 80 포트로 도착하는 트래픽이 클러스터로 **허용되는지**부터 확인합니다. 트래픽을 허용하는 것은 **리스너의 역할**입니다.

```bash
istioctl proxy-config listeners deploy/istio-ingressgateway -n istio-system
```

```plain text
ADDRESSES PORT  MATCH DESTINATION
0.0.0.0   8080  ALL   Route: http.8080          # 8080 포트에 대한 요청은 루트 http.8080에 따라 라우팅
0.0.0.0   15021 ALL   Inline Route: /healthz/ready*
0.0.0.0   15090 ALL   Inline Route: /stats/prometheus*
```

**왜 80이 아니라 8080에서 리스닝할까요?**

```bash
kubectl -n istio-system get svc istio-ingressgateway -oyaml | grep "ports:" -A 10
```

```yaml
ports:
- name: status-port
  nodePort: 31652
  port: 15021
  protocol: TCP
  targetPort: 15021
- name: http2
  nodePort: 31733
  port: 80        # 80포트의 트래픽은 파드의 8080 포트를 대상으로 함
  protocol: TCP
  targetPort: 8080
```

**80에서 8080으로 흐르는 트래픽은 쿠버네티스 서비스 `istio-ingressgateway` 가 전달합니다.** 인그레스 게이트웨이가 8080에서 리스닝하는 이유는 **8080이 제한된(privileged) 포트가 아니기 때문**입니다.

> **여기까지는 정상입니다.** 트래픽이 8080에 도달하고, 허용하는 리스너가 존재합니다. 라우팅은 루트 `http.8080` 이 수행하므로 다음은 루트를 봅니다.

#### [RDS] 엔보이 루트 설정 쿼리하기

```bash
istioctl pc routes deploy/istio-ingressgateway -n istio-system --name http.8080
```

```plain text
NAME          VHOST NAME                      DOMAINS                      MATCH     VIRTUAL SERVICE
```

**세 필드가 사건을 설명합니다.**

- **`response_flags: "UT"`** — 요청이 **Upstream request Timeout** 으로 중단됨
- **`duration: 500`** — **타임아웃 설정값(0.5s=500ms)과 정확히 일치.** 앱이 스스로 끝낸 게 아니라 **프록시가 잘랐다**는 증거
- **`upstream_host: "172.17.0.17:3000"`** — **요청을 처리하던 워크로드의 실제 IP 주소**

**엔보이 응답 플래그** — 커넥션 실패에 대한 정보를 안내합니다.

| 플래그 | 의미 |
| --- | --- |
| **UT** | Upstream request timeout. 제한 시간에 비춰 업스트림이 너무 느렸음. **제한 시간 초과 결정을 내린 주체가 애플리케이션이 아니라 프록시**임을 의미 |
| **UH** | No healthy upstream hosts. 클러스터에 정상적인 업스트림이 없음 |
| **NR** | No route configured. 설정된 루트 없음 |
| **UC** | Upstream connection termination. 업스트림 커넥션 종료 |
| **DC** | Downstream connection termination. 다운스트림 커넥션 종료 |

> **part9에서 본 `NR`(`filter_chain_not_found`)이 바로 이 표의 NR입니다.** 응답 플래그는 보안·복원력·트러블슈팅에 걸쳐 같은 어휘로 쓰입니다.

### 10.3.4 ksniff로 네트워크 트래픽 검사

**ksniff** 는 **tcpdump를 사용해 파드의 네트워크 트래픽을 포착하고 이를 와이어샤크로 리다이렉트**합니다.

```bash
# krew 설치 후
kubectl krew install sniff

# SLOW_POD에 tcpdump를 겁니다 (요청 루프는 계속 유지)
kubectl sniff $SLOW_POD -n istioinaction -p -i lo
```

| 옵션 | 의미 |
| --- | --- |
| `-p`, `--privileged` | 대상 파드의 **netns를 공유하는 ksniff 파드(privileged)** 를 띄움 |
| `-i lo` | 트래픽을 감시할 인터페이스. 여기서는 **루프백** — 사이드카와 앱 사이 구간이기 때문 |

> ⚠️ **arm 환경 주의.** M1 minikube, parallels 등 **arm 환경 클러스터에서는 ksniff의 파드 tcpdump 출력이 안 되는 것이 확인**되었습니다. **x86 환경에서 수행**하세요.
> `Error: exec: "wireshark": executable file not found` 가 나면 **PATH에 wireshark 실행 경로를 추가**하세요.

**와이어샤크에서 확인하는 법**

1. 필터에 `http contains "GET /items"` 입력
2. 첫 번째 아이템 우클릭 → **Follow** → **TCP Stream**
3. 뜬 창은 `close` 하고 패킷 목록 확인

504가 난 스트림에서는 이런 흐름이 보입니다.

| 패킷 | 내용 |
| --- | --- |
| 4185 | 요청 `GET /items` |
| 4186 | **서버 측 ACK** |
| 4192 | **클라이언트에서 FIN, ACK (연결 종료)** |

> **왜 클라이언트가 끊었을까요?** **4186과 4192의 시간 차가 약 500ms** 입니다 (`0.501683 = 91.020323 - 90.518640`).
> **결정적인 지점입니다.** 서버는 ACK까지 정상적으로 보냈고 **응답을 만들고 있던 중**이었습니다. 끊은 쪽은 **클라이언트(인그레스 게이트웨이)** 입니다. 10.3.3에서 본 `UT` 와 **정확히 같은 사건을 반대편에서 본 것**입니다.

## 10.4 엔보이 텔레메트리로 자신의 애플리케이션 이해하기

로그와 패킷은 **개별 요청**을 봅니다. 이번엔 **집계된 메트릭**으로 같은 사건을 봅니다 — part7·part8에서 세운 그 파이프라인입니다.

```bash
istioctl dashboard grafana
istioctl dashboard kiali
```

### 10.4.1 그라파나에서 실패한 요청 비율 찾기

**Istio Service Dashboard** 를 열고 **Reporter를 `source` 로 설정**합니다 — **송신(client) 측 엔보이가 보고한 메트릭**을 보겠다는 뜻입니다.

**Client / Server Success Rate (non-5xx) 가 다릅니다.**

| 지표 | 값 |
| --- | --- |
| **Client** Success Rate | **76.9%** |
| **Server** Success Rate | **100%** |

무슨 의미일까요?

- **Client 응답에는 5xx가 있습니다 (23.1%)**
- **Server 응답에는 5xx가 없습니다 (0%)**

왜 그럴까요?

- **서버에서 수신한 데이터는 모두 성공** → **서버 문제가 아닙니다.** 서버 문제였다면 서버의 Success Rate도 100%가 아니었겠죠.
- 다만 **클라이언트에서는 서버가 제한 시간(500ms)을 넘기는 경우 UT** 로 끊습니다.

> **이 한 장의 대시보드가 사건의 성격을 규정합니다.** "5xx가 난다"는 신고를 받았을 때 **Reporter를 source/destination으로 번갈아 보는 것**만으로 **앱 장애인지 타임아웃 정책 문제인지**가 갈립니다. part7에서 `reporter` 라벨을 설명한 이유가 여기에 있습니다.

### 10.4.2 프로메테우스를 사용해 영향받는 파드 쿼리하기

**서버 측 얘기도 들어봅니다.** 프로메테우스 대시보드에서 PromQL을 조회합니다.

```plain text
sort_desc(sum(irate(istio_requests_total{reporter="destination", destination_service=~"catalog.istioinaction.svc.cluster.local",response_flags="DC"}[5m]))by(response_code, pod, version))
```

```plain text
sort_desc(
  sum(
    irate(
      istio_requests_total {
        reporter="destination",   # 서버 측에서 리포트
        destination_service=~"catalog.istioinaction.svc.cluster.local",   # 서버 측이 목적지
        response_flags="DC"       # DC - 클라이언트에서 커넥션을 끊음
      }[5m]
    )
  ) by (response_code, pod, version)
)
```

서버 쪽에 5분간 발생한 **DC**가 있는지 쿼리한 결과입니다.

> **같은 사건, 세 개의 이름.**
> 게이트웨이(클라이언트) 입장에서는 **UT** — "업스트림이 늦어서 내가 끊었다"
> catalog-v2(서버) 입장에서는 **DC** — "대답하려는데 상대가 일방적으로 끊었다"
> 와이어샤크에서는 **클라이언트가 보낸 FIN, ACK**
> **서버 오류로 발생한 5xx가 아니라, 클라이언트의 UT — 즉 서버 입장에서는 DC에 의한 5xx입니다.**
> `by (response_code, pod, version)` 로 묶었으므로 **어느 파드인지도 바로 나옵니다.**

### xDS 대조표

| xDS | istioctl | 이스티오 리소스 | 답하는 질문 |
| --- | --- | --- | --- |
| **LDS** | `pc listeners` | **Gateway** | 트래픽이 **들어올 수는** 있나? |
| **RDS** | `pc routes` | **VirtualService** | 어느 **클러스터로 보낼지** 정해졌나? |
| **CDS** | `pc clusters` | **DestinationRule** | 그 **클러스터가 실제로 존재**하나? (부분집합 포함) |
| **EDS** | `pc endpoints` | (서비스 디스커버리) | 그 클러스터 뒤에 **살아있는 파드**가 있나? |
| **SDS** | `pc secret` | (Istio CA) | **인증서**가 제대로 있나? (part9) |

> **클러스터 이름 한 줄이 세 개를 이어줍니다.**
> `outbound|80|version-v1|catalog.istioinaction.svc.cluster.local`
> RDS 출력에서 이 이름을 얻어 → CDS에 `--fqdn/--port/--subset` 으로 넣고 → EDS에 `--cluster` 로 통째로 넣습니다.

### 헷갈리는 짝 대조표

| 짝 | 무엇이 다른가 |
| --- | --- |
| **설정 오류** vs **앱 문제** | **항상** 실패 vs **간헐적** 실패. 전자는 analyze/키알리, 후자는 로그/메트릭 |
| **UT** vs **DC** | **같은 사건의 양쪽 시점.** 클라이언트가 끊었다(UT) = 서버가 끊겼다(DC) |
| **UT** vs **UC** | 프록시가 **타임아웃으로** 끊음 vs **업스트림이 커넥션을 종료** |
| **`reporter="source"`** vs **`destination`** | 클라이언트 측 엔보이 보고 vs 서버 측 엔보이 보고. **둘의 차이가 곧 네트워크·정책 문제** |
| **`NOT SENT`** vs **`STALE`** | 보낼 게 없어서(정상인 경우 많음) vs **보냈는데 확인 못 받음(문제)** |
| **다운스트림 커넥션 ID** vs **업스트림 커넥션 ID** | 로그의 `[C9446]`(클라이언트→GW) vs `[C9386]`(GW→앱) |

### 트러블슈팅 치트시트

```bash
# 0. 설정이 프록시까지 갔는가
istioctl proxy-status

# 1. 설정이 틀렸는가 (네임스페이스 / 워크로드 / 파일)
istioctl analyze -n <ns>
istioctl analyze <file>.yaml -n <ns>          # 적용 전 검증
istioctl x describe pod <pod> -n <ns>

# 2. 엔보이 설정을 LDS -> RDS -> CDS -> EDS 순서로 좁히기
istioctl pc listeners deploy/istio-ingressgateway -n istio-system
istioctl pc routes    deploy/istio-ingressgateway -n istio-system --name http.8080 [-o json]
istioctl pc clusters  deploy/istio-ingressgateway -n istio-system \
  --fqdn <svc>.<ns>.svc.cluster.local --port 80 [--subset <subset>] [-o json]
istioctl pc endpoints deploy/istio-ingressgateway -n istio-system \
  --cluster "outbound|80|<subset>|<svc>.<ns>.svc.cluster.local"

# 3. 엔드포인트 IP -> 파드 역추적
kubectl get pod -n <ns> --field-selector status.podIP=<IP>

# 4. 액세스 로그 (JSON으로 바꿔두면 훨씬 낫다)
kubectl -n istio-system logs deploy/istio-ingressgateway | grep <code> | tail -n 1 | jq
#   볼 것: response_flags, duration, upstream_host, upstream_cluster, response_code_details

# 5. 범인 파드 자동 특정
SLOW_POD_IP=$(kubectl -n istio-system logs deploy/istio-ingressgateway \
  | grep 504 | tail -n 1 | jq -r .upstream_host | cut -d ":" -f1)
kubectl get pods -n <ns> --field-selector status.podIP=$SLOW_POD_IP

# 6. 요청 생애주기 추적 (필요한 로거만!)
istioctl pc log deploy/istio-ingressgateway -n istio-system
istioctl pc log deploy/istio-ingressgateway -n istio-system \
  --level http:debug,router:debug,connection:debug,pool:debug
kubectl logs -n istio-system deploy/istio-ingressgateway > /tmp/ingress-logs.txt
#   읽는 법: 에러코드 검색 -> [Cxxxx] 커넥션 ID 추출 -> 그 ID로 재검색
istioctl pc log deploy/istio-ingressgateway -n istio-system --level info   # 원복 잊지 말 것

# 7. 패킷 (x86 클러스터에서)
kubectl krew install sniff
kubectl sniff $SLOW_POD -n <ns> -p -i lo

# 8. 엔보이 관리 인터페이스
istioctl dashboard envoy deploy/<app> -n <ns>          # :15000
curl -s localhost:15000/config_dump | wc -l
```

### 마무리

- **순서가 곧 방법입니다.** `proxy-status`(전달됐나) → `analyze`/`describe`(설정이 맞나) → `proxy-config`(엔보이에 어떻게 들어갔나) → **로그·패킷·메트릭**(런타임에 무슨 일이 나나). 이 순서를 건너뛰면 1만 4천 줄짜리 `config_dump` 앞에서 길을 잃습니다.
- **`istioctl proxy-config` 는 xDS를 그대로 반영합니다.** LDS → RDS → CDS → EDS 순으로 좁혀 들어가면, **어느 단계에서 끊겼는지가 그 자체로 원인**입니다. 이번 실습에서는 **CDS에서 결과가 비어 있었고**, 그게 곧 "DestinationRule이 없다"였습니다.
- **응답 플래그를 외워두세요.** `UT / UH / NR / UC / DC` 다섯 개면 대부분의 사건을 분류할 수 있습니다. **UT와 DC가 같은 사건의 양쪽 얼굴**이라는 것이 이 장의 백미입니다.
- **로그 레벨은 올린 만큼 반드시 내리세요.** debug로 켜둔 채 잊으면 로그 인프라가 먼저 죽습니다. JSON 액세스 로그를 **메시 전체에 켜는 것**도 마찬가지입니다.
- **트러블슈팅 도구는 part7·part8의 결과물 위에서 돌아갑니다.** 메트릭 파이프라인과 대시보드를 미리 세워두지 않았다면 10.4는 아예 쓸 수 없습니다. **관측을 먼저 깔아두는 것이 트러블슈팅 준비**입니다.
- **이 장에서 얻는 진짜 자산은 답이 아니라 순서**입니다. 실전에서 마주치는 설정은 이 실습보다 훨씬 복잡하지만, 물어야 할 질문은 똑같습니다 — *들어올 수 있나 → 어디로 보낼지 정해졌나 → 그게 존재하나 → 살아있나 → 제때 대답하나.*

> **버전 좌표부터.** 책은 **1.13** 기준이고, 이 페이지 실습 자료는 **1.16 계열 / 1.27**, 현재 공식 문서는 **1.31** 기준입니다(2026년 9월). **개념 — xDS 4단계, 응답 플래그, 로그 읽는 순서 — 은 그대로 유효**하지만 **도구 쪽은 꽤 달라졌습니다.** 아래는 확인된 것만 적었습니다.

### ① 앰비언트 모드 — 이 장의 도구 절반이 안 통합니다

**가장 큰 변화입니다.** 앰비언트 모드는 **1.24(2024-11)에서 GA**가 되었고, 2026년 KubeCon EU에서는 **ambient multicluster beta**까지 발표됐습니다. 앰비언트에는 **사이드카가 없습니다.** 노드마다 **ztunnel**이 L4를, 필요할 때만 **waypoint** 프록시가 L7을 처리합니다.

**즉, `istioctl proxy-config` 를 쓸 수 없습니다.** 10.3.2 전체가 사이드카를 전제로 하기 때문입니다.

| 사이드카 모드 (이 장) | 앰비언트 모드 |
| --- | --- |
| `istioctl proxy-config listener/route/cluster/endpoint` | **`istioctl ztunnel-config`** (`all`, `certificate`, `connections`, `log`, `policy`, `service`, `workload`) |
| 파드 안 `:15000/config_dump` | ztunnel 파드에 `kubectl debug` 로 접근 |
| L4·L7 모두 사이드카가 처리 | **L4는 ztunnel, L7(메서드·경로·헤더)은 waypoint 필요** |

```bash
# 워크로드 디스커버리 — 파드 IP, 실행 노드, 연결된 waypoint, 프로토콜(HBONE/TCP)
istioctl ztunnel-config workloads

# 인증서 — 서비스 어카운트별 리프/루트 인증서 (part9의 SVID를 여기서 봅니다)
istioctl ztunnel-config certificates

# 전체
istioctl ztunnel-config all -o json

# ztunnel 원본 설정 덤프
kubectl debug -it $ZTUNNEL -n istio-system --image=curlimages/curl \
  -- curl localhost:15000/config_dump

# istiod가 그 ztunnel용으로 들고 있는 xDS 상태
kubectl debug -it $ISTIOD -n istio-system --image=curlimages/curl \
  -- curl localhost:15014/debug/config_dump?proxyID="$ZTUNNEL".istio-system
```

> **10.3.2의 사고방식은 살아남습니다.** waypoint는 여전히 엔보이라서 LDS→RDS→CDS→EDS가 그대로 적용됩니다. 다만 **"어느 프록시를 보느냐"가 파드별 사이드카에서 ztunnel(노드 단위) + waypoint(서비스/네임스페이스 단위)로 바뀐 것**입니다. 트래픽이 waypoint까지 안 가는 것 같으면 **ztunnel 액세스 로그부터** 확인해 목적지 서비스/워크로드가 맞는지 봅니다.

### ② 액세스 로그 — meshConfig 전역 설정 대신 Telemetry API

10.3.3에서 **"메시 전체에 JSON 로그를 켜면 로그양이 폭증하니 대규모 클러스터에서는 쓰지 말라"** 고 경고했었죠. **그 문제의 정답이 Telemetry API입니다.** meshConfig는 전역 단일 설정만 가능하지만, Telemetry API는 **네임스페이스·워크로드 단위 + 조건부 로깅**이 됩니다.

```yaml
# 워크로드 하나만
spec:
  selector:
    matchLabels:
      app: httpbin
  accessLogging:
  - providers:
    - name: otel
```

```yaml
# 5xx만 로깅 (CEL 표현식)
accessLogging:
- providers:
  - name: otel
  filter:
    expression: response.code >= 500
```

```yaml
# 메시 전역이되 '예외 상황만' — 정상 트래픽은 아예 기록하지 않음
apiVersion: telemetry.istio.io/v1alpha1
kind: Telemetry
metadata:
  namespace: istio-system
spec:
  accessLogging:
  - providers:
    - name: otel
    filter:
      expression: "response.code >= 400 || xds.cluster_name == 'BlackHoleCluster'"
```

> **커넥션 실패는 `response.code` 자체가 없습니다.** 그래서 실무에서는 `!has(response.code) || response.code >= 500` 처럼 씁니다. 10.3.3에서 우리가 찾던 **UT는 504가 찍히므로 잡히지만, UH·NR 같은 케이스는 `has()` 검사를 넣지 않으면 놓칩니다.**
> `match.mode: SERVER / CLIENT` 로 인바운드/아웃바운드만 골라 끄고 켜는 것도 됩니다 — 10.4.1의 `reporter=source/destination` 과 같은 축입니다.

### ③ `istioctl bug-report` — 재현이 어려운 문제를 통째로 뜨기

책에 없는 명령입니다(1.8+). **로그·설정·프록시 상태·리소스 정의·클러스터 정보를 한 번에 아카이브**로 만듭니다. 이 장에서 손으로 하나씩 모은 것들을 한 방에 뜨는 셈입니다.

```bash
istioctl bug-report

# 대규모 클러스터에서는 그냥 돌리면 실패할 수 있으므로 범위를 좁힙니다
istioctl bug-report --include istioinaction,istio-system

# 멀티클러스터는 클러스터마다 따로
istioctl bug-report --context <ctx>
```

> **혼자 디버깅할 때보다 남에게 넘길 때 진가가 나옵니다.** 이슈를 올리거나 동료에게 인계할 때 `bug-report.tgz` 하나면 됩니다. `--include|--exclude` 는 `ns/dep/pod/label/annotation/container` 순의 슬래시 표기를 받습니다.

### ④ `istioctl proxy-status <pod>` — STALE 여부가 아니라 '무엇이 다른지'

10.2.1에서는 인자 없이 돌려 **SYNCED/STALE만** 봤습니다. **파드 이름을 인자로 주면 istiod가 보낸 설정과 프록시의 실제 설정 사이의 diff를 보여줍니다.**

```bash
istioctl proxy-status details-v1-6dcc6fbb9d-wsjz4.default
```

> STALE인데 원인을 모를 때, `config_dump` 1만 4천 줄을 뒤지기 전에 여기부터 보세요.

### ⑤ `istioctl experimental check-inject` — 사이드카가 안 붙을 때

책에 없는 명령입니다. **어느 웹훅이 주입을 하는지/안 하는지와 그 이유**를 표로 보여줍니다. 리비전 레이블이 섞인 환경에서 특히 유용합니다.

```bash
istioctl experimental check-inject -n <ns> <pod-name>
istioctl experimental check-inject -n <ns> deploy/<deployment-name>
istioctl experimental check-inject -n <ns> -l <key>=<value>
```

```plain text
WEBHOOK                      REVISION  INJECTED      REASON
istio-revision-tag-default   default   ✔             Namespace label istio-injection=enabled matches
istio-sidecar-injector-1-18  1-18      ✘             No matching namespace labels (istio.io/rev=1-18) or pod labels (istio.io/rev=1-18)
```

> **10.2.3의 `istioctl x describe pod` 가 "이 파드가 메시에 있나"를 알려준다면, 이건 "왜 안 들어왔나"를 알려줍니다.** 사이드카가 아예 없어서 나는 문제를 `proxy-config` 로 파헤치는 건 시간 낭비입니다.

### ⑥ Gateway API — 진입점이 리소스 status로 바뀝니다

Gateway/VirtualService 대신 **Kubernetes Gateway API(Gateway + HTTPRoute)** 를 쓰면 1차 진단이 **리소스 자신의 status**가 됩니다.

```bash
kubectl get httproute <name> -n <ns> -o yaml
# status.parents[].conditions 에서 Accepted / ResolvedRefs 확인
```

흔한 원인은 **백엔드 서비스가 없음**, **부모 Gateway가 그 네임스페이스의 라우트를 허용하지 않음**(`allowedRoutes`, 교차 네임스페이스면 `ReferenceGrant` 필요), **match/filter 설정이 잘못됨** 입니다.

> ⚠️ **다만 status를 믿기만 해선 안 됩니다.** 잘못된 헤더 설정 값 같은 경우 **Gateway와 라우트 양쪽 status는 정상인데 실제 엔보이 설정에는 라우트가 들어가지 않는** 사례가 보고돼 있습니다. **결국 `istioctl proxy-config route` 로 교차 확인해야 합니다** — 즉 10.3.2에서 배운 절차는 Gateway API에서도 그대로 필요합니다.

### ⑦ ksniff 대신 `kubectl debug` 임시 컨테이너

10.3.4의 ksniff는 **krew 플러그인 의존 + arm 클러스터에서 동작하지 않는** 제약이 있었습니다. 공식 문서도 요즘은 임시 컨테이너 방식을 씁니다.

```bash
# istio-proxy는 non-root라 tcpdump가 바로 안 붙습니다 → 임시 컨테이너로 netns 공유
kubectl debug -it $SLOW_POD -n istioinaction --image=nicolaka/netshoot --target=istio-proxy -- bash
tcpdump -i lo -s0 -w /tmp/c.pcap
```

> **와이어샤크로 실시간 리다이렉트가 필요 없다면 이쪽이 훨씬 간단합니다.** pcap을 떠서 나중에 열면 됩니다. part9 9.2.2에서 `values.global.proxy.privileged=true` 로 tcpdump를 켰던 것과 달리, **프록시 권한을 격상시키지 않아도 된다는 점**이 운영 환경에서 중요합니다.

### 한 줄 대조표

| 책/실습에서 한 것 | 지금 더 나은 선택 | 왜 |
| --- | --- | --- |
| `istioctl proxy-config ...` | 앰비언트라면 **`istioctl ztunnel-config ...`** | 사이드카가 없음 |
| `meshConfig.accessLogEncoding: JSON` 전역 | **Telemetry API + CEL `filter.expression`** | 워크로드 단위 + 에러만 → 로그 폭증 회피 |
| 상태·로그를 손으로 하나씩 수집 | **`istioctl bug-report`** | 인계·이슈 리포트용 아카이브 한 방 |
| `istioctl proxy-status` (인자 없이) | **`istioctl proxy-status <pod>`** | STALE 여부가 아니라 **diff** |
| (없음) | **`istioctl experimental check-inject`** | 사이드카 미주입 원인 특정 |
| Gateway + VirtualService | **Gateway API**: 리소스 `status.conditions` 먼저 | 단, `proxy-config route` 교차 확인은 여전히 필요 |
| `kubectl sniff` (ksniff) | **`kubectl debug --target=istio-proxy`** | krew 불필요, arm 제약 없음, 권한 격상 불필요 |

> **바뀌지 않은 것이 더 중요합니다.** 응답 플래그(`UT/UH/NR/UC/DC`), xDS 4단계, `reporter=source/destination` 대비, 커넥션 ID로 요청 생애주기를 좇는 법 — **이 장의 사고방식은 앰비언트에서도 그대로 씁니다.** 바뀐 건 명령어 이름과 프록시가 있는 위치뿐입니다.
