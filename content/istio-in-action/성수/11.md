## 11.1 컨트롤 플레인의 주요 목표

> **"데이터 플레인을 원하는 상태(desired state)로 동기화하는 것"** — 이 한 문장이 컨트롤 플레인의 존재 이유입니다.

![컨트롤 플레인은 Istio 커스텀 리소스와 쿠버네티스 이벤트를 받아 프록시(엔보이)로 싱크한다](images/notes/istio-in-action/11-1.avif)

컨트롤 플레인은 서비스 메시의 **"뇌"** 입니다. 입력은 크게 두 갈래입니다.

| 입력 | 무엇 | 특징 |
| --- | --- | --- |
| **① 메시 운영자 API** | Gateway, VirtualService, DestinationRule … (part4\~9에서 다룬 것들) | 사람이 **의도적으로** 바꿈 |
| **② 쿠버네티스 이벤트** | 서비스 디스커버리, 파드 상태, 오토스케일링 이벤트 등 런타임 환경 변화 | **끊임없이, 예측 불가능하게** 바뀜 |

지금까지는 주로 ①을 다뤘지만, 성능 관점에서 더 무서운 건 ②입니다. istiod는 쿠버네티스 이벤트를 **watch** 하면서 새 원하는 상태를 **지속적으로** 메시 설정에 반영해야 하고, 이 과정에는 언제든 **타이밍 이슈**가 끼어듭니다.

### 유령 워크로드(phantom workload)

![이미 죽은 워크로드인데 살아 있는 줄 알고 트래픽을 보내는 상황](images/notes/istio-in-action/11-2.avif)

- 컨트롤 플레인에 **일시적 장애**가 나거나 업데이트가 **지연**되면 → 프록시는 **stale(오래된) 설정**을 계속 들고 있게 됩니다.
- stale 설정 → **이미 제거된 엔드포인트로 트래픽을 라우팅** → 이게 **유령 워크로드**입니다.
- 이스티오가 비정상 워크로드로 라우팅을 결정하는 시점과, 쿠버네티스가 그 워크로드를 정리하는 이벤트 사이에 **미묘한 타이밍 차이**가 있기 때문입니다.

> **데이터 플레인은 궁극적 일관성(eventually consistent)** 입니다 — part10 10.2.1에서 본 그 문장입니다. stale 설정은 **없앨 수 없고, 언제든 생깁니다.** 그래서 part6(복원력)에서 이미 두 가지 안전장치를 배웠습니다.
> ① **retry** — 다른 정상 엔드포인트로 다시 보내기<br>② **outlier detection** — 실패한 엔드포인트를 클러스터에서 빼기

### 11.1.1 데이터 플레인 동기화 단계 이해하기

동기화를 한 줄로 요약하면 **이벤트 수신 → 엔보이 설정으로 변환 → 프록시로 푸시** 입니다. 조금 더 쪼개보면 이렇습니다.

![그림 11.2 최신 설정을 워크로드로 푸시하는 일련의 단계](images/notes/istio-in-action/11-3.avif)

| 단계 | 하는 일 |
| --- | --- |
| **1. Incoming event** | 쿠버네티스 API 서버에서 이벤트가 들어와 동기화가 **트리거**됨 |
| **2. Debounce** | istiod의 Discovery server가 이벤트를 받자마자 큐에 넣지 **않고**, 정해진 시간 동안 **후속 이벤트를 모아 병합(batch & merge)** 함 |
| **3. Add to queue** | 디바운스가 끝난 이벤트를 푸시 큐에 추가 |
| **4. Throttle** | 큐에서 **변환 단계로 넘어가는 양을 조절** — 동시에 처리하는 푸시 수 제한 |
| **(Convert)** | 그림에는 생략됐지만 **이벤트 → 엔보이 설정 변환**이 핵심 작업. 쓰로틀링의 목적도 이 단계의 CPU 부하 조절 |
| **5. Push** | 변환된 엔보이 설정을 각 워크로드로 푸시 |

> **디바운스를 비유하면** — 토글 버튼을 연타하는 사용자를 생각해보세요. 클릭마다 처리하지 않고 **잠깐 기다렸다가 마지막 상태만 한 번 판정**하면 시스템 부담이 줄어듭니다. 이벤트도 "생겼다 → 지워졌다 → 다시 생겼다"처럼 **와리가리** 할 수 있으니, 모아서 중복을 없애고 한 번에 처리하는 겁니다.

### 11.1.2 성능을 결정짓는 요소

![그림 11.3 컨트롤 플레인 성능에 영향을 주는 요소](images/notes/istio-in-action/11-4.avif)

| 요소 | 질문 |
| --- | --- |
| **변화율** (Rate of changes) | 이벤트가 **자주, 많이** 발생하나? |
| **할당된 리소스** (Allocated resources) | 처리량 대비 istiod **CPU/메모리가 충분**한가? |

> **이 네 개가 11.3의 튜닝 레버와 1:1로 대응합니다.** 변화율 → 이벤트 무시·배치 / 리소스 → 스케일 업·아웃 / 설정 크기·워크로드 수 → Sidecar 리소스. 먼저 **어디가 병목인지** 봐야 레버를 고를 수 있으니, 다음은 모니터링입니다.

### 11.2.1 컨트롤 플레인의 네 가지 황금 신호

**Latency, Saturation, Traffic, Errors** 순서로 봅니다.

#### ① LATENCY — 데이터 플레인 업데이트에 걸리는 시간

> 레이턴시는 **엔드유저 시각의 외부 뷰**입니다. "느리다"는 건 알려주지만 **왜 느린지는 알려주지 않습니다.** 원인은 다른 신호와 같이 봐야 합니다.

컨트롤 플레인은 **업데이트를 데이터 플레인에 배포하는 데 걸리는 시간**을 세 구간으로 측정합니다.

![그림 11.4 메트릭별로 측정하는 레이턴시 구간](images/notes/istio-in-action/11-5.avif)

| 번호 | 메트릭 | 측정 구간 |
| --- | --- | --- |
| ① | `pilot_proxy_convergence_time` | **전체** — 푸시 요청이 큐에 들어간 뒤 워크로드에 배포될 때까지 (그라파나 **Proxy Push Time** 패널) |
| ② | `pilot_proxy_queue_time` | **큐에서 대기**한 시간 |
| ③ | `pilot_xds_push_time` | 엔보이 설정을 **실제로 푸시**하는 데 걸린 시간 |

```plain text
# ① Proxy Push Time
histogram_quantile(0.5,   sum(rate(pilot_proxy_convergence_time_bucket[1m])) by (le))
histogram_quantile(0.9,   sum(rate(pilot_proxy_convergence_time_bucket[1m])) by (le))
histogram_quantile(0.99,  sum(rate(pilot_proxy_convergence_time_bucket[1m])) by (le))
histogram_quantile(0.999, sum(rate(pilot_proxy_convergence_time_bucket[1m])) by (le))
```

![Proxy Push Time (pilot_proxy_convergence_time)](images/notes/istio-in-action/11-6.avif)

```plain text
histogram_quantile(0.9,   sum(rate(pilot_proxy_queue_time_bucket[1m])) by (le))
histogram_quantile(0.99,  sum(rate(pilot_proxy_queue_time_bucket[1m])) by (le))
```

![Proxy Queue Time — 히스토그램 모양이 Proxy Push Time과 비슷하다](images/notes/istio-in-action/11-7.avif)

```plain text
histogram_quantile(0.5,   sum(rate(pilot_xds_push_time_bucket[1m])) by (le))
histogram_quantile(0.9,   sum(rate(pilot_xds_push_time_bucket[1m])) by (le))
histogram_quantile(0.99,  sum(rate(pilot_xds_push_time_bucket[1m])) by (le))

```

![xDS Push Time — 99분위수가 10ms 이내](images/notes/istio-in-action/11-8.avif)

> **읽는 법.** Queue Time이 Push Time과 비슷한 모양이라는 건 **전체 지연의 대부분이 큐 대기**라는 뜻입니다. 실제 푸시(③)는 10ms 이내로 빠릅니다. 즉 이 환경에서 느려진다면 **푸시 자체가 아니라 큐에 쌓이는 쪽**을 먼저 의심해야 합니다.

워크로드가 늘수록 이 레이턴시는 **점진적으로 증가**합니다. 약간의 증가는 괜찮지만 **임계값을 정해 알람**을 거는 것이 좋습니다. 책의 권장값은 다음과 같습니다.

| 수준 | 조건 |
| --- | --- |
| **Warning** | **10초 이상** 동안 레이턴시가 **1초 초과** |
| **Critical** | **10초 이상** 동안 레이턴시가 **2초 초과** |

> 첫 알람에 당황할 필요는 없습니다 — **"성능 최적화가 필요하다"는 신호**일 뿐입니다. 다만 방치하면 엔드유저가 영향을 받습니다. **레이턴시는 성능 저하를 가장 잘 알려주는 지표지만, 근본 원인은 알려주지 않는다**는 점을 기억하세요.

#### ② SATURATION — 컨트롤 플레인에 리소스 여유가 있나?

**포화도**는 리소스 사용률입니다. 사용률이 **90% 이상**이면 포화 상태로 봅니다. istiod가 포화되면 푸시 요청이 **큐에서 오래 대기** → 업데이트 배포가 느려집니다(= ①의 Queue Time이 늘어남).

포화는 보통 **가장 부족한 리소스**에서 먼저 옵니다. **istiod는 CPU 집약적**이라 대부분 **CPU가 먼저** 포화됩니다.

| 메트릭 | 집계 주체 |
| --- | --- |
| `container_cpu_usage_seconds_total` | 쿠버네티스 컨테이너 기준 CPU 사용률 |
| `process_cpu_seconds_total` | istiod 자체 계측 기준 CPU 사용률 |

> **"선최적화, 후리소스."** 포화됐다고 바로 리소스를 늘리지 말고, **컨트롤 플레인 동작을 먼저 최적화**(11.3)해본 뒤에도 안 되면 리소스를 늘리는 것이 최선일 수 있습니다.

#### ③ TRAFFIC — 컨트롤 플레인에 걸리는 부하는?

웹 앱의 부하는 RPS 하나로 보지만, **컨트롤 플레인은 들어오는 쪽과 나가는 쪽을 둘 다** 봐야 합니다.

| 방향 | 무엇 | 메트릭 |
| --- | --- | --- |
| **incoming** | 설정 변경에 따른 **이벤트 유입** | `pilot_inbound_updates` — 초당 들어오는 설정 업데이트 수<br>`pilot_push_triggers` — 푸시를 트리거한 이벤트 총수 (유형: service, endpoint, config)<br>`pilot_services` — pilot이 관리하는 서비스 수 (**서비스가 많을수록 이벤트당 처리량 증가**) |
| **outgoing** | 데이터 플레인으로 **업데이트 푸시** | `pilot_xds_pushes` — 모든 푸시 유형(listener, route, cluster, endpoint)<br>`pilot_xds` — pilot 인스턴스당 관리하는 워크로드 커넥션 수<br>`envoy_cluster_upstream_cx_tx_bytes_total` — 전송된 설정 크기 |

![envoy_cluster_upstream_cx_tx_bytes_total — 워크로드로 전송된 설정 크기](images/notes/istio-in-action/11-9.avif)

**방향을 구분해야 대처법이 갈립니다.** 이게 트래픽 신호의 핵심입니다.

| 포화 원인 | 병목 | 대처 |
| --- | --- | --- |
| **incoming** 트래픽 | 변화율(rate of changes) | 이벤트 **배치 처리를 늘리기**, 또는 **스케일 업** |
| **outgoing** 트래픽 | istiod 한 대가 맡은 워크로드 수 | **스케일 아웃**해서 istiod 인스턴스당 워크로드 수를 줄이기 |

#### ④ ERRORS — 컨트롤 플레인의 실패율은?

에러는 포화·성능 저하 상황에서 **항상** 따라옵니다. 가장 중요한 에러 메트릭은 다음과 같습니다.

| 메트릭 | 의미 |
| --- | --- |
| `pilot_total_xds_rejects` | 엔보이가 **거부(reject)한 설정 푸시** 수. 하위 집계로 `pilot_xds_eds_reject`, `pilot_xds_lds_reject`, `pilot_xds_rds_reject`, `pilot_xds_cds_reject` |
| `pilot_xds_write_timeout` | 푸시를 시작하다 **에러·타임아웃**이 난 수 |
| `pilot_xds_push_context_errors` | 엔보이 설정 **생성 중** pilot 에러 수 (대부분 **버그**에 기인) |

> **part10과 연결됩니다.** `xds_rejects` 가 오른다면 part10 10.2.1의 **STALE**(보냈는데 확인 못 받음)을 의심하고, `istioctl proxy-status` 로 어떤 프록시가 거부했는지 좁혀가면 됩니다. LDS/RDS/CDS/EDS 구분도 그대로입니다.

#### Sidecar 리소스

사이드카 프록시의 **인바운드/아웃바운드 설정 범위를 세밀하게 제한**하는 커스텀 리소스입니다.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: Sidecar
metadata:
  name: default
  namespace: istioinaction
spec:
  workloadSelector:
    labels:
      app: foo
  egress:
  - hosts:
    - "./bar.istioinaction.svc.cluster.local"
    - "istio-system/*"
```

| 필드 | 의미 |
| --- | --- |
| `workloadSelector` | 이 설정을 **적용할 워크로드**를 제한 |
| `ingress` | 애플리케이션으로 **들어오는** 트래픽 처리. 생략하면 파드 정의를 보고 자동 설정 |
| `egress` | 사이드카를 거쳐 **나가는** 트래픽 처리. 생략하면 더 일반적인 Sidecar(네임스페이스·메시 범위)의 설정을 **상속**하고, 그것도 없으면 **모든 서비스 접근** 기본 동작 |
| `outboundTrafficPolicy` | 아웃바운드 처리 모드 — `REGISTRY_ONLY`(등록된 곳만) / `ALLOW_ANY`(전부 허용) |

> **효과.** Sidecar를 설정하면 istiod가 **각 프록시에 관련된 설정만 골라** 보냅니다. "모든 서비스에 가는 법"을 전 사이드카에 일괄 생성·배포하지 않으니 **CPU·메모리·네트워크 대역폭**이 함께 줄어듭니다.

#### 메시 범위(mesh-wide) Sidecar 설정

**기본값을 최소로 깔아둡니다.** istio-system 네임스페이스에 Sidecar를 두면 메시 전체의 기본값이 되고, 모든 프록시가 **컨트롤 플레인에 붙는 데 필요한 최소 설정만** 갖게 됩니다.

![위: mesh-wide 설정 없이 모든 데이터 플레인이 서로를 앎 / 아래: REGISTRY_ONLY egress로 컨트롤 플레인만 앎](images/notes/istio-in-action/11-14.avif)

```yaml
# ch11/sidecar-mesh-wide.yaml
apiVersion: networking.istio.io/v1beta1
kind: Sidecar
metadata:
  name: default
  namespace: istio-system   # istio-system에 두면 mesh-wide 범위
spec:
  egress:
  - hosts:
    - "istio-system/*"      # istio-system 네임스페이스
    - "prometheus/*"        # prometheus 네임스페이스
  outboundTrafficPolicy:
    mode: REGISTRY_ONLY     # 등록된 곳만 허용
```

```bash
kubectl -n istio-system apply -f ch11/sidecar-mesh-wide.yaml

# 설정 크기 다시 측정
CATALOG_POD=$(kubectl -n istioinaction get pod -l app=catalog -o jsonpath={.items..metadata.name} | cut -d ' ' -f 1)
kubectl -n istioinaction exec -ti $CATALOG_POD -c catalog -- curl -s localhost:15000/config_dump > /tmp/config_dump
du -sh /tmp/config_dump
```

```plain text
516K    /tmp/config_dump
```

```bash

  --prom-url prometheus.istio-system.svc.cluster.local:9090
```

```plain text

Push count: 70                                  # <-- 514
Latency in the last minute: 0.0990 seconds      # <-- 0.10 seconds
```

| 지표 | 최적화 전 | mesh-wide Sidecar 후 |
| --- | --- | --- |
| 설정 크기 (catalog 1개) | **2.3M** | **516K** (약 1/4) |
| Push count | **514** | **70** (약 1/7) |

> **Sidecar 한 장으로 가장 큰 효과가 났습니다.** mesh-wide Sidecar는 성능뿐 아니라 **메시 운영 비용 절감**에도 도움이 되고, **워크로드별로 egress를 명시적으로 정의하는 것은 좋은 습관**입니다. 단, `REGISTRY_ONLY` 를 메시 기본값으로 걸면 **egress를 명시하지 않은 워크로드는 통신이 막히므로** 네임스페이스·워크로드 단위 Sidecar를 함께 설계해야 합니다.

### 11.3.3 이벤트 무시하기: 디스커버리 셀렉터로 디스커버리 범위 줄이기

> **놀랍게도 기본값은 "클러스터의 모든 네임스페이스, 모든 쿠버네티스 리소스"를 watch 합니다.** 메시에 들어오지도 않은 네임스페이스의 이벤트까지 istiod가 처리하고 있다는 뜻입니다.

**Istio 1.10+** 의 `meshConfig.discoverySelectors` 로 **watch 범위 자체를 줄입니다.** Sidecar가 "보낼 설정"을 줄였다면, 이건 "받는 이벤트"를 줄입니다.

```yaml
# 방법 ① 포함 방식 — 레이블이 붙은 네임스페이스만 watch
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  namespace: istio-system
spec:
  meshConfig:
    discoverySelectors:
      - matchLabels:
          istio-discovery: enabled
```

```yaml
# 방법 ② 제외 방식 — istio-exclude=true 인 네임스페이스만 빼고 watch
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  namespace: istio-system
spec:
  meshConfig:
    discoverySelectors:
      - matchExpressions:
        - key: istio-exclude
          operator: NotIn
          values:
            - "true"
```

```bash
istioctl install -y -f ch11/istio-discovery-selector.yaml

# 제외할 네임스페이스에 레이블
kubectl label ns new-namespace istio-exclude=true
```

> **어느 방식을 고를까.** ①은 새 네임스페이스가 **기본으로 제외**되니 안전하지만 메시에 넣을 때마다 레이블을 잊지 말아야 합니다. ②는 기존 동작(전부 watch)을 유지하면서 **무거운 네임스페이스만 골라 빼는** 방식이라 이미 운영 중인 메시에 적용하기 쉽습니다.

### 11.3.4 이벤트 배치 처리 및 푸시 스로틀링 속성

#### 배치 기간 늘리기

11.1.1의 **Debounce** 단계를 조절해 **푸시 횟수**를 줄이는 전략입니다. 배치 기간 동안 이벤트를 병합해 중복을 없애면 큐에 들어가는 이벤트 수가 줄어듭니다.

![Debounce 단계(Discovery server)에서 이벤트를 모아 병합한다](images/notes/istio-in-action/11-15.avif)

| istiod 환경 변수 | 의미 | 기본값 |
| --- | --- | --- |
| `PILOT_DEBOUNCE_AFTER` | 이벤트를 큐에 넣기 전 **대기 시간**. 이 시간 안에 새 이벤트가 없으면 큐에 추가, 있으면 **병합 후 다시 대기** | **100ms** |
| `PILOT_DEBOUNCE_MAX` | 디바운스를 허용하는 **최대 시간**. 계속 이벤트가 와도 이 시간이 지나면 푸시 | **10s** |
| `PILOT_ENABLE_EDS_DEBOUNCE` | **엔드포인트 업데이트**도 디바운스할지 여부 | **true** |
| `PILOT_PUSH_THROTTLE` | istiod가 **동시에 처리하는 푸시 요청 수** | **100** |

```bash
istioctl install --set profile=demo --set values.pilot.env.PILOT_DEBOUNCE_AFTER="2500ms"

# 적용 확인
kubectl get deploy/istiod -n istio-system -o yaml | grep -A1 PILOT_DEBOUNCE_AFTER
#   - name: PILOT_DEBOUNCE_AFTER
#     value: 2500ms
```

```bash
bin/performance-test.sh --reps 10 --delay 2.5 \
  --prom-url prometheus.istio-system.svc.cluster.local:9090
```

```plain text

Push count: 63                                   # <-- 70
Latency in the last minute: 0.0990 seconds
```

#### ⚠️ 레이턴시 메트릭에는 디바운스 기간이 포함되지 않습니다

![전체 레이턴시(①) = 큐 대기(②) + 푸시(③). 디바운스는 큐에 들어가기 전이라 어느 구간에도 안 잡힌다](images/notes/istio-in-action/11-16.avif)

- 레이턴시 메트릭은 **푸시 큐에 들어간 시점부터** 잽니다.
- 디바운스 기간 동안에는 업데이트가 **아예 전송되지 않습니다.**
- 그래서 실제로는 업데이트가 **더 늦게 도착**하는데도 **레이턴시 그래프에는 안 나타납니다.**
- 디바운스로 늘어난 지연은 **stale 설정**과 **성능 저하**를 부를 수 있으므로 → **배치 설정은 조금씩만** 조정하세요.

> **함정입니다.** 배치 기간을 늘리면 Push count가 줄고 레이턴시 그래프도 멀쩡해서 "좋아졌다"고 착각하기 쉽습니다. 하지만 **11.1의 유령 워크로드 창이 그만큼 넓어진 것**입니다. part6의 retry·outlier detection이 그 창을 메워주고 있는지 함께 봐야 합니다.
> **엔드포인트 반영이 늦는 게 문제라면** `PILOT_ENABLE_EDS_DEBOUNCE=false` 로 **엔드포인트 업데이트만 디바운스를 건너뛰게** 할 수 있습니다. 설정 변경은 모아서 보내되, 파드가 죽고 뜨는 건 바로 반영하는 절충입니다.

#### 컨트롤 플레인에 리소스 추가 할당하기

```bash
istioctl install --set profile=demo \
  --set values.pilot.resources.requests.cpu=1000m \
  --set values.pilot.resources.requests.memory=1Gi \
  --set values.pilot.replicaCount=2
```

- **`replicaCount` ↑ = 스케일 아웃** → outgoing 트래픽 포화 대응 (istiod당 워크로드 수 분산)
- **`resources.requests` ↑ = 스케일 업** → incoming 트래픽 포화 대응 (설정 생성 속도·동시 푸시 처리량)

## 11.4 성능 튜닝 가이드라인

> **이스티오는 원래 성능이 좋습니다.** 책에 인용된 공식 테스트 결과: **Istio Pilot 1.13.4 한 대(1 vCPU / 1.5GB 메모리)** 가 **쿠버네티스 서비스 1,000개**, **워크로드(사이드카) 2,000개**, **70,000 rps** 를 처리했습니다. 프로덕션 권장 스펙은 **2 vCPU / 2GB, 레플리카 3개** 입니다.

| 원칙 | 내용 |
| --- | --- |
| **1. 성능 문제가 맞는지부터** | 데이터 플레인 ↔ 컨트롤 플레인 **연결 상태**를 확인하고, kube-apiserver 같은 **플랫폼 문제**가 아닌지 봅니다. **Sidecar 리소스가 범위별로 제대로 걸려 있는지**도 먼저 확인합니다. |
| **2. 병목을 식별** | 네 가지 황금 신호로 판단합니다.<br>예1) **레이턴시는 높은데 리소스는 여유** → 푸시 동시성(`PILOT_PUSH_THROTTLE`) ↑<br>예2) **이벤트 폭주 시 리소스 부족** → istiod 수 ↑ 또는 배치(debounce) 기간 ↑ |
| **3. 점진적으로 변경** | 디바운스 조정은 stale 설정을 부를 수 있으므로 **10\~30% 범위에서 미세 조정**하고, **1\~2일 모니터링**하며 조금씩 늘리거나 줄입니다. |
| **4. 안전 우선** | istiod는 **메시 전체 네트워크를 관리**하므로 다운타임이 곧 통신 장애입니다. **레플리카 2개 이상**을 유지하고 보수적으로 운영합니다. |
| **5. Burstable QoS 고려** | istiod는 **항상 CPU를 쓰지 않고**, 이벤트 폭주 같은 **피크 때만 몰아서** 씁니다. requests와 limits를 같게 두는 Guaranteed보다 **Burstable**이 특성에 맞습니다. |

### Sidecar 적용 범위

| 범위 | 위치 | 우선순위 |
| --- | --- | --- |
| **mesh-wide** | istio-system 네임스페이스, `workloadSelector` 없음 | 가장 낮음 (기본값) |
| **namespace-wide** | 해당 네임스페이스, `workloadSelector` 없음 | mesh-wide를 덮어씀 |
| **workload-specific** | 해당 네임스페이스, `workloadSelector` 있음 | **가장 높음** — 위 둘을 모두 덮어씀 |

### 네 가지 황금 신호 대조표

| 신호 | 핵심 메트릭 | 이상하면 |
| --- | --- | --- |
| **Latency** | `pilot_proxy_convergence_time`, `pilot_proxy_queue_time`, `pilot_xds_push_time` | 1초(Warning)/2초(Critical) 10초 지속 시 알람. 원인은 다른 신호로 |
| **Saturation** | `container_cpu_usage_seconds_total`, `process_cpu_seconds_total` | 90%↑ 포화. 먼저 최적화, 그래도 안 되면 리소스 |
| **Traffic** | in: `pilot_inbound_updates`, `pilot_push_triggers`, `pilot_services`<br>out: `pilot_xds_pushes`, `pilot_xds`, `envoy_cluster_upstream_cx_tx_bytes_total` | incoming 원인 → 배치↑·스케일 업 / outgoing 원인 → 스케일 아웃 |
| **Errors** | `pilot_total_xds_rejects`, `pilot_xds_write_timeout`, `pilot_xds_push_context_errors` | reject → `proxy-status` 로 STALE 프록시 추적 (part10) |

### 헷갈리는 짝 대조표

| 짝 | 무엇이 다른가 |
| --- | --- |
| **Sidecar** vs **discoverySelectors** | **보내는 설정**을 줄임(프록시별) vs **받는 이벤트**를 줄임(istiod 전체) |
| **스케일 업** vs **스케일 아웃** | istiod 한 대를 **세게**(incoming 포화) vs istiod를 **여러 대로**(outgoing 포화) |
| **Debounce** vs **Throttle** | 큐에 **넣기 전**에 모음(푸시 횟수↓) vs 큐에서 **꺼내는 속도** 제한(동시 처리량 조절) |
| **convergence_time** vs **xds_push_time** | 큐 대기 + 푸시 **전체** vs **푸시만**. 둘 다 **디바운스 시간은 포함 안 함** |
| **`REGISTRY_ONLY`** vs **`ALLOW_ANY`** | 등록된 서비스만 나갈 수 있음 vs 어디든 나갈 수 있음 |

### 컨트롤 플레인 튜닝 치트시트

```bash
# 0. 대시보드와 원본 메트릭
istioctl dashboard grafana                       # Istio Control Plane Dashboard
kubectl exec -it -n istio-system deploy/istiod -- curl localhost:15014/metrics

# 1. 프록시 하나가 받는 설정 크기
kubectl -n <ns> exec -ti <pod> -c <app> -- curl -s localhost:15000/config_dump > /tmp/config_dump
du -sh /tmp/config_dump

# 2. mesh-wide Sidecar로 기본 egress 최소화
kubectl -n istio-system apply -f ch11/sidecar-mesh-wide.yaml

# 3. watch 범위 줄이기 (discoverySelectors)
istioctl install -y -f ch11/istio-discovery-selector.yaml
kubectl label ns <ns> istio-exclude=true

# 4. 배치 기간 조정 (10~30%씩, 1~2일 관찰)
istioctl install --set profile=demo --set values.pilot.env.PILOT_DEBOUNCE_AFTER="2500ms"
kubectl get deploy/istiod -n istio-system -o yaml | grep -A1 PILOT_

# 5. 리소스 (스케일 업 + 스케일 아웃)
istioctl install --set profile=demo \
  --set values.pilot.resources.requests.cpu=1000m \
  --set values.pilot.resources.requests.memory=1Gi \
  --set values.pilot.replicaCount=2

# 6. 측정
bin/performance-test.sh --reps 10 --delay 2.5 \
  --prom-url prometheus.istio-system.svc.cluster.local:9090
```
