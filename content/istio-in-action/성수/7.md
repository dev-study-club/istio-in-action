## 들어가며 — 관찰 가능성(Observability)이란

![관찰 가능성과 제어의 관계](images/notes/istio-in-action/7-1.avif)

**외부 신호와 특성만 보고도 시스템의 내부 상태를 이해하고 추론할 수 있는 수준**을 말합니다. 이 개념은 루돌프 칼만(Rudolf E. Kalman)이 1960년 논문 「제어 시스템의 일반 이론에 관해」에서 발표한 **제어 이론**에 뿌리를 두고 있습니다. 시스템이 잘 동작할 때를 이해해야 문제가 생겼을 때 판단할 수 있고, 적절한 수준의 자동·수동 제어를 구현할 수 있기 때문입니다.

이스티오의 데이터 플레인은 **시스템을 거쳐가는 요청의 동작에 영향을 미치는 위치**에 있습니다. 트래픽 전환·복원력·정책 강제 같은 제어를 구현할 수 있지만, **어떤 제어를 언제 써야 할지 알려면 먼저 무슨 일이 일어나고 있는지 이해**해야 합니다. 그래서 메트릭을 수집하는 이스티오의 기능도 같은 계층(애플리케이션 요청의 네트워크 수준)에 있습니다.

> **주의:** 관찰 가능성은 기성 솔루션이 아니라 **시스템의 특성**입니다. 애플리케이션 계측, 네트워크 계측, 시그널 수집 인프라, 데이터베이스, 그리고 예기치 못한 일이 벌어졌을 때 방대한 데이터를 추리고 결합해 전체 그림을 그려내는 방법까지 포함해야 합니다. **이스티오는 그중 '애플리케이션 수준 네트워크 계측'을 보조할 뿐입니다.**

## 7.1 관찰 가능성이란 무엇인가?

### 7.1.1 관찰 가능성 vs 모니터링

**모니터링**은 메트릭·로그·트레이스를 수집·집계하고, 시스템 상태를 **미리 정의한 기준과 비교**하는 관행입니다. 예를 들어 DB 인스턴스의 디스크 사용량을 집계해두었다가 용량에 가까워지면 경보를 울리고 조치를 시작합니다.

| 구분 | 모니터링 (Monitoring) | 관찰 가능성 (Observability) |
| --- | --- | --- |
| 전제 | 바람직하지 않다고 **알려진** 상태가 있다 | 시스템은 예측하기 어렵고, **모든 고장을 사전에 알 수는 없다** |
| 데이터 | 미리 정의한 메트릭을 수집·집계 | 훨씬 더 많은 데이터. 사용자 ID·요청 ID·소스 IP 등 **카디널리티가 높은 데이터**까지 |
| 치르는 대가 | 시계열 수가 예측 가능 | **카디널리티 폭발** 위험 — 저장·쿼리 비용이 급증 |
| 사용 방식 | 임계값 비교 → 경고 | 도구로 **빠르게 탐색하고 질문** |
| 관계 | 관찰 가능성의 **부분집합** | 모니터링을 **포함하는 상위 개념** |

> **카디널리티(cardinality)란:** 라벨 값 조합의 가지수입니다. **조합 하나가 시계열 하나**가 되므로, 사용자 ID처럼 값이 수만 가지인 라벨을 붙이면 시계열이 폭발합니다. **이 단어가 이번 장 전반을 관통합니다** — 이스티오가 엔보이 통계를 기본적으로 잘라내는 이유(7.2.1), 디멘션을 함부로 늘리면 안 되는 이유(7.4.1)가 전부 여기서 나옵니다.
>
> **왜 이 차이가 중요한가:** 사용자 ID 400000021인 홍길동이 결제 옵션을 고를 때 10초의 지연을 겪었다고 해봅시다. 미리 정의해둔 임계값(디스크 사용량, 대기열 깊이, 머신 상태)은 **전부 정상**일 수 있지만 사용자는 무척 짜증이 났습니다. 관찰 가능성을 염두에 두고 설계했다면 **서비스의 여러 계층을 살펴보고 그 요청이 실제로 거쳐간 경로를 정확히 확인**할 수 있습니다.

### 7.1.2 이스티오는 어떻게 관찰 가능성을 돕는가?

이스티오는 관찰 가능한 시스템을 구축하는 데 **독특한 위치**에 있습니다. 데이터 플레인 프록시인 **엔보이가 서비스 간 네트워크 요청 경로에 그대로 자리**하고 있기 때문입니다.

- **중요 메트릭 포착:** 초당 요청 수, 요청 처리 시간(백분위수), 실패한 요청 수 등
- **새 메트릭 동적 추가:** 미처 생각하지 못했던 정보를 나중에 포착할 수 있습니다.
- **분산 트레이싱:** 요청이 어떤 서비스를 거쳤고 각 노드에서 얼마나 걸렸는지 → **8장**에서 다룹니다.
- **시각화 도구:** 프로메테우스·그라파나·키알리 기본 샘플이 포함돼 있습니다.

> **참고:** 2장에서 데모용으로 설치했던 기본 샘플 애드온(프로메테우스/그라파나/키알리)은 **삭제**하고, 이번 장부터는 좀 더 현실적인 설정(kube-prometheus-stack)을 사용합니다.

## 7.2 이스티오 메트릭 살펴보기

데이터 플레인은 요청을 처리하고, 컨트롤 플레인은 데이터 플레인이 요청을 처리하도록 설정합니다. **둘 다 메트릭이 아주 방대**하므로 각각 어떤 메트릭을 쓸 수 있는지 살펴봅니다.

### 7.2.1 데이터 플레인의 메트릭

엔보이는 커넥션·요청·런타임 메트릭을 다양하게 갖추고 있습니다. 사이드카 프록시가 유지하는 통계를 직접 쿼리해봅니다.

```bash
# 프록시가 보관하는 정보는 훨씬 더 많지만, 카디널리티 문제 때문에 대부분은 기본적으로 제거됩니다
# grep 없이 돌리면 수천 줄이 쏟아지니 반드시 걸러서 보세요
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- curl -s localhost:15000/stats | grep istio_requests_total
```

> **아래 출력은 가독성을 위해 줄바꿈한 것**입니다. 실제 엔보이 `/stats`는 이 디멘션들을 `;.;` 구분자로 이어붙인 **한 줄**로 뱉습니다.

```plain text
destination_service=.=webapp.istioinaction.svc.cluster.local;.;
destination_service_name=.=webapp;.;
destination_service_namespace=.=istioinaction;.;
request_protocol=.=http;.;response_flags=.=-;.;
connection_security_policy=.=mutual_tls;.;response_code=.=200;.;
destination_cluster=.=Kubernetes;.;source_cluster=.=Kubernetes;.;
istio_requests_total: 2
```

가장 중요한 부분은 마지막 `istio_requests_total`입니다. 나머지를 읽어보면 이것이 **인그레스 게이트웨이에서 webapp 서비스로 들어오는 요청**에 대한 메트릭이며 그 요청이 총 2개임을 알 수 있습니다.

**각 프록시가 인바운드/아웃바운드 호출에 유지하는 표준 이스티오 메트릭**

| 메트릭 | 타입 | 설명 |
| --- | --- | --- |
| istio_requests_total | COUNTER | 이스티오 프록시가 처리한 요청마다 증가 |
| istio_request_bytes | DISTRIBUTION | HTTP 요청 바디 크기의 분포 |
| istio_response_bytes | DISTRIBUTION | HTTP 응답 바디 크기의 분포 |
| istio_request_duration_milliseconds | DISTRIBUTION | 요청 지속 시간의 분포 |

> **COUNTER는 엄격하게 증가하는 정수**, **DISTRIBUTION은 값의 범위를 빈도에 매핑**합니다. 텔레메트리 구성 요소는 **Proxy-wasm 플러그인**(엔보이에 기능을 꽂는 확장 메커니즘 — 자세히는 7.4.1)으로 구현돼 있습니다.
>
> **distroless 이미지를 쓴다면:** 최소 종속성 이미지에는 `curl`이 없습니다. `pilot-agent request`로 대체하세요.

```bash
istioctl install --set values.global.variant=distroless
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- pilot-agent request GET /stats
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- pilot-agent request GET /stats/prometheus
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- pilot-agent request GET /clusters
# 혹은 디버그 컨테이너 주입
kubectl debug --image istio/base --target istio-proxy -it <pod>
```

**프록시가 엔보이 통계를 더 많이 보고하도록 설정하기**

표준 이스티오 메트릭보다 더 많은 정보가 필요할 때가 있습니다. 애플리케이션 호출이 클라이언트 측 프록시를 거쳐갈 때 프록시는 라우팅 결정을 내리고 **업스트림 클러스터**(로드밸런싱·보안·서킷브레이커 설정을 적용해 실제 호출되는 서비스)로 보냅니다. 여기서는 `webapp` → `catalog` 호출의 추가 정보를 활성화합니다.

**방법 1 — IstioOperator: 메시 전체에 적용**

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  name: control-plane
spec:
  profile: demo
  meshConfig:
    defaultConfig:              # 모든 서비스용 기본 프록시 설정
      proxyStatsMatcher:        # 보고할 메트릭 커스터마이징
        inclusionPrefixes:      # 기본 메트릭 + 이 접두사와 일치하는 메트릭
        - "cluster.outbound|80||catalog.istioinaction"
```

**방법 2 — 워크로드별 애너테이션 (권장)**

```yaml
# ch7/webapp-deployment-stats-inclusion.yaml
  template:
    metadata:
      annotations:
        proxy.istio.io/config: |-
          proxyStatsMatcher:
            inclusionPrefixes:
            - "cluster.outbound|80||catalog.istioinaction"
      labels:
        app: webapp
```

> **메시 전체에 적용할 때는 아주 신중하게.** 수집하는 메트릭을 늘리면 **메트릭 수집 시스템을 과부하 상태로 만들 수 있습니다.** 워크로드 단위 애너테이션이 더 안전한 선택입니다.

```bash
# 적용 전 확인 → 적용 → 호출테스트 → 적용 후 확인
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- curl localhost:15000/stats | grep catalog
kubectl apply -n istioinaction -f ch7/webapp-deployment-stats-inclusion.yaml
curl -s http://webapp.istioinaction.io:30000/api/catalog | jq
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- curl localhost:15000/stats | grep catalog
```

*애너테이션 적용 후의 **`grep catalog`** 결과. 갑자기 폭증한 이 항목들을 아래 ①~⑤로 나누어 읽습니다.*

**① 서킷 브레이커 작동 여부** — 업스트림 클러스터로 향하는 커넥션/요청에 서킷 브레이킹이 적용되고 있는지

```plain text
cluster.outbound|80||catalog....circuit_breakers.default.cx_open: 0
cluster.outbound|80||catalog....circuit_breakers.default.cx_pool_open: 0
cluster.outbound|80||catalog....circuit_breakers.default.rq_open: 0
cluster.outbound|80||catalog....circuit_breakers.default.rq_pending_open: 0
cluster.outbound|80||catalog....circuit_breakers.default.rq_retry_open: 0
```

**② internal / external 구분** — 엔보이는 트래픽 출처가 내부인지 외부인지를 구분합니다. **내부**는 메시 내부 트래픽, **외부**는 메시 외부에서 시작한 트래픽(인그레스 게이트웨이로 들어온 것)입니다.

```bash
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- curl localhost:15000/stats | grep catalog | grep internal
```

```plain text
cluster.outbound|80||catalog....internal.upstream_rq_200: 2
cluster.outbound|80||catalog....internal.upstream_rq_2xx: 2
cluster.outbound|80||catalog....internal.upstream_rq_completed: 2
```

**③ ssl 메트릭** — 트래픽이 TLS로 업스트림에 도달하는지, cipher·curve 등 커넥션 세부 정보를 알아내는 데 매우 유용합니다.

```plain text
cluster.outbound|80||catalog....ssl.ciphers.TLS_AES_128_GCM_SHA256: 2
cluster.outbound|80||catalog....ssl.curves.X25519: 2
cluster.outbound|80||catalog....ssl.handshake: 2
cluster.outbound|80||catalog....ssl.versions.TLSv1.3: 2
cluster.outbound|80||catalog....ssl.fail_verify_error: 0
```

**④ upstream_cx / upstream_rq** — 네트워크에서 실제로 일어나는 일에 대한 더 정확한 정보

```bash
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- curl -s localhost:15000/stats \
  | grep catalog | egrep 'local.upstream_cx|local.upstream_rq'
```

```plain text
cluster.outbound|80||catalog....upstream_cx_active: 2        # 현재 열려있는 커넥션
cluster.outbound|80||catalog....upstream_cx_total: 2         # 누적 커넥션 수
cluster.outbound|80||catalog....upstream_cx_connect_fail: 0  # 커넥션 수립 실패
cluster.outbound|80||catalog....upstream_rq_active: 0        # 처리 중인 요청
cluster.outbound|80||catalog....upstream_rq_total: 2         # 누적 요청 수
cluster.outbound|80||catalog....upstream_rq_timeout: 0       # 타임아웃된 요청
```

> **읽는 법:** `cx`는 **커넥션** 단위, `rq`는 **요청** 단위입니다. part6에서 서킷 브레이킹을 판독할 때 `upstream_cx_overflow`와 `upstream_rq_pending_overflow`를 **함께** 봐야 했던 것과 같은 계열입니다. 즉 이 메트릭들은 관찰용이기도 하지만 **복원력 설정이 실제로 어떻게 작동하는지를 검증하는 수단**이기도 합니다.

**⑤ 엔드포인트별 상세 정보** — 앞의 통계가 **클러스터 전체** 정보였다면, `/clusters`는 **엔드포인트별**로 자세한 정보를 보여줍니다.

```bash
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- curl localhost:15000/clusters | grep catalog
```

```plain text
outbound|80||catalog....::10.10.0.10:3000::cx_active::2
outbound|80||catalog....::10.10.0.10:3000::rq_success::2
outbound|80||catalog....::10.10.0.10:3000::rq_error::0
outbound|80||catalog....::10.10.0.10:3000::health_flags::healthy
outbound|80||catalog....::10.10.0.10:3000::region::
outbound|80||catalog....::10.10.0.10:3000::zone::
outbound|80||catalog....::10.10.0.10:3000::priority::0
outbound|80||catalog....::10.10.0.10:3000::success_rate::-1
```

*`/clusters` 출력. 클러스터 이름 뒤에 엔드포인트 IP:PORT가 붙고, 그 뒤로 해당 엔드포인트만의 통계가 따로 나오는 점을 보세요.*

프록시는 메트릭을 잘 수집하고 있지만, **이걸 보자고 서비스 인스턴스마다 일일이 접근할 수는 없습니다.** 그래서 프로메테우스·데이터독 같은 수집 시스템이 필요합니다(7.3절).

### 7.2.2 컨트롤 플레인의 메트릭

컨트롤 플레인 `istiod`에는 자기 동작에 대한 정보가 풍부합니다. 프록시와 설정을 동기화한 횟수, 동기화 소요 시간, 잘못된 설정, 인증서 발급/로테이션 정보 등입니다.

```bash
# istiod 파드의 LISTEN 포트 확인
kubectl exec -it deploy/istiod -n istio-system -- netstat -tnl
# 컨트롤 플레인 메트릭
kubectl exec -it -n istio-system deploy/istiod -- curl -s localhost:15014/metrics
```

```plain text
Proto Recv-Q Send-Q Local Address       Foreign Address     State
tcp        0      0 127.0.0.1:9876      0.0.0.0:*           LISTEN
tcp6       0      0 :::8080             :::*                LISTEN
tcp6       0      0 :::15010            :::*                LISTEN
tcp6       0      0 :::15012            :::*                LISTEN
tcp6       0      0 :::15014            :::*                LISTEN
tcp6       0      0 :::15017            :::*                LISTEN
```

> **이미지가 distroless라 `netstat`·`curl`이 없다면** 앞서 7.2.1에서 봤던 것처럼 `kubectl debug`로 디버그 컨테이너를 붙이거나, `kubectl port-forward deploy/istiod -n istio-system 15014` 후 로컬에서 쿼리하세요.

**위 포트들이 각각 무엇인지**

| 포트 | 용도 |
| --- | --- |

**① Citadel — 인증서 관련** (CSR: Certificate Signing Request, Citadel: 이스티오 보안 컴포넌트)

```plain text
# 컨트롤 플레인에 들어온 CSR 요청 개수

# 성공한 인증서 발급 개수
citadel_server_success_cert_issuance_count 4
```

**② 컨트롤 플레인 버전**

```plain text

```

**③ 설정 수렴 시간** — 설정을 데이터 플레인 프록시에 밀어넣고 동기화하는 데 걸린 시간의 분포입니다.

```plain text
# HELP pilot_proxy_convergence_time Delay in seconds between config change
#      and a proxy receiving all required configuration.
pilot_proxy_convergence_time_bucket{le="0.1"} 24   # 0.1초 내에 24개 업데이트가 배포됨
pilot_proxy_convergence_time_bucket{le="0.5"} 25   # 하나는 0.1~0.5초 범위
pilot_proxy_convergence_time_bucket{le="1"}   25
...
pilot_proxy_convergence_time_count 25
```

*`grep convergence` 실행 결과. 버킷이 **`le`** 오름차순으로 누적된다는 점(24 → 25 → 25 → …)을 보세요.*

**④ 메시 규모 관련**


**⑤ xDS API 업데이트 횟수** — 3장에서 다룬 CDS/EDS/LDS/RDS 각 영역의 푸시 횟수입니다.

```plain text

pilot_xds_pushes{type="rds"} 2
```

> 컨트롤 플레인 메트릭은 **11장(컨트롤 플레인 성능 튜닝)** 에서 더 깊게 다룹니다.

## 7.3 프로메테우스로 이스티오 메트릭 긁어오기

프로메테우스는 사운드클라우드에서 시작된 **메트릭 수집 엔진**이자 모니터링·얼럿 도구 집합으로, 구글의 내부 모니터링 시스템 **Borgmon**에 기반을 두고 있습니다(쿠버네티스가 Borg에 기반을 둔 것처럼).

가장 큰 차이는 **에이전트가 메트릭을 밀어넣기(push)를 기다리지 않고, 프로메테우스가 직접 당겨온다(pull)는** 점입니다. 애플리케이션이나 이스티오 서비스 프록시가 최신 메트릭을 담은 엔드포인트를 제공하면 프로메테우스가 그것을 **긁어(scrape)** 갑니다.

![프로메테우스의 pull 방식 수집](images/notes/istio-in-action/7-2.avif)

> **pull 방식의 부수 효과:** 동일한 대상을 긁어가는 프로메테우스 서버를 **여럿 띄울 수 있습니다.** 이것이 프로메테우스를 **고가용(HA)** 으로 구성하는 방법입니다.

**프로메테우스의 특징**

- 메트릭 이름 + key/value 쌍으로 식별되는 **시계열 데이터(TSDB)** 기반 다차원 데이터 모델
- **PromQL** — 이 다차원성을 활용하는 유연한 쿼리 언어
- **분산 스토리지에 의존하지 않음** — 단일 서버 노드가 자율적으로 동작
- **service discovery** 또는 static 설정으로 대상 탐색
- 짧게 살다 죽는 잡(short-lived job)은 **push gateway** 경유로 지원

![프로메테우스 공식 아키텍처](images/notes/istio-in-action/7-3.avif)

*프로메테우스 공식 아키텍처도. 가운데 Prometheus Server가 왼쪽 대상들을 pull하고, 오른쪽으로 Alertmanager·Grafana가 붙는 구조입니다. 단명 잡을 위한 Pushgateway만 예외적으로 push 방향입니다.*

**메트릭 엔드포인트 직접 확인하기** — 프로메테우스를 쓰는 이점 중 하나는 단순 HTTP 클라이언트나 브라우저만으로도 메트릭 엔드포인트를 들여다볼 수 있다는 것입니다.

```bash
# 사이드카의 LISTEN 포트 확인
kubectl exec -it deploy/webapp -n istioinaction -c istio-proxy -- netstat -tnl
# /stats 를 프로메테우스 형식으로
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- curl localhost:15090/stats/prometheus
kubectl exec -it deploy/webapp -c istio-proxy -n istioinaction -- curl localhost:15020/metrics
```

*위쪽은 **`netstat -tnl`** — 15000·15001·15006·15020·15021·15090이 떠 있습니다. 아래쪽은 15090의 **`/stats/prometheus`** 출력으로, **`# TYPE ... counter`** 형식의 프로메테우스 표기법인 점을 보세요.*

| 포트 | 역할 |
| --- | --- |
| 15090 | 엔보이 프록시 메트릭 노출 — xDS 통계, 커넥션/HTTP 통계, 이상값 감지, 헬스 체크, 서킷 브레이커 통계 등 |
| 15020 | ① **15090의 메트릭을 집계·노출** (+ 애플리케이션 메트릭, 자체 메트릭) ② 엔보이·DNS 프록시 **헬스 체크** ③ pilot-agent **디버깅** 엔드포인트 |

> **`/stats` vs `/stats/prometheus`:** `/stats`는 디버깅·모니터링용 출력이며 `/reset_counters`로 초기화할 수 있습니다. `/stats/prometheus`는 프로메테우스에 제공하기 위한 **exporter 엔드포인트**로, `/reset_counters`로 초기화할 수 없습니다.
>
> **포트가 세 개라 헷갈릴 때 — 한 줄 정리**
>
> - **15000** = 엔보이 **admin 인터페이스**. localhost 전용이고 **사람이 디버깅할 때** 씁니다(stats, clusters, reset_counters). 프로메테우스는 여기를 긁지 않습니다.
> - **15090** = 엔보이가 내놓는 **원본 exporter**. 엔보이 자기 통계만 있습니다.
> - **15020** = pilot-agent가 **15090 + 애플리케이션 메트릭 + 자체 메트릭을 머지**해 내놓는 곳. **프로메테우스가 실제로 긁는 대상은 여기입니다.** 바로 아래 PodMonitor가 15020 + /stats/prometheus 를 지정하는 이유가 그것입니다.

### 7.3.2 이스티오 컨트롤 플레인과 워크로드를 긁어가도록 프로메테우스 오퍼레이터 설정하기

프로메테우스 오퍼레이터의 커스텀 리소스 **ServiceMonitor**와 **PodMonitor**를 사용합니다.

![ServiceMonitor와 PodMonitor의 대상 차이](images/notes/istio-in-action/7-4.avif)

![프로메테우스 오퍼레이터가 설정을 대신 생성하는 흐름](images/notes/istio-in-action/7-5.avif)

*앞 그림: ServiceMonitor는 Service를, PodMonitor는 Pod를 대상으로 삼는다는 좌/우 대응 관계를 보세요. 뒤 그림: CR 생성 → 오퍼레이터가 감지 → 프로메테우스 설정을 대신 생성·리로드 하는 흐름이 이 절 전체의 전제입니다. 즉 우리는 scrape_config를 직접 손대지 않고 CR만 만듭니다.*

**① 컨트롤 플레인 수집 — ServiceMonitor**

```yaml
# ch7/service-monitor-cp.yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: istio-component-monitor
  namespace: prometheus
  labels:
    monitoring: istio-components
    release: prom
spec:
  jobLabel: istio
  targetLabels: [app]
  selector:
    matchExpressions:
    - {key: istio, operator: In, values: [pilot]}   # istiod 서비스의 istio=pilot 레이블과 매칭
  namespaceSelector:
    any: true
  endpoints:
  - port: http-monitoring    # 15014
    interval: 15s
```

```bash
# istiod 서비스에 istio=pilot 레이블과 http-monitoring(15014) 포트가 있는지 확인
kubectl describe svc istiod -n istio-system
kubectl get pod -n istio-system -l istio=pilot
# 적용 및 확인
kubectl apply -f ch7/service-monitor-cp.yaml -n prometheus
kubectl get servicemonitor -n prometheus
kubectl exec -it netshoot -- curl -s istiod.istio-system:15014/metrics | grep pilot_xds
kubectl exec -it netshoot -- curl -s istiod.istio-system:15014/metrics | grep citadel
```

이제 프로메테우스에서 컨트롤 플레인 텔레메트리를 볼 수 있습니다 — **연결된 사이드카 개수, 설정 충돌, 메시 내부 변동량, 컨트롤 플레인의 메모리/CPU 사용량**.

![프로메테우스 Targets에서 컨트롤 플레인 수집 확인](images/notes/istio-in-action/7-6.avif)

*프로메테우스 UI > Status > Targets. **`prometheus/istio-component-monitor/0 (1/1 up)`** 이 UP으로 뜨는지, Labels에 **`job="pilot"`과** **`endpoint="http-monitoring"`이** 붙었는지를 확인하세요. 수집이 안 될 때 가장 먼저 볼 화면입니다.*

**② 데이터 플레인 수집 — PodMonitor**

`istio-proxy` 컨테이너를 포함하는 **모든 파드**에서 메트릭을 수집합니다. 사이드카가 주입된 파드에는 이미 다음 애너테이션이 붙어 있습니다.

```plain text
prometheus.io/path: /stats/prometheus
prometheus.io/port: 15020
prometheus.io/scrape: true
```

```yaml
# ch7/pod-monitor-dp.yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: envoy-stats-monitor
  namespace: prometheus
  labels:
    monitoring: istio-proxies
    release: prom
spec:
  selector:
    matchExpressions:
    - {key: istio-prometheus-ignore, operator: DoesNotExist}
  namespaceSelector:
    any: true
  jobLabel: envoy-stats
  podMetricsEndpoints:
  - path: /stats/prometheus
    interval: 15s
    relabelings:
    - action: keep                                   # istio-proxy 컨테이너만
      sourceLabels: [__meta_kubernetes_pod_container_name]
      regex: "istio-proxy"
    - action: keep                                   # scrape 애너테이션이 달린 파드만
      sourceLabels: [__meta_kubernetes_pod_annotationpresent_prometheus_io_scrape]
      regex: "true"                                  # ← regex 를 생략하면 기본값 (.*) 로 전부 통과합니다
    - sourceLabels: [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
      action: replace
      regex: ([^:]+)(?::\d+)?;(\d+)
      replacement: $1:$2
      targetLabel: __address__
    - action: labeldrop
      regex: "__meta_kubernetes_pod_label_(.+)"
    - sourceLabels: [__meta_kubernetes_namespace]
      action: replace
      targetLabel: namespace
    - sourceLabels: [__meta_kubernetes_pod_name]
      action: replace
      targetLabel: pod_name
```

```bash
kubectl apply -f ch7/pod-monitor-dp.yaml -n prometheus
kubectl get podmonitor -n prometheus
# 메트릭이 쌓이도록 호출 테스트
while true; do curl -s http://webapp.istioinaction.io:30000/api/catalog ; sleep 1; echo; done
WEBAPP=$(kubectl get pod -n istioinaction -l app=webapp -o jsonpath='{.items[0].status.podIP}')
kubectl exec -it netshoot -- curl -s $WEBAPP:15020/stats/prometheus
```

프로메테우스 UI에서 `istio_request`를 입력하면 이스티오 메트릭이 자동완성으로 뜹니다.

## 7.4 이스티오 표준 메트릭 커스터마이징하기

여기까지로 표준 메트릭을 모으는 파이프라인은 완성됐습니다. 문제는 **표준 메트릭만으로는 답할 수 없는 질문들**이 있다는 것입니다 — "이 에러를 맞은 호출자는 어느 팀의 서비스인가", "업그레이드 중인 프록시 버전별로 오류율이 다른가", "`/items` API만 따로 떼어서 보면 어떤가". 이런 질문은 **우리 도메인의 정보를 메트릭에 얹어야** 답할 수 있습니다.

그러려면 먼저 **기본 메트릭이 무엇으로 구성되어 있는지**를 알아야 합니다. 7.2.1에서 본 표준 메트릭 4종에 더해, gRPC용 2종이 더 있습니다.

| 메트릭 | 설명 |
| --- | --- |
| istio_requests_total 외 3종 | 7.2.1 표준 메트릭 표 참조 (requests_total, request_bytes, response_bytes, request_duration_ms) |
| istio_request_messages_total | (gRPC) COUNTER — 클라이언트에게서 메시지가 올 때마다 증가 |
| istio_response_messages_total | (gRPC) COUNTER — 서버가 메시지를 보낼 때마다 증가 |

메트릭이 표시·커스터마이징·생성되는 방식은 엔보이 사이드카의 **플러그인**으로 제어합니다. 그 전에 **세 가지 핵심 개념**을 먼저 잡아야 합니다.

### 세 가지 핵심 개념 — 메트릭 / 디멘션 / 속성

**① 메트릭(metric)** — 서비스 호출(인바운드/아웃바운드) 간 텔레메트리의 **카운터·게이지·히스토그램/분포**입니다. 예를 들어 서비스에 인바운드와 아웃바운드 요청이 모두 있다면 `istio_requests_total`에는 **항목이 2개** 표시됩니다.

**② 디멘션(dimension)** — 인바운드/아웃바운드 같은 구분이 디멘션의 예시입니다. 프록시에 통계를 쿼리하면 **메트릭 × 디멘션 조합마다 통계가 따로** 표시됩니다.

```plain text
# TYPE istio_requests_total counter
istio_requests_total{
  response_code="200",                        # 요청 세부 정보
  reporter="destination",                     # 메트릭이 누구 관점인가?
  source_workload="istio-ingressgateway",
  source_app="istio-ingressgateway",          # 호출 주체 (Caller)
  destination_workload="webapp",
  destination_app="webapp",                   # 호출 대상 (Target)
  destination_service="webapp.istioinaction.svc.cluster.local",
  request_protocol="http",
  response_flags="-",
  connection_security_policy="mutual_tls",
  ...
} 6                                            # 호출 개수
```

> **`reporter` — 증가하는 것이 아니라 같은 요청을 두 번 세는 것:** 요청 1건은 **호출자 측 사이드카(`reporter="source"`)와 피호출자 측 사이드카(`reporter="destination"`) 양쪽에서 각각 기록**되어 **두 줄**이 생깁니다. 이걸 모르면 PromQL로 합을 구할 때 조용히 2배가 됩니다 — 보통 `reporter="destination"` 으로 고정해서 집계합니다.
>
> 또 `source` 관점 메트릭의 `connection_security_policy`는 항상 **`unknown`** 으로 찍힙니다. mTLS가 깨졌다는 뜻이 아니라 **커넥션 보안 판정은 수신 측에서만 확정되기 때문**입니다. (7.4.1 출력에서 실제로 이 값을 보게 됩니다)

디멘션 중 **하나라도 다르면 새로운 항목**으로 보입니다. 응답 코드가 500인 호출이 있으면 별도 줄로 표시됩니다.

```plain text
istio_requests_total{response_code="200", ...} 5   # HTTP 200 호출 개수
istio_requests_total{response_code="500", ...} 3   # HTTP 500 호출 개수
```

**③ 속성(attribute)** — 특정 디멘션의 **값을 어디서 가져올지**를 정합니다. 엔보이 프록시가 **런타임에 갖고 있는 값**이 곧 속성입니다.

| 기본 엔보이 요청 속성 | 설명 |
| --- | --- |
| request.path | URL 중 경로 부분 |
| request.url_path | URL 중 경로 부분, **쿼리 문자열 제외** |
| request.host | URL 중 호스트 부분 |
| request.scheme | URL 중 스킴 부분 (예: 'http') |
| request.method | 요청 메서드 (예: 'GET') |
| request.headers | 모든 요청 헤더. 헤더 이름은 **소문자로 변환** |
| request.referer / request.useragent | Referer / User-Agent 요청 헤더 |
| request.time / request.id / request.protocol | 첫 바이트 수신 시간 / x-request-id 값 / 요청 프로토콜 |

이 외에도 **응답 속성, 커넥션 속성, 업스트림 속성, 메타데이터/필터 상태 속성, 웹어셈블리 속성**이 있습니다.

또 다른 속성 집합은 이스티오 프록시에 내장된 **peer-metadata 필터**에서 나오며, 서비스 호출의 `upstream_peer`와 `downstream_peer` 모두에서 사용할 수 있습니다.

> **내 프록시가 어떻게 상대편의 버전을 아는가:** 두 사이드카는 **커넥션을 맺을 때 서로의 워크로드 메타데이터를 교환**해 둡니다(metadata exchange). 그래서 내쪽 프록시가 상대편의 네임스페이스·버전·클러스터 같은 값을 **자기 메트릭 디멘션으로 쓸 수 있는** 겁니다. `upstream_peer.istio_version` 같은 표현이 마법처럼 보이는 이유가 여기에 있습니다.

| 메타데이터 교환 필터 속성 | 설명 |
| --- | --- |
| name / namespace | 파드 이름 / 파드가 위치한 네임스페이스 |
| labels / owner / workload_name | 워크로드 레이블 / 소유자 / 이름 |
| istio_version | 프록시의 버전 식별자 |
| mesh_id / cluster_id | 메시의 고유 식별자 / 워크로드가 속한 클러스터 식별자 |
| platform_metadata / app_containers | 접두사 키가 있는 플랫폼 메타데이터 / 앱 컨테이너 짧은 이름 목록 |

> **접두사 규칙:** 업스트림(프록시에서 나가는) 메트릭이면 `upstream_peer.`, 다운스트림(프록시로 들어오는) 메트릭이면 `downstream_peer.`를 붙입니다. 호출자의 프록시 버전은 `downstream_peer.istio_version`, 업스트림 서비스의 클러스터는 `upstream_peer.cluster_id`입니다.

### 7.4.1 기존 메트릭 설정하기

기본적으로 이스티오 메트릭은 설치 시 함께 만들어지는 **EnvoyFilter 리소스**를 통해 **stats 프록시 플러그인**에서 설정됩니다.

```bash
kubectl get envoyfilter -n istio-system
# stats-filter-1.13 / 1.14 / 1.15 / 1.16 / 1.17
# tcp-stats-filter-1.13 / ... (프록시 버전별로 존재)
kubectl get envoyfilter stats-filter-1.13 -n istio-system -o yaml
```

> **왜 버전별로 여러 개가 깔려 있나:** 이스티오는 지원하는 프록시 버전마다 stats-filter를 하나씩 배포해 두고, 각 프록시는 자기 버전과 `proxyVersion`이 맞는 것만 적용받습니다(카나리 배포나 업그레이드 중 버전이 섞여 있을 수 있기 때문). **내용은 모두 동일하므로 구조를 볼 때는 아무거나 열어보면 됩니다.** 다만 **설정 변경이 제대로 먹혔는지 검증할 때는 반드시 내 프록시 버전(여기서는 1.17)의 필터를 보세요.**

```yaml
spec:
  configPatches:
  - applyTo: HTTP_FILTER
    match:
      context: SIDECAR_OUTBOUND
      listener:
        filterChain:
          filter:
            name: envoy.filters.network.http_connection_manager
            subFilter:
              name: envoy.filters.http.router
      proxy:
        proxyVersion: ^1\.13.*
    patch:
      operation: INSERT_BEFORE
      value:
        name: istio.stats            # 필터 이름
        typed_config:
          '@type': type.googleapis.com/udpa.type.v1.TypedStruct
          type_url: type.googleapis.com/envoy.extensions.filters.http.wasm.v3.Wasm
          value:
            config:                  # 필터 설정
              configuration:
                '@type': type.googleapis.com/google.protobuf.StringValue
                value: |
                  { "debug": "false", "stat_prefix": "istio" }
              root_id: stats_outbound
              vm_config:
                code:
                  local:
                    inline_string: envoy.wasm.stats
                runtime: envoy.wasm.runtime.null     # NULL VM
                vm_id: stats_outbound
```

> **`istio.stats`는 웹어셈블리(Wasm) 플러그인**이지만, 실제로는 **엔보이 코드베이스 내에서 직접 컴파일돼 NULL 가상머신에서 실행**되므로 웹어셈블리 VM에서 돌지 않습니다. 진짜 Wasm VM에서 돌리려면 설치 시 `--set values.telemetry.v2.prometheus.wasmEnabled=true`를 전달해야 합니다. (웹어셈블리는 14장)

**기존 메트릭에 디멘션 추가하기**

`istio_requests_total`에 디멘션 2개(`upstream_proxy_version`, `source_mesh_id`)를 추가하고, 필요 없는 `request_protocol`은 제거해봅니다.

```yaml
# ch7/metrics/istio-operator-new-dimensions.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: demo
  values:
    telemetry:
      v2:
        prometheus:
          configOverride:
            inboundSidecar:
              metrics:
              - name: requests_total          # istio_ 접두사는 붙이지 않는다
                dimensions:                   # 추가한 새 디멘션
                  upstream_proxy_version: upstream_peer.istio_version
                  source_mesh_id: node.metadata['MESH_ID']
                tags_to_remove:               # 제거한 태그 목록
                - request_protocol
            outboundSidecar:
              metrics:
              - name: requests_total
                dimensions:
                  upstream_proxy_version: upstream_peer.istio_version
                  source_mesh_id: node.metadata['MESH_ID']
                tags_to_remove:
                - request_protocol
            gateway:
              metrics:
              - name: requests_total
                dimensions:
                  upstream_proxy_version: upstream_peer.istio_version
                  source_mesh_id: node.metadata['MESH_ID']
                tags_to_remove:
                - request_protocol
```

```bash
# 적용 전 : request_protocol 디멘션이 있는지 먼저 확인
kubectl -n istioinaction exec -it deploy/webapp -c istio-proxy \
  -- curl -s localhost:15000/stats/prometheus | grep istio_requests_total
# istio_requests_total{... request_protocol="http", response_code="200", ...} 10
#                          ↑ 지금은 있고, 적용 후에는 사라집니다
# 적용
docker exec -it myk8s-control-plane bash
istioctl verify-install -f istio-operator-new-dimensions.yaml   # 리소스별 적용 결과 출력
istioctl install -f istio-operator-new-dimensions.yaml -y
exit
# 변경 확인 : IstioOperator + 모든 버전의 EnvoyFilter 에 반영됐는지
kubectl get istiooperator -n istio-system installed-state -o yaml | grep -E "prometheus:" -A9
kubectl get envoyfilter stats-filter-1.17 -n istio-system -o yaml | grep MESH_ID
```

```plain text
# EnvoyFilter 에 이렇게 반영된다
{"metrics":[{"dimensions":{"source_mesh_id":"node.metadata['MESH_ID']",
"upstream_proxy_version":"upstream_peer.istio_version"},
"name":"requests_total","tags_to_remove":["request_protocol"]}]}
```

**프록시에 새 디멘션을 알려주기** — 설정만으로는 부족합니다. 디플로이먼트의 **파드 템플릿(`spec.template.metadata`)** 에 애너테이션을 달아야 합니다.

```yaml
# ch7/metrics/webapp-deployment-extrastats.yaml
  template:
    metadata:
      annotations:
        proxy.istio.io/config: |-
          extraStatTags:
          - "upstream_proxy_version"
          - "source_mesh_id"
      labels:
        app: webapp
```

> **주의 — 디플로이먼트 메타데이터가 아니라 파드 템플릿(`spec.template.metadata`)에 붙여야 합니다.**
>
> **이 단계는 1.17부터 이미 의미가 없습니다:** Telemetry API가 Wasm 기반 확장 대신 **네이티브 stats 확장**을 쓰도록 바뀌면서 CPU/메모리 오버헤드가 개선됐고, **커스텀 디멘션에 regex와 bootstrap 애너테이션(`extraStatTags`)이 더 이상 필요 없습니다.**
>
> **그럼 이 실습에서는 붙여야 하나 말아야 하나:** 실습 환경이 **1.17.8** 이므로 이미 네이티브 stats 확장이 기본입니다. 즉 **이 애너테이션을 붙여도 안 붙여도 결과는 같습니다.** 책의 흐름을 따라가기 위해 그대로 적용하지만, **1.16 이하에서만 실제로 필요한 단계**라고 이해하면 됩니다. 필드 자체는 1.30에도 남아 있지만 proto 주석에 **Deprecated**로 표시돼 있습니다.

```bash
kubectl apply -n istioinaction -f ch7/metrics/webapp-deployment-extrastats.yaml
while true; do curl -s http://webapp.istioinaction.io:30000/api/catalog ; sleep 1; echo; done
# 확인 : request_protocol 이 사라지고 새 디멘션 2개가 붙었는지
kubectl -n istioinaction exec -it deploy/webapp -c istio-proxy \
  -- curl localhost:15000/stats/prometheus | grep istio_requests_total
```

```plain text
istio_requests_total{
  reporter="source",
  source_workload="webapp",
  destination_workload="catalog",
  destination_service="catalog.istioinaction.svc.cluster.local",
  response_code="200",
  connection_security_policy="unknown",
  source_mesh_id="cluster.local",        # ← 새 디멘션 (메시 ID)
  upstream_proxy_version="1.17.8"        # ← 새 디멘션 (업스트림 프록시 버전)
} 10
```

*프로메테우스 UI에서 **`istio_requests_total`** 조회. 범례에 **`source_mesh_id`와** **`upstream_proxy_version`이** 새로 보이고, 반대로 **`request_protocol`은** 사라진 것을 비교해 보세요.*

![새 디멘션이 붙은 istio_requests_total](images/notes/istio-in-action/7-8.avif)

> **(참고) Telemetry API로 네임스페이스 단위 적용:** IstioOperator로 메시 전체를 다시 설치하는 대신, `Telemetry` 리소스로 특정 네임스페이스에만 디멘션을 추가/삭제할 수 있습니다.

```yaml
apiVersion: telemetry.istio.io/v1alpha1
kind: Telemetry
metadata:
  name: add-dimension-tags
  namespace: istioinaction
spec:
  metrics:
  - providers:
    - name: prometheus
    overrides:
    - match:
        metric: REQUEST_COUNT
        mode: CLIENT_AND_SERVER
      disabled: false
      tagOverrides:
        upstream_proxy_version:
          operation: UPSERT
          value: upstream_peer.istio_version
        source_mesh_id:
          operation: UPSERT
          value: node.metadata['MESH_ID']
        request_protocol:
          operation: REMOVE
```

### 7.4.2 새로운 메트릭 만들기

기존 메트릭의 디멘션을 바꾸는 것을 넘어, **stats 플러그인에 새 메트릭을 정의**할 수 있습니다.

```yaml
# ch7/metrics/istio-operator-new-metric.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: demo
  values:
    telemetry:
      v2:
        prometheus:
          configOverride:
            inboundSidecar:
              definitions:
              - name: get_calls                                    # istio_ 접두사는 자동으로 붙는다
                type: COUNTER                                      # GAUGE, HISTOGRAM 도 가능
                value: "(request.method.startsWith('GET') ? 1 : 0)"  # CEL 표현식
            outboundSidecar:
              definitions:
              - name: get_calls
                type: COUNTER
                value: "(request.method.startsWith('GET') ? 1 : 0)"
            gateway:
              definitions:
              - name: get_calls
                type: COUNTER
                value: "(request.method.startsWith('GET') ? 1 : 0)"
```

- 정의한 이름은 `get_calls`지만 실제 메트릭 이름은 **`istio_get_calls`** 입니다 — `istio_` 접두사가 자동으로 붙습니다.
- 메트릭의 값은 **CEL(Common Expression Language)** 표현식 문자열이며, COUNTER 타입에는 **정수를 반환**해야 합니다.
- CEL 표현식은 **속성(attribute)에 대해** 작동합니다. 위 예시는 HTTP GET 요청 개수를 셉니다.

```bash
docker exec -it myk8s-control-plane bash
istioctl verify-install -f istio-operator-new-metric.yaml
istioctl install -f istio-operator-new-metric.yaml -y
exit
# 확인
kubectl get istiooperator -n istio-system installed-state -o yaml | grep -A2 get_calls$
kubectl get envoyfilter -n istio-system stats-filter-1.17 -o yaml | grep get_calls
```

**프록시에 노출하라고 알리기** — 새 디멘션과 마찬가지로, 새 메트릭도 프록시에서 노출하도록 지정해야 합니다. **단, `proxyStatsMatcher` 는 `extraStatTags` 와 달리 지금도 유효한 설정입니다** — 엔보이 통계를 얼마나 보고할지 고르는 용도라 메트릭 구현 방식과 무관하기 때문입니다.

```yaml
# ch7/metrics/webapp-deployment-new-metric.yaml
  template:
    metadata:
      annotations:
        proxy.istio.io/config: |-
          proxyStatsMatcher:
            inclusionPrefixes:
            - "istio_get_calls"
      labels:
        app: webapp
```

```bash
kubectl -n istioinaction apply -f ch7/metrics/webapp-deployment-new-metric.yaml
while true; do curl -s http://webapp.istioinaction.io:30000/api/catalog ; sleep 1; echo; done
kubectl -n istioinaction exec -it deploy/webapp -c istio-proxy \
  -- curl localhost:15000/stats/prometheus | grep istio_get_calls
# TYPE istio_get_calls counter
# istio_get_calls{} 20
```

![새로 만든 istio_get_calls 메트릭](images/notes/istio-in-action/7-9.avif)

*프로메테우스 UI에서 **`istio_get_calls`** 조회. 디멘션을 지정하지 않았기 때문에 범례가 **`container`**/**`pod`** 같은 수집 과정에서 붙는 라벨만으로 구분되는 점을 보세요.*

이 메트릭에는 **디멘션을 하나도 지정하지 않았습니다.** 시스템 내 모든 요청 중 GET 요청의 개수를 셀 뿐입니다. 그렇다면 **catalog 서비스의 `/items` 엔드포인트로 향하는 GET 요청만** 세려면 어떻게 해야 할까요? → 다음 절.

### 7.4.3 새 속성으로 호출 그룹화하기

기존 속성을 조합해 **더 세분화하거나 도메인에 특화된 새 속성**을 만들 수 있습니다. 여기서는 `request.url_path`와 `request.method`를 조합한 **`istio_operationId`** 라는 새 속성을 만듭니다.

> **왜 `/items`인가 — 지금까지 친 curl은 전부 `/api/catalog`였는데?** 사용자가 치는 경로는 `/api/catalog`이지만, **webapp이 내부적으로 catalog를 부를 때의 경로는 `/items`** 입니다. 이번에 만드는 속성은 **webapp → catalog 아웃바운드 홉**에 붙으므로 기준 경로는 `/items`가 됩니다. (그래서 아래 EnvoyFilter의 context가 `SIDECAR_OUTBOUND` 이고, IstioOperator도 `outboundSidecar` 에만 넣습니다)

이를 위해 **attribute-gen 프록시 플러그인**(또 다른 Wasm 확장)을 사용합니다.

> **stats 플러그인과의 관계:** attribute-gen은 stats 플러그인을 **보완**하는 역할을 하며, **stats 플러그인보다 먼저 적용**됩니다. 그래서 attribute-gen이 만들어내는 **모든 속성을 stats에서 그대로 사용**할 수 있습니다.

```yaml
# ch7/metrics/attribute-gen.yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: attribute-gen-example
  namespace: istioinaction
spec:
  configPatches:
  ## Sidecar Outbound
  - applyTo: HTTP_FILTER
    match:
      context: SIDECAR_OUTBOUND
      listener:
        filterChain:
          filter:
            name: envoy.filters.network.http_connection_manager
            subFilter:
              name: istio.stats                 # stats 필터 '앞에' 삽입
      proxy:
        proxyVersion: ^1\.17.*                  # 설치된 istio 버전에 맞게 수정
    patch:
      operation: INSERT_BEFORE
      value:
        name: istio.attributegen
        typed_config:
          '@type': type.googleapis.com/udpa.type.v1.TypedStruct
          type_url: type.googleapis.com/envoy.extensions.filters.http.wasm.v3.Wasm
          value:
            config:
              configuration:
                '@type': type.googleapis.com/google.protobuf.StringValue
                value: |
                  {
                    "attributes": [
                      {
                        "output_attribute": "istio_operationId",   # 속성 이름
                        "match": [
                          {
                            "value": "getitems",                   # 속성 값
                            "condition": "request.url_path == '/items' && request.method == 'GET'"
                          },
                          {
                            "value": "createitem",
                            "condition": "request.url_path == '/items' && request.method == 'POST'"
                          },
                          {
                            "value": "deleteitem",
                            "condition": "request.url_path == '/items' && request.method == 'DELETE'"
                          }
                        ]
                      }
                    ]
                  }
              vm_config:
                code:
                  local:
                    inline_string: envoy.wasm.attributegen
                runtime: envoy.wasm.runtime.null
```

> **적용 전 반드시 `proxyVersion`을 설치된 이스티오 버전에 맞게 수정하세요.** 책 예제는 `^1\.13.*`이지만 실습 환경이 1.17이면 `^1\.17.*`로 바꿔야 필터가 적용됩니다.

```bash
docker exec -it myk8s-control-plane istioctl version   # control plane / data plane 버전 확인
vi ch7/metrics/attribute-gen.yaml                      # proxyVersion 수정
# EnvoyFilter 를 배포한 네임스페이스의 istio-proxy 들에 적용된다
kubectl apply -f ch7/metrics/attribute-gen.yaml -n istioinaction
kubectl get envoyfilter -n istioinaction
```

이제 이 속성을 쓰는 **새 디멘션 `upstream_operation`** 을 `istio_requests_total`에 추가합니다.

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: demo
  values:
    telemetry:
      v2:
        prometheus:
          configOverride:
            outboundSidecar:              # webapp -> catalog 아웃바운드에만 필요
              metrics:
              - name: requests_total
                dimensions:
                  upstream_operation: istio_operationId   # 새 디멘션
```

7.4.1·7.4.2와 **같은 3단계**를 밟습니다 — ① IstioOperator 적용 → ② 프록시에 새 디멘션 알리기 → ③ 호출 후 검증.

```bash
# ① 적용
docker exec -it myk8s-control-plane bash
cat << EOF > istio-operator-new-attribute.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: demo
  values:
    telemetry:
      v2:
        prometheus:
          configOverride:
            outboundSidecar:
              metrics:
              - name: requests_total
                dimensions:
                  upstream_operation: istio_operationId
EOF
istioctl verify-install -f istio-operator-new-attribute.yaml
istioctl install -f istio-operator-new-attribute.yaml -y
exit
# ② 프록시에 새 디멘션 알리기 — webapp 파드 템플릿에 extraStatTags 로 "upstream_operation" 추가
kubectl -n istioinaction apply -f ch7/metrics/webapp-deployment-extrastats.yaml
# ③ 호출 후 검증
for i in {1..10}; do curl -s http://webapp.istioinaction.io:30000/api/catalog > /dev/null; done
kubectl -n istioinaction exec -it deploy/webapp -c istio-proxy \
  -- curl -s localhost:15000/stats/prometheus | grep istio_requests_total | grep upstream_operation
```

```plain text
istio_requests_total{
  reporter="source",
  source_workload="webapp",
  destination_workload="catalog",
  response_code="200",
  upstream_operation="getitems"        # ← /items 로의 GET 호출만 따로 집계된다
} 10
```

이렇게 하면 `/items`로 향하는 GET/POST/DELETE 호출을 (위 그림: 같은 `istio_requests_total`이라도 **operation별로 줄이 나뉘어** 집계되는 점을 보세요) **`getitems` / `createitem` / `deleteitem`** 이라는 의미 있는 단위로 그룹화해 셀 수 있습니다.

> **디멘션이 안 보일 때 체크 순서:** ① `kubectl get envoyfilter -n istioinaction` 에 attribute-gen이 있는가 → ② 그 필터의 `proxyVersion`이 내 프록시 버전과 맞는가 → ③ IstioOperator에 `upstream_operation`이 들어갔는가 → ④ 파드가 재생성돼 `extraStatTags`가 반영됐는가. **네 가지 중 하나라도 어긋나면 에러 없이 그냥 디멘션만 안 보입니다.**

## 7.5 지금은 이렇게 합니다 (2026년 기준)

책은 **Istio 1.13** 시점에 쓰였고, 현재 최신은 **1.30**입니다(지원 버전은 1.29·1.30 둘뿐). 다행히 **메트릭 이름과 라벨은 거의 그대로**입니다 — `istio_requests_total`과 그 디멘션들은 1.13과 1.30이 동일합니다. **바뀐 것은 그걸 설정하는 방법 전부**입니다.

> **한 줄 요약:** 7.4절에서 쓴 **`IstioOperator` + `telemetry.v2.prometheus.configOverride` 경로는 1.21에서 완전히 삭제**됐습니다. 지금은 **`Telemetry` API**가 유일한 지원 경로입니다. 다만 7.2·7.3절(엔보이 통계 읽기, 프로메테우스 수집)은 **지금도 그대로 유효**합니다.

### 7.5.1 책 ↔ 현행 매핑표

| 책 (1.13) | 현재 (1.29/1.30) | 바뀐 버전 |
| --- | --- | --- |
| `stats-filter-1.13` EnvoyFilter 확인 | **그런 EnvoyFilter 없음.** `kubectl get telemetry -A` 로 확인 | 1.21 제거 |
| `configOverride` 로 디멘션 추가 | `Telemetry` CR → `tagOverrides.<name>.value: "<CEL>"` | 1.21 제거 |
| `tags_to_remove` 로 디멘션 제거 | `tagOverrides.<name>.operation: REMOVE` | 〃 |
| `definitions` 로 새 메트릭(`istio_get_calls`) | **Telemetry API로 불가.** 디멘션만 추가하고 PromQL로 집계 | 1.21 제거 |
| CEL 값 `upstream_peer.istio_version` | `filter_state.upstream_peer.<field>` (inbound는 `downstream_peer`) | 1.17 변경 |
| `extraStatTags` 애너테이션 추가 | **불필요.** 필드는 남았으나 Deprecated | 1.17부터 불필요 |
| EnvoyFilter + `envoy.wasm.attributegen` | `WasmPlugin`  • `Telemetry` `tagOverrides` | 전환 버전 미확인 |
| `proxyStatsMatcher.inclusionPrefixes` | **그대로 유효.** `sidecar.istio.io/statsInclusion*` 만 Deprecated | 변경 없음 |
| `istioctl operator init` | **제거됨.** `istioctl install -f` 또는 Helm (공식은 Helm 권장) | 1.24 제거 |
| ServiceMonitor / PodMonitor | **그대로 유효** (`monitoring.coreos.com/v1`, `release:` 라벨) | 변경 없음 |
| kube-prometheus-stack **13.13.1** | **88.2.0** (Prometheus **3.13.2**, k8s 1.25+) | — |
| PromQL `reporter="destination"` | 사이드카는 동일. **앰비언트면 `reporter=~"source\|waypoint"`** | 1.24 (ambient GA) |

### 7.5.2 사라진 것 — stats-filter EnvoyFilter와 configOverride

7.4.1에서 `kubectl get envoyfilter -n istio-system` 으로 봤던 `stats-filter-*` 목록은 **현재 버전에서 아예 존재하지 않습니다.** 세 단계로 진행됐습니다.

| 버전 | 무슨 일이 있었나 |
| --- | --- |
| **1.17** (2023-02) | Wasm 기반 stats 확장 → **네이티브 확장**으로 교체. CPU·메모리 개선. 이때부터 **커스텀 디멘션에 regex와 bootstrap 애너테이션이 불필요**해졌습니다 |
| **1.18** (2023-06) | 기본 설치가 EnvoyFilter 대신 `meshConfig.defaultProviders` 를 쓰도록 변경. 단 `configOverride`를 설정하면 여전히 EnvoyFilter가 생성됨 |
| **1.21** (2024-03) | 레거시 EnvoyFilter 구현 **전면 삭제**. `prometheus.configOverride` 를 포함한 필드들이 "no longer respected" |

> **즉, 최신 버전에서 7.4절을 그대로 따라 하면 아무 일도 일어나지 않습니다.** `IstioOperator`의 `TelemetryV2PrometheusConfig` 는 1.30 기준 필드가 `enabled` **하나뿐**이며, 그마저 "프로메테우스 provider를 만들지 말지" 스위치 역할만 합니다.

### 7.5.3 지금의 정답 — Telemetry API

`telemetry.istio.io/v1` 은 **1.22에서 v1으로 승격**했고, 기능 단계도 **Stable**입니다. 7.4.1에서 한 일(디멘션 2개 추가 + `request_protocol` 제거)을 현행 방식으로 쓰면 이렇게 됩니다.

```yaml
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: add-dimension-tags
  namespace: istioinaction
spec:
  metrics:
  - providers:
    - name: prometheus
    overrides:
    - match:
        metric: REQUEST_COUNT          # ALL_METRICS 또는 개별 메트릭
        mode: CLIENT_AND_SERVER        # CLIENT / SERVER / CLIENT_AND_SERVER
      tagOverrides:
        upstream_proxy_version:
          operation: UPSERT            # 생략해도 UPSERT
          value: filter_state.upstream_peer.istio_version   # ← filter_state. 접두사가 필수
        source_mesh_id:
          operation: UPSERT
          value: node.metadata['MESH_ID']
        request_protocol:
          operation: REMOVE
```

**책과 달라진 세 가지**

- 적용 단위가 **메시 전체 재설치 → 네임스페이스/워크로드 단위 CR** 로 바뀌었습니다. `istioctl install`을 다시 돌릴 필요가 없습니다.
- **CEL 표현식에 `filter_state.` 접두사가 붙습니다.** peer 메타데이터 접근이 Wasm 속성 → filter_state로 바뀐 것으로, **1.17에서 깨진 부분**입니다. 사용 가능 필드는 `app, version, service, revision, name, namespace, type, workload, cluster` 입니다.
- `overrides[].disabled: true` 로 **메트릭을 끌 수도** 있습니다(카디널리티 제어용).

> **주의:** 공식 문서가 **"Telemetry API는 EnvoyFilter와 함께 동작하지 않는다"** 고 명시합니다. 둘을 섞지 마세요.

### 7.5.4 Telemetry API로 **안 되는** 것 — 새 메트릭 정의

7.4.2의 `istio_get_calls` 처럼 **이름과 값 표현식을 가진 메트릭을 새로 만드는 것은 현재 Telemetry API로 불가능합니다.**

- `match.customMetric` 이 있지만 이건 **"어떤 메트릭에 override를 적용할지 고르는 셀렉터"** 일 뿐, 값 표현식을 정의하는 수단이 아닙니다.
- 값 표현식을 담는 `definitions` 필드는 proto에 남아 있지만, **istiod가 이 필드를 생성하는 코드 자체가 없습니다.**

**현실적인 대안:** 메트릭을 새로 만들지 말고 **디멘션만 추가한 뒤 PromQL에서 집계**하세요. 사실 이쪽이 카디널리티 관리 측면에서도 더 낫습니다.

```yaml
# 책: istio_get_calls 라는 새 메트릭을 만든다
# 현재: request_method 디멘션만 추가하고
      tagOverrides:
        request_method:
          value: request.method
```

```javascript
# 그리고 쿼리 시점에 걸러낸다
sum(rate(istio_requests_total{request_method="GET"}[5m]))
```

### 7.5.5 attribute-gen → WasmPlugin

7.4.3의 `EnvoyFilter` + `envoy.wasm.attributegen` 은 지금 **`WasmPlugin`(`extensions.istio.io/v1alpha1`) + `Telemetry`** 조합으로 바뀌었습니다.

```yaml
apiVersion: extensions.istio.io/v1alpha1
kind: WasmPlugin
metadata:
  name: istio-attributegen-filter
spec:
  selector:
    matchLabels: { app: webapp }
  url: https://storage.googleapis.com/istio-build/proxy/attributegen-359dcd3a19f109c50e97517fe6b1e2676e870c4d.wasm
  imagePullPolicy: Always
  phase: AUTHN
  pluginConfig:
    attributes:
    - output_attribute: "istio_operationId"
      match:
      - value: "getitems"
        condition: "request.url_path == '/items' && request.method == 'GET'"
---
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: custom-tags
spec:
  metrics:
  - providers:
    - name: prometheus
    overrides:
    - match: { metric: REQUEST_COUNT, mode: CLIENT_AND_SERVER }
      tagOverrides:
        request_operation:
          value: filter_state['wasm.istio_operationId']   # ← 참조 키가 바뀌었다
```

> **이 방법은 아직 거칠다는 점을 알고 쓰세요.** ① `WasmPlugin` 은 기능 단계상 여전히 **Alpha** ② 공식 예제 문서가 `test: no` 라 **CI 자동검증을 받지 않습니다** ③ Wasm URL이 **2021년 빌드 해시에 고정**되어 오랫동안 갱신되지 않았습니다 ④ attributegen·stats의 **레퍼런스 문서는 삭제**됐습니다(attributegen 1.18이후, stats 1.25이후 404).
>
> **경로가 단순하다면** attributegen 없이 `tagOverrides` 값에 CEL 삼항식을 직접 넣는 방법도 있습니다(`has(request.host) ? request.host : "unknown"` 형태). 다만 이 용법의 공식 예제는 없어서 **검증된 방법은 아닙니다.**

### 7.5.6 앰비언트 모드 — 7장 메트릭이 바뀝니다

사이드카 없는 **앰비언트 모드**는 **1.22 Beta → 1.24 GA**로 정식 배포됐습니다. 그런데 이게 7장 내용을 정면으로 건드립니다.

|  | ztunnel (노드 공유) | waypoint (네임스페이스/서비스별) |
| --- | --- | --- |
| 계층 | **L4 전용** | L7 (Envoy) |
| 메트릭 | `istio_tcp_*` 4종 + `istio_build` 뿐. **`istio_requests_total` 없음** | **풀 세트** (7장에서 다룬 그것) |
| 포트 | 15020 (`/metrics`, `/stats/prometheus`) | 15020·15021·15090 — 사이드카와 동일 |
| `reporter` 라벨 | **`source` 만** | **`waypoint`** ← 책에도, 공식 메트릭 레퍼런스에도 없는 세 번째 값 |
| Telemetry API | 미지원(추정) | 1.24부터 지원. 단 **`selector` 가 아니라 `targetRefs`** 로 붙여야 함 |

> **가장 큰 함정:** 책과 이 페이지에 나오는 **`reporter="destination"` 쿼리는 순수 앰비언트 메시에서 아무것도 반환하지 않습니다.** ztunnel은 `source`만, waypoint는 `waypoint`를 씁니다. Istio 자체 mesh 대시보드도 `reporter=~"source|waypoint"` 로 바뀌었는데, **공식 메트릭 레퍼런스 문서는 아직 두 값만 적어둔 문서 갭입니다.**
>
> **앰비언트에서 L7 메트릭을 보려면 waypoint를 배포해야 합니다.** ztunnel 메인테이너는 "ztunnel에서 L7을 파싱하거나 L7 텔레메트리를 내보낼 계획은 없다"고 밝혔습니다. 또 Grafana의 service/workload 대시보드는 1.30에서도 `reporter="destination"` 이 하드코딩돼 있어 **앰비언트에서는 여전히 깨집니다.**

### 7.5.7 수집 스택 최신화 시 주의점

**ServiceMonitor/PodMonitor YAML 자체는 그대로 쓰면 됩니다.** `monitoring.coreos.com/v1`도, `release:` 라벨 관례도, 포트명 규칙(`http-monitoring`, `-envoy-prom`)도 모두 현행입니다. 깨지는 건 주변 환경입니다.

**차트 측**

- **v22→v23**: Istio 프로토콜 판별 때문에 포트명이 바뀌었습니다 — Prometheus/Alertmanager `web` → **`http-web`**, node-exporter `metrics` → `http-metrics`
- **v46~v48**: CRD가 별도 서브차트로 분리 → 업그레이드 시 `kubectl apply --server-side` 로 수동 적용
- **v72→v73**: **쿠버네티스 최소 1.25**, PodSecurityPolicy 전량 제거
- **v78→v79**: 그라파나 기본 비밀번호 `prom-operator` 폐지(랜덤 시크릿)

**Prometheus 3.x 측** (2024-11 출시) — 이젠 기본이 3.x입니다

- **UI가 전면 교체**돼 이 페이지의 프로메테우스 스크린샷과 화면이 다릅니다 (`--enable-feature=old-ui` 로 임시 복구)
- **`le`/`quantile` 라벨이 float로 정규화** — `le="1"` → `le="1.0"`. **히스토그램 쿼리를 하드코딩해둔 것이 깨집니다** (7.2.2에서 본 `pilot_proxy_convergence_time_bucket{le="0.1"}` 같은 형태)
- **스크레이프 프로토콜 엄격화** — `Content-Type` 불량이면 2.x는 텍스트로 폴백했지만 **3.x는 스크레이프 실패**
- **range selector가 left-open/right-closed** 로 변경 → 서브쿼리에서 `rate`가 No Data가 되는 경우
- 정규식 `.` 이 `\n` 도 매칭, UTF-8 메트릭명 기본 허용, `no-default-scrape-port` 기본 → **`instance` 라벨 값이 달라집니다**

> **이스티오 측 함정 — 중복 스크레이프:** **메트릭 병합(`enablePrometheusMerge`)이 여전히 기본 ON** 입니다. 이스티오가 데이터플레인 파드에 `prometheus.io/*` 애너테이션을 덮어쓰고 **15020으로 병합 노출**하므로, 7.3.2의 PodMonitor와 **중복 수집**이 생길 수 있습니다. 끄려면 `--set meshConfig.enablePrometheusMerge=false`, 파드 단위로는 `prometheus.istio.io/merge-metrics: "false"`.
>
> 참고로 **istio.io는 사이드카용 PodMonitor/ServiceMonitor 샘플을 공식 제공하지 않습니다.** raw `scrape_configs` 만 문서화돼 있어, 이 장의 PodMonitor는 실상 커뮤니티 관례입니다. 대규모에서는 이제 **계층적 federation**을 권장합니다.

### 7.5.8 OpenTelemetry는 어디까지 왔나

기대와 달리 **메트릭은 아직 프로메테우스 스크레이프가 유일한 공식 경로**입니다.

- `meshConfig.extensionProviders` 의 전체 목록을 보면 **메트릭 provider는 `prometheus` 하나뿐**이며, **OTLP 메트릭 provider는 존재하지 않습니다.**
- OTel이 쓰이는 곳은 **트레이싱(`opentelemetry`)과 액세스 로그(`envoyOtelAls`)** 입니다.
- Lightstep(1.22 deprecated)·OpenCensus(1.25 deprecated)는 **1.27에서 제거**되었고 대체는 OpenTelemetry입니다.

### 7.5.9 그 밖에 2026년에 걸리는 것들

- **포트는 그대로입니다** — 15000/15001/15006/15008/15020/15021/15053/15090 모두 유지.
- **distroless는 여전히 기본이 아니라 opt-in** 입니다(`--set values.global.variant=distroless`). 켜면 shell·curl이 없어 이 장의 `kubectl exec ... -- curl` 이 전부 실패합니다.
- **1.30**: `source_app`/`destination_app` 산출이 `app` → `app.kubernetes.io/name` → `service.istio.io/canonical-name` 순으로 폴백합니다.
- **1.30**: 서킷 브레이커의 `remaining_*` 메트릭이 **기본 비활성**으로 바뀝니다(메모리 절감).
- **1.30**: stats 엔드포인트 **압축이 기본 ON** 입니다. 수동 `curl` 시 `Accept-Encoding` 에 유의하세요.
- 통계 확인은 `istioctl experimental envoy-stats <pod> -o prom` (줄임 `istioctl x es`) 로도 됩니다.

> **조사에서 확인하지 못한 것:** ① 1.21+ 에 `configOverride`를 넣으면 조용히 무시되는지 validation 에러인지 ② EnvoyFilter로 `istio.stats`의 `definitions`를 MERGE해 새 메트릭을 만드는 방법이 1.30에서 실제 동작하는지 ③ attributegen이 WasmPlugin 방식으로 전환된 정확한 버전 ④ "Telemetry API가 ztunnel에 적용되지 않는다"는 공식 명시 문장(추정입니다).

## 7.6 이스티오 밖에 쓰는 기술들 — 관찰 가능성 스택 전체 지도

7장은 **이스티오가 메트릭을 내놓는 부분 → 프로메테우스가 긁어가는 부분 → 그라파나로 보는 부분**까지를 다뤘습니다. 프로덕션 스택에서는 **계측 계층의 일부와 시각화 계층의 일부**일 뿐입니다.

> **먼저 알아둘 것:** 책과 이 장에서 쓴 데모용 프로메테우스(`samples/addons/prometheus.yaml`)는 **Istio 공식 문서가 직접 "프로덕션에 쓰지 말라"고 못 박은 구성**입니다. 보존 기간이 의도적으로 **6시간**입니다. 이 절은 결국 "그럼 프로덕션에서는 무엇을 쓰는가"에 대한 답입니다.

### 7.6.1 계층도

![관찰 가능성 스택 계층도](images/notes/istio-in-action/7-10.avif)

*다섯 계층 중 7장이 다루는 것은 파란 테두리 네 개입니다. ⑤ 알림·SLO 계층은 통째로 비어 있습니다.*

### 7.6.2 표준·수집 — OpenTelemetry와 이스티오의 비대칭

**OpenTelemetry는 2026-05-11 CNCF를 졸업**했습니다(공지 2026-05-21). "incubating"이라 적힌 자료는 전부 낡은 것입니다.

> **이 절에서 가장 중요한 한 줄 — 이스티오는 메트릭을 OTLP로 내보내지 않습니다.**
>
> `meshConfig.extensionProviders` 에서 **메트릭 provider는 `prometheus` 단 하나**이며 OTLP 메트릭 provider는 아예 존재하지 않습니다. 반면 **트레이스(`opentelemetry`)와 액세스 로그(`envoyOtelAls`)는 OTLP로 직접 나갑니다.**
>
> ⇒ 이스티오 메트릭을 OTel 파이프라인에 넣으려면 **OTel Collector의 `prometheusreceiver`로 스크랩하는 수밖에 없습니다.** 이 비대칭이 아키텍처 설계에서 계속 발목을 잡습니다.

**OTel 시그널 성숙도 — 스펙이 아니라 언어 구현을 보세요**

| 언어 | Traces | Metrics | Logs |
| --- | --- | --- | --- |
| Java / .NET / C++ / PHP | Stable | Stable | **Stable** |
| Go | Stable | Stable | **Beta** |
| Python / JavaScript | Stable | Stable | **Development** |
| Rust | Beta | Beta | Beta |

> **"OTel 로그로 통일하자"는 2026년에도 Java/.NET/C++/PHP에서만 안전합니다.** Python·JS 로그는 아직 Development입니다.
>
> **메시와 OTel 자동계측을 같이 쓰려는 팀이 반드시 먼저 알아야 할 것:** OTel Operator의 자동계측은 Java/.NET/Node.js/Python 4종이 정식입니다. **Go는 feature gate + privileged/root가 필요하고 멀티 컨테이너 파드를 지원하지 않아서**, 사이드카가 붙은 파드에서는 사실상 못 씁니다.

**프로메테우스 3.x에서 달라진 것 (7.5.7에 이어서)**

- **OTLP 수신이 Stable입니다** — `/api/v1/otlp/v1/metrics`, 기본 비활성이라 `--web.enable-otlp-receiver` 필요. 3.0에서 플래그 이름이 바뀌었기 때문에 "아직 experimental"이라는 오해가 많습니다.
- 단, `otlp.promote_resource_attributes` 를 설정하지 않으면 `service.name`·`k8s.pod.name` 같은 것이 라벨로 승격되지 않아 **그라파나에서 조인이 안 됩니다.**
- **네이티브 히스토그램이 v3.8.0(2025-12)부터 Stable** 입니다. `istio_request_duration_milliseconds_bucket` 의 `le` 라벨 폭발을 줄일 수 있는 길이 열렸고, **v4.0에서 기본값이 됩니다.**
- **OpenMetrics는 2024-07-02 CNCF 아카이브**되어 프로메테우스로 흡수됐습니다. 죽은 것은 아니고 **OpenMetrics 2.0**이 Prometheus 산하에서 진행 중이며, 명시적으로 **OTel 데이터 모델과의 호환성 개선**을 목표로 걸었습니다. (⚠️ `openmetrics.io` 는 낡았습니다 — 아직도 "CNCF sandbox"라고 적혀 있으니 인용하지 마세요)

> **이름 충돌 함정:** 이스티오는 `istio_requests_total`(프로메테우스 네이밍), OTel 계측 앱은 `http.server.request.duration`(HTTP semconv)을 씁니다. OTLP 수신기를 거치면 `otlp.translation_strategy` 에 따라 이름이 바뀌므로, **전사적으로 하나의 전략을 고정하지 않으면 중복·분기된 시계열이 생겨 대시보드가 깨집니다.**

### 7.6.3 메트릭 장기저장 — 단일 프로메테우스의 한계를 넘기

이스티오를 켜는 순간 `istio_requests_total` 은 (source_workload × destination_service × response_code × …) 곱으로 **카디널리티가 폭발**합니다. 단일 프로메테우스의 한계에 가장 먼저 부딪히는 게 바로 이 메트릭입니다.

| 선택지 | 라이선스 / 거버넌스 | 언제 고르나 |
| --- | --- | --- |
| **Thanos** | Apache-2.0 / **CNCF Incubating** | 이미 프로메테우스 서버가 여러 대고 **그걸 그대로 두고 싶을 때.** 사이드카만 붙이면 전역 쿼리 + 오브젝트 스토리지 보존. **침습성이 가장 낮음** |
| **Cortex** | Apache-2.0 / **CNCF Incubating** | push 기반 멀티테넌트를 **단일 벤더 통제 없이** 원할 때 |
| **Grafana Mimir** | **AGPL-3.0** / Grafana Labs 단독 | 이미 그라파나 생태계에 투자했고 **AGPL을 받아들일 수 있을 때.** 설정이 가장 단순 |
| **VictoriaMetrics** | Apache-2.0 (오픈코어) | **운영·하드웨어 풋프린트 최소화.** 단 다운샘플링·retention filter·mTLS·LTS가 **Enterprise 유료** |

> **흔한 오해 정정 — Cortex는 죽지 않았습니다.** Mimir가 Cortex를 대체한 게 아니라, **2022-03-30에 Cortex를 포크해 갈라져 나간 것**이고 Cortex는 CNCF 아래에서 독립적으로 계속 갑니다(2026-08에도 기능 커밋). Mimir가 AGPLv3인 이유도 발표 블로그에 나옵니다 — Apache-2.0이 상용 전략과 맞지 않아 재라이선싱했다고 명시합니다.
>
> **순서가 중요합니다:** 넷 다 프로메테우스 **뒤에** 붙습니다. 장기저장을 붙이기 전에 **Istio 공식 권장인 계층적 페더레이션 + 레코딩 룰로 카디널리티를 먼저 줄이세요.** 예: `sum without(instance, kubernetes_namespace, kubernetes_pod_name) (istio_requests_total)`

### 7.6.4 로그 · 트레이스 · 프로파일링

**로그** — 이스티오 액세스 로그는 Envoy 사이드카(앰비언트에서는 ztunnel)의 stdout으로 나옵니다. 노드 에이전트가 tail해서 백엔드로 보내지만, **OTLP로 직접 보낼 수도 있습니다.**

```yaml
meshConfig:
  extensionProviders:
  - name: otel
    envoyOtelAls:
      service: opentelemetry-collector.observability.svc.cluster.local
      port: 4317
---
apiVersion: telemetry.istio.io/v1
kind: Telemetry
spec:
  accessLogging:
  - providers: [{ name: otel }]
```

- **Loki**는 라벨만 인덱싱하고 **로그 본문은 인덱싱하지 않습니다.** 수집·저장은 싸지만 라벨로 안 좁혀지는 쿼리는 전수 스캔입니다. Istio와 궁합이 좋은 건 pod/namespace/workload 라벨이 메트릭 라벨과 그대로 정렬되기 때문입니다.
- **수집 에이전트**: Fluentd는 아카이브되지 않았고 여전히 CNCF Graduated지만, **CNCF가 직접 Fluentd → Fluent Bit 마이그레이션 가이드를 냈습니다(2025-10).** 신규는 **Fluent Bit**를 쓰세요.
- **Grafana Agent는 아카이브됐고 Grafana Alloy가 대체**합니다. Vector는 **Datadog 소유**(MPL-2.0)라 로드맵이 상용 벤더를 위해 움직입니다.
- 라이선스 변화 두 건: **Elasticsearch는 2024-08 AGPL로 돌아왔고**(마케팅 페이지 말고 `LICENSE.txt`를 보세요), **OpenSearch는 2024-09 Linux Foundation 산하**로 이관했습니다.

**트레이싱 (8장 예고)**

- **Jaeger v2**는 2024-11 발표로 **OTel Collector 프레임워크 위에 재구축**됐습니다 — Jaeger 바이너리가 곧 OTel Collector 배포판입니다. **Jaeger 클라이언트 SDK는 2022년 은퇴**하고 OTel SDK로 대체됐습니다.
- **Tempo 3.0**(2026-05 GA)은 아키텍처 파괴적 변경입니다 — **ingester와 compactor가 제거**되고 Kafka 버퍼링으로 대체, `tempo-cli migrate config` 필요. TraceQL metrics가 GA.
- 이스티오는 **`meshConfig`의 레거시 트레이싱 옵션 대신 Telemetry API로 전환하라**고 안내합니다. 백엔드는 `extensionProviders`에 한 번 정의하고, 범위별로 `Telemetry` CR로 고르는 2단계 패턴이 정석입니다.

**프로파일링** — 메트릭·로그·트레이스로 "어느 서비스가 느린가"까지 좁힌 뒤 **"어느 코드 라인이 CPU를 먹는가"를** 답하는 계층입니다. **이스티오 메트릭이 절대 답하지 못하는 질문**이고, 그래서 eBPF의 가장 논쟁 없는 승리 영역입니다. **Grafana Pyroscope**(AGPL-3.0) / **Parca**(Apache-2.0) 중 선택. OTel Profiles는 아직 **Alpha**라 프로덕션 크리티컬 경로에 두지 마세요.

### 7.6.5 eBPF — 대체재가 아니라 보완재

"사이드카 없이 eBPF로 하면 되지 않나"는 7장을 읽고 나면 자연스럽게 드는 생각입니다. 결론부터 말하면 **성립하지 않습니다.**

![eBPF와 서비스 메시의 가시성 차이](images/notes/istio-in-action/7-11.avif)

*핵심은 암호화 지점이 어디냐 입니다. eBPF는 커널 소켓 레벨에서 보는데, 그 지점에서 트래픽은 이미 암호문입니다. 오른쪽 앰비언트 모드를 보면 사이드카를 없앨수록 eBPF 가시성이 오히려 나빠진다는 것도 보입니다.*

**얻는 것**

- 사이드카 주입도, **파드 재시작도 없습니다.** 앱 변경 0, 언어 무관.
- 프록시가 파드마다가 아니라 노드마다 하나(혹은 아예 없음) → **파드당 오버헤드가 낮음.**
- **메시에 가입하지 않은 프로세스까지** 보입니다 — DB, 데몬셋, 레거시 서비스.
- **네트워크 플로·DNS·정책 드롭 관측**은 이스티오가 잘 못하는 영역이고 eBPF가 압도적으로 쌉니다.

**못 하는 것 — 이스티오 환경에서 특히 치명적인 것들**

| 문제 | 내용 |
| --- | --- |
| **TLS/mTLS 앞에서 눈이 멀다** | uprobe로 TLS 라이브러리 함수를 후킹해 평문을 가로채야 합니다. OpenSSL·Go는 뚫리지만 **정적 링크 바이너리·Rust rustls·Java JSSE는 어렵거나 별도 에이전트가 필요**합니다 |
| **메시와 같이 못 씁니다** | Cilium 문서 원문: *"Cilium과 Istio의 L7 HTTP 정책 제어를 둘 다 쓰는 것은 권장되지 않는다"*, *"Istio가 mTLS로 암호화한 트래픽은 Cilium이 L7 정책 강제를 위해 접근할 수 없다"* |
| **앰비언트에서는 더 나빠집니다** | ztunnel이 HBONE으로 터널링(포트 15008)하므로 *"실제 출발지·목적지도, L7 정보도 전혀 보이지 않는다"*. 즉 **사이드카를 없앨수록 eBPF 가시성은 오히려 나빠집니다** |
| **트레이스 컨텍스트 전파** | OBI 문서 자체 인정: HTTPS에서는 TCP/IP 패킷 레벨에 넣기 때문에 **"다른 OBI 계측 서비스에만" 보낼 수 있고, "L7 프록시와 로드밸런서가 이 전파를 파괴"합니다**. **Envoy가 바로 그 L7 프록시입니다** |
| **관측할 뿐 제어하지 못함** | 재시도·타임아웃·서킷 브레이킹·카나리·폴트 인젝션 — **전부 메시의 영역**입니다 |
| **노드 전역 특권 필요** | OBI는 커널 5.8+, root 또는 해당 capability. **Go 컨텍스트 전파는 `CAP_SYS_ADMIN`/privileged**가 필요하고, **Secure Boot(커널 lockdown)가 켜져 있으면 동작하지 않습니다** |

> **Cilium 고유 함정 — L7 관측과 L7 강제가 같은 기능입니다.** 공식 문서 원문: *"L7 네트워크 정책은 가시성을 켜는 데서 그치지 않고 파드를 드나드는 트래픽을 제한한다"*. 즉 **Hubble L7을 켜는 건 모니터링 토글이 아니라 보안 태세 변경**입니다. 예전에 관측만 켜던 `io.cilium.proxy-visibility` 애너테이션은 v1.20 문서에서 사라졌습니다.

**그래서 언제 어느 쪽을 고르나**

| 상황 | 선택 |
| --- | --- |
| 메시가 없고, 앱 수정 없이 **빠르게** RED 메트릭을 원한다 | **OBI / Coroot / Odigos** |
| 이미 Cilium이 CNI고, **L3/L4 플로·DNS·정책 드롭** 가시성이 주 관심 | **Hubble** |
| **모든 서비스에 보편적 HTTP RED 메트릭**이 필요하다 | **eBPF 아님** — Istio(사이드카 또는 waypoint) |
| 관측을 넘어 **재시도·카나리·폴트 인젝션**이 필요하다 | **eBPF 아님** — 메시 |
| **코드 라인 수준 성능 분석** | **Pyroscope / Parca** (메시와 무관, 병행) |
| Istio mTLS가 켜진 상태에서 eBPF로 L7을 보겠다 | **성립하지 않음** |

> **도구 상태 메모:** **Beyla는 2025-05 OpenTelemetry에 기증되어 OBI**가 됐고 아직 **v0.10(pre-1.0)** 입니다 — 마이너 버전 간 breaking change를 공지하는 단계라 프로덕션 전제로 소개하면 안 됩니다. **Pixie는 아카이브되진 않았지만 정식 릴리스가 19개월째 없습니다.** **Odigos는 CNCF Sandbox 프로젝트가 아니라 멤버사**입니다.

### 7.6.6 서비스 메시 대안 — 관찰 가능성 관점

|  | Istio 사이드카 | Istio 앰비언트 | Linkerd | Cilium |
| --- | --- | --- | --- | --- |
| L7 RED 메트릭 기본 제공 | 전 구간 자동 | **waypoint 있어야만** | 전 구간 자동 | **아니오** — 워크로드별 L7 정책 필요 |
| 메트릭 스키마 | `istio_*` | `istio_*` | `request_total` / `response_latency_ms` | `cilium_*`/`hubble_*`/`envoy_*` |
| 라이선스 / 배포 | Apache-2.0 | **무료 stable OSS 빌드 없음 — edge만** | Apache-2.0 | **BUSL** |

- **Linkerd**: 라이선스가 아니라 **배포**가 바뀌었습니다. 2024-05부터 오픈소스 프로젝트는 **edge 릴리스만** 발행하고 stable 아티팩트는 벤더(사실상 Buoyant 하나)가 만듭니다. CNCF Graduated 상태는 유지. ⚠️ **`response_latency_ms`는 time-to-first-byte이지 전체 응답 시간이 아닙니다** — `istio_request_duration_milliseconds` 와 **의미가 달라서 직접 비교하면 안 됩니다.**
- **Consul**: 2023-08 **BUSL** 전환(IBM 인수 후에도 되돌리지 않음). 관찰 가능성이 **기본 비활성**이며, 하부가 Envoy라 메트릭 어휘가 `envoy_*` — **기존 Istio 대시보드는 이식되지 않습니다.**
- **Gateway API**: GAMMA는 GA이지만 **관찰 가능성을 표준화하지는 않습니다** — 메트릭·텔레메트리 명세가 없습니다. **Gateway API를 도입해도 Istio·Cilium·Linkerd의 메트릭이 호환되지는 않습니다.** 또 이스티오 문서는 Gateway API를 *"미래에 기본 API로 만들 의도"* 라고만 하며, **아직 기본/권장 경로가 아닙니다.**
- **Kiali 버전 호환**: Istio **1.30 → Kiali 2.26+**, Istio **1.29 → Kiali 2.21+**. 프로메테우스를 끄면 Kiali는 뜨긴 하지만 **그래프·메트릭 탭·트래픽 탭·요청률 기반 health가 전부 사라집니다.**

### 7.6.7 상용·매니지드 — 기존 대시보드를 지킬 수 있는가

이스티오는 **메트릭은 프로메테우스 포맷, 트레이스는 OTLP**로 냅니다. 그래서 실질적으로 중요한 질문은 하나입니다 — **기존 PromQL과 기존 Istio 대시보드를 그대로 쓸 수 있는가?**

| 벤더 | OTLP 수신 | remote_write | PromQL | Istio 대시보드 |
| --- | --- | --- | --- | --- |
| **Grafana Cloud** | 예 (HTTP) | **예** | **예** | **그대로 유지** |
| **AWS AMP** / **Azure 관리형 Prometheus** | 아니오 | **예** | **예** | **그대로 유지** |
| **Chronosphere** | 예 | **예** | **예** | **그대로 유지** |
| **New Relic** | **예 (gRPC+HTTP, 권장 경로)** | **예** | 아니오 (NRQL) | 재작성 필요 |
| **Honeycomb** | **예 (gRPC+HTTP)** | 아니오 | 아니오 | 재작성 필요 |
| Dynatrace / Elastic / Splunk / Datadog / AWS CloudWatch | 예 — **HTTP만** | 대체로 아니오 | 아니오 | 재작성 필요 |

> **함정 ① — Google GMP는 `remote_write`를 명시적으로 비권장합니다.** 문서 원문: *"수집 파이프라인의 어느 지점에서든 Prometheus Remote Write를 쓰는 것은 권장되지 않는다 — 이 프로토콜은 의도적으로 TYPE 정보를 버리기 때문"*. 즉 **"기존 프로메테우스의 remote_write를 매니지드로 돌린다"는 이관 계획은 AWS·Azure에서는 되고 Google에서는 실패합니다.**
>
> **함정 ② — Istio `opentelemetry` provider의 gRPC 문제.** Dynatrace·Splunk(메트릭)·Elastic·**모든 AWS OTLP 엔드포인트가 HTTP 전용**입니다. OTLP/gRPC를 직접 받는 곳은 **New Relic·Honeycomb·Google뿐**이고, 나머지는 전송 다운그레이드를 위해 **중간에 Collector가 반드시 필요**합니다.

### 7.6.8 SLO·알림 — 7장 최대의 공백

7장은 메트릭을 만들고 보는 법까지만 다룹니다. **대시보드는 사람이 볼 때만 작동합니다.**

SLO 계산에 필요한 건 딱 두 가지 — **좋은 이벤트 수**와 **전체 이벤트 수**. 이스티오는 이 둘을 **애플리케이션 코드를 한 줄도 건드리지 않고** 제공합니다. 이게 **서비스 메시가 SLO 실무에서 갖는 가장 실질적인 가치**입니다 — 조직 전체에 **균일한 스키마의 SLI**를 강제할 수 있다는 점.

> **쓰기 전에 함정 3가지를 못 박습니다.**
>
> ① **`reporter`를 반드시 고정하세요.** 안 고르면 source와 destination 양쪽이 같은 요청을 세서 **정확히 2배**가 됩니다.
>
> ② **앰비언트에서는 `reporter="waypoint"`** 입니다. waypoint가 없는 앰비언트 워크로드에는 `istio_requests_total` 이 아예 없어서 **SLO가 조용히 빈 값이 됩니다.**
>
> ③ **`response_code!~"5.."`는 4xx를 성공으로 칩니다.** 보통 이게 맞지만, 의도적 선택임을 문서화하세요.

**① 가용성 SLI — 성공률**

```plain text
sum(rate(istio_requests_total{
    reporter="destination",
    destination_service_name="catalog",
    destination_service_namespace="prod",
    response_code!~"5.."
  }[5m]))
/
sum(rate(istio_requests_total{
    reporter="destination",
    destination_service_name="catalog",
    destination_service_namespace="prod"
  }[5m]))
```

**② 지연 SLI — 분위수가 아니라 비율로**

분위수는 평균낼 수도, 합칠 수도, error budget으로 환산할 수도 없습니다. SLO에는 **"임계값 이내 요청의 비율"** 을 쓰세요.

```plain text
sum(rate(istio_request_duration_milliseconds_bucket{
    reporter="destination", destination_service_name="catalog", le="500"
  }[5m]))
/
sum(rate(istio_request_duration_milliseconds_count{
    reporter="destination", destination_service_name="catalog"
  }[5m]))
```

> ⚠️ **`le="500"` 버킷 경계가 실제로 존재해야 합니다.** 기본 버킷에 원하는 경계가 없으면 값이 안 나옵니다. Telemetry API로 버킷을 조정하거나 가장 가까운 경계에 목표를 맞추세요. (프로메테우스 3.x에서는 `le="500"` 이 `le="500.0"` 으로 정규화된다는 점도 같이 기억하세요 — 7.5.7 참조)

**③ Multi-window multi-burn-rate 알림**

Google SRE Workbook 권장 조합 — 30일 기간, **99.9% SLO** 기준:

| 심각도 | 긴 창 | 짧은 창 | Burn rate | 소진 budget |
| --- | --- | --- | --- | --- |
| **Page** | 1시간 | 5분 | **14.4×** | 2% |
| **Page** | 6시간 | 30분 | **6×** | 5% |
| **Ticket** | 3일 | 6시간 | **1×** | 10% |

짧은 창은 보통 긴 창의 1/12이며, **복구된 뒤에도 알림이 계속 울리는 것을 막는 역할**입니다.

> **손으로 쓰지 마세요.** **Sloth**나 **Pyrra**에 SLI 쿼리와 목표치만 주면 3쌍의 버닝 룰 + 레코딩 룰을 전부 생성해 줍니다. **OpenSLO는 도구가 아니라 명세**이므로 "Sloth냐 Pyrra냐 OpenSLO냐"는 잘못된 질문입니다 — OpenSLO로 정의하고 Sloth/Pyrra로 렌더링하는 조합이 자연스럽습니다.
>
> **보너스 — `response_flags`:** 이스티오 고유 라벨로 Envoy가 왜 실패시켰는지를 구분합니다(`UO` 서킷브레이커, `URX` 재시도 소진, `UT` 타임아웃 — part6에서 본 그 플래그들). **"앱이 5xx를 냈다"와 "메시가 요청을 끊었다"를 분리**할 수 있어 error budget 소진의 책임 소재를 가릴 때 유용합니다.

### 7.6.9 한 장 대조표

| 계층 | 7장이 가르치는 것 | 프로덕션에서 추가로 필요한 것 | 왜 |
| --- | --- | --- | --- |
| **계측** | Envoy가 `istio_*` 노출 | 앱 레벨 OTel SDK, 프로파일링, (선택) eBPF | 메시는 **네트워크 경계**만 봅니다. 앱 내부·코드 라인·DB 쿼리는 못 봅니다 |
| **수집** | PodMonitor로 스크랩 | 페더레이션 + 레코딩 룰, OTel Collector, 로그 에이전트 | 카디널리티. **Istio 공식 문서가 직접 권장** |
| **저장** | 단일 프로메테우스 | Thanos/Cortex/Mimir/VM + 로그·트레이스 백엔드 | 데모 구성은 보존 **6시간**, 공식적으로 **프로덕션 금지** |
| **시각화** | 그라파나, Kiali | Correlations, 로그·트레이스 UI | 메트릭만으로는 근본 원인에 도달 못 함 |
| **알림** | **(없음)** | Alertmanager + Sloth/Pyrra + error budget | **7장 최대의 공백.** 대시보드는 사람이 볼 때만 작동합니다 |

> **메트릭 → 트레이스 이동에 exemplar를 기대하지 마세요.** istio.io 메트릭 문서 전체에 exemplar 언급이 **0건**입니다(명시적 부정 문구가 없어 "미지원"으로 단정하진 않습니다). 현실적인 경로는 **Grafana Correlations(GA)** 로 명시적 링크를 만들거나, 앱 레벨 OTel SDK 계측에서 exemplar를 얻거나, Tempo metrics-generator가 만든 RED 메트릭을 쓰는 것입니다.

### 트러블슈팅 치트시트

```bash
# 1. 프록시가 어떤 통계를 갖고 있는가
kubectl exec -it deploy/<app> -c istio-proxy -n <ns> -- curl localhost:15000/stats | grep <target>
kubectl exec -it deploy/<app> -c istio-proxy -n <ns> -- curl localhost:15000/clusters | grep <target>

# 5. 프로메테우스가 긁어가고 있는가
#    UI > Status > Service Discovery / Targets 에서 job=pilot, job=envoy-stats 확인
```

### 마무리

- **관찰 가능성은 도구가 아니라 시스템의 특성**입니다. 이스티오는 그중 **애플리케이션 수준 네트워크 계측**을 담당할 뿐, 애플리케이션 계측·수집 인프라·탐색 도구가 함께 있어야 합니다.
- 데이터 플레인과 컨트롤 플레인은 **내부에서 일어나는 일을 아주 자세히 보고**합니다. 다만 기본값은 카디널리티를 고려해 **잘려 있으므로**, 필요한 것만 골라서 켜야 합니다.
- 메트릭 커스터마이징은 **메트릭 → 디멘션 → 속성**의 계층을 이해하는 것이 전부입니다. 속성이 디멘션의 값을 채우고, 디멘션 조합이 메트릭의 항목을 나눕니다.
- **EnvoyFilter는 강력하지만 버전에 민감합니다.** `proxyVersion`이 실제 프록시 버전과 어긋나면 조용히 아무 일도 일어나지 않습니다. 1.17+ 에서는 상당 부분을 **Telemetry API**로 대체할 수 있습니다.
- **책은 1.13 기준입니다.** 개념(메트릭·디멘션·속성)과 7.2·7.3절은 그대로 유효하지만, **7.4절의 설정 경로는 1.21에서 사라졌습니다.** 지금 쓰는 방법은 7.5절을 보세요.
- **7장은 저장과 알림 계층이 통째로 비어 있습니다.** 프로덕션 이관 순서는 ① 페더레이션+레코딩 룰로 카디널리티 줄이기 → ② 장기 저장소 붙이기 → ③ SLO 기반 알림 세우기 입니다(7.6절).
- **eBPF는 이스티오의 대체재가 아닙니다.** mTLS가 켜진 메시 안에서는 L7을 볼 수 없고(Cilium 문서가 직접 인정), 앰비언트의 HBONE 터널에서는 출발지·목적지 신원까지 가려지며, **관측할 뿐 재시도·카나리를 하지 못합니다.** 서로 다른 계층의 보완재입니다.
