## 들어가며 — '기본적으로 안전하다'는 말의 의미

애플리케이션 보안이란 **인가받지 않은 사용자가 오염시키거나 훔치거나 접근해서는 안 되는 데이터를 지키는 모든 행동**을 말합니다. 사용자 데이터를 지키려면 두 가지가 필요합니다.

- 리소스 접근을 허가하기 전에 **사용자 인증 및 인가**
- 여러 네트워크 장치를 거쳐가는 동안 도청을 막는 **전송 중 데이터 암호화**

> **인증(authentication)** 은 클라이언트나 서버가 자신의 정체를 입증하는 절차입니다. 아는 것(패스워드), 갖고 있는 것(장치·인증서), 자기 자신(지문 같은 고유 특성)을 이용합니다.
> **인가(authorization)** 는 이미 **인증된** 사용자가 생성·조회·갱신·삭제 같은 작업을 수행하는 것을 허용하거나 거부하는 절차입니다. 순서가 중요합니다 — **인가는 언제나 인증 다음**입니다.

part4에서 트래픽을 메시로 들이는 방법을 다루면서 보안을 몇 가지 건드렸다면, 이번 장은 **서비스 메시 기능으로 보안 태세(security posture)를 투명하게 개선하는 방법**을 정면으로 다룹니다. 흔히 "이스티오는 기본적으로 안전하다"고 하지만, 정확히는 **기본적으로는 대부분 안전하다**는 뜻이고 나머지는 우리가 해야 할 몫입니다. 이번 장은 그 나머지가 무엇인지에 대한 이야기입니다.

> **보안 태세(security posture)란:** 조직이 사이버 위협을 얼마나 잘 예견·방지·대응할 수 있는지를 뜻합니다. 방화벽, 침입탐지, 인증/권한 프로토콜, 암호화 같은 모든 지침을 포함하며, 새 기술과 함께 오는 취약점에 대한 이해와 그것을 감지·방어할 사람·절차·기술을 갖춘 조직을 필요로 합니다.

## 9.1 애플리케이션 네트워크 보안의 필요성

### 9.1.1 서비스 간 인증 — SPIFFE

안전하려면 서비스는 **자신이 상호작용하는 서비스를 모두 인증**해야 합니다. 다시 말해 **확인할 수 있는 ID 문서를 제시한 후에만** 다른 서비스를 신뢰해야 하고, 보통 그 문서는 발급한 신뢰할 수 있는 제3자에게 확인합니다.

이스티오는 **SPIFFE**(Secure Production Identity Framework For Everyone)를 사용해 서비스들의 ID 발급을 자동화합니다.

- 분산 환경에서 **보편적인 Identity 컨트롤 플레인**을 제공하는 표준 프레임워크입니다.
- CNCF 프로젝트이며 Kubernetes, AWS/GCP/Azure, Istio, Consul 등에서 구현합니다. 표준 구현체로 **SPIRE**가 있습니다.
- 명세의 핵심은 **수명이 짧은 암호학적 ID 문서 — SVID** 를 간단한 API로 발급하는 부분입니다. 워크로드는 이 문서로 다른 워크로드에 인증합니다(TLS 커넥션 수립, JWT 서명/검증 등).

### 9.1.2 최종 사용자 인증 — 자격 증명

최종 사용자 인증은 사용자의 개인 데이터를 저장하는 애플리케이션의 핵심입니다. 프로토콜은 여러 가지지만 대부분 **인증 서버로 리다이렉션하는 것**이 핵심입니다.

1. 사용자가 인증 서버에서 로그인에 성공하면 사용자 정보를 담은 **자격 증명**(HTTP 쿠키나 JWT)을 받습니다.
2. 사용자는 인증을 위해 이 자격 증명을 서비스에 제시합니다.
3. 서비스는 접근을 허용하기 전에 **발급한 인증 서버에 자격 증명을 검증**합니다.

### 9.1.3 인가

인가는 **호출자가 인증된 후** 진행됩니다. 호출자가 '누구'인지 서버가 식별하고 나면, 서버는 이 ID가 '어떤' 작업을 수행하도록 허용돼 있는지 확인하고 승인하거나 거부합니다. 이스티오는 서비스 인증과 ID 모델을 기반으로 **서비스 사이에, 그리고 최종 사용자와 서비스 사이에** 세분화된 인가 기능을 제공합니다.

### 9.1.4 모놀리스와 마이크로서비스의 보안 비교

둘 다 최종 사용자 및 서비스 간 인증·인가를 구현해야 한다는 점은 같습니다. 차이는 **무엇을 ID의 근거로 삼을 수 있는가**에서 갈립니다.

| 구분 | 모놀리스 | 마이크로서비스 |
| --- | --- | --- |
| 커넥션 수 | 적음 | 보호해야 할 커넥션·요청이 훨씬 많음 |
| 운영 환경 | 가상/물리 머신 같은 **정적** 인프라 | 클라우드·컨테이너 오케스트레이션 같은 **동적** 환경 |
| ID의 근거 | **고정 IP**를 심기 좋음 (인증서·방화벽 규칙에 그대로 사용) | 수많은 서버로 스케줄링되고 수명이 짧아 **IP는 미덥지 못함** |
| 네트워크 경계 | 대체로 하나 | 여러 클라우드 프로바이더, 온프레미스에 걸쳐 있을 수 있음 |

마이크로서비스는 쉽게 수백, 수천 개로 불어나므로 정적 환경에서는 운영할 수 없습니다. 그래서 **IP 주소를 쓰는 전통적인 방법이 무너지고**, 이 문제를 해결해 고도로 동적이고 이질적인 환경에서 ID를 제공하고자 이스티오는 SPIFFE 명세를 사용합니다.

### 9.1.5 이스티오가 SPIFFE를 구현하는 방법 — SVID

SPIFFE ID는 RFC 3986 호환 URI로, 다음 형식입니다.

```plain text
spiffe://trust-domain/path
```

- **trust-domain** — 개인이나 조직 같은 **ID 발급자**
- **path** — trust-domain 내에서 워크로드를 **유일하게 식별**

path가 워크로드를 식별하는 방법은 명세에 정해져 있지 않아 **구현자가 결정**합니다. **이스티오는 이 path를 워크로드가 사용하는 서비스 어카운트로 채웁니다.**

```plain text
spiffe://cluster.local/ns/istioinaction/sa/catalog
```

SPIFFE ID는 **SVID**(SPIFFE Verifiable Identity Document)라고 하는 **X.509 인증서로 인코딩**되며, 이스티오 컨트롤 플레인이 워크로드마다 만들어냅니다. 이 인증서가 서비스 간 통신의 전송을 암호화해 보호합니다.

> **왜 서비스 어카운트인가:** 쿠버네티스가 이미 파드마다 부여하고 관리해 주는, 플랫폼이 보증하는 유일한 워크로드 ID이기 때문입니다. 9.3.7에서 `principals: ["cluster.local/ns/istioinaction/sa/webapp"]` 같은 정책을 쓸 수 있는 근거가 전부 여기서 나옵니다.

### 9.1.6 이스티오 보안 요약 — 리소스 세 개

프록시를 설정하는 **메시 운영자의 관점**으로 바꿔보면, 이스티오 보안은 커스텀 리소스 세 개로 정리됩니다.

| 리소스 | 하는 일 |
| --- | --- |
| **PeerAuthentication** | 서비스 간 트래픽을 인증하도록 프록시를 설정. 인증에 성공하면 **피어 인증서에 인코딩된 정보를 추출**해 인가에 쓸 수 있게 함 |
| **RequestAuthentication** | 최종 사용자 자격 증명을 **발급 서버에 확인**해 인증하도록 프록시를 설정. 역시 자격 증명의 정보를 추출 |
| **AuthorizationPolicy** | 앞선 두 리소스가 추출한 정보를 토대로 요청을 **인가하거나 거부** |

> **핵심 연결고리 — 필터 메타데이터.** 자격 증명(SVID나 JWT)에서 추출한 정보는 **필터 메타데이터**로 저장되고, 이것이 곧 **커넥션 ID**를 나타냅니다. AuthorizationPolicy는 그 커넥션 ID에 기반해 허용/거부를 결정합니다. 즉 **앞의 두 리소스는 "누구인지"를 채워 넣기만 하고, 실제 판단은 전부 AuthorizationPolicy가 합니다.**

이스티오 보안 아키텍처를 한 줄씩 옮기면 이렇습니다.

- **Istio CA는 키와 인증서를 관리**하며, 인증서의 SAN은 SPIFFE 형식입니다.
- **istiod는 인증·인가 보안 정책을 메시의 모든 사이드카에 배포**합니다.
- **사이드카는 istiod가 배포한 보안 정책에 따라 인증·인가를 시행**합니다.

## 9.2 자동 상호 TLS (Auto mTLS)

사이드카 프록시가 주입된 서비스 사이의 트래픽은 **기본적으로 암호화되고 서로 인증**합니다. 인증서를 발급하고 로테이션하는 절차를 자동화하는 것은 매우 중요한데, 역사적으로 사람이 관리할 때 오류가 발생하기 쉬웠고 그로 인해 **불필요하고 비용이 많이 드는 서비스 중단**이 발생했기 때문입니다.

그런데 '기본적으로 안전한' 상태에서 더 나아가려면 두 가지를 해야 합니다.

1. **서로 인증한 트래픽만 허용하도록 설정**해야 합니다. 왜 이게 설치 기본값이 아닌지 궁금할 수 있는데, 이는 **메시 채택을 쉽게 하려는 설계 결정**입니다. 여러 팀이 각자 서비스를 관리하는 큰 조직에서는 모든 서비스를 메시로 옮기는 데 몇 달, 몇 년이 걸릴 수 있습니다.
2. **최소 권한 원칙을 지켜** 서비스마다 정책을 만들고 기능에 필요한 최소한의 접근만 허용해야 합니다. 서비스의 ID를 나타내는 **인증서가 잘못된 사람에게 넘어갔을 때 피해 범위를 좁힐 수 있기** 때문에 아주 중요합니다.

> **TLS vs mTLS.** TLS는 도청·간섭·위조를 막기 위해 설계됐고 (1) 지원 알고리듬 교환 (2) 키 교환·인증 (3) 대칭키 암호화 및 메시지 인증의 3단계를 거칩니다. **mTLS는 여기에 서버도 클라이언트의 인증서를 확인하는 단계가 더해진 것**입니다. 즉 "양쪽 다 신분증을 보여준다"가 전부입니다.

### 9.2.1 환경 설정하기

실습에는 서비스 세 개를 씁니다. 이번 장의 주인공은 **sleep** 인데, **사이드카 프록시가 없어서 상호 인증을 할 수 없는 레거시 워크로드** 역할입니다.

```bash
# catalog와 webapp 배포
kubectl apply -f services/catalog/kubernetes/catalog.yaml -n istioinaction
kubectl apply -f services/webapp/kubernetes/webapp.yaml -n istioinaction

# webapp과 catalog의 gateway, virtualservice 설정
kubectl apply -f services/webapp/istio/webapp-catalog-gw-vs.yaml -n istioinaction

# default 네임스페이스에 sleep 앱 배포
kubectl apply -f ch9/sleep.yaml -n default

# 확인
kubectl get deploy,pod,sa,svc,ep
kubectl get deploy,svc -n istioinaction
kubectl get gw,vs -n istioinaction
```

```yaml
# ch9/sleep.yaml
...
    spec:
      serviceAccountName: sleep
      containers:
      - name: sleep
        image: governmentpaas/curl-ssl
        command: ["/bin/sleep", "3650d"]
        imagePullPolicy: IfNotPresent
        volumeMounts:
        - mountPath: /etc/sleep/tls
          name: secret-volume
      volumes:
      - name: secret-volume
        secret:
          secretName: sleep-secret
          optional: true
```

레거시 sleep 워크로드에서 webapp으로 **평문 요청**을 보내봅니다.

```bash
# 요청 실행
kubectl exec deploy/sleep -c sleep -- curl -s webapp.istioinaction/api/catalog -o /dev/null -w "%{http_code}\n"

# 반복 요청
watch 'kubectl exec deploy/sleep -c sleep -- curl -s webapp.istioinaction/api/catalog -o /dev/null -w "%{http_code}\n"'
```

응답이 성공했다는 것은 서비스들이 올바르게 준비됐으며 **webapp이 sleep의 평문 요청을 받아들였다**는 뜻입니다. 키알리에서 네임스페이스(default, istioinaction)를 선택하고 Show Legend를 켜보면 `unknown → webapp` 구간이 **평문 통신**으로 표시됩니다.

> 기본적으로 이스티오가 평문 요청을 허용하는 이유는 앞서 말한 그대로입니다 — **모든 워크로드를 메시로 옮길 때까지 서비스 중단을 일으키지 않고 점진적으로 채택**할 수 있게 하기 위해서입니다. 그리고 이 기본값은 PeerAuthentication으로 바꿀 수 있습니다.

### 9.2.2 PeerAuthentication 리소스 이해하기

PeerAuthentication은 워크로드가 **mTLS를 엄격하게 요구**하거나 **평문 트래픽도 받아들이게** 설정합니다. 각각 `STRICT`, `PERMISSIVE` 모드입니다. 적용 범위는 세 가지입니다.

| 범위 | 적용 대상 | 조건 |
| --- | --- | --- |
| **Mesh-wide** | 메시의 모든 워크로드 | **이스티오 설치 네임스페이스**에 만들고 이름이 **`default`** 여야 함 |
| **Namespace-wide** | 해당 네임스페이스의 모든 워크로드 | 이름 `default` 컨벤션 |
| **Workload-specific** | 셀렉터에 부합하는 워크로드 | `selector.matchLabels` 지정 |

> 메시 범위 리소스 이름을 `default`로 짓는 것은 **필수가 아닌 컨벤션**입니다. 메시 범위 PeerAuthentication을 **딱 하나만** 두기 위한 장치입니다.

#### ① 메시 범위 정책으로 모든 미인증 트래픽 거부하기

```yaml
# ch9/meshwide-strict-peer-authn.yaml
apiVersion: "security.istio.io/v1beta1"
kind: "PeerAuthentication"
metadata:
  name: "default"             # Mesh-wide policies must be named "default"
  namespace: "istio-system"   # Istio installation namespace
spec:
  mtls:
    mode: STRICT              # mutual TLS mode
```

```bash
# 적용
kubectl apply -f ch9/meshwide-strict-peer-authn.yaml -n istio-system

# 요청 실행
kubectl exec deploy/sleep -c sleep -- curl -s http://webapp.istioinaction/api/catalog -o /dev/null -w "%{http_code}\n"
000
command terminated with exit code 56

# 확인
kubectl get PeerAuthentication -n istio-system
kubectl logs -n istioinaction -l app=webapp -c istio-proxy -f
```

```plain text
[2025-05-01T08:32:08.511Z] "- - -" 0 NR filter_chain_not_found - "-" 0 0 0 - "-" "-" "-" "-" "-" - - 10.10.0.17:8080 10.10.0.16:51930 - -
```

> **로그 읽는 법.** `NR`은 **Non-Route** — 엔보이에서 **라우팅까지 가지 못한 단계**에서 난 에러라는 뜻입니다. `filter_chain_not_found`는 해당 리스너에서 제공된 **SNI·IP·포트·ALPN 조건에 맞는 filter_chain이 설정에 없다**는 뜻입니다. 즉 평문으로 들어온 커넥션을 받아줄 체인 자체가 사라진 것입니다. **403이 아니라 커넥션 자체가 끊어지는 것**이 인가(9.3) 거부와의 결정적 차이입니다.

STRICT는 좋은 기본값이지만, **진행 중인 프로젝트에서 그런 급격한 변화는 실현 가능성이 없습니다.** 워크로드를 옮기려면 여러 팀의 협업이 필요하기 때문입니다. 더 나은 방법은 제한을 **점진적으로 늘리고** 팀들에게 시간을 주는 것이고, `PERMISSIVE`가 정확히 그 역할입니다.

#### ② 상호 인증하지 않은 트래픽 허용하기

**네임스페이스 범위 정책은 메시 범위 정책을 덮어씁니다.**

```bash
cat << EOF | kubectl apply -f -
apiVersion: "security.istio.io/v1beta1"
kind: "PeerAuthentication"
metadata:
  name: "default"             # "default" 네이밍 컨벤션 — 네임스페이스 범위 리소스는 하나만
  namespace: "istioinaction"  # 정책을 적용할 네임스페이스
spec:
  mtls:
    mode: PERMISSIVE          # PERMISSIVE allows HTTP traffic.
EOF
```

```bash
# 요청 실행
kubectl exec deploy/sleep -c sleep -- curl -s http://webapp.istioinaction/api/catalog -o /dev/null -w "%{http_code}\n"

# 확인
kubectl get PeerAuthentication -A

istio-system    default   STRICT       2m51s
istioinaction   default   PERMISSIVE   7s

# 다음 실습을 위해 삭제 : PeerAuthentication 단축어 pa
kubectl delete pa default -n istioinaction
```

하지만 이건 **istioinaction 네임스페이스 전체**를 열어버린 것입니다. 좀 더 좁혀봅시다 — 미인증 트래픽은 **sleep → webapp 구간만** 허용하고, **catalog에는 STRICT를 계속 유지**합니다. 이렇게 하면 보안이 뚫렸을 때 **공격 표면을 더 좁힐 수 있습니다.**

#### ③ 워크로드별 PeerAuthentication 정책 적용하기

```yaml
# ch9/workload-permissive-peer-authn.yaml
apiVersion: "security.istio.io/v1beta1"
kind: "PeerAuthentication"
metadata:
  name: "webapp"
  namespace: "istioinaction"
spec:
  selector:
    matchLabels:
      app: "webapp"   # 레이블이 일치하는 워크로드만 PERMISSIVE로 동작
  mtls:
    mode: PERMISSIVE
```

이름을 `default`에서 `webapp`으로 바꾼 것은 **동작이 달라져서가 아니라**, 네임스페이스 전체에 적용되는 정책만 `default`로 짓는 컨벤션을 따르려는 것입니다.

#### ④ 추가 인증 모드 두 가지

대부분은 STRICT나 PERMISSIVE를 쓰지만 두 가지가 더 있습니다.

| 모드 | 의미 |
| --- | --- |
| **UNSET** | 부모의 PeerAuthentication 정책을 **상속**한다 |
| **DISABLE** | 트래픽을 **터널링하지 않는다**. 프록시를 거치지 않고 서비스로 바로 보낸다 |

#### ⑤ tcpdump로 서비스 간 트래픽 스니핑하기

이스티오 프록시에는 **tcpdump가 설치돼 있습니다.** 다만 보안상 **권한(privileged)이 필요**하고 기본적으로 꺼져 있어, `values.global.proxy.privileged=true`로 설치를 업데이트해야 합니다.

> ⚠️ **격상시킨 서비스 프록시의 권한은 악의적 공격의 매개체가 될 수 있습니다.** 운영 환경 클러스터에서 이스티오를 설치할 때는 **프록시의 권한을 격상시키지 마세요.** 서비스 하나를 빠르게 디버깅하고 싶을 때는 `kubectl edit`로 디플로이먼트 필드를 수작업으로 바꿀 수 있습니다.

```bash

      proxy:
        privileged: true
...

kubectl exec -it -n istioinaction deploy/webapp -c istio-proxy -- whoami
kubectl exec -it -n istioinaction deploy/webapp -c istio-proxy -- sudo tcpdump -h
```

```bash
# 패킷 모니터링 실행 해두기
kubectl exec -it -n istioinaction deploy/webapp -c istio-proxy \
  -- sudo tcpdump -l --immediate-mode -vv -s 0 '(((ip[2:2] - ((ip[0]&0xf)<<2)) - ((tcp[12]&0xf0)>>2)) != 0) and not (port 53)'
```

| 옵션 | 의미 |
| --- | --- |
| `-l` | stdout을 라인 버퍼 모드로. 실시간으로 보기 좋게 |
| `--immediate-mode` | 커널 버퍼에 모으지 않고 캡처 즉시 사용자 공간으로 → 딜레이 최소화 |
| `-vv` | 패킷에 대한 최대한의 상세 정보 |
| `-s 0` | snap length 0 → **패킷 전체 내용** 캡처 |
| `'(((ip[2:2] - ...)) != 0) and not (port 53)'` | DNS 제외 + **TCP payload 길이가 0이 아닌 패킷만** — SYN/ACK/FIN 같은 핸드셰이크 패킷은 무시하고 실제 데이터만 |

#### ⑥ 워크로드 ID가 서비스 어카운트에 연결돼 있는지 확인하기

상호 인증 절을 끝내기 전에, 발급된 인증서가 **유효한 SVID인지**, **SPIFFE ID가 인코딩돼 있는지**, 그 ID가 **워크로드 서비스 어카운트와 일치하는지** 확인합니다.

```bash
# 루트 인증서 위치 확인
kubectl -n istioinaction exec deploy/webapp -c istio-proxy -- ls -l /var/run/secrets/istio/root-cert.pem
kubectl exec -it -n istioinaction deploy/webapp -c istio-proxy -- openssl x509 -in /var/run/secrets/istio/root-cert.pem -text -noout

# catalog 의 X.509 인증서 내용 확인
# openssl s_client   → TLS 서버에 연결해 handshake와 인증서 체인을 보여줌
# -showcerts         → 서버가 보낸 전체 인증서 체인 출력
# -connect ...:80    → Istio 서비스 catalog로 TCP 80 연결
# -CAfile ...        → Istio의 root CA로 서버 인증서 검증
kubectl -n istioinaction exec deploy/webapp -c istio-proxy \
  -- openssl s_client -showcerts \
  -connect catalog.istioinaction.svc.cluster.local:80 \
  -CAfile /var/run/secrets/istio/root-cert.pem | \
  openssl x509 -in /dev/stdin -text -noout
```

## 9.3 서비스 간 트래픽 인가하기

정책은 **인증된 주체('누가')** 와 **인가('무엇')** 를 결합해 형성되며, 누가 무슨 일을 할 수 있는지 정의합니다. 이스티오의 **AuthorizationPolicy**는 메시 범위·네임스페이스 범위·워크로드별 접근 정책을 정의하는 선언적 API입니다. 목적은 하나입니다 — **특정 ID가 뚫렸을 때 폭발 반경(blast radius)을 제한하는 것.**

### 9.3.1 이스티오에서 인가 이해하기

**각 서비스와 함께 배포되는 서비스 프록시가 곧 인가 집행(enforcement) 엔진입니다.** 요청을 거절할지 허용할지 판단하는 정책을 프록시가 모두 갖고 있기 때문에, **모든 결정이 프록시에서 직접 내려집니다** — 그래서 이스티오의 접근 제어는 대단히 효율적입니다.

```yaml
# ch9/allow-catalog-requests-in-web-app.yaml
apiVersion: "security.istio.io/v1beta1"
kind: "AuthorizationPolicy"
metadata:
  name: "allow-catalog-requests-in-web-app"
  namespace: istioinaction
spec:
  selector:
    matchLabels:
      app: webapp
  rules:
  - to:
    - operation:
        paths: ["/api/catalog*"]
  action: ALLOW
```

**인가 정책의 속성 세 가지**

| 필드 | 역할 |
| --- | --- |
| **selector** | 정책을 적용할 **워크로드 부분집합**을 정의 |
| **action** | 이 정책이 **ALLOW / DENY / CUSTOM** 중 무엇인지. **규칙 중 하나가 요청과 일치하는 경우에만** 적용됨 |
| **rules** | 정책을 **활성화할 요청을 식별**하는 규칙 목록 |

**규칙(rules) 이해하기**

인가 정책 규칙은 **커넥션의 출처(source)** 를 지정하고, 원한다면 부합해야 규칙을 활성화하는 **작업(operation) 조건**도 지정합니다. **정책은 규칙 중 하나의 출처와 작업 조건을 모두 만족할 때만 집행됩니다.**

| 필드 | 내용 |
| --- | --- |
| **from** | 요청의 출처. `principals`(출처 ID = SPIFFE ID, 부정형 `notPrincipals`), `namespaces`(출처 네임스페이스), `ipBlocks`(IP/CIDR) |
| **to** | 요청의 작업. 호스트, 메서드, 경로 등 |
| **when** | 규칙이 부합한 후 **충족해야 하는 조건** 목록 |

> ⚠️ **`principals` 와 `namespaces` 는 mTLS가 전제입니다.** 출처 ID와 출처 네임스페이스는 **참가자의 SVID에서 가져오기** 때문입니다. 사이드카가 없는 워크로드에는 SVID가 없고, 따라서 이 두 필드로는 절대 매칭되지 않습니다. **9.3.5에서 정확히 이 함정에 걸립니다.**

### 9.3.3 워크로드에 정책 적용 시 동작 변경 — deny-by-default 함정

> ⚠️ **세부 사항으로 들어가기 전에 미리 알아둬야 할 것이 있습니다. 문제가 발생하기 쉽고, 디버깅에 시간이 많이 낭비되기 때문입니다.**
> **워크로드에 ALLOW 인가 정책이 하나라도 적용되면, 그 워크로드로의 모든 트래픽은 기본적으로 거부됩니다.** 트래픽을 받아들이려면 **ALLOW 정책이 최소 하나는 부합해야** 합니다.

앞의 정책(`/api/catalog*` 만 허용)을 적용하고 두 경로를 호출해봅니다.

```bash
# 적용 전 확인 
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/api/catalog
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/hello/world   # 404 리턴

# AuthorizationPolicy 리소스 적용
kubectl apply -f ch9/allow-catalog-requests-in-web-app.yaml
kubectl get authorizationpolicy -n istioinaction

# 적용 후 확인
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/api/catalog
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/hello/world   # 403 리턴
RBAC: access denied

# 다음 실습을 위해 정책 삭제
kubectl delete -f ch9/allow-catalog-requests-in-web-app.yaml
```

**적용 전 404였던 요청이 적용 후 403이 됩니다.** 정책이 그 요청을 허용하지도 거부하지도 않았는데 거부된 것 — 이것이 **ALLOW 정책을 적용했을 때만 나타나는 deny-by-default 동작**입니다.

```json
                        ] } }
                    ],
                    "principals": [ { "andIds": { "ids": [ { "any": true } ] } } ]
                }
            }
        },
        "shadowRulesStatPrefix": "istio_dry_run_allow_"
    }
}
```

> `shadowRulesStatPrefix: istio_dry_run_allow_` 는 **실제로 차단하지 않고 통계만 수집**하는 dry-run 경로입니다. `istio_dry_run_allow_` 접두사가 붙은 메트릭이 생성됩니다 — part7에서 다룬 메트릭 체계와 그대로 이어집니다.

거부 로그는 rbac 로거를 debug로 올려두면 정확한 이유까지 보입니다.

```bash
docker exec -it myk8s-control-plane istioctl proxy-config log deploy/webapp -n istioinaction --level rbac:debug
kubectl logs -n istioinaction -l app=webapp -c istio-proxy -f
```

```plain text
[2025-05-03T10:08:52.918Z] "GET /hello/world HTTP/1.1" 403 - rbac_access_denied_matched_policy[none] - "-" 0 19 0 - "-" "curl/8.5.0" ... inbound|8080|| - 10.10.0.3:8080 10.10.0.13:50172 - -
```

> **`rbac_access_denied_matched_policy[none]`** — **일치한 정책이 없어서(none)** 거부됐다는 뜻입니다. 9.2의 `filter_chain_not_found`(커넥션 자체가 안 붙음)와 달리, 여기서는 **커넥션은 붙었고 HTTP 403이 돌아옵니다.** 증상을 보고 어느 계층 문제인지 가르는 기준입니다.

매번 "이 서비스에 ALLOW 정책이 붙어 있던가?"를 되묻지 않으려면, **다른 정책이 적용되지 않을 때 활성화되는 catch-all 거부 정책**을 두는 것이 좋습니다. 그러면 **허용하려는 트래픽만 생각하고 그 정책만 만들면 됩니다.**

### 9.3.4 전체 정책으로 기본적으로 모든 요청 거부하기

```yaml
# ch9/policy-deny-all-mesh.yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: deny-all
  namespace: istio-system   # 이스티오를 설치한 네임스페이스의 정책은 메시의 모든 워크로드에 적용된다
spec: {}                    # spec 이 비어있는 정책은 모든 요청을 거부한다
```

```bash
# 적용 전 확인 
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/api/catalog
curl -s http://webapp.istioinaction.io:30000/api/catalog

# 정책 적용
kubectl apply -f ch9/policy-deny-all-mesh.yaml
kubectl get authorizationpolicy -A

# 적용 후 : 내부 호출도, 인그레스 경유 호출도 모두 403
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/api/catalog
kubectl logs -n istioinaction -l app=webapp -c istio-proxy -f
```

```plain text
[2025-05-03T14:45:31.051Z] "GET /api/catalog HTTP/1.1" 403 - rbac_access_denied_matched_policy[none] - "-" 0 19 0 - ... inbound|8080|| - 10.10.0.3:8080 10.10.0.13:60780 - -
```

> **`spec: {}` 와 `spec.rules: [{}]` 를 헷갈리지 마세요.** 빈 spec은 **모든 요청 거부**, **빈 규칙**은 **모든 요청 허용**입니다.

```yaml
# ch9/policy-allow-all-mesh.yaml — 참고용 (모두 허용)
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-all
  namespace: istio-system
spec: 
  rules: 
  - {}
```

### 9.3.5 특정 네임스페이스에서 온 요청 허용하기

특정 네임스페이스에서 시작한 트래픽을 허용하려면 `source.namespaces` 를 씁니다.

```bash
cat << EOF | kubectl apply -f -
apiVersion: "security.istio.io/v1beta1"
kind: "AuthorizationPolicy"
metadata:
  name: "webapp-allow-view-default-ns"
  namespace: istioinaction   # istioinaction의 워크로드
spec:
  rules:
  - from:                    # default 네임스페이스에서 시작한
    - source:
        namespaces: ["default"]
    to:                      # HTTP GET 요청에만 적용 
    - operation:
        methods: ["GET"]
EOF
```

프록시 설정을 보면 네임스페이스 조건이 **SVID를 정규식으로 훑는 형태**로 번역돼 있습니다.

```json
"principals": [ { "andIds": { "ids": [ { "orIds": { "ids": [
  { "filterState": {
      "key": "io.istio.peer_principal",
      "stringMatch": { "safeRegex": { "regex": ".*/ns/default/.*" } }
  } }
] } } ] } } ]
```

그런데 호출하면 여전히 거부됩니다.

```bash
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/api/catalog
```

> **왜 그럴까요.** **sleep은 레거시 워크로드라 사이드카가 없고, 따라서 ID도 없습니다.** `io.istio.peer_principal` 이 비어 있으니 webapp 프록시는 이 요청이 default 네임스페이스에서 왔는지 **확인할 방법이 없습니다.** 9.3.1의 경고가 여기서 현실이 됩니다.

해결책은 두 가지입니다.

1. **sleep 서비스에 서비스 프록시 주입하기** ← **권장**. ID를 부트스트랩하고 상호 인증을 수행하므로 다른 워크로드가 요청의 출처와 네임스페이스를 확인할 수 있습니다.
2. **webapp에서 미인증 요청 허용하기** ← 덜 안전함

먼저 권장안을 실습해봅니다.

```bash
kubectl label ns default istio-injection=enabled
kubectl delete pod -l app=sleep

docker exec -it myk8s-control-plane istioctl proxy-status
NAME                                CLUSTER      CDS      LDS      EDS      RDS      ECDS       ISTIOD                  VERSION
sleep-6f8cfb8c8f-wncwh.default      Kubernetes   SYNCED   SYNCED   SYNCED   SYNCED   NOT SENT   istiod-8d74787f-n4c7b   1.17.8

# 호출 테스트 : default -> webapp 은 성공
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction

# 그러나 webapp -> catalog 는 deny-all 로 거부됨
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/api/catalog 
error calling Catalog service
```

```plain text
"GET /items HTTP/1.1" 403 - via_upstream - "-" 0 19 0 0 "-" "beegoServer" ... outbound|80||catalog.istioinaction.svc.cluster.local ...
"GET /api/catalog HTTP/1.1" 500 - via_upstream - "-" 0 29 1 1 "-" "curl/8.5.0" ... inbound|8080|| ...
```

> **로그 두 줄을 붙여서 읽으세요.** 안쪽 `GET /items` 가 **403**으로 막히고, 바깥쪽 `GET /api/catalog` 는 그 결과로 **500**을 냅니다. 사용자에게 보이는 500은 원인이 아니라 **증상**입니다 — part6에서 복원력 설정을 판독할 때와 같은 읽기 방식입니다.

다만 이 실습에서는 **"팀 전체가 휴가 중이라 사이드카를 못 넣는다"** 는 상황을 가정하고, 두 번째(덜 안전한) 접근법으로 진행합니다. 그래서 default 네임스페이스를 원복합니다.

```bash
kubectl label ns default istio-injection-
kubectl rollout restart deploy/sleep
docker exec -it myk8s-control-plane istioctl proxy-status
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction   # 거부 확인
```

### 9.3.6 미인증 레거시 워크로드에서 온 요청 허용하기

미인증 워크로드의 요청을 허용하려면 **`from` 필드를 삭제**해야 합니다. 그리고 이 정책을 **webapp에만** 적용하기 위해 셀렉터를 추가합니다. **이렇게 하면 catalog 서비스에는 여전히 상호 인증이 필요합니다.**

```yaml
# ch9/allow-unauthenticated-view-default-ns.yaml
apiVersion: "security.istio.io/v1beta1"
kind: "AuthorizationPolicy"
metadata:
  name: "webapp-allow-unauthenticated-view-default-ns"
  namespace: istioinaction
spec:
  selector:
    matchLabels:
      app: webapp
  rules:
    - to:
      - operation:
          methods: ["GET"]
```

```bash
kubectl apply -f ch9/allow-unauthenticated-view-default-ns.yaml
kubectl get AuthorizationPolicy -A

istio-system    deny-all                                       12h
istioinaction   webapp-allow-unauthenticated-view-default-ns   14s
istioinaction   webapp-allow-view-default-ns                   11h

# 호출 테스트 : default -> webapp 은 성공
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction

# webapp -> catalog 는 여전히 deny-all 로 거부됨
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/api/catalog

```

**webapp은 sleep의 요청을 허용했지만, 메시 범위 전체 거부 정책이 catalog로의 후속 요청을 거부했습니다.** 다음 절에서 해결합니다.

### 9.3.7 특정 서비스 어카운트에서 온 요청 허용하기

트래픽이 webapp에서 왔는지 인증하는 가장 간단한 방법은 **트래픽에 주입된 서비스 어카운트**를 쓰는 것입니다. 서비스 어카운트 정보는 **SVID에 인코딩돼 있고, 상호 인증 중에 검증되어 필터 메타데이터에 저장**됩니다(9.1.6, 9.2.2⑥에서 확인한 그 값입니다).

```yaml
# ch9/catalog-viewer-policy.yaml
apiVersion: "security.istio.io/v1beta1"
kind: "AuthorizationPolicy"
metadata:
  name: "catalog-viewer"
  namespace: istioinaction
spec:
  selector:
    matchLabels:
      app: catalog
  rules:
  - from:
    - source: 
        principals: ["cluster.local/ns/istioinaction/sa/webapp"]   # Allows requests with the identity of webapp
    to:
    - operation:
        methods: ["GET"]
```

```bash
kubectl apply -f ch9/catalog-viewer-policy.yaml

docker exec -it myk8s-control-plane istioctl proxy-config listener deploy/catalog.istioinaction --port 15006 -o json
```

```json
"principals": [ { "andIds": { "ids": [ { "orIds": { "ids": [
  { "filterState": {
      "key": "io.istio.peer_principal",
      "stringMatch": { "exact": "spiffe://cluster.local/ns/istioinaction/sa/webapp" }
  } }
] } } ] } } ]
```

> 9.3.5의 네임스페이스 매칭이 `safeRegex: ".*/ns/default/.*"` 였던 것과 달리, 여기는 **`exact` 매칭**입니다. 훨씬 좁고 정확합니다.

```bash
# 호출 테스트 : sleep --(미인증 레거시 허용)--> webapp --(principals webapp 허용)--> catalog
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction
kubectl exec deploy/sleep -- curl -sSL webapp.istioinaction/api/catalog 
kubectl logs -n istioinaction -l app=webapp -c istio-proxy -f
kubectl logs -n istioinaction -l app=catalog -c istio-proxy -f
```

**전체 경로가 다시 뚫렸습니다.** 그러나 더 중요한 것은, **워크로드 ID가 도난당했을 때 피해를 가능한 한 최소한의 범위로 제한하는 엄격한 인가 정책을 갖게 됐다는 점**입니다.

### 9.3.8 정책의 조건부 적용 — `when`

어떤 정책은 **특정 조건이 충족될 때만** 적용돼야 합니다. "사용자가 관리자일 때는 모든 작업을 허용" 같은 경우입니다.

```yaml
apiVersion: "security.istio.io/v1beta1"
kind: "AuthorizationPolicy"
metadata:
  name: "allow-mesh-all-ops-admin"
  namespace: istio-system
spec:
  rules:
  - from:
    - source:
        requestPrincipals: ["auth@istioinaction.io/*"]
    when:
    - key: request.auth.claims[groups]   # 이스티오 속성을 지정한다
      values: ["admin"]                  # 반드시 일치해야 하는 값의 목록을 지정한다
```

이 정책은 **두 조건이 모두** 충족될 때만 요청을 허용합니다.

1. 토큰은 요청 주체 `auth@istioinaction.io/*` 가 발급한 것이어야 하고,
2. JWT에 값이 `admin` 인 group 클레임이 포함돼 있어야 합니다.

반대로 `notValues` 로 **이 정책을 적용하지 않아야 하는 값들**을 정의할 수도 있습니다. 조건에서 쓸 수 있는 이스티오 속성 전체 목록은 [공식 문서](https://istio.io/latest/docs/reference/config/security/conditions/)에 있습니다.

> ⚠️ **`principals` vs `requestPrincipals` — 이름이 비슷해서 가장 많이 틀리는 지점입니다.**
> **`principals`** 는 **PeerAuthentication으로 설정한 mTLS 커넥션의 참가자**, 즉 **서비스**입니다(SVID에서 옴).
> **`requestPrincipals`** 는 **RequestAuthentication용, 최종 사용자**입니다(**JWT에서 옴**).
> 하나는 "어느 서비스가 불렀나", 다른 하나는 "어느 사람이 불렀나"입니다.

### 9.3.9 값 비교 표현식 이해하기

값이 항상 정확히 일치할 필요는 없습니다. 이스티오는 간단한 비교 표현식을 지원합니다.

| 방식 | 표기 | 예 |
| --- | --- | --- |
| **Exact** 일치 | 그대로 | `GET` 은 값이 정확히 일치해야 함 |
| **Prefix** 접두사 비교 | `값*` | `/api/catalog*` → `/api/catalog/1` 에 부합 |
| **Suffix** 접미사 비교 | `*값` | `*.istioinaction.io` → `login.istioinaction.io` 등 모든 서브도메인에 부합 |
| **Presence** 존재성 비교 | `*` | **필드가 존재하기만 하면** 값은 무엇이든 무관 |

**정책 규칙이 어떻게 평가되는가**

좀 더 복잡한 규칙을 구체적으로 분석해봅니다.

```yaml
apiVersion: "security.istio.io/v1beta1"
kind: "AuthorizationPolicy"
metadata:
  name: "allow-mesh-all-ops-admin"
  namespace: istio-system
spec:
  rules: 
  - from:                    # 첫 번째 규칙
    - source:
        principals: ["cluster.local/ns/istioinaction/sa/webapp"]
    - source:
        namespace: ["default"]
    to:
    - operation:
        methods: ["GET"]
        paths: ["/users*"]
    - operation:
        methods: ["POST"]
        paths: ["/data"]
    when:
    - key: request.auth.claims[group]
      values: ["beta-tester", "admin", "developer"]
  - to:                      # 두 번째 규칙
    - operation:
        paths: ["*.html", "*.js", "*.png"]
```

**규칙끼리는 OR, 규칙 안에서는 AND** 입니다. 정리하면 이렇습니다.

- 위 정책이 요청에 적용되려면 **첫 번째 규칙이나 두 번째 규칙에 해당**해야 합니다. (규칙 간 **OR**)
- 첫 번째 규칙에 해당하려면 **세 가지 속성에서 모두** 부합해야 합니다. `from` 에서 정의한 source 하나가, `to` 에 정의한 operation 하나와 **AND** 되고, 둘 다 `when` 의 조건들 모두와 **AND** 됩니다.
- **목록 안에서는 OR** 입니다. source 목록 중 **하나**만 맞으면 되고, operation 목록 중 **하나**만 맞으면 됩니다.
- 그러나 **하나의 operation 안에서는 다시 AND** 입니다. `methods: ["GET"]` 과 `paths: ["/users*"]` 는 **둘 다** 맞아야 그 operation이 부합합니다.
- `when` 조건들도 **AND** 로 연결되어 모든 조건이 부합해야 합니다.

### 9.3.10 인가 정책이 평가되는 순서 이해하기

한 워크로드에 정책이 많이 적용되면 순서를 이해하기 어려워집니다. 많은 솔루션이 `priority` 필드로 순서를 정하지만, **이스티오는 다른 접근법을 씁니다.**

1. **CUSTOM 정책이 가장 먼저** 평가됩니다. (9.5의 외부 인가 서버가 여기 해당)
2. 다음으로 **DENY 정책**이 평가됩니다. 일치하는 DENY가 없으면…
3. **ALLOW 정책**이 평가됩니다. 일치하는 것이 있으면 허용됩니다. 그렇지 않으면…
4. **catch-all 정책의 존재 유무**에 따라 결과가 갈립니다.
	- catch-all 정책이 **있으면** → 그 정책이 승인 여부를 결정합니다.
	- catch-all 정책이 **없으면** → **ALLOW 정책이 하나도 없으면 허용**, **ALLOW 정책은 있는데 아무것도 해당되지 않으면 거부**됩니다.

> **흐름이 복잡해 보이지만, catch-all DENY 정책 하나만 정의하면 훨씬 간단해집니다.** 요청을 거부하는 CUSTOM·DENY 정책이 없으면, **허용할 ALLOW 정책이 있는지만 확인하면 되기** 때문입니다. 9.3.4에서 `deny-all` 을 먼저 깔라고 한 이유가 이것입니다.

## 9.4 최종 사용자 인증 및 인가

여기까지가 **워크로드 사이**의 인증·인가였습니다. 이제 **사람**입니다.

### 9.4.1 JSON 웹 토큰이란 무엇인가?

JWT는 **클라이언트를 서버에 인증하는 데 사용하는 간결한 클레임 표현**입니다. 세 부분으로 이뤄집니다.

| 부분 | 내용 |
| --- | --- |
| **헤더** | 유형 및 해싱 알고리듬 |
| **페이로드** | **사용자 클레임** |
| **서명** | JWT의 **진위 여부**를 파악하는 데 사용 |

세 부분이 점(`.`)으로 구분되고 **Base64 URL로 인코딩**되기 때문에 HTTP 요청에 싣기 좋습니다.

```bash
cat ./ch9/enduser/user.jwt

# 디코딩 방법 1
jwt decode $(cat ./ch9/enduser/user.jwt)

# 디코딩 방법 2
cat ./ch9/enduser/user.jwt | cut -d '.' -f1 | base64 --decode | sed 's/$/}/'  | jq
```

```json
{
  "exp": 4745145038,                              // 만료 시간 Expiration time
  "group": "user",                                // 'group' 클레임
  "iat": 1591545038,                              // 발행 시각 Issue time
  "iss": "auth@istioinaction.io",                 // 토큰 발행자 Token issuer
  "sub": "9b792b56-7dfa-4e4b-a83f-e20679115d79"   // 토큰의 주체 Subject or principal of the token
}
```

**클레임을 신뢰하려면 토큰이 검증될 수 있어야 합니다.**

**JWT는 어떻게 발행되고 검증되는가**

- 인증 서버는 토큰을 **서명하는 비밀 키**와 **검증하는 공개 키**를 갖고 있습니다.
- 공개 키는 **JWKS**(JSON Web Key Set)라고 하며 **well-known HTTP 엔드포인트에 노출**됩니다.
- 서비스는 이 엔드포인트에서 공개 키를 가져와 인증 서버가 발급한 토큰을 검증합니다.
- **서명을 복호화해 얻은 해시값과 토큰 데이터의 해시값을 비교**하고, 일치하면 클레임에 변조가 없었음이 보장되므로 신뢰할 수 있습니다.

인증 서버는 애플리케이션 백엔드 프레임워크로 직접 구현하거나, **OpenIAM·Keycloak** 같은 솔루션으로 자체 구축하거나, **Auth0·Okta** 같은 IDaaS로 준비할 수 있습니다.

> **JWKS에는 JWK가 하나 이상 들어 있고, 그중 JWT의 식별자(`kid`)와 일치하는 JWK로 검증**합니다.

### 9.4.2 인그레스 게이트웨이에서의 최종 사용자 인증 및 인가

최종 사용자 인가는 **모든 워크로드 수준에서 수행할 수 있지만, 보통은 인그레스 게이트웨이에서** 합니다. 이유는 두 가지입니다.

- **유효하지 않은 요청을 조기에 거부하므로 성능이 좋아집니다.**
- **요청에서 JWT를 제거**해, 후속 서비스에서 사고로 유출되거나 악의적인 사용자가 **재전송 공격(replay attack)** 에 쓰는 것을 방지합니다.

### 9.4.3 RequestAuthentication으로 JWT 검증하기

**RequestAuthentication의 주목적은 JWT를 검증하고, 유효한 토큰의 클레임을 추출해 필터 메타데이터에 저장하는 것**입니다. 이 필터 메타데이터를 인가 정책이 근거로 삼습니다. (필터 메타데이터란 서비스 프록시에서 필터 간에 요청을 처리하는 동안 쓸 수 있는 **키-값 쌍의 모음**으로, 사용자 입장에서는 대부분 구현 세부 사항입니다.)

요청은 셋 중 하나로 갈립니다.

| 요청 | 결과 |
| --- | --- |
| **유효한 토큰** 있음 | 클러스터로 받아들여지고, 클레임이 **필터 메타데이터 형태로 정책에 전달**됨 |
| **유효하지 않은 토큰** 있음 | **거부** |
| **토큰 없음** | **클러스터로 받아들여지지만 요청 ID가 없음** — 어떤 클레임도 필터 메타데이터에 저장되지 않음 |

> ⚠️ **여기서 암시하는 중요한 세부 사항 — RequestAuthentication 리소스 그 자체는 인가를 강제하지 않습니다.** 토큰 검증과 클레임 추출로 **인증의 유효성을 검증하고 인가에서 쓸 정보를 저장하는 역할**만 합니다. **인가를 위해서는 여전히 AuthorizationPolicy가 필요합니다.**

#### ④ JWT가 없는 요청 거부하기

명시적으로 거부하는 AuthorizationPolicy를 만듭니다. 이 정책은 **`requestPrincipals` 속성이 없는 source에서 온 모든 요청**에 적용되어 요청을 거부합니다.

> **`requestPrincipals` 가 어떻게 초기화되는지 알면 놀랄지도 모릅니다** — **JWT의 발행자(iss)와 주체(sub) 클레임을 `iss/sub` 형태로 결합한 것**입니다. 클레임은 RequestAuthentication으로 인증되고, AuthorizationPolicy 필터 등 다른 필터가 쓸 수 있도록 커넥션 메타데이터로 가공됩니다.

```yaml
# ch9/enduser/app-gw-requires-jwt.yaml   # 포트 30000 추가
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: app-gw-requires-jwt
  namespace: istio-system
spec:
  selector:
    matchLabels:
      app: istio-ingressgateway
  action: DENY
  rules:
  - from:
    - source:
        notRequestPrincipals: ["*"]                    # 요청 주체에 값이 없는 source는 모두 해당된다
    to:
    - operation:
        hosts: ["webapp.istioinaction.io:30000"]       # 이 규칙은 이 특정 호스트에만 적용된다
        ports: ["30000"]
```

```bash
kubectl apply -f ch9/enduser/app-gw-requires-jwt.yaml

# 호출 1 : 토큰 없음
curl -sSl -o /dev/null -w "%{http_code}" webapp.istioinaction.io:30000/api/catalog
403

# 호출 2 : 유효한 토큰
curl -H "Authorization: Bearer $USER_TOKEN" \
     -sSl -o /dev/null -w "%{http_code}" webapp.istioinaction.io:30000/api/catalog
```

```plain text
[2025-05-04T07:04:01.791Z] "GET /api/catalog HTTP/1.1" 403 - rbac_access_denied_matched_policy[ns[istio-system]-policy[app-gw-requires-jwt]-rule[0]] - ...
```

> 이번에는 `matched_policy[none]` 이 아니라 **어떤 정책이 막았는지 이름이 찍힙니다.** DENY 정책에 명시적으로 걸린 경우와, ALLOW가 하나도 안 맞아서 떨어진 경우를 로그만으로 구분할 수 있습니다.

#### ⑤ JWT 클레임에 기반한 다양한 접근 수준

일반 사용자는 **읽기만**, 관리자는 **모든 권한**을 갖도록 나눠봅니다. 두 토큰의 차이는 `group` 클레임뿐입니다.

```bash
# 일반 사용자 토큰 : 'group: user' 클레임

  "exp": 4745145038,
  "group": "user",
  "iss": "auth@istioinaction.io",
  "sub": "9b792b56-7dfa-4e4b-a83f-e20679115d79"
}

# 관리자 토큰 : 'group: admin' 클레임
jwt decode $(cat ch9/enduser/admin.jwt)
{
  "exp": 4745145071,
  "group": "admin",
  "iss": "auth@istioinaction.io",
  "sub": "218d3fb9-4628-4d20-943c-124281c80e7b"
}
```

```yaml
# ch9/enduser/allow-all-with-jwt-to-webapp.yaml   # 포트 30000 추가
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-all-with-jwt-to-webapp
  namespace: istio-system
spec:
  selector:
    matchLabels:
      app: istio-ingressgateway
  action: ALLOW
  rules:
  - from:
    - source:
        requestPrincipals: ["auth@istioinaction.io/*"]   # 최종 사용자 요청 주체를 표현
    to:
    - operation:
        hosts: ["webapp.istioinaction.io:30000"]
        methods: ["GET"]
```

```yaml
# ch9/enduser/allow-mesh-all-ops-admin.yaml
apiVersion: "security.istio.io/v1beta1"
```

## 9.5 커스텀 외부 인가 서비스와 통합하기

이스티오는 **엔보이의 기본 RBAC 기능**으로 인가를 구현합니다. 그런데 **더 정교한 커스텀 메커니즘**이 필요하면 어떻게 할까요? 요청을 허용할지 결정할 때 **외부 인가(ExtAuthz) 서비스를 호출하도록** 서비스 프록시를 설정할 수 있습니다.

- 서비스 프록시에 들어온 요청은 **프록시가 외부 인가 서비스를 호출하는 동안 잠시 멈춥니다.**
- 외부 인가 서비스는 **애플리케이션 사이드카로 메시 안에** 있을 수도, **메시 바깥에** 있을 수도 있습니다.
- 외부 인가는 **엔보이의 CheckRequest API를 구현**해야 하며, **'허용'이나 '거부' 메시지를 반환**하면 프록시가 그것으로 인가를 집행합니다.

이 API를 구현하는 예로는 **Open Policy Agent**, **Signal Sciences**, **Gloo Edge Ext Auth**, **Istio sample Ext Authz** 등이 있습니다.

> ⚠️ **ExtAuthz 성능 트레이드오프.** **요청 경로 중에 외부 인가 서비스를 호출하기 때문에 지연 시간 증가에 대비해야 합니다.** 이스티오의 내장 인가 기능은 대체로 충분하고 유연하므로, 완벽히 통제해야 하는 경우에만 트레이드오프를 평가해 도입하세요. **외부 인가 서비스를 애플리케이션 사이드카로 배포하면 네트워크 오버헤드를 최소화**할 수 있습니다.

### 9.5.1 외부 인가 실습


### 9.5.2 이스티오에 외부 인가 설정하기

이스티오가 새 외부 인가 서비스를 인식하도록 **meshconfig의 `extensionProviders`** 를 설정합니다. 이 설정은 **istio-system 네임스페이스의 `istio` configmap**에 있습니다.

```bash
KUBE_EDITOR="nano" kubectl edit -n istio-system cm istio
```

```yaml
...
    extensionProviders:
    - name: "sample-ext-authz-http"
      envoyExtAuthzHttp:
        service: "ext-authz.istioinaction.svc.cluster.local"
        port: "8000"
        includeRequestHeadersInCheck: ["x-ext-authz"]
...
```

```bash
kubectl describe -n istio-system cm istio
```

- `sample-ext-authz-http` 라는 새 확장을 정의했습니다 — **envoyExtAuthz 서비스의 HTTP 구현체**입니다.
- 위치는 `ext-authz.istioinaction.svc.cluster.local` 로, 앞 절의 쿠버네티스 서비스에 맞췄습니다.
- **외부 인가 서비스에 전달할 헤더를 구성**할 수 있으며, 여기서는 `x-ext-authz` 를 전달합니다. 예제 서비스는 이 헤더로 인가 결과를 결정합니다.

> `includeHeadersInCheck` 는 **deprecated** 이므로 `includeRequestHeadersInCheck` 를 씁니다.

### 9.5.3 커스텀 AuthorizationPolicy 리소스 사용하기

앞에서는 action이 `DENY`나 `ALLOW`였습니다. 여기서는 **`CUSTOM`** 을 쓰고 **정확히 어떤 외부 인가 서비스를 사용할지 지정**합니다.

```bash
# istioinaction 네임스페이스의 webapp 워크로드에 적용되며,
# sample-ext-authz-http 이라는 외부 인가 서비스에 위임한다.
cat << EOF | kubectl apply -f -
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: ext-authz
  namespace: istioinaction
spec:
  selector:
    matchLabels:
      app: webapp
  action: CUSTOM                   # custom action 사용
  provider:
    name: sample-ext-authz-http    # meshconfig 이름과 동일해야 한다
  rules:
  - to:
    - operation:
        paths: ["/*"]              # 인가 정책을 적용할 경로
EOF
```

```bash
docker exec -it myk8s-control-plane istioctl proxy-config log deploy/webapp -n istioinaction --level rbac:debug
kubectl logs -n istioinaction -l app=webapp -c istio-proxy -f
kubectl logs -n istioinaction -l app=ext-authz -c ext-authz -f

# 헤더 없이 호출
kubectl -n default exec -it deploy/sleep -- curl webapp.istioinaction/api/catalog
denied by ext_authz for not found header `x-ext-authz: allow` in the request
```

## 부록 C 메모 — SPIFFE는 어떻게 신뢰를 만드는가

본문에서 두 번 "부록 C 참조"로 넘긴 부분입니다. 핵심만 남겨둡니다.

- **PKI(Public Key Infrastructure)** 는 서버에 **자신의 정체를 증명할 디지털 인증서**를 제공하고, 클라이언트에는 **그 인증서의 유효성을 검증할 수단**을 제공하는 절차를 정의하는 프레임워크입니다.
- 인증서에는 **공개 키와 개인 키**가 있습니다. 클라이언트에게는 인증서를 인증 수단으로 제시하며 **공개 키는 이 인증서 안에 포함**됩니다.
- 클라이언트는 공개된 네트워크로 데이터를 보내기 전에 **공개 키로 암호화**하고, **개인 키를 가진 서버만 복호화**할 수 있습니다. 이렇게 데이터가 전송 중에 보호됩니다.
- 이스티오에서는 이 역할을 **Istio CA(istiod)** 가 맡고, 발급물이 **SVID**, 신원 표기가 **SPIFFE ID**, 검증 근거가 **`/var/run/secrets/istio/root-cert.pem`** 입니다. 9.2.2⑥에서 `openssl verify` 로 확인한 것이 바로 이 체인입니다.

## 정리

| 주제 | 리소스 / 설정 위치 | 핵심 포인트 |
| --- | --- | --- |
| 워크로드 ID (9.1.5) | Istio CA가 발급하는 **SVID** | `spiffe://cluster.local/ns/<ns>/sa/<sa>` — **서비스 어카운트가 path** |
| 서비스 간 인증 (9.2) | **PeerAuthentication** | `STRICT` / `PERMISSIVE` / `UNSET`(상속) / `DISABLE`(터널링 안 함) |
| 정책 범위 (9.2.2) | 메시 / 네임스페이스 / 워크로드 | 메시 범위는 **istio-system + 이름 `default`**. 좁은 범위가 넓은 범위를 덮어씀 |
| 서비스 간 인가 (9.3) | **AuthorizationPolicy** | `selector`  • `action`  • `rules(from/to/when)` |
| **deny-by-default 함정** (9.3.3) | ALLOW 정책 1개라도 붙으면 | **나머지 전부 거부.** 404였던 요청이 403이 됨 |
| catch-all (9.3.4) | `spec: {}` vs `spec.rules: [{}]` | **빈 spec = 전부 거부**, **빈 규칙 = 전부 허용** |
| 출처 매칭 (9.3.5\~9.3.7) | `namespaces` / `principals` | 둘 다 **SVID 기반 → mTLS 필수**. 사이드카 없는 워크로드는 매칭 불가 |
| 최종 사용자 인증 (9.4.3) | **RequestAuthentication** | JWT 검증 + 클레임 추출만. **인가는 강제하지 않음** |
| 토큰 없는 요청 (9.4.3) | `allowMissing: {}` | 기본 통과. 막으려면 **`notRequestPrincipals: ["*"]` DENY 정책** 필요 |
| 평가 순서 (9.3.10) | CUSTOM → DENY → ALLOW → catch-all | **catch-all DENY 하나로 흐름이 단순해짐** |
| 외부 인가 (9.5) | meshConfig `extensionProviders`  • `action: CUSTOM` | 엔보이 **CheckRequest API** 구현. **요청 경로에 있으므로 지연 시간 증가** |

### 헷갈리는 짝 대조표

| 짝 | 무엇이 다른가 |
| --- | --- |
| `principals` vs `requestPrincipals` | **서비스**(SVID, PeerAuthentication) vs **최종 사용자**(JWT, RequestAuthentication) |
| `spec: {}` vs `rules: [{}]` | 전부 **거부** vs 전부 **허용** |
| `filter_chain_not_found` vs `rbac_access_denied` | **커넥션 자체가 안 붙음**(mTLS/PeerAuthentication) vs **커넥션은 붙고 403**(인가) |
| 401 vs 403 | **JWT 인증 실패**(`jwt_authn_access_denied`) vs **인가 거부**(RBAC / ext_authz) |
| `matched_policy[none]` vs `matched_policy[ns[...]-policy[...]]` | **ALLOW가 하나도 안 맞음** vs **특정 DENY 정책에 명시적으로 걸림** |
| STRICT vs PERMISSIVE | 평문 거부 vs **평문·암호문 모두 수용**(마이그레이션용) |

### 트러블슈팅 치트시트

```bash
# 1. 어떤 정책들이 걸려 있는가
kubectl get peerauthentication,requestauthentication,authorizationpolicy -A

# 2. 프록시에 실제로 꽂힌 RBAC / JWT 필터 확인
#    인바운드는 15006, 게이트웨이는 8080
docker exec -it myk8s-control-plane istioctl proxy-config listener deploy/<app>.<ns> --port 15006 -o json | jq
docker exec -it myk8s-control-plane istioctl proxy-config listener deploy/istio-ingressgateway.istio-system --port 8080 -o json | jq

# 3. 왜 막혔는지 이유를 보려면 rbac 로거를 debug로
docker exec -it myk8s-control-plane istioctl proxy-config log deploy/<app> -n <ns> --level rbac:debug
kubectl logs -n <ns> -l app=<app> -c istio-proxy -f

# 4. 정책이 프록시까지 갔는가 (LDS PUSH 확인)
docker exec -it myk8s-control-plane istioctl proxy-status
kubectl logs -n istio-system -l app=istiod -f | grep LDS

# 5. 워크로드 ID가 제대로 발급됐는가
kubectl -n <ns> exec deploy/<app> -c istio-proxy \
  -- openssl s_client -showcerts -connect <svc>.<ns>.svc.cluster.local:80 \
  -CAfile /var/run/secrets/istio/root-cert.pem | openssl x509 -in /dev/stdin -text -noout | grep -A1 "Subject Alternative Name"
kubectl describe pod -n <ns> -l app=<app> | grep 'Service Account'

# 6. 트래픽이 진짜 암호화되는가 (privileged 프록시에서만)
kubectl exec -it -n <ns> deploy/<app> -c istio-proxy \
  -- sudo tcpdump -l --immediate-mode -vv -s 0 'tcp port <port>'

# 7. JWT 내용 확인
jwt decode $(cat ch9/enduser/user.jwt)
cat token.jwt | cut -d '.' -f2 | base64 --decode | sed 's/$/"}/' | jq
```
