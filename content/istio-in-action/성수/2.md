## 1. 쿠버네티스 클러스터 및 기본 환경 구성

Docker Desktop을 실행하여 쿠버네티스 환경을 준비합니다.

- **설정 방법**: Docker Desktop의 설정에서 내장 Kubernetes를 활성화하거나, `kind`(Kubernetes in Docker)를 활용해 로컬 클러스터를 생성합니다.
- **장점**: 이 방식으로 구성하면 `kubernetes-cli(kubectl)` 및 `helm`과 같은 필수 도구들의 컨텍스트가 자동으로 인식되어, 별도의 복잡한 연동 없이 바로 사용할 수 있습니다.

### docker-desktop 없이 진행하려면

```bash
brew install kind
brew install kubernetes-cli
brew install helm
```

### 모니터링 관련 설치

kube-ops-view

```bash
helm repo add geek-cookbook https://geek-cookbook.github.io/charts/
helm install kube-ops-view geek-cookbook/kube-ops-view --version 1.2.2 --set service.main.type=NodePort,service.main.ports.http.nodePort=30005 --set env.TZ="Asia/Seoul" --namespace kube-system
```

k9s

```bash
brew install k9s
```

## 2. 필수 유틸리티 설치

터미널에서 쿠버네티스를 다룰 때 작업 효율과 가독성을 극대화해 주는 필수 툴들을 설치합니다.

```bash
brew install krew       # kubectl 플러그인 매니저
brew install kube-ps1   # 터미널 프롬프트에 현재 컨텍스트와 네임스페이스를 표시
brew install kubectx    # 클러스터(kubectx) 및 네임스페이스(kubens)를 빠르게 전환
brew install kubecolor  # kubectl 출력 결과에 구문 강조(색상)를 추가하여 가독성 향상
```

> **참고**: `kube-ps1`의 경우 설치 후 쉘 설정 파일(`.zshrc` 또는 `.bash_profile`)에 별도의 적용 코드를 추가해야 프롬프트에 정상적으로 표시됩니다. 설치 후 터미널에 출력되는 안내 문구를 확인해 주세요.

## 3. Krew 유용 플러그인 설치

설치한 `krew`를 사용해 디버깅과 매니페스트 관리를 도와줄 플러그인을 설치합니다.

```bash
kubectl krew install neat stern
```

- **`neat`**: `kubectl get pod -o yaml` 등 매니페스트를 출력할 때, 쿠버네티스가 자동 생성한 지저분한 메타데이터를 제거하고 핵심 내용만 깔끔하게 보여줍니다.
- **`stern`**: 여러 파드(Pod)와 컨테이너의 로그를 색상별로 구분하여 한 번에 스트리밍(tail)할 수 있는 강력한 로깅 툴입니다.

## 6. 샘플 애드온(Addons) 설치

Istio는 마이크로서비스 간의 트래픽 흐름을 시각화하고 모니터링하기 위해 유용한 서드파티 툴들을 기본 샘플로 제공합니다. 다운로드한 Istio 폴더 내부의 `samples/addons` 디렉터리에 있는 매니페스트를 적용하여 실행할 수 있습니다.

![애드온 설치](images/notes/istio-in-action/2-3.png)

**설치되는 주요 서비스**

- **Kiali**: 서비스 메시 토폴로지 시각화 및 구성 검증 대시보드
- **Prometheus**: 서비스 메시 전반의 메트릭(트래픽, 에러율 등) 수집
- **Grafana**: Prometheus가 수집한 데이터를 기반으로 시각적인 모니터링 대시보드 제공
- **Jaeger**: 분산 트레이싱을 통해 요청이 여러 마이크로서비스를 거치는 경로와 지연 시간 추적

![애드온 파드 실행 결과](images/notes/istio-in-action/2-4.png)

**결과 확인**: 기존의 `istiod` 등과 더불어 `kiali`, `prometheus`, `grafana`, `jaeger` 파드들이 새롭게 생성되어 `Running` 상태가 된 것을 확인할 수 있습니다.

## 사이드카 확인

```bash
istioctl kube-inject -f catalog/kubernetes/catalog.yaml
```

이 명령어는 기존의 평범한 쿠버네티스 배포 파일(`catalog.yaml`)을 읽어와서, 그 안에 **Istio 사이드카 프록시(Envoy) 설정을 끼워 넣은(Inject) 새로운 YAML 텍스트를 화면에 그대로 뱉어내는(출력하는) 역할**을 합니다.

**화면에 내용이 쏟아지는 이유**: 원래 파일에는 앱 컨테이너 하나만 정의되어 있었겠지만, `kube-inject`를 거치면서 다음 항목들이 자동으로 추가된 매우 긴 YAML로 변환되기 때문입니다.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: catalog
---
apiVersion: v1
kind: Service
metadata:
  labels:
    app: catalog
  name: catalog
spec:
  ports:
    - name: http
      port: 80
      protocol: TCP
      targetPort: 3000
  selector:
    app: catalog
---
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: catalog
    version: v1
  name: catalog
spec:
  replicas: 1
  selector:
    matchLabels:
      app: catalog
      version: v1
  strategy: {}
  template:
    metadata:
      annotations:
        istio.io/rev: default
        kubectl.kubernetes.io/default-container: catalog
        kubectl.kubernetes.io/default-logs-container: catalog
        prometheus.io/path: /stats/prometheus
        prometheus.io/port: "15020"
        prometheus.io/scrape: "true"
        sidecar.istio.io/status: '{"initContainers":["istio-init"],"containers":["istio-proxy"],"volumes":["workload-socket","credential-socket","workload-certs","istio-envoy","istio-data","istio-podinfo","istio-token","istiod-ca-cert","istio-ca-crl"],"imagePullSecrets":null,"revision":"default"}'
      labels:
        app: catalog
        security.istio.io/tlsMode: istio
        service.istio.io/canonical-name: catalog
        service.istio.io/canonical-revision: v1
        version: v1
    spec:
      containers:
        - env:
            - name: KUBERNETES_NAMESPACE
              valueFrom:
                fieldRef:
                  fieldPath: metadata.namespace
          image: istioinaction/catalog:latest
          imagePullPolicy: IfNotPresent
          name: catalog
          ports:
            - containerPort: 3000
              name: http
              protocol: TCP
          resources: {}
          securityContext:
            privileged: false
        - args:
            - proxy
            - sidecar
            - --domain
            - $(POD_NAMESPACE).svc.cluster.local
            - --proxyLogLevel=warning
            - --proxyComponentLogLevel=misc:error
            - --log_output_level=default:info
          env:
            - name: PILOT_CERT_PROVIDER
              value: istiod
            - name: CA_ADDR
              value: istiod.istio-system.svc:15012
            # ...
```

### 파드 실행 및 사이드카 주입 확인


`kubectl get pod` 명령어 대신, 터미널에서 `k9s`를 실행하면 대시보드 형태의 UI로 파드 상태를 실시간 모니터링하고 제어할 수 있습니다.

### 포트 포워딩을 통한 서비스 로컬 접속

쿠버네티스 내부에 배포된 서비스는 기본적으로 외부(내 PC)에서 직접 접근할 수 없습니다. 이때 `kubectl port-forward` 명령어를 사용하면 내 PC의 포트와 클러스터 내부 파드의 포트를 임시로 연결(터널링)하여 간편하게 접속 테스트를 할 수 있습니다.

```bash
❯ kubectl port-forward deploy/webapp 8080:8080

Forwarding from [::1]:8080 -> 8080
Handling connection for 8080
Handling connection for 8080
```

### Istio Ingress Gateway를 통한 외부 트래픽 정식 노출

임시 터널링(Port-Forward) 방식에서 벗어나, 클러스터 외부에서 들어오는 트래픽을 안전하고 체계적으로 내부 서비스로 연결하기 위해 Istio의 **Gateway**와 **VirtualService** 리소스를 배포했습니다.

**1. 라우팅 룰(매니페스트) 배포**

```bash
❯ kubectl apply -f ch2/ingress-gateway.yaml
gateway.networking.istio.io/outfitters-gateway created
virtualservice.networking.istio.io/webapp-virtualservice created
```

**2. 외부 도메인(localhost)을 통한 통신 테스트**

```bash
❯ curl http://localhost:80/api/catalog/items/1
{"id":1,"color":"amber","department":"Eyewear","name":"Elinor Glasses","price":"282.00"}
```

```bash
❯ URL=$(kubectl -n istio-system get svc istio-ingressgateway -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
❯ curl $URL/api/catalog/items/1

# 나는 미니큐브를 안 써서 이렇게는 안 나옴

❯ curl http://localhost/api/catalog/items/1
{"id":1,"color":"amber","department":"Eyewear","name":"Elinor Glasses","price":"282.00"}
```

포트포워딩도 가능합니다.

```bash
❯ kubectl port-forward deploy/istio-ingressgateway -n istio-system 8080:8080
Forwarding from 127.0.0.1:8080 -> 8080
Forwarding from [::1]:8080 -> 8080
```

```bash
❯ istioctl proxy-config routes deploy/istio-ingressgateway.istio-system
NAME          VHOST NAME     DOMAINS     MATCH                  VIRTUAL SERVICE
```

## 이스티오 트래픽 제어 및 복원력 패턴 적용 (VirtualService)

앞서 의도적으로 주입한 장애(HTTP 500 에러) 상황을 완화하고 시스템의 복원력을 높이기 위해, 애플리케이션 코드 수정 없이 이스티오의 네트워킹 정책을 적용할 수 있습니다.

`VirtualService`는 이스티오에서 서비스로 들어오는 트래픽을 어떻게 라우팅하고 제어할지 정의하는 핵심 커스텀 리소스(CRD)입니다.

```bash
❯ kubectl apply -f ch2/catalog-virtualservice.yaml
virtualservice.networking.istio.io/catalog created
```

## 목적지 규칙(DestinationRule) 적용 및 안정적인 트래픽 제어 (v1 고정)

새로운 버전(v2)의 애플리케이션 파드(Pod)가 클러스터에 배포되어 실행 중이더라도, 서비스 메시 환경에서는 트래픽 라우팅을 명시적으로 제어하여 예상치 못한 트래픽 유입을 막을 수 있습니다.

```bash
❯ kubectl apply -f ch2/catalog-destinationrule.yaml
destinationrule.networking.istio.io/catalog created

❯ kubectl apply -f ch2/catalog-virtualservice-all-v1.yaml
virtualservice.networking.istio.io/catalog configured
```

```bash
❯ curl http://localhost/api/catalog
[{"id":1,"color":"amber",...,"price":"282.00"}, ...]   # 항상 v1 응답

❯ curl http://localhost/api/catalog
[{"id":1,"color":"amber",...,"price":"282.00"}, ...]   # 항상 v1 응답
```

## 다크 론치(Dark Launch)를 통한 헤더 기반 트래픽 제어 및 안전한 테스트

새로운 버전(v2)을 실제 운영 환경에 배포하더라도, 모든 사용자에게 즉시 노출하는 것은 위험할 수 있습니다. 이스티오의 라우팅 기능을 활용하면 특정 HTTP 헤더를 가진 요청만 선별하여 새 버전으로 유도할 수 있습니다.

```bash
❯ kubectl apply -f ch2/catalog-virtualservice-dark-v2.yaml
virtualservice.networking.istio.io/catalog configured

# 일반 요청 -> v1
❯ curl http://localhost/api/catalog
[{"id":1,"color":"amber","department":"Eyewear","name":"Elinor Glasses","price":"282.00"}, ...]

# x-dark-launch 헤더가 있는 요청 -> v2 (imageUrl 포함)
❯ curl http://localhost/api/catalog -H "x-dark-launch: v2"
[{"id":1,"color":"amber","department":"Eyewear","name":"Elinor Glasses","price":"282.00","imageUrl":"http://lorempixel.com/640/480"}, ...]
```
