> 5장 **Traffic control: Fine-grained traffic routing**
> 이번 장의 목표 — ① 트래픽 라우팅 기초 ② 새 릴리스 중 트래픽 전환 ③ 릴리스 위험을 줄이는 트래픽 미러링 ④ 클러스터를 떠나는 트래픽 제어

4장에서는 트래픽을 **클러스터 안으로 가져오는 방법**(Ingress Gateway)을 다뤘습니다. 이번 장은 그 다음 질문에 답합니다.

- 요청이 클러스터에 들어온 뒤, **적절한 서비스로 어떻게 라우팅**되는가?
- 클러스터 내부 서비스는 **같은 클러스터 / 클러스터 외부**의 다른 서비스와 어떻게 통신하는가?
- 가장 중요한 것 — 서비스를 변경하고 새 버전을 도입할 때 **고객에게 미치는 영향을 최소화**하려면?

이스티오 서비스 프록시(Envoy)는 서비스 간 통신을 가로채는 지점을 제공하므로, **개별 요청 단위까지** 트래픽을 제어할 수 있습니다.

## 5.1 새로운 코드 배포의 위험 줄이기

### Blue/Green의 한계

ACME는 v2(green)를 v1(blue) 옆에 배포해두고, 릴리스 시점에 트래픽을 v2로 넘기는 blue/green 배포를 도입했습니다. 중단은 줄었지만 **v1 → v2 전환이 여전히 "빅뱅"** 이라는 문제가 남습니다. 모든 코드 변경이 한 번에 전체 사용자에게 풀립니다.

### 5.1.1 배포(Deployment) vs 릴리스(Release)

![배포와 릴리스의 분리](images/notes/istio-in-action/5-1.png)

| 구분             | 정의                                                       | 사용자 영향                            | 성격            |
| ---------------- | ---------------------------------------------------------- | -------------------------------------- | --------------- |
| 배포 Deployment  | 새 코드를 운영 환경 리소스(서버·컨테이너)에 설치. 트래픽은 보내지 않는다 | 없음 — 아직 어떤 사용자 요청도 받지 않음 | 인프라 작업     |
| 릴리스 Release   | 실제 사용자 트래픽을 신규 배포로 전달·이관                   | 있음 — 노출 범위를 제어 가능            | 비즈니스 의사결정 |

배포만 된 상태에서도 **스모크 테스트를 돌리고, 메트릭·로그로 정상 동작을 검증**할 수 있습니다. 그 다음 "누구에게, 얼마나" 릴리스할지 결정합니다.

> **핵심:** 릴리스가 꼭 한 번에 전부 갈 필요는 없습니다. 이것이 배포/릴리스 분리의 핵심 가치입니다.

### 점진적 릴리스 흐름

1. **내부 직원에게만 공개** — 운영자가 로그·메트릭으로 변경 효과를 관찰 (다크 런치)
2. **카나리 릴리스** — 소수 사용자 그룹에 노출하고 동작 관찰. 이상하면 즉시 트래픽 회수
3. **범위 확대** — 무과금/실버 등급 → … → 전체 고객
4. 어느 단계에서든 문제가 보이면 **트래픽을 이전 버전으로 되돌려 롤백**

과거 ACME는 롤링 업그레이드로 배포와 릴리스를 결합했기 때문에, 신 버전이 클러스터에 들어오는 순간 사용자가 **신 버전의 버그에도 즉시 노출**됐습니다.

## 5.2 이스티오로 요청 라우팅하기 — 다크 런치(Dark Launch)

**다크 런치**: 대다수 사용자는 검증된 버전으로 보내고, 특정 클래스의 사용자만 최신 버전으로 보내는 기법. 사용자에게는 보이지 않지만 백엔드에는 실제 배포되어 있는 상태입니다.

### 5.2.2 catalog 서비스 v1 배포하기

```bash
kubectl apply -f services/catalog/kubernetes/catalog.yaml -n istioinaction
```

```yaml
# ch5/catalog-gateway.yaml
```

### 5.2.3 catalog 서비스 v2 배포하기 — 배포가 곧 릴리스가 되어버리는 문제

```bash
# v2에는 imageUrl 필드가 추가되어 있다
kubectl apply -f services/catalog/kubernetes/catalog-deployment-v2.yaml -n istioinaction

kubectl get deploy -n istioinaction --show-labels
# catalog      1/1  ...  app=catalog,version=v1
# catalog-v2   1/1  ...  app=catalog,version=v2

# 호출 테스트 → v1, v2가 번갈아 응답한다 (원하지 않는 상황!)
for i in {1..10}; do curl -s http://catalog.istioinaction.io:30000/items/ ; printf "\n\n"; done
```

두 Deployment가 같은 Service의 엔드포인트로 잡히기 때문에 **배포하는 순간 릴리스도 함께 일어나 버립니다.** 이걸 막는 것이 DestinationRule + VirtualService의 역할입니다.

```bash
docker exec -it myk8s-control-plane istioctl proxy-config endpoint \
  deploy/istio-ingressgateway.istio-system \
  --cluster 'outbound|80||catalog.istioinaction.svc.cluster.local'
# ENDPOINT            STATUS      OUTLIER CHECK     CLUSTER
# 10.10.0.16:3000     HEALTHY     OK                outbound|80||catalog...
# 10.10.0.17:3000     HEALTHY     OK                outbound|80||catalog...   ← v2도 함께 잡힘
```

### 5.2.4 모든 트래픽을 catalog 서비스 v1으로 라우팅하기 (DestinationRule)

이스티오에게 "어느 워크로드가 v1이고 v2인지" 힌트를 줘야 합니다. Deployment의 `version` 레이블을 기준으로 **subset(부분집합)** 을 선언합니다.

![DestinationRule과 VirtualService의 역할 분담](images/notes/istio-in-action/5-2.png)

```yaml
# ch5/catalog-dest-rule.yaml
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: catalog
spec:
  host: catalog.istioinaction.svc.cluster.local
  subsets:
    - name: version-v1
      labels:
        version: v1
    - name: version-v2
      labels:
        version: v2
```

```yaml
# ch5/catalog-vs-v1.yaml — subset 지정 추가
http:
  - route:
      - destination:
          host: catalog
          subset: version-v1
```

```bash
kubectl apply -f ch5/catalog-dest-rule.yaml -n istioinaction
kubectl apply -f ch5/catalog-vs-v1.yaml -n istioinaction

# subset 별 cluster가 생성됐는지 확인
docker exec -it myk8s-control-plane istioctl proxy-config cluster \
  deploy/istio-ingressgateway.istio-system --fqdn catalog.istioinaction.svc.cluster.local
# SERVICE FQDN                                PORT   SUBSET       DIRECTION   TYPE   DESTINATION RULE
# catalog.istioinaction.svc.cluster.local     80     -            outbound    EDS    catalog.istioinaction
# catalog.istioinaction.svc.cluster.local     80     version-v1   outbound    EDS    catalog.istioinaction
# catalog.istioinaction.svc.cluster.local     80     version-v2   outbound    EDS    catalog.istioinaction

# subset 별 엔드포인트 분리 확인
docker exec -it myk8s-control-plane istioctl proxy-config endpoint \
  deploy/istio-ingressgateway.istio-system | egrep 'ENDPOINT|istioinaction'
# 10.10.0.16:3000   HEALTHY  OK  outbound|80|version-v1|catalog...
# 10.10.0.17:3000   HEALTHY  OK  outbound|80|version-v2|catalog...
```

> **기본 문법:** DestinationRule은 버전 분류(누가 v1/v2인가), VirtualService는 라우팅 규칙(어디로 보낼까)을 담당합니다. 이 둘의 조합이 5장 전체의 기본 문법입니다.

### 5.2.5 특정 요청을 v2로 라우팅하기 (헤더 매칭)

```yaml
# ch5/catalog-vs-v2-request.yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: catalog-vs-from-gw
spec:
  hosts:
    - "catalog.istioinaction.io"
  gateways:
    - catalog-gateway
  http:
    - match: # 1순위: 헤더가 있으면 v2
        - headers:
            x-istio-cohort:
              exact: "internal"
      route:
        - destination:
            host: catalog
            subset: version-v2
    - route: # 2순위: 나머지 전부 v1
        - destination:
            host: catalog
            subset: version-v1
```

```bash
kubectl apply -f ch5/catalog-vs-v2-request.yaml -n istioinaction

curl http://catalog.istioinaction.io:30000/items                              # → v1
curl http://catalog.istioinaction.io:30000/items -H "x-istio-cohort: internal" # → v2
```

**중요: `http` 목록의 순서가 곧 매칭 우선순위입니다.** 위에서부터 평가되므로, 조건 없는 `route`를 위에 두면 아래 `match`는 영원히 도달하지 않습니다.

```bash
# route가 2개로 늘어난 것을 확인
docker exec -it myk8s-control-plane istioctl proxy-config routes \
  deploy/istio-ingressgateway.istio-system --name http.8080
# NAME        DOMAINS                    MATCH   VIRTUAL SERVICE
# http.8080   catalog.istioinaction.io   /*      catalog-vs-from-gw.istioinaction
# http.8080   catalog.istioinaction.io   /*      catalog-vs-from-gw.istioinaction
```

`-o json`으로 보면 첫 route에 `headers.stringMatch.exact: internal` → `outbound|80|version-v2|...`, 두 번째 route는 조건 없이 `outbound|80|version-v1|...` 로 매핑돼 있습니다.

> 이때 **catalog 파드의 istio-proxy에는 route가 1개뿐**입니다. 즉 분기 판단은 **호출하는 쪽 프록시(ingressgateway)** 가 수행합니다. 이스티오 라우팅은 클라이언트 사이드에서 결정된다는 것을 보여주는 지점입니다.

### 5.2.6 호출 그래프 내 깊은 위치에서 라우팅 (`mesh` 게이트웨이)

지금까지는 **에지(ingress gateway)** 에서만 라우팅했습니다. 같은 규칙을 메시 내부 서비스 간 호출(webapp → catalog)에도 적용할 수 있습니다.

```bash
kubectl delete gateway,virtualservice,destinationrule --all -n istioinaction
kubectl apply -n istioinaction -f services/webapp/kubernetes/webapp.yaml
kubectl apply -f services/webapp/istio/webapp-catalog-gw-vs.yaml -n istioinaction

# 외부 → ingressgw → webapp → catalog
curl -s http://webapp.istioinaction.io:30000/api/catalog | jq
```

액세스 로그를 켜서 **webapp이 catalog를 어떻게 부르는지** 확인합니다.

```bash
cat << EOF | kubectl apply -f -
apiVersion: telemetry.istio.io/v1alpha1
kind: Telemetry
metadata:
  name: webapp
  namespace: istioinaction
spec:
  selector:
    matchLabels:
      app: webapp
  accessLogging:
  - providers:
    - name: envoy
    disabled: false
EOF

kubectl logs -n istioinaction -l app=webapp -c istio-proxy -f
```

VirtualService 적용 **전** — 평범한 k8s Service(ClusterIP) 라우팅입니다.

```text
"GET /items HTTP/1.1" 200 ... "catalog.istioinaction:80" "10.10.0.16:3000"
outbound|80||catalog.istioinaction.svc.cluster.local 10.10.0.18:45152 10.200.1.254:80
```

이제 `gateways: mesh`를 붙인 VirtualService를 적용합니다.

```yaml
# ch5/catalog-vs-v1-mesh.yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: catalog
spec:
  hosts:
    - catalog
  gateways:
    - mesh # 메시 내 모든 사이드카에 적용 (에지는 제외)
  http:
    - route:
        - destination:
            host: catalog
            subset: version-v1
```

적용 **후** — subset 클러스터로 라우팅됩니다.

```text
outbound|80|version-v1|catalog.istioinaction.svc.cluster.local
```

| gateways 값       | 적용 대상                                  |
| ----------------- | ------------------------------------------ |
| 생략              | 암묵적으로 `mesh` — 메시 내 모든 사이드카   |
| `mesh`            | 메시 내 모든 사이드카 (ingress gateway 제외) |
| 특정 Gateway 이름 | 해당 게이트웨이를 통과하는 트래픽만          |

헤더 기반 라우팅도 동일하게 메시 내부에 적용할 수 있습니다 (`ch5/catalog-vs-v2-request-mesh.yaml`).

```bash
while true; do curl -s http://webapp.istioinaction.io:30000/api/catalog -I | head -n 1 ; sleep 1; echo; done
while true; do curl -s http://webapp.istioinaction.io:30000/api/catalog -H "x-istio-cohort: internal" -I | head -n 1 ; sleep 2; echo; done
```

### (보충) xDS 디버깅 명령 정리

라우팅이 의도대로 안 될 때 **Envoy 설정을 직접 확인**하는 것이 가장 빠릅니다.

| xDS | 의미                                    | 확인 명령                                                        |
| --- | --------------------------------------- | ---------------------------------------------------------------- |
| LDS | Listener — 어떤 포트를 듣는가            | `istioctl proxy-config listener deploy/<svc>.<ns>`                |
| RDS | Route — 어떤 조건으로 어느 cluster로 보내는가 | `istioctl proxy-config routes deploy/<svc>.<ns> --name 80 -o json` |
| CDS | Cluster — 목적지 그룹(subset 포함)       | `istioctl proxy-config cluster deploy/<svc>.<ns> --fqdn <FQDN>`   |
| EDS | Endpoint — 실제 파드 IP:PORT             | `istioctl proxy-config endpoint deploy/<svc>.<ns> --cluster '<cluster>'` |

```bash
# 전체 프록시 싱크 상태 (SYNCED 아니면 설정이 안 내려간 것)
docker exec -it myk8s-control-plane istioctl proxy-status

# Envoy Admin 콘솔
kubectl port-forward deploy/istio-ingressgateway -n istio-system 15000:15000
open http://127.0.0.1:15000
```

**cluster 이름 읽는 법**: `outbound|80|version-v1|catalog.istioinaction.svc.cluster.local`
= `방향 | 포트 | subset | FQDN`. subset 자리가 비어 있으면(`outbound|80||...`) DestinationRule을 타지 않은 기본 클러스터입니다.

## 5.3 트래픽 전환 (수동 카나리 — 가중치 라우팅)

다크 런치가 "누가"로 나눈다면, 트래픽 전환은 **"몇 %"** 로 나눕니다. v2에 10%만 주면, 문제가 생겨도 영향받는 사용자는 10%로 제한됩니다.

```yaml
# ch5/catalog-vs-v2-10-90-mesh.yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: catalog
spec:
  hosts:
    - catalog
  gateways:
    - mesh
  http:
    - route:
        - destination:
            host: catalog
            subset: version-v1
          weight: 90
        - destination:
            host: catalog
            subset: version-v2
          weight: 10
```

```bash
kubectl apply -f ch5/catalog-vs-v2-10-90-mesh.yaml -n istioinaction

# v2 응답에만 imageUrl이 있으므로 개수를 세면 비율이 나온다 → 약 10
for i in {1..100}; do curl -s http://webapp.istioinaction.io:30000/api/catalog | grep -i imageUrl ; done | wc -l

# 50:50 으로 확대
kubectl apply -f ch5/catalog-vs-v2-50-50-mesh.yaml -n istioinaction
```

Envoy 설정에서는 `weightedClusters`로 표현됩니다.

```text
"route": {
  "weightedClusters": {
    "clusters": [
      { "name": "outbound|80|version-v1|catalog...", "weight": 90 },
      { "name": "outbound|80|version-v2|catalog...", "weight": 10 }
    ],
    "totalWeight": 100
```

**주의사항**

- 가중치 총합은 **반드시 100**. 아니면 예기치 못한 라우팅이 발생합니다.
- v1/v2 외 다른 버전이 있으면 **DestinationRule에 subset을 먼저 선언**해야 합니다.
- 롤백은 v2 가중치를 줄이는 것(필요하면 0까지)만으로 끝납니다.
- 파드에 `version` 레이블이 없으면 canonical-revision이 `latest`가 되고, **Kiali Workload Details에 "Missing Version"** 으로 표기됩니다.
- 이 방식은 **여러 버전을 동시에 실행할 수 있도록 서비스가 설계돼 있어야** 성립합니다. 서비스가 상태를 많이 가질수록(특히 외부 상태에 의존할수록) 어려워집니다.

### 5.3.1 Flagger로 카나리 릴리스하기

![Flagger의 카나리 진행 흐름](images/notes/istio-in-action/5-3.png)

수동 가중치 조정은 릴리스가 수백 건 동시에 진행되면 **설정 오류와 사람 실수**의 원천이 됩니다. Flagger(Stefan Prodan 제작)는 Progressive Delivery Operator로서 이 과정을 자동화합니다.

```bash
# 기존 수동 리소스 제거 → Flagger가 라우팅/배포를 모두 관장하게 한다
kubectl delete virtualservice catalog -n istioinaction
kubectl delete deploy catalog-v2 -n istioinaction
kubectl delete service catalog -n istioinaction
kubectl delete destinationrule catalog -n istioinaction

# CRD 설치
kubectl apply -f https://raw.githubusercontent.com/fluxcd/flagger/main/artifacts/flagger/crd.yaml
```

## 5.4 위험을 더욱 줄이기: 트래픽 미러링(Traffic Mirroring / Shadowing)

요청 라우팅과 트래픽 전환은 **라이브 트래픽을 실제로 신 버전에 태우기** 때문에, 범위를 아무리 좁혀도 사용자에게 영향이 갈 수 있습니다. 미러링은 운영 트래픽을 **복사**해서 신 버전으로 보내고, 응답은 버립니다.

> **미러링 vs 복제(Replication)**
> 미러링은 트래픽(패킷) 레벨의 실시간 복사로 분석·검증 목적에 한정되며 서비스에 영향을 주지 않습니다.
> 복제는 데이터 레벨의 복사로, 가용성·확장성·장애 대비 등 실제 서비스 운영에 직접 활용됩니다.

```bash
# 실습 환경 초기화
kubectl apply -f services/catalog/kubernetes/catalog-svc.yaml -n istioinaction
kubectl apply -f services/catalog/kubernetes/catalog-deployment.yaml -n istioinaction
kubectl apply -f services/catalog/kubernetes/catalog-deployment-v2.yaml -n istioinaction
kubectl apply -f ch5/catalog-dest-rule.yaml -n istioinaction
kubectl apply -f ch5/catalog-vs-v1-mesh.yaml -n istioinaction

for i in {1..100}; do curl -s http://webapp.istioinaction.io:30000/api/catalog | grep -i imageUrl ; done | wc -l
#      0   ← v1만 응답
```

```yaml
# ch5/catalog-vs-v2-mirror.yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: catalog
spec:
  hosts:
    - catalog
  gateways:
    - mesh
  http:
    - route:
        - destination:
            host: catalog
            subset: version-v1
          weight: 100
      mirror:
        host: catalog
        subset: version-v2
```

미러링은 **"보내고 잊는(fire-and-forget)" 방식**입니다. 미러링을 수행하는 이스티오 프록시가 미러 클러스터의 응답을 **성공이든 실패든 전부 무시**하므로, 실제 요청에 영향을 줄 수 없습니다.

```bash
# catalog 액세스 로그 활성화
cat << EOF | kubectl apply -f -
apiVersion: telemetry.istio.io/v1alpha1
kind: Telemetry
metadata:
  name: catalog
  namespace: istioinaction
spec:
  accessLogging:
  - disabled: false
    providers:
    - name: envoy
  selector:
    matchLabels:
      app: catalog
EOF

kubectl apply -f ch5/catalog-vs-v2-mirror.yaml -n istioinaction

# 응답은 여전히 v1만
for i in {1..100}; do curl -s http://webapp.istioinaction.io:30000/api/catalog | grep -i imageUrl ; done | wc -l
#      0
```

**핵심 관찰 — Host 헤더의 `-shadow` 접미사**

```bash
kubectl logs -n istioinaction -l app=catalog -l version=v1 -c catalog -f
# GET catalog.istioinaction:80 /items 200 502 - 0.375 ms

kubectl logs -n istioinaction -l app=catalog -l version=v2 -c catalog -f
# GET catalog.istioinaction-shadow:80 /items 200 698 - 0.503 ms
```

미러링된 트래픽은 Host 헤더가 `catalog.istioinaction` → `catalog.istioinaction-shadow`로 수정됩니다. 수신 서비스는 이를 보고 **"이건 미러 요청"** 임을 식별할 수 있습니다.

> 이 식별이 중요한 이유: 응답이 어차피 버려질 것이므로 **트랜잭션을 커밋/롤백하지 않거나, 결제·메일 발송 같은 부수효과를 건너뛰거나, 비용 큰 외부 호출을 생략**하도록 애플리케이션이 대응할 수 있습니다. 미러링을 도입하려면 애플리케이션이 미러 모드를 인지하도록 설계돼 있어야 합니다.

Envoy route 설정에서는 `requestMirrorPolicies`로 나타납니다.

```text
"route": {
  "cluster": "outbound|80|version-v1|catalog.istioinaction.svc.cluster.local",
  "requestMirrorPolicies": [
    {
      "cluster": "outbound|80|version-v2|catalog.istioinaction.svc.cluster.local",
      "runtimeFraction": { "defaultValue": { "numerator": 100 } },
      "traceSampled": false
    }
  ]
```

## 5.5 이스티오의 서비스 디스커버리 기능을 사용해 클러스터 외부의 서비스로 라우팅하기

### 기본 동작과 위험

이스티오는 **기본적으로 메시 밖으로 나가는 트래픽을 허용**합니다(`ALLOW_ANY`). 하지만 이는 보안상 위험합니다.

> 메시 내 서비스가 손상됐을 때, 공격자가 **자신이 제어하는 서버로 데이터를 유출(call home)** 하는 것을 막지 못합니다.

단, 아웃바운드 차단만으로는 충분하지 않습니다 — **손상된 파드는 프록시를 우회할 수 있으므로**, L3/L4 차단 등 심층 방어(defense in depth)가 함께 필요합니다.

### `outboundTrafficPolicy` 를 REGISTRY_ONLY 로

![이그레스 트래픽 제어](images/notes/istio-in-action/5-4.png)

| 모드                    | 동작                                                          |
| ----------------------- | ------------------------------------------------------------- |
| `ALLOW_ANY` (기본값)    | 모든 외부 트래픽 허용. 알려지지 않은 목적지는 `PassthroughCluster`로 통과 |
| `REGISTRY_ONLY`         | 서비스 레지스트리에 등록된 목적지만 허용 (화이트리스트)          |
| `ALLOW_LIST`            | 명시적 허용 목록 방식                                          |

```bash
docker exec -it myk8s-control-plane bash
----------------------------------------
istioctl install --set profile=default --set meshConfig.outboundTrafficPolicy.mode=REGISTRY_ONLY
y
exit
----------------------------------------

# 외부 다운로드 시도 → 차단
kubectl exec -it deploy/webapp -n istioinaction -c webapp -- \
  wget https://raw.githubusercontent.com/gasida/KANS/refs/heads/main/msa/sock-shop-demo.yaml
# Connecting to raw.githubusercontent.com (185.199.109.133:443)
# wget: error getting response: Connection reset by peer
```

**차단 로그를 읽는 법** — 두 가지 표식이 나옵니다.

```text
# ① TCP/TLS 직접 아웃바운드 → BlackHoleCluster
[...] "- - -" 0 UH - - "-" 0 0 0 - "-" "-" "-" "-" "-" BlackHoleCluster - 185.199.109.133:443 ...
#  UH = NoHealthyUpstream (업스트림에 정상 호스트 없음, 503)

# ② HTTP 라우팅 단계에서 차단 → block_all + direct_response
[...] "GET /users HTTP/1.1" 502 - direct_response - "-" ... "jsonplaceholder.typicode.com" ... - - block_all
#  direct_response = Envoy가 외부로 보내지 않고 자체 차단 응답을 반환
#  block_all       = egress 전면 차단 상태
```

```bash
docker exec -it myk8s-control-plane istioctl proxy-config cluster \
  deploy/webapp.istioinaction --fqdn BlackHoleCluster -o json
# [ { "name": "BlackHoleCluster", "type": "STATIC", "connectTimeout": "10s" } ]
```

### ServiceEntry — 서비스 레지스트리에 외부 서비스 등록

이스티오는 **내부 서비스 저장소(internal service registry)** 를 구축합니다. 쿠버네티스에서는 istiod가 k8s API의 Service/Endpoints를 감시해 자동으로 채웁니다. 메시 밖의 서비스는 여기에 없으므로, **ServiceEntry로 직접 항목을 삽입**해야 합니다.

실습 시나리오: 가상 상점에 외부 포럼(`jsonplaceholder.typicode.com`)을 연동합니다.

```bash
kubectl apply -f services/forum/kubernetes/forum-all.yaml -n istioinaction

curl -s http://webapp.istioinaction.io:30000/api/users
# error calling Forum service   ← REGISTRY_ONLY라 차단됨

kubectl logs -n istioinaction -l app=forum -c istio-proxy -f
# "GET /users HTTP/1.1" 502 - direct_response ... "jsonplaceholder.typicode.com" ... block_all
```

```yaml
# ch5/forum-serviceentry.yaml
apiVersion: networking.istio.io/v1alpha3
kind: ServiceEntry
metadata:
  name: jsonplaceholder
spec:
  hosts:
    - jsonplaceholder.typicode.com
  ports:
    - number: 80
      name: http
      protocol: HTTP
  resolution: DNS # 도메인 기반 주소 해석
  location: MESH_EXTERNAL # 메시 외부 서비스임을 명시
```

```bash
# 적용 전후 proxy-config diff — 무엇이 추가되는지 확인
docker exec -it myk8s-control-plane istioctl proxy-config all deploy/forum.istioinaction -o short > forum-1.json
kubectl apply -f ch5/forum-serviceentry.yaml -n istioinaction
docker exec -it myk8s-control-plane istioctl proxy-config all deploy/forum.istioinaction -o short > forum-2.json

diff forum-1.json forum-2.json
# > jsonplaceholder.typicode.com   80   -   outbound   STRICT_DNS      ← CDS에 cluster 추가
# > 80    jsonplaceholder.typicode.com    /*                            ← RDS에 route 추가
```

```bash
# DNS 질의 결과가 엔드포인트로 등록됨
docker exec -it myk8s-control-plane istioctl proxy-config endpoint \
  deploy/forum.istioinaction --cluster 'outbound|80||jsonplaceholder.typicode.com'
# ENDPOINT            STATUS    OUTLIER CHECK   CLUSTER
# 104.21.112.1:80     HEALTHY   OK              outbound|80||jsonplaceholder.typicode.com
# 104.21.16.1:80      HEALTHY   OK              ...
# (Cloudflare Anycast IP 여러 개)

# 이제 정상 호출
curl -s http://webapp.istioinaction.io:30000/api/users
```

`resolution: DNS`이므로 cluster 타입이 `STRICT_DNS`가 되고, Envoy가 주기적으로 DNS를 질의해 엔드포인트를 갱신합니다.

## 정리

![릴리스 전략 비교](images/notes/istio-in-action/5-5.png)

| 기능                | 리소스                           | 용도                                          | 장점 / 주의                                      |
| ------------------- | -------------------------------- | --------------------------------------------- | ------------------------------------------------ |
| 버전 분류           | DestinationRule (subset)         | 레이블 기준으로 워크로드를 v1/v2 부분집합으로 분리 | 모든 세밀 라우팅의 전제                           |
| 다크 런치           | VirtualService (match.headers)   | 내부 사용자·베타 테스터에게만 신 버전 노출       | 위험 최소화 / http 목록 **순서가 우선순위**        |
| 카나리 (트래픽 전환) | VirtualService (weight)          | 점진적 트래픽 이관 (10% → 50% → 100%)          | 롤백 = 가중치만 되돌리면 끝 / **합계 100 필수**    |
| 카나리 자동화       | Flagger `Canary`                 | 메트릭 기반 자동 진행·승격·롤백                 | 수작업 설정 오류 제거 / **프로메테우스 필수**      |
| 트래픽 미러링       | VirtualService (mirror)          | 운영 트래픽 복사본으로 신 버전 검증              | 실사용자 영향 0 / Host `-shadow` 인지 설계 필요    |
| 외부 트래픽 차단    | meshConfig.outboundTrafficPolicy | REGISTRY_ONLY로 egress 화이트리스트화           | 데이터 유출 방어 / 프록시 우회는 못 막음           |
| 외부 서비스 허용    | ServiceEntry                     | 메시 레지스트리에 외부 호스트 등록               | 외부 서비스에도 세밀 라우팅 적용 가능              |

**핵심 정리**

- 라우팅은 **DestinationRule(버전 분류) + VirtualService(라우팅 규칙)** 조합으로 구현합니다.
- 모든 설정은 **재시작 없이 동적으로** 적용되지만, 이는 서비스가 **다중 버전을 동시에 실행 가능**하다는 전제 위에 성립합니다.
- `gateways: mesh`를 쓰면 에지뿐 아니라 **호출 그래프 깊은 곳(서비스 간 호출)** 에도 같은 규칙을 적용할 수 있습니다.
- 라우팅 분기는 **호출하는 쪽 사이드카**가 수행합니다 (수신 측 프록시의 route는 1개뿐입니다).
- 릴리스 위험 감소 강도는 **미러링 > 카나리 > 다크 런치 > 빅뱅** 순이며, 미러링만이 사용자 영향이 0입니다.

**막혔을 때 확인 순서**

1. `istioctl proxy-status` — 모두 SYNCED인가? (NOT SENT/STALE이면 설정이 안 내려간 것)
2. `proxy-config routes ... -o json` — match 조건과 cluster 이름이 기대대로인가?
3. `proxy-config cluster --fqdn ...` — subset 컬럼이 나오는가? (안 나오면 DestinationRule 미적용)
4. `proxy-config endpoint --cluster '...'` — 엔드포인트가 실제로 잡히는가?
