## 들어가며 — 7장에서 이어지는 이야기

7장이 **메트릭을 어떻게 모으는가**였다면, 8장은 **모아둔 것을 어떻게 보는가**입니다. 프로메테우스에 쌓인 시계열은 그 자체로는 사람이 읽을 수 있는 형태가 아니고, 그래서 이 장은 도구 세 개를 붙입니다.

| 도구 | 답해주는 질문 | 뿌리 |
| --- | --- | --- |
| **그라파나(Grafana)** | "값이 얼마인가" — 요청량·성공률·지연 백분위수 | 프로메테우스 메트릭 |
| **예거(Jaeger)** | "**어느 홉에서** 오래 걸렸나" | 사이드카가 만든 스팬 |
| **키알리(Kiali)** | "**누가 누구를 부르는가**, 설정은 맞는가" | 프로메테우스 메트릭 + 예거 트레이스 |

세 도구는 서로 대체재가 아니라 **질문의 층이 다릅니다.** 그라파나에서 "webapp 성공률이 떨어졌다"를 보고, 키알리에서 "webapp → catalog 엣지가 빨갛다"를 보고, 예거에서 "catalog 홉에서 3초를 썼다"를 봅니다. 그리고 그 뒤 — "왜 3초인가"는 이 장의 도구로는 답이 안 나옵니다. 그 지점부터가 **부록(덤프·프로파일링)**의 영역입니다.

> **전제:** 7장에서 설치한 `kube-prometheus-stack`이 돌고 있고, 컨트롤 플레인·데이터 플레인 메트릭이 이미 수집되고 있어야 합니다. 2장에서 데모로 깔았던 샘플 애드온이 아니라 7장 구성 기준입니다.

#### 개념 정리

**Pilot Push Time / Convergence**

- `pilot_proxy_convergence_time` — 변경사항이 프록시들에 **전파 완료되기까지 걸린 시간**입니다. 컨트롤 플레인 건강을 하나만 본다면 이것입니다.
- Convergence는 메시 구성요소 간 **설정 일관성을 맞춰가는 과정**입니다. 각 구성요소가 서로 다른 소스(Istio CRD, ConfigMap, Vault 인증서 등)에서 설정을 가져오기 때문에, 변경이 생길 때마다 전체에 전파하고 일관성을 보장하는 작업이 필요합니다.

**Pilot Conflicts** — 이 값이 0이 아니면 설정 충돌이 있다는 뜻입니다.

| 충돌 | 예 | 해결(우선순위) |
| --- | --- | --- |
| endpoint conflict | 같은 서비스/포트에 동일 엔드포인트 다수 | 최신 버전 Endpoint로 업데이트 |
| port conflict | 동일 서비스에 다른 포트 사용 | 먼저 설정된 포트 사용 |
| route conflict | VirtualService/DestinationRule 설정 충돌 | **더 구체적인 설정이 우선** |

**ADS(Aggregated Discovery Service)** — 여러 Discovery Service를 하나로 묶어 엔보이 사이드카(istio-proxy) ↔ istiod 통신을 관리하는 핵심 컴포넌트입니다.

| xDS | 관리 대상 |
| --- | --- |
| LDS (Listener) | 엔보이 리스너 |
| RDS (Route) | 라우팅 규칙 |
| CDS (Cluster) | 클러스터 |
| EDS (Endpoint) | 엔드포인트 |
| SDS (Secret) | 보안 구성(인증서) |
| NDS (Name) | 서비스 이름·IP 주소 |

### 8.1.3 데이터 플레인 메트릭 보기

**Istio Service Dashboard**를 선택하고 상단 콤보에서 서비스(`webapp` 등)를 고릅니다.

여기서 반드시 이해해야 하는 것은 **`reporter` 레이블**입니다.

- `reporter="source"` → **호출한 쪽(클라이언트) 사이드카**가 보고한 값
- `reporter="destination"` → **호출된 쪽(서버) 사이드카**가 보고한 값

같은 호출이 양쪽에서 **두 번** 기록되고, **둘의 차이가 곧 네트워크 구간에서 생긴 지연·실패**입니다. 대시보드가 Client/Server를 나눠 보여주는 이유가 이것입니다. 7장에서 "그냥 합하면 값이 2배가 된다"고 했던 함정의 반대편 활용이기도 합니다 — 나눠 보면 정보가 되고, 합치면 거짓말이 됩니다.

#### General — SERVICE: `webapp.istioinaction.svc.cluster.local`

```javascript
# Client Request Volume
round(sum(irate(istio_requests_total{reporter="source",destination_service=~"webapp.istioinaction.svc.cluster.local"}[5m])), 0.001)

# Client Success Rate (non-5xx)
sum(irate(istio_requests_total{reporter="source",destination_service=~"webapp.istioinaction.svc.cluster.local",response_code!~"5.*"}[5m]))
/ sum(irate(istio_requests_total{reporter="source",destination_service=~"webapp.istioinaction.svc.cluster.local"}[5m]))

# Client Request Duration (p50/p90/p99)
(histogram_quantile(0.99, sum(irate(istio_request_duration_milliseconds_bucket{reporter="source",destination_service=~"webapp.istioinaction.svc.cluster.local"}[1m])) by (le)) / 1000)
  or histogram_quantile(0.99, sum(irate(istio_request_duration_seconds_bucket{reporter="source",destination_service=~"webapp.istioinaction.svc.cluster.local"}[1m])) by (le))

# Server 쪽은 위 쿼리에서 reporter="destination" 으로 바꾼 것
round(sum(irate(istio_requests_total{reporter="destination",destination_service=~"webapp.istioinaction.svc.cluster.local"}[5m])), 0.001)

# TCP
sum(irate(istio_tcp_received_bytes_total{reporter="destination", destination_service=~"webapp.istioinaction.svc.cluster.local"}[1m]))
sum(irate(istio_tcp_sent_bytes_total{reporter="destination", destination_service=~"webapp.istioinaction.svc.cluster.local"}[1m]))
```

#### Client Workloads — "누가 나를 부르는가"

`source_workload`로 그룹핑합니다. 조건에 `connection_security_policy="mutual_tls"`가 붙어 있는 것도 눈여겨볼 부분입니다 — **mTLS 여부까지 메트릭에 실려 있습니다.**

```javascript
# Incoming Requests By Source And Response Code
round(sum(irate(istio_requests_total{connection_security_policy="mutual_tls",destination_service=~"webapp.istioinaction.svc.cluster.local",reporter="source",source_workload=~"istio-ingressgateway",source_workload_namespace=~"istio-system"}[5m])) by (source_workload, source_workload_namespace, response_code), 0.001)

# Incoming Success Rate By Source
sum(irate(istio_requests_total{reporter="source", connection_security_policy="mutual_tls", destination_service=~"catalog.istioinaction.svc.cluster.local",response_code!~"5.*", source_workload=~"webapp", source_workload_namespace=~"istioinaction"}[5m])) by (source_workload, source_workload_namespace)
/ sum(irate(istio_requests_total{reporter="source", connection_security_policy="mutual_tls", destination_service=~"catalog.istioinaction.svc.cluster.local", source_workload=~"webapp", source_workload_namespace=~"istioinaction"}[5m])) by (source_workload, source_workload_namespace)

# Request/Response Size By Source
histogram_quantile(0.99, sum(irate(istio_request_bytes_bucket{reporter="source", destination_service=~"catalog.istioinaction.svc.cluster.local", source_workload=~"webapp"}[1m])) by (source_workload, source_workload_namespace, le))
histogram_quantile(0.99, sum(irate(istio_response_bytes_bucket{reporter="source", destination_service=~"catalog.istioinaction.svc.cluster.local", source_workload=~"webapp"}[1m])) by (source_workload, source_workload_namespace, le))
```

#### Service Workloads — "내 뒤의 워크로드는 어떤가"

`destination_workload`로 그룹핑합니다. Deployment가 여러 버전(v1/v2)일 때 **버전별 상태를 가르는 데** 씁니다 — 5장의 카나리를 이 화면으로 지켜보게 됩니다.

```javascript
round(sum(irate(istio_requests_total{connection_security_policy="mutual_tls",destination_service=~"catalog.istioinaction.svc.cluster.local",reporter="destination",destination_workload=~"catalog",destination_workload_namespace=~"istioinaction"}[5m])) by (destination_workload, destination_workload_namespace, response_code), 0.001)
```

> 이 그래프들은 전부 **이스티오 표준 메트릭**으로 채워집니다. 커스텀 메트릭이나 특정 엔보이 메트릭을 켜는 방법은 7장(7.4 디멘션·속성)을 보세요.

## 8.2 분산 트레이싱

### 왜 필요한가

모놀리스에서는 디버거·프로파일러·메모리 분석 도구로 "코드의 어느 부분이 느린가"를 찾을 수 있습니다. 그런데 애플리케이션이 **분산 구성요소의 네트워크**가 되는 순간 같은 질문에 답할 도구가 사라집니다. 홉이 여러 개인 요청 하나가 3초 걸렸을 때, **어느 홉에서** 3초를 썼는지는 메트릭만으로는 알 수 없습니다.

![여러 홉을 거치는 요청 — 어디서 느려졌는지 메트릭만으로는 모른다](images/notes/istio-in-action/8-2.avif)

- 분산 트레이싱은 **구글 Dapper 논문(2010)**에서 도입된 개념입니다. [Dapper, a Large-Scale Distributed Systems Tracing Infrastructure](https://research.google/pubs/dapper-a-large-scale-distributed-systems-tracing-infrastructure/)
- 요청에 주석(annotation)을 붙입니다: **correlation ID**(서비스 간 호출을 나타냄)와 **trace ID**(호출 그래프를 관통하는 **특정 요청 하나**를 식별).
- 이스티오 데이터 플레인은 요청이 통과할 때 이 메타데이터를 **추가**하고, 인식할 수 없거나 **외부에서 들어온 것은 제거**합니다. 이건 보안상 중요한 동작입니다 — 외부인이 임의 trace ID를 주입해 내부 트레이스를 오염시키는 것을 막습니다.

**OpenTracing / OpenTelemetry**

- **OpenTracing** — 분산 트레이싱의 개념과 API를 정의하는 *사양(spec)*
- **OpenTelemetry** — OpenTracing을 포함하는 커뮤니티 주도 프레임워크. 메트릭·로그·트레이스를 계측/생성/수집/내보내기 위한 API·SDK·도구 모음

**그래도 개발자 몫이 남습니다**

- 코드 계측(instrumenting code) 삽입
- 요청에 어노테이션(correlation ID, trace ID) 추가 — 정확히는 **헤더 전파**

**이스티오를 쓰는 이유**: 위 둘 중 "스팬 생성과 트레이싱 엔진 전송"을 이스티오가 대신 해줍니다. **남는 개발자 책임은 헤더 전파 하나**입니다. 그리고 이 하나가 실무에서 제일 자주 빠집니다.

### 8.2.1 분산 트레이싱은 어떻게 작동하는가?

가장 단순한 형태의 흐름입니다.

1. 서비스에서 **스팬(Span) 생성** — 시작시각, 종료시각, 작업 이름, 태그, 로그
2. **트레이싱 엔진으로 스팬 전송**
3. 다음에 호출할 서비스로 **트레이스 컨텍스트 전파**
4. 업스트림 서비스도 같은 일을 반복
5. 엔진이 스팬 + 트레이스 컨텍스트를 조립해 **트레이스 기록** → 서비스 간 인과성 추적
6. **Span ID / Trace ID**로 서비스 간 작업을 상관(correlate)

즉 **스팬 + 트레이스 컨텍스트 ⇒ 트레이스**입니다.

![스팬과 트레이스 컨텍스트가 하나의 트레이스로 조립되는 과정](images/notes/istio-in-action/8-3.avif)

**이스티오가 하는 일**: 요청이 서비스 프록시를 통과할 때 진행 중인 트레이스가 없으면 새로 시작하고, 요청의 시작·종료 시각을 스팬에 기록해 **트레이싱 엔진으로 전송**합니다. 이미 트레이싱 헤더가 있으면 **진행 중인 트레이스로 취급하고 새로 만들지 않습니다.**

**Zipkin 트레이싱 헤더 (B3)**

| 헤더 | 역할 |
| --- | --- |
| `x-request-id` | 이스티오 correlation ID |
| `x-b3-traceid` | 요청 전체를 식별하는 Trace ID |
| `x-b3-spanid` | 현재 Span ID |
| `x-b3-parentspanid` | 부모 Span ID (인과관계) |
| `x-b3-sampled` | 이 요청을 샘플링할지 여부 |
| `x-b3-flags` | 디버그 등 플래그 |
| `x-ot-span-context` | OpenTracing span context |

![프록시가 트레이스 헤더를 붙이고 애플리케이션이 그것을 다음 홉으로 전파하는 흐름](images/notes/istio-in-action/8-4.avif)

**⚠️ 가장 중요한 함정 — 애플리케이션이 헤더를 전파해야 합니다**

위 그림을 말로 풀면 이렇습니다.

1. 요청이 들어옵니다 → 트레이싱 헤더가 없습니다 → 새 요청입니다
2. 이스티오 프록시가 트레이스 헤더를 생성합니다 (`x-request-id: c9421…`)
3. 프록시는 이 헤더를 **애플리케이션으로 전달**합니다
4. **애플리케이션이 다음 서비스를 호출할 때 이 헤더를 실어 보내야 합니다**
5. 전파하지 않으면 다음 홉의 요청에 트레이스 헤더가 **누락**됩니다
6. 이스티오는 "이 아웃바운드 호출이 어떤 인바운드 요청의 결과인지" 알 방법이 없습니다 → **트레이스가 끊깁니다**

프록시는 이 일을 자동으로 할 수 없습니다. 인바운드 요청의 헤더를 **저장했다가 모든 아웃바운드 요청에 삽입**하는 것은 앱 코드의 몫입니다. 대부분의 RPC 프레임워크가 OpenTracing과 통합돼 자동 전파해주지만, **보장은 애플리케이션 책임**입니다.

**OpenTracing 구현체**: 예거(Jaeger), 집킨(Zipkin), 라이트스텝(Lightstep), 인스타나(Instana)

### 8.2.2 분산 트레이싱 시스템 설치하기

예거를 제대로 설치하면 데이터베이스가 필요해 복잡합니다. 그래서 실습은 이스티오가 제공하는 **all-in-one 샘플**을 씁니다. 이 샘플은 `zipkin` 쿠버네티스 서비스도 함께 만드는데, **이스티오의 기본 기대 설정(`zipkin.istio-system:9411`)에 맞춰져 있어** 바로 연결됩니다.

```bash
cd istio-1.17.2
kubectl apply -f samples/addons/jaeger.yaml
# deployment.apps/jaeger created
# service/tracing created
# service/zipkin created
# service/jaeger-collector created

kubectl get po,svc -n istio-system -o name
```

샘플이 만드는 리소스입니다.

| 리소스 | 포트 | 용도 |
| --- | --- | --- |
| `deploy/jaeger` | — | `jaegertracing/all-in-one:1.35`, 스토리지는 badger(emptyDir) |
| `svc/tracing` | 80 → 16686 | **예거 UI** |
| `svc/tracing` | 16685 | gRPC query (키알리 연동용) |
| `svc/zipkin` | 9411 | **집킨 호환 수집 엔드포인트** ← 이스티오가 여기로 스팬 전송 |
| `svc/jaeger-collector` | 14268/14250/9411 | 컬렉터 |

> `svc/zipkin`이 따로 있는 이유: 예거가 **집킨 API를 구현**하고 있고, 트레이싱 백엔드를 갈아끼울 수 있도록 이름을 `zipkin`으로 고정해뒀기 때문입니다. 이스티오 입장에서는 "집킨 프로토콜을 받는 무언가"면 됩니다.

```bash
# UI 접근 — 포트포워딩
istioctl dashboard jaeger --browser=false     # → http://localhost:16686

# UI 접근 — NodePort (kind 실습)
kubectl patch svc -n istio-system tracing \
  -p '{"spec": {"type": "NodePort", "ports": [{"port": 80, "targetPort": 16686, "nodePort": 30004}]}}'
# → http://127.0.0.1:30004
```

### 8.2.3 분산 트레이싱을 수행하도록 이스티오 설정하기

이스티오는 **메시 전체 / 네임스페이스 / 특정 워크로드** 수준에서 트레이싱을 설정할 수 있습니다.

> **Note** — Istio 1.12부터 로깅·메트릭·트레이싱을 위한 더 세분화된 **Telemetry API**가 도입됐습니다. 아래 방법들은 그 이전의 `meshConfig` 방식이며, 새로 구성한다면 Telemetry API를 먼저 검토하는 편이 좋습니다. (7장에서 EnvoyFilter가 Telemetry API로 대체된 것과 같은 흐름입니다.)

#### 방법 1 — 설치 시 IstioOperator (실습에서 사용)

지원 백엔드: Zipkin, Datadog, Jaeger(집킨 호환), Lightstep, Stackdriver 등

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  namespace: istio-system
spec:
  meshConfig:
    defaultConfig:
      tracing:
        lightstep: {}
        zipkin: {}
        datadog: {}
        stackdriver: {}
```

실습에서 쓰는 예거(집킨 호환) 설정입니다.

```yaml
# ch8/install-istio-tracing-zipkin.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  namespace: istio-system
spec:
  meshConfig:
    defaultConfig:
      tracing:
        sampling: 100
        zipkin:
          address: zipkin.istio-system:9411
```

```bash
istioctl install -y -f ch8/install-istio-tracing-zipkin.yaml

# 확인
kubectl describe cm -n istio-system istio
#   tracing:
#     sampling: 100
#     zipkin:
#       address: zipkin.istio-system:9411
```

#### 방법 2 — istio ConfigMap(MeshConfig) 직접 수정

```bash
kubectl edit cm -n istio-system istio
```

```yaml
apiVersion: v1
data:
  mesh: |-
    defaultConfig:
      discoveryAddress: istiod.istio-system.svc:15012
      proxyMetadata: {}
      tracing:
        zipkin:
          address: zipkin.istio-system:9411
    enablePrometheusMerge: true
    rootNamespace: istio-system
    trustDomain: cluster.local
```

메시 범위 기본값은 무엇이든 `defaultConfig.tracing`에서 바꿀 수 있습니다.

#### 방법 3 — 워크로드별 어노테이션

파드 spec의 `proxy.istio.io/config` 어노테이션으로 설정합니다.

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    metadata:
      annotations:
        proxy.istio.io/config: |
          tracing:
            zipkin:
              address: zipkin.istio-system:9411
```

#### 실습 — 헤더·ID 자동 주입 확인

이스티오가 정말 OpenTracing 헤더와 correlation ID를 자동 주입하는지 눈으로 봅니다. `httpbin.istioinaction.io`로 요청하면 외부 `http://httpbin.org`를 호출하게 만들고, httpbin이 되돌려주는 **요청 헤더**를 확인하는 방식입니다.

```yaml
# ch8/tracing/thin-httpbin-virtualservice.yaml
apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: coolstore-gateway
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "webapp.istioinaction.io"
    - "httpbin.istioinaction.io"
---
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: thin-httpbin-virtualservice
spec:
  hosts:
  - "httpbin.istioinaction.io"
  gateways:
  - coolstore-gateway
  http:
  - route:
    - destination:
        host: httpbin.org
---
apiVersion: networking.istio.io/v1alpha3
kind: ServiceEntry
metadata:
  name: external-httpbin-org
spec:
  hosts:
  - httpbin.org
  ports:
  - number: 80
    name: http
    protocol: HTTP
  location: MESH_EXTERNAL
  resolution: DNS
```

```bash
kubectl apply -n istioinaction -f ch8/tracing/thin-httpbin-virtualservice.yaml
kubectl get gw,vs,serviceentry -n istioinaction

# kind 실습 시 도메인 질의용 임시 설정 (실습 후 삭제)
echo "127.0.0.1  httpbin.istioinaction.io" | sudo tee -a /etc/hosts
```

호출 경로는 `client(curl) → istio-ingressgateway → httpbin.org(외부)`입니다.

```bash
curl -s -H "Host: httpbin.istioinaction.io" http://localhost/headers | jq
```

```json
{
  "headers": {
    "Accept": "*/*",
    "Host": "httpbin.istioinaction.io",
    "User-Agent": "curl/8.7.1",
    "X-Amzn-Trace-Id": "Root=1-680de9d9-33db643526404d6b0dc37527",
    "X-B3-Sampled": "1",
    "X-B3-Spanid": "3726f7dcb215ac12",
    "X-B3-Traceid": "9a4a7076cf8b5f633726f7dcb215ac12",
    "X-Envoy-Attempt-Count": "1",
    "X-Envoy-Decorator-Operation": "httpbin.org:80/*",
    "X-Envoy-Internal": "true",
    "X-Envoy-Peer-Metadata": "<base64 …>",
    "X-Envoy-Peer-Metadata-Id": "router~10.10.0.22~istio-ingressgateway-…istio-system.svc.cluster.local"
  }
}
```

- `X-B3-*` 집킨 헤더가 **자동으로** 붙었습니다. 이 헤더를 근거로 스팬이 만들어져 예거로 전송됩니다.
- `X-B3-Traceid`의 뒤쪽 16자리가 `X-B3-Spanid`와 같은 것도 눈여겨볼 부분입니다 — 128bit trace ID의 하위 64bit가 루트 스팬 ID입니다.
- 보너스: `X-Envoy-Peer-Metadata`는 base64 protobuf입니다. 디코딩하면 상대 워크로드 정보가 들어 있습니다.

```bash
echo "ChQKDkFQUF9DT05UQUlORVJTEgIaAAoaCgpDTFVTVEVSX0lE…" | base64 -d
```

### 8.2.5 트레이스 샘플링, 강제 트레이스, 커스텀 태그

분산 트레이싱과 스팬 수집은 **상당한 성능 저하**를 초래할 수 있습니다. 그래서 정상 운영 중에는 수집 빈도를 제한합니다. demo 프로필의 샘플링 **100%**는 실습 편의를 위한 값이지 운영값이 아닙니다.

#### 메시의 트레이스 샘플링 비율 조정하기

```bash
kubectl edit -n istio-system cm istio
```

```yaml
mesh: |-
    defaultConfig:
      discoveryAddress: istiod.istio-system.svc:15012
      proxyMetadata: {}
      tracing:
        sampling: 10        # <-- from 100
        zipkin:
          address: zipkin.istio-system:9411
```

이로써 메시 내 **모든 워크로드의 샘플링 비율이 전역 10%**로 바뀝니다.

```bash
# 샘플링 적용에는 istio-ingressgateway 재배포가 필요하다
kubectl rollout restart deploy -n istio-system istio-ingressgateway
```

> **실습에서 걸린 지점**
> - istiod 로그에 istio ConfigMap 변경 로그는 찍히지만, 게이트웨이 재배포 없이는 반영이 확실하지 않았습니다. `rollout restart`로 되는지 파드 삭제까지 필요한지는 환경을 탑니다.
> - **워크로드 단위 샘플링이 기대대로 동작하지 않았습니다.** 책은 어노테이션으로 워크로드별 샘플링이 된다고 하는데, 실제로는 `meshConfig`의 sampling 비율로 동작했습니다.

```yaml
# ch8/webapp-deployment-zipkin.yaml — 어노테이션으로 워크로드별 샘플링 시도
template:
  metadata:
    annotations:
      proxy.istio.io/config: |
        tracing:
          sampling: 10
          zipkin:
            address: zipkin.istio-system:9411
```

> → 예거 UI에서 트레이스가 줄어들긴 했지만 정확히 지정 비율대로인지는 확인되지 않았습니다. **운영에서 워크로드별 샘플링에 의존하기 전에 반드시 자기 환경에서 검증해야 합니다.**

#### 클라이언트에서 트레이싱 강제하기 (FORCE-TRACING)

운영에서는 **샘플링을 낮게 유지하고, 문제가 있을 때만** 특정 요청에 트레이싱을 강제하는 것이 이치에 맞습니다. `x-envoy-force-trace` 헤더 하나면 됩니다.

```bash
curl -s -H "x-envoy-force-trace: true" \
     -H "Host: webapp.istioinaction.io" http://localhost/api/catalog
```

- 이 헤더가 있으면 **샘플링 비율과 무관하게 무조건 샘플링**됩니다.
- 해당 요청과 그 요청이 만드는 **호출 그래프 전체**에 대해 트레이싱을 트리거합니다.
- 활용: 이 헤더를 주입할 수 있는 **API 게이트웨이나 진단 서비스**를 이스티오 위에 두면, 특정 요청만 골라 깊게 볼 수 있습니다.

#### 트레이스 태그 커스터마이징하기 (CUSTOM TAG)

태그는 단순 **키-값 쌍**으로, 애플리케이션·조직별 커스텀 정보를 스팬에 실어 백엔드로 보냅니다. 값의 출처는 세 가지입니다.

1. **직접 입력(literal)** — 명시적으로 값 지정
2. **환경 변수** — 환경 변수에서 값 가져오기
3. **요청 헤더** — 요청 헤더에서 값 가져오기

```yaml
# ch8/webapp-deployment-zipkin-tag.yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    metadata:
      annotations:
        proxy.istio.io/config: |
          tracing:
            sampling: 100
            customTags:
              custom_tag:              # 커스텀 태그의 키
                literal:
                  value: "Test Tag"    # 커스텀 태그의 값
            zipkin:
              address: zipkin.istio-system:9411
```

```bash
kubectl apply -n istioinaction -f ch8/webapp-deployment-zipkin-tag.yaml
curl -s -H "Host: webapp.istioinaction.io" localhost/api/catalog
```

webapp 스팬의 **Tags**에 `custom_tag`가 추가됩니다.

![스팬 Tags에 추가된 custom_tag](images/notes/istio-in-action/8-8.avif)

**용도**: 트레이스 데이터 **탐색 / 리포팅 / 필터링** (자세히는 [Istio Distributed Tracing 문서](https://istio.io/v1.17/docs/tasks/observability/distributed-tracing/))

#### 백엔드 트레이싱 엔진 커스터마이징하기

지금까지는 백엔드의 **호스트네임과 포트**만 설정했습니다. 그보다 세밀한 조정이 필요하면(예: 예거 컬렉터의 특정 엔드포인트로 스팬 전송) **커스텀 부트스트랩**을 씁니다. 이 값들은 기본적으로 이스티오 프록시의 **정적 설정**입니다.

```bash
istioctl pc bootstrap -n istioinaction deploy/webapp -o json | jq .bootstrap.tracing
```

```json
{
  "http": {
    "name": "envoy.tracers.zipkin",
    "typedConfig": {
      "@type": "type.googleapis.com/envoy.config.trace.v3.ZipkinConfig",
      "collectorCluster": "zipkin",
      "collectorEndpoint": "/api/v2/spans",
      "traceId128bit": true,
      "sharedSpanContext": false,
      "collectorEndpointVersion": "HTTP_JSON"
    }
  }
}
```

기본값 정리 — 트레이싱 엔진은 **Zipkin 기반**, 스팬은 **`/api/v2/spans`**로, **JSON 엔드포인트**(`HTTP_JSON`)로 전달됩니다.

**1단계 — 튜닝할 설정 스니펫을 ConfigMap으로**

```yaml
# ch8/istio-custom-bootstrap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: istio-custom-zipkin
data:
  custom_bootstrap.json: |
    {
      "tracing": {
        "http": {
          "name": "envoy.tracers.zipkin",
          "typedConfig": {
            "@type": "type.googleapis.com/envoy.config.trace.v3.ZipkinConfig",
            "collectorCluster": "zipkin",
            "collectorEndpoint": "/zipkin/api/v1/spans",
            "traceId128bit": "true",
            "collectorEndpointVersion": "HTTP_JSON"
          }
        }
      }
    }
```

```bash
# 덮어쓰려는 워크로드가 있는 네임스페이스에 적용해야 한다
kubectl apply -n istioinaction -f ch8/istio-custom-bootstrap.yaml
kubectl get cm -n istioinaction
```

**2단계 — Deployment에 `sidecar.istio.io/bootstrapOverride` 어노테이션**

```yaml
# ch8/webapp-deployment-custom-boot.yaml
template:
  metadata:
    annotations:
      sidecar.istio.io/bootstrapOverride: "istio-custom-zipkin"
      proxy.istio.io/config: |
        tracing:
          sampling: 10
          zipkin:
            address: zipkin.istio-system:9411
    labels:
      app: webapp
```

```bash
kubectl apply -n istioinaction -f ch8/webapp-deployment-custom-boot.yaml

# 반영 확인 — collectorEndpoint 가 바뀌었다
istioctl pc bootstrap -n istioinaction deploy/webapp -o json | jq .bootstrap.tracing
# "collectorEndpoint": "/zipkin/api/v1/spans"

curl -s -H "Host: webapp.istioinaction.io" http://localhost/api/catalog
```

**결과 — 예거 대시보드에 webapp 스팬이 나오지 않습니다.**

![커스텀 부트스트랩 이후 webapp 스팬이 사라진 예거 화면](images/notes/istio-in-action/8-9.avif)

> 💡 **놀랄 일이 아닙니다.** 일부러 **존재하지 않는 `collectorEndpoint`**로 바꿨기 때문에 스팬이 안 보이는 게 정상입니다.
> 이 실습의 교훈은 두 가지입니다 — "커스텀 부트스트랩은 실제로 먹는다", 그리고 **"엔드포인트 하나 틀리면 트레이싱이 조용히 죽는다"**. 에러가 아니라 **침묵**으로 실패한다는 점이 무섭습니다.

**원복**

```bash
kubectl apply -n istioinaction -f services/webapp/kubernetes/webapp.yaml
curl -s -H "Host: webapp.istioinaction.io" http://localhost/api/catalog
```

## 8.3 키알리를 이용한 시각화

### 그라파나와 무엇이 다른가

|  | 그라파나 | 키알리 |
| --- | --- | --- |
| 강점 | 게이지·카운터·차트가 담긴 **대시보드** | 서비스 간 **방향 그래프(directed graph)** |
| 보는 것 | "값이 얼마인가" | "**누가 누구를 부르는가**" |
| 갱신 | 시계열 조회 | 실시간 갱신 메트릭으로 그래프 구성 |
| 한계 | 클러스터 내 서비스의 **상호작용 지도**를 못 보여줌 | 세밀한 시계열 분석에는 부족 |

키알리는 프로메테우스에 저장된 **이스티오 메트릭**을 가져와 메시 구성요소의 런타임 그래프를 만들고, 그래프와 상호작용해 문제 영역을 파고들 수 있게 해줍니다.

### 8.3.1 키알리 설치하기

**전제**

- 이스티오도 키알리 샘플을 제공하지만, **이스티오 팀과 키알리 팀 모두 실제 배포에는 [키알리 오퍼레이터](https://github.com/kiali/kiali-operator)를 권장**합니다. 여기서도 오퍼레이터를 씁니다.
- 앞에서 설치한 `kube-prometheus-stack`, 예거와 연동합니다.
- 책은 kiali-operator 1.40.1 기준, 아래는 Istio 1.16/1.17에 맞춘 1.63.2 기준입니다.

**Step 1 — 키알리 오퍼레이터 설치**

```bash
helm repo add kiali https://kiali.org/helm-charts
helm repo update

helm install \
  --namespace kiali-operator \
  --create-namespace \
  --version 1.63.2 \
  kiali-operator \
  kiali/kiali-operator

kubectl get pod -n kiali-operator
# NAME                             READY   STATUS    RESTARTS   AGE
# kiali-operator-584858fb7-zcjv2   1/1     Running   0          61s
```

**Step 2 — 키알리 인스턴스(대시보드) 배포**

```yaml
# ch8/kiali.yaml
apiVersion: kiali.io/v1alpha1
kind: Kiali
metadata:
  namespace: istio-system
  name: kiali
spec:
  istio_namespace: "istio-system"
  istio_component_namespaces:
    prometheus: prometheus
  auth:
    strategy: anonymous          # 익명 접근 허용 (실습용)
  deployment:
    accessible_namespaces:
    - '**'
  external_services:
    prometheus:                  # 클러스터 내 프로메테우스 연동
      cache_duration: 10
      cache_enabled: true
      cache_expiration: 300
      url: "http://prom-kube-prometheus-stack-prometheus.prometheus:9090"
    tracing:                     # 클러스터 내 예거 연동
      enabled: true
      in_cluster_url: "http://tracing.istio-system:16685/jaeger"
      use_grpc: true
```

```bash
kubectl apply -f ch8/kiali.yaml

kubectl get deploy,svc -n istio-system kiali
# deployment.apps/kiali   1/1   1   1   36s
# service/kiali   ClusterIP  10.200.1.179  <none>  20001/TCP,9090/TCP

# 접속 — 포트포워딩
kubectl -n istio-system port-forward deploy/kiali 20001    # http://localhost:20001

# 접속 — NodePort (kind 실습)
kubectl patch svc -n istio-system kiali \
  -p '{"spec": {"type": "NodePort", "ports": [{"port": 20001, "targetPort": 20001, "nodePort": 30003}]}}'
# → http://127.0.0.1:30003
```

> ⚠️ **보안 주의** — 프로메테우스와 예거는 기본적으로 통신 보안 전략이 없습니다. **앞단에 리버스 프록시를 두는 것을 권장**합니다. 키알리→프로메테우스 연결에는 TLS와 기본 인증을 쓸 수 있습니다. 위 `auth.strategy: anonymous`는 실습용이며 운영에 그대로 쓰면 안 됩니다.

삭제는 **커스텀 리소스를 먼저** 지워야 오퍼레이터가 정리해 줍니다.

```bash

helm uninstall kiali -n kiali-operator # 2. 오퍼레이터 삭제
kubectl delete ns kiali-operator       # 3. 네임스페이스 삭제
```

#### Application vs Workload — 왜 개수가 다른가?

같은 네임스페이스인데 Apps는 2, Workloads는 3입니다. `prometheus` Apps에 그라파나(`prom-grafana`)가 **포함되지 않기** 때문입니다.

**이유**: Apps로 집계되려면 파드에 **`app` 레이블**이 있어야 합니다. `prom-grafana` 파드에는 `app` 레이블이 없어 Workload로만 잡힙니다. (레이블 추가 후 **재배포 필요**)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: prom-grafana
spec:
  template:
    metadata:
      labels:
        app: prom-grafana   # <-- Pod label 추가
```

[키알리 공식 용어 정의](https://kiali.io/docs/architecture/terminology/concepts/) 기준입니다.

| 개념 | 정의 |
| --- | --- |
| **Workload** | 동일한 복제 리플리카에 해당하는 **실행 바이너리 집합**. 쿠버네티스에서는 Deployment에 포함된 파드들. 리플리카 3개짜리 서비스 A의 Deployment 하나가 워크로드 하나 → `istioinaction`에는 `catalog`, `webapp` |
| **Application** | 유저가 **레이블로 표시한 워크로드들의 논리적 그룹**. 서비스·설정 같은 관련 구성요소까지 포함. 이스티오에서는 **Label App**으로 정의 |
| **Label App** | `app` 레이블로 정의. 파드 레이블로 `app`(필수), `version`(옵션)을 권장 |

- **`app` (필수)** — 분산 트레이싱에서 애플리케이션을 식별하는 데 쓰입니다.
- **`version` (옵션)** — 애플리케이션 버전 식별에 쓰입니다.

![app / version 레이블이 붙은 워크로드 화면](images/notes/istio-in-action/8-12.avif)

> 이 레이블 규칙은 키알리만의 취향이 아닙니다. **`app`/`version` 레이블이 없으면 트레이싱 식별과 카나리 관측이 모두 반쪽**이 됩니다.

#### 트레이스·메트릭·로그의 상관관계(Correlation)

키알리는 관찰 가능성 관점의 **통합 대시보드**로 진화하고 있습니다. **Workloads** 메뉴에서 워크로드를 선택하면 서브탭별로 아래를 제공합니다.

![키알리 워크로드 상세의 서브탭들](images/notes/istio-in-action/8-15.avif)

| 서브탭 | 내용 |
| --- | --- |
| **Overview** | 서비스 파드들, 적용된 이스티오 설정, 업스트림/다운스트림 콜 그래프 |
| **Traffic** | 인바운드/아웃바운드 트래픽 성공률 |
| **Logs** | **앱 로그 + 엔보이 액세스 로그 + 스팬 정보를 함께** 제공 |
| **Inbound/Outbound Metrics** | 스팬과 연관시켜 제공 |
| **Traces** | 예거가 보고한 트레이스 리포트 |
| **Envoy** | 워크로드에 적용된 엔보이 설정(Clusters, Listeners, Routes) |

**왜 중요한가**: 연관된 지표가 한 곳에 모이면 디버깅이 극적으로 단순해집니다. 여러 창을 오가며 시점을 맞춰 그래프를 비교할 필요가 없습니다. 예를 들어 대시보드에서 **요청 스파이크**를 발견하면, 그 자리에서 "새 버전 혹은 degraded 서비스로부터 요청이 처리됐다"는 **트레이스**를 바로 확인할 수 있습니다.

#### 키알리의 Validation — 운영에서 진짜 도움 되는 기능

키알리는 이스티오 리소스에 대한 **정적 검증**을 제공합니다. 아래는 실수하기 쉬운데 증상이 모호해 찾기 어려운 것들입니다.

- 존재하지 않는 **Gateway**를 가리키는 VirtualService
- 존재하지 않는 **목적지(destination)**로의 라우팅
- **동일한 호스트에 대한 VirtualService가 2개 이상**
- DestinationRule에서 **서비스 서브셋을 찾을 수 없음**

### 8.3.2 세 도구 정리

| 도구 | 역할 |
| --- | --- |
| **그라파나** | 프로메테우스 메트릭 기반 시각화 (컨트롤/데이터 플레인 대시보드) |
| **예거** | 콜 그래프의 **레이턴시**를 이해하는 분산 트레이싱. 요청 메타데이터에 어노테이션 → 스팬을 트레이싱 엔진에 전송 |
| **키알리** | 트래픽 흐름을 **콜 그래프**로 표현 + 상세 구성 정보 + Validation |

## 요약

**그라파나**

- 이스티오 메트릭을 시각화합니다. 컨트롤/데이터 플레인 **기본 대시보드**를 제공합니다.
- ConfigMap + `grafana_dashboard=1` 레이블로 대시보드를 주입합니다.

**분산 트레이싱(예거)**

- 요청 처리에 관여한 구성요소에 대한 **인사이트**를 줍니다. 서비스 프록시가 요청에 **트레이스 헤더로 주석**을 붙입니다.
- **트레이스 = 스팬의 집합.** 분산 환경에서 요청의 홉과 지연을 디버깅하는 데 씁니다.
- 간트 차트와 구조가 같습니다 — 위가 간트 차트, 아래가 트레이스입니다.

![간트 차트](images/notes/istio-in-action/8-16.avif)

![같은 구조로 그려지는 트레이스 화면](images/notes/istio-in-action/8-17.avif)

- **애플리케이션은 트레이스 헤더를 전파해야 합니다.** 그래야 요청 흐름의 전체 그림을 얻습니다.
- 설정 위치 — **전역**: 설치 시 `meshConfig.defaultConfig` / **워크로드 단위**: 어노테이션 `proxy.istio.io/config`
- 샘플링 전략: 평시 낮은 비율 + 필요할 때 `x-envoy-force-trace`로 강제

**키알리**

- 오퍼레이터 설정으로 **메트릭은 프로메테우스**, **트레이스는 예거**에서 읽어옵니다.

![키알리 콜 그래프](images/notes/istio-in-action/8-18.avif)

![키알리의 메트릭 상관관계 화면](images/notes/istio-in-action/8-19.avif)

- 네트워킹 그래프 + 메트릭 상관관계 + 이스티오 리소스 Validation을 제공합니다.
- **`app` / `version` 레이블은 선택이 아닙니다** — 없으면 Application 집계와 트레이싱 식별이 깨집니다.

## 정리하며 — 실무에서 기억할 것 5가지

1. **`reporter` 레이블을 읽습니다.** source와 destination의 차이가 곧 네트워크 구간의 문제입니다.
2. **`pilot_proxy_convergence_time`과 `pilot_conflict_*`**는 컨트롤 플레인 건강의 핵심 지표입니다. 후자는 0이 아니면 설정 충돌입니다.
3. **트레이싱은 침묵으로 실패합니다.** `collectorEndpoint` 오타 하나로 스팬이 사라지지만 에러는 나지 않습니다. 커스텀 부트스트랩을 쓸 땐 `istioctl pc bootstrap`으로 항상 확인합니다.
4. **운영 샘플링은 낮게, 진단은 `x-envoy-force-trace`로.** 100% 샘플링은 demo 프로필 값입니다.
5. **헤더 전파는 애플리케이션 책임입니다.** 이스티오를 깔았다고 트레이스가 완성되지 않습니다. 앱이 `x-b3-*`를 릴레이하지 않으면 그래프가 끊깁니다.

## 부록 — 덤프·프로파일링 인계표: 관측이 끝나는 지점에서

> 그라파나·예거·키알리는 **어디를 파야 하는지 정해주는 도구**입니다. 실제로 파는 것은 덤프입니다.
> 트레이스가 "webapp → catalog 홉에서 3초"를 알려줘도, 그게 GC인지 CPU 스로틀링인지 커넥션 풀 대기인지는 **스레드 덤프 5장**이 말해줍니다.

### 증상 → 덤프 순서 (치트시트)

| 증상 | 뜨는 순서 |
| --- | --- |
| **p99만 튄다** | cgroup `cpu.stat` 스로틀링 → GC 로그 → async-profiler `wall` → FlameScope |
| **전부 느리다** | 엔보이 `/clusters` → `curl -w` 시간 분해 → 스레드 덤프 ×5 |
| **메모리가 계속 오른다** | `GC.heap_info` → 힙 덤프 2장 diff → 안 잡히면 **NMT** |
| **OOMKilled인데 힙은 여유** | NMT → direct buffer / Metaspace / 스레드 스택 수 |
| **커넥션이 안 돌아온다** | `ss -tanp` CLOSE_WAIT → 스레드 덤프(풀 대기 스택) → `/proc/PID/fd` 개수 |
| **간헐적 5xx** | 액세스 로그 `RESPONSE_FLAGS` → `/clusters` 서킷 → `nstat` 재전송 → tcpdump |
| **특정 요청 하나만 느리다** | 트레이스에서 스팬 특정 → **span profile**(그 구간만 플레임그래프) → Arthas `trace` |
| **배포 후에만 깨진다** | `istioctl proxy-status` STALE → `pc all` diff → `/actuator/env` |

### 1. 엔보이 사이드카 — 메시에서 제일 먼저 뜰 덤프

| 덤프 | 명령 | 잡는 것 |
| --- | --- | --- |
| 설정 전량 | `istioctl pc all POD -o json` | 라우팅이 생각한 대로 박혔나 |
| 클러스터 상태 | `curl localhost:15000/clusters` | 엔드포인트별 `health_flags`, `cx_active`, `rq_pending`, 서킷 오픈 |
| 동기화 상태 | `istioctl proxy-status` | `STALE`이면 컨트롤 플레인이 못 밀어준 것 |
| 인증서 | `curl localhost:15000/certs` | mTLS 만료·SAN 불일치 |
| 로그 레벨(런타임) | `curl -XPOST localhost:15000/logging?connection=debug` | 재배포 없이 커넥션 단위 추적 |
| 메모리 | `curl localhost:15000/memory` | 사이드카 자체 누수 |

> **`%RESPONSE_FLAGS%` 액세스 로그가 사실상 tcpdump보다 빠른 덤프입니다.**
> `UO` 서킷 오픈 · `UF` 업스트림 연결 실패 · `UT` 타임아웃 · `DC` 다운스트림이 끊음 · `NR` 라우트 없음 · `URX` 재시도 소진
> 이 두 글자면 아래 단계를 서너 개 건너뜁니다.

### 2. JVM — Kotlin/Spring Boot이면 여기가 본진

```bash

jcmd PID GC.heap_dump /tmp/h.hprof       # 힙, 최소 2장(간격 10분) 떠서 diff
```

| 덤프 | 결정적으로 잡는 것 |
| --- | --- |
| **Thread dump ×5** | 데드락, 커넥션 풀 고갈(전부 `getConnection` 대기), 외부 API 대기 스택 |

| **NMT** | `-Xmx`는 안 넘었는데 컨테이너가 OOMKilled 될 때. Metaspace / direct buffer / 스레드 스택 |
| **JFR** | 락 경합, allocation 핫스팟, 소켓 read 대기 — **운영에서 켜둘 수 있는 유일한 프로파일** |

**프로세스에 들어가지 않고 뜨는 법 (Spring Boot Actuator)**

| 엔드포인트 | 대신하는 것 |
| --- | --- |
| `/actuator/threaddump` | `jcmd Thread.print` |

> HikariCP는 `leakDetectionThreshold`를 켜두면 반납되지 않은 커넥션의 **획득 시점 스택을 로그로 덤프**해 줍니다. 커넥션 누수는 이것 하나로 대부분 끝납니다.

### 3. 프로파일링의 전제 — on-CPU인가 off-CPU인가

이 그림 하나를 깔고 가야 합니다. **스레드는 CPU 위에 있거나(on-CPU), 뭔가를 기다리거나(off-CPU) 둘 중 하나입니다.**

![스레드 상태 전이 — on-CPU와 off-CPU](images/notes/istio-in-action/8-21.avif)

*개념도 · 출처: [Brendan Gregg — Off-CPU Analysis](https://www.brendangregg.com/offcpuanalysis.html)*

CPU 프로파일러는 **왼쪽만** 봅니다. "CPU는 20%인데 응답이 3초"인 상황은 전부 오른쪽에서 벌어지므로 CPU 플레임그래프를 아무리 들여다봐도 나오지 않습니다. `wall` / `offcputime`을 따로 떠야 하는 이유가 이것입니다.

### 4. async-profiler — JVM에서 기본으로 쓸 것

JVM 프로파일러의 고전적 문제는 **safepoint bias**였습니다. `jstack` 계열은 safepoint에 도달한 스레드만 관측해서, 실제 핫스팟이 아니라 "safepoint에 잘 서는 지점"이 부풀려집니다. async-profiler는 `AsyncGetCallTrace` + `perf_events`를 써서 이 편향 없이 샘플링하고, **JVM 코드와 네이티브·커널 스택을 한 그림에** 담습니다.

![async-profiler가 만든 플레임그래프](images/notes/istio-in-action/8-22.avif)

*출처: [async-profiler 공식 저장소](https://github.com/async-profiler/async-profiler) (Apache-2.0)*

**읽는 법은 세 줄이면 끝납니다**

- **x축은 시간순이 아니라 알파벳순**입니다. 넓다 = 표본에 자주 잡혔다.
- **위로 갈수록 호출 스택의 안쪽**입니다. 맨 위 평평한 곳(leaf)이 실제로 시간을 쓴 함수입니다.
- **넓은 고원(plateau)을 찾습니다.** 뾰족한 봉우리는 대개 무해합니다.

```bash
# 붙이기 — 컨테이너 안에서 PID는 보통 1
./asprof -e cpu   -d 30 -f /tmp/cpu.html   1
./asprof -e wall  -d 30 -f /tmp/wall.html  -t 1   # ★ -t 로 스레드별 분리
./asprof -e alloc -d 30 -f /tmp/alloc.html 1
./asprof -e lock  -d 30 -f /tmp/lock.html  1

# JFR로 떠서 나중에 여러 각도로 쪼개기
./asprof -e cpu -d 60 -f /tmp/p.jfr 1
```

| 이벤트 | 언제 쓰나 | 답하는 질문 |
| --- | --- | --- |
| `-e cpu` | CPU를 태우고 있을 때 | 어느 함수가 사이클을 먹나 |
| **`-e wall`** | ★ CPU는 노는데 느릴 때 | 어디서 **기다리나** (I/O·락·외부 API) |
| `-e alloc` | GC가 자주 돌 때 | 누가 쓰레기를 만드나 |
| `-e lock` | 스레드는 많은데 처리량이 안 오를 때 | 어느 락에서 막히나 |
| `-e itimer` | `perf_events`가 막힌 컨테이너 | 대체 샘플링 수단 |

> 🐳 **컨테이너에서 쓸 때 걸리는 것들**
> - `perf_events` 접근에 **`CAP_SYS_ADMIN` 또는 `perf_event_paranoid` 완화**가 필요합니다. 막히면 `-e itimer`로 우회합니다.
> - 커널 스택까지 보려면 노드 커널 심볼이 필요합니다 — 없으면 `[unknown]` 프레임이 뜹니다.
> - JVM 옵션에 **`-XX:+UnlockDiagnosticVMOptions -XX:+DebugNonSafepoints`**를 주면 인라인된 프레임까지 정확해집니다. 운영에 미리 넣어두면 사고 때 다시 띄울 일이 없습니다.
> - 프로세스가 이미 죽었으면 못 씁니다. 그래서 아래 **상시 프로파일링**이 필요합니다.

### 5. off-CPU 플레임그래프 — "안 돌고 있던 시간"의 스택

![off-CPU 플레임그래프 예시](images/notes/istio-in-action/8-23.avif)

*개념 예시 · 출처: [Brendan Gregg — Off-CPU Analysis](https://www.brendangregg.com/offcpuanalysis.html)*

여기서 넓은 것은 **오래 기다린 것**입니다. 락 대기, 소켓 read, 디스크 I/O, 커넥션 풀 대기가 이 그림에서만 보입니다. JVM 밖(네이티브·커널)까지 포함해 보려면 bcc의 `offcputime`을 씁니다.

### 6. FlameScope — 평균에 묻힌 스파이크를 잘라낸다

![FlameScope 히트맵 화면](images/notes/istio-in-action/8-24.avif)

*출처: [Netflix/flamescope](https://github.com/Netflix/flamescope) (Apache-2.0)*

세로축이 **초 안의 밀리초**, 가로축이 **경과 초**인 히트맵입니다. 60초를 통째로 플레임그래프로 만들면 1초짜리 스파이크는 1/60로 눌려 보이지 않습니다. FlameScope는 히트맵에서 **밝은 줄무늬 구간만 드래그해 그 구간의 플레임그래프**를 뽑습니다. 주기적으로 튀는 GC·배치·타이머를 잡는 데 특히 강합니다.

### 7. 지연 히트맵 — 평균과 p99가 거짓말할 때

![지연 히트맵](images/notes/istio-in-action/8-25.avif)

*개념도 · 출처: [Brendan Gregg — Latency Heat Maps](https://www.brendangregg.com/HeatMaps/latency.html)*

분포가 **여러 덩어리(multi-modal)**로 갈라지면 평균은 아무 데도 없는 값이 됩니다. "캐시 히트 0.5ms 덩어리 + 미스 40ms 덩어리"가 섞인 것을 p99 하나로 보면 원인이 보이지 않습니다.

### 8. "오래 걸린 그 요청"만 프로파일하기

지금까지의 프로파일링에는 공통된 한계가 있습니다 — **사람이 붙어 있을 때만 뜹니다.** 새벽 3시에 한 번 튄 요청은 이미 끝났고, 30초 프로파일을 떠도 그 안에 없습니다. 여기에 대한 답이 세 갈래로 나와 있습니다.

#### (1) 상시 프로파일링 (continuous profiling)

프로파일을 **항상 낮은 오버헤드로 수집해 저장**해두고, 사고가 난 시각으로 되감아 보는 방식입니다. 메트릭·로그·트레이스에 이어 **네 번째 신호**로 자리잡았습니다.

![Pyroscope 클라이언트-서버 구조](images/notes/istio-in-action/8-26.avif)

*출처: [Grafana Pyroscope 문서](https://grafana.com/docs/pyroscope/) (2024년 판 다이어그램)*

| 도구 | 성격 |
| --- | --- |
| **Grafana Pyroscope** | 2026-04에 2.0 발표. **OTLP 프로파일 수집을 네이티브 지원**하고, SDK 없이 붙이는 eBPF 프로파일러도 제공 |
| **Parca** | eBPF 기반, 언어 무관. 쿠버네티스 친화 |
| **OTel profiling signal** | OpenTelemetry의 **네 번째 시그널**. 현재 **alpha** — 스펙이 아직 바뀝니다. 실전 투입 전 버전 고정 필요 |

#### (2) Span Profiles — 트레이스에서 프로파일로 바로 점프

**느린 스팬 옆의 "Profiles" 버튼을 누르면, 그 스팬의 시간 범위와 서비스로 좁혀진 플레임그래프가 열립니다.**

> 🔗 **동작 원리** — 프로파일 샘플에 `trace_id` / `span_id`를 레이블로 붙입니다. 그러면 "이 스팬이 살아 있던 동안 이 스레드에서 잡힌 스택"만 골라낼 수 있습니다.
> **전제** — 언어별 **span profiling bridge**(연동 패키지)를 앱에 넣어야 합니다. 이게 없으면 트레이스와 프로파일은 서로 모르는 남남입니다. Java·Go·.NET·Python용이 제공되며, **Java는 내부적으로 async-profiler를 씁니다** — 위 4절과 같은 엔진입니다.

이렇게 되면 8장의 흐름이 한 단계 더 이어집니다.

```plain text
키알리(어디가) → 그라파나(얼마나) → 예거(어느 홉에서)
                                        ↓  ← 여기가 예전엔 끊겼다
                            span profile (그 홉의 어느 함수에서)
```

#### (3) 그 순간 메서드 단위로 파고들기 — Arthas

프로파일러가 "어느 함수가 오래 걸렸나"까지 말한다면, **Arthas는 "이번 호출이 왜 오래 걸렸나"를 메서드 인자·반환값까지 보여줍니다.** 재배포도 재기동도 없이 붙습니다.

```bash
java -jar arthas-boot.jar        # 실행 중인 JVM에 붙는다

trace com.example.OrderService placeOrder '#cost > 500'   # 내부 호출별 소요시간, 500ms 넘을 때만
watch com.example.OrderService placeOrder '{params, returnObj, throwExp}' -x 2
stack com.example.Repo findById  # 이 메서드를 누가 부르나 (역추적)
profiler start -e wall           # async-profiler가 내장돼 있다
thread -b                        # 블로킹 스레드만
```

> `trace`의 `#cost` 조건이 실무에서 제일 유용합니다. **정상 호출은 버리고 느린 호출만** 잡아 그 안의 어느 라인에서 시간이 갔는지 보여줍니다. 재현되지 않는 간헐적 지연에 강합니다.

| 상황 | 고를 것 |
| --- | --- |
| 이미 지나간 사고를 되감아 본다 | 상시 프로파일링 (Pyroscope / Parca) |
| 느린 트레이스 하나를 파고든다 | Span Profile |
| 지금 재현되는 문제를 메서드까지 판다 | Arthas `trace` / async-profiler `wall` |
| 주기적으로 튀는 스파이크 | FlameScope |

### 9. 커널·프로세스 덤프

어떤 도구가 커널의 어느 지점을 보는지는 이 지도 하나로 정리됩니다.

![리눅스 관찰 도구 지도](images/notes/istio-in-action/8-27.avif)

*개념도 · 출처: [Brendan Gregg — Linux Performance](https://www.brendangregg.com/linuxperf.html)*

```bash
cat /proc/PID/limits          # FD 한도 — "Too many open files" 나기 전에
ls /proc/PID/fd | wc -l       # FD 누수 추적, 반복 측정해서 기울기를 본다
cat /proc/PID/status          # VmRSS, Threads
cat /proc/PID/stack           # 커널에서 어디에 걸려 있나
ss -tanp                      # CLOSE_WAIT 더미 = 앱이 close() 안 함
ss -lnt                       # Recv-Q가 차 있으면 accept 백로그 넘침
nstat -az | grep -i retrans   # 재전송, listen overflow, SYN drop
conntrack -S                  # insert_failed / drop = NAT 테이블 포화
dmesg -T | grep -iE 'oom|conntrack'
iptables-save                 # istio-init이 만든 REDIRECT 규칙
```

#### cgroup — p99의 숨은 범인 1순위

```bash
cat /sys/fs/cgroup/cpu.stat        # ★ throttled_time / nr_throttled
cat /sys/fs/cgroup/memory.events   # oom_kill 카운트
cat /sys/fs/cgroup/memory.current
```

> CPU limit을 걸어두고 스로틀링당하는 것을 **"네트워크가 느리다"로 오진하는 경우가 정말 많습니다.** 애플리케이션 스택 어디에도 흔적이 남지 않고, 오직 `nr_throttled`만 올라갑니다.

### 10. eBPF — bpftrace / bcc

앞의 덤프들이 **"이미 벌어진 상태의 스냅샷"**이라면, eBPF는 **"지금 벌어지는 사건을 커널에서 직접 세는 것"**입니다. 재현되지 않는 간헐적 문제에서 강합니다.

![bpftrace가 붙일 수 있는 probe 지도](images/notes/istio-in-action/8-28.avif)

*출처: [bpftrace 공식 저장소](https://github.com/bpftrace/bpftrace) (Apache-2.0). 2018년 판이지만 저장소가 지금도 싣고 있는 유일한 probe 지도이고, probe 종류 자체는 그대로입니다*

붙일 수 있는 지점이 이만큼입니다 — 커널 함수(kprobe), 유저 함수(uprobe), 트레이스포인트, USDT, 주기 샘플링. **앱을 재시작하지 않고 붙였다 뗄 수 있다**는 게 핵심입니다.

```bash
# 1. 이 노드에서 TCP 재전송이 어디로 나가나 — 네트워크 탓인지 판별
bpftrace -e 'kprobe:tcp_retransmit_skb { @[comm] = count(); }'

# 2. 파일 열기 실패 추적 — 설정파일·인증서 경로 오타
bpftrace -e 'tracepoint:syscalls:sys_exit_openat /args->ret < 0/ { @[comm, args->ret] = count(); }'

# 3. 프로세스가 왜 죽었나 — 누가 시그널을 보냈나
bpftrace -e 'tracepoint:signal:signal_generate { printf("%s -> pid %d sig %d\n", comm, args->pid, args->sig); }'

# 4. 새로 뜨는 프로세스 전부 — 사이드카·init 컨테이너가 뭘 실행하는지
bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("%s %s\n", comm, str(args->filename)); }'

# 5. 런큐 대기 — CPU 스로틀링·과밀의 실체
/usr/share/bcc/tools/runqlat 10 1
```

#### bcc 툴 지도 — 증상별로 골라 쓰는 기성품

![bcc 트레이싱 툴 지도](images/notes/istio-in-action/8-29.avif)

*출처: [iovisor/bcc](https://github.com/iovisor/bcc) (Apache-2.0). 저장소의 최신본이 2019년 판입니다 — 이후 추가된 툴은 지도에 없으니 `ls /usr/share/bcc/tools`로 실물을 확인하세요*

| 도구 | 답하는 질문 |
| --- | --- |
| `execsnoop` | 지금 뭐가 실행됐나 (짧게 살다 죽는 프로세스도 잡음) |
| `opensnoop` | 어떤 파일을 열려다 실패했나 |
| `tcpconnect` / `tcpaccept` | 누가 어디로 연결하나 — **메시 밖으로 새는 트래픽 탐지** |
| `tcpretrans` | 재전송이 실제로 나는가 (체감 vs 실측) |
| `biolatency` | 디스크 지연 분포 |
| `runqlat` | CPU를 못 받아서 기다린 시간 |
| `offcputime` | 대기 스택 → off-CPU 플레임그래프 원재료 |
| `profile` | on-CPU 스택 샘플링 → CPU 플레임그래프 원재료 |

> 🚨 **쿠버네티스에서의 전제 조건**
> - 노드 커널 기준이며 **컨테이너 안이 아니라 노드에서** 돌려야 합니다 (`kubectl debug node/NODE`).
> - `privileged` 또는 `CAP_BPF`/`CAP_PERFMON` 권한이 필요합니다 — 보안 정책이 막으면 못 씁니다.
> - 커널 5.8 미만이면 상당수 기능이 없습니다.
> - **파드를 특정하려면** cgroup ID나 PID 네임스페이스로 걸러야 합니다. 안 그러면 노드 전체가 섞여 나옵니다.

> 상시 운영으로 올릴 거면 원라이너 대신 **Cilium Hubble**(L3~L7 흐름), **OBI(구 Grafana Beyla)**(OTel 스팬 자동 생성), **Pixie**(자동 서비스맵) 같은 상주형을 씁니다. bpftrace는 **장애 현장에서 손으로 꽂는 도구**에 가깝습니다.

### 11. 네트워크 캡처 — 메시에서의 함정 포함

```bash
# istio-proxy는 non-root라 tcpdump가 안 붙는다 → 임시 컨테이너로
kubectl debug -it POD --image=nicolaka/netshoot --target=istio-proxy -- bash
tcpdump -i any -s0 -w /tmp/c.pcap 'port 8080 or port 15006'
kubectl cp POD:/tmp/c.pcap ./c.pcap    # → Wireshark로 열기
```

![Wireshark 3분할 화면](images/notes/istio-in-action/8-30.avif)

*출처: [Wikimedia Commons — Wireshark 3.6](https://commons.wikimedia.org/wiki/File:Wireshark_3.6_screenshot.png) — 현재는 4.x가 나와 있으나 자유 라이선스로 구할 수 있는 최신 스크린샷이 이것이며, 3분할 레이아웃은 4.x와 같습니다*

3분할이 전부입니다 — 위는 패킷 목록, 가운데는 계층별 해석(Ethernet → IP → TCP → HTTP), 아래는 원본 바이트. 실무에서 제일 많이 쓰는 건 **Follow TCP Stream**(한 대화만 이어붙이기)과 **Statistics → Conversations**(누가 제일 많이 주고받았나)입니다.

> 🔐 **mTLS라 캡처해도 암호문입니다.**
> 평문을 보려면 **앱 ↔ 사이드카 구간**(loopback)을 노려야 합니다 — 인바운드는 15006, 아웃바운드는 15001을 지난 뒤가 평문입니다. `tcpdump -i lo`로 잡으면 애플리케이션이 실제로 보낸 바이트를 볼 수 있습니다.

**Wireshark를 켜지 않고 끝내는 것들**

```bash
tshark -r c.pcap -z conv,tcp -q            # 대화 요약만
tshark -r c.pcap -z io,stat,1 -q           # 초당 처리량

# ★ 3초 만에 DNS/TCP/TLS/TTFB 분해 — 대부분 여기서 끝난다
curl -o /dev/null -s -w 'dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://target/

arping -I eth0 10.0.0.5                    # 같은 IP를 두 대가 쓰나 (MAC 두 개 응답)
ip neigh                                   # ARP 캐시 덤프
dig +trace example.com                     # ndots:5 로 헛질의하는지
openssl s_client -connect host:443 -servername host   # 인증서 체인·SNI
mtr -rw target                             # 중간 홉 유실
```

### 13. 8장과의 연결 — 트레이스가 끝나는 지점

![예거 트레이스 상세 화면](images/notes/istio-in-action/8-31.avif)

*출처: [Jaeger 공식 문서](https://www.jaegertracing.io/)*

예거의 이 화면이 알려주는 것은 **"어느 홉에서 얼마나"**까지입니다. 그 다음은 전부 덤프와 프로파일의 영역입니다.

| 트레이스가 말해준 것 | 이어받을 것 |
| --- | --- |
| 특정 워크로드의 스팬만 길다 | **span profile** → 없으면 스레드 덤프 ×5 + `cpu.stat` |
| 스팬 사이의 **빈 구간**이 길다 (네트워크) | 엔보이 `/clusters` → `nstat` 재전송 → `tcpdump` |
| DB 호출 스팬이 길다 | `pg_stat_activity` · `EXPLAIN (ANALYZE)` · HikariCP 풀 상태 |
| 스팬은 짧은데 전체가 느리다 | 계측 공백 — async-profiler `wall` 또는 `offcputime` |
| 어느 메서드인지까지 알아야 한다 | Arthas `trace ... '#cost > 500'` |
| 트레이스가 **아예 끊겼다** | 덤프 이전 문제 — 앱의 `x-b3-*` / `traceparent` 전파 확인 |

> 마지막 줄이 「정리하며」 5번과 같은 이야기입니다. **헤더 전파가 안 되면 덤프를 뜰 지점조차 고르지 못합니다.**

> 🖼️ **이미지 출처와 연식에 대해**
> 구글 이미지 검색 결과가 아니라 **원 저작자·프로젝트 공식 저장소에서 직접** 가져왔습니다 (async-profiler, Netflix/flamescope, bpftrace, iovisor/bcc, Grafana Pyroscope, Jaeger, Wikimedia Commons, Brendan Gregg).
> **연식이 있는 것들** — bpftrace probe 지도(2018)와 bcc 툴 지도(2019)는 각 저장소가 지금도 싣고 있는 최신본입니다. 그림은 오래됐지만 **구조는 바뀌지 않았고** 새로 추가된 툴만 지도에 없습니다. Wireshark 스크린샷(3.6)도 자유 라이선스로 구할 수 있는 최신본이며 레이아웃은 4.x와 같습니다. 스레드 상태·off-CPU·히트맵은 **개념도라 연식과 무관**합니다.
> **주의** — 각 이미지의 라이선스(Apache-2.0 / CC 등)는 원 저장소 기준입니다. 브랜든 그레그의 그림은 개인 사이트 자산이므로 상업적 재배포 전 별도 확인이 필요합니다.

## 마무리

- 8장의 도구 셋은 **질문의 층이 다릅니다.** 키알리로 "어디가", 그라파나로 "얼마나", 예거로 "어느 홉에서"를 봅니다. 하나로 다 하려 들면 각각의 강점을 잃습니다.
- **`reporter` 하나로 네트워크 구간을 분리해 볼 수 있습니다.** 클라이언트 성공률과 서버 성공률이 갈라지는 지점이 곧 메시가 개입한 지점(재시도·타임아웃·서킷 브레이커)입니다.
- **트레이싱의 실패는 조용합니다.** 헤더 전파 누락도, 잘못된 `collectorEndpoint`도 에러를 내지 않고 그냥 데이터가 없어집니다. "트레이스가 없다"를 **정상**으로 착각하지 않는 것이 이 장의 핵심 방어선입니다.
- **`app` / `version` 레이블은 관측의 전제조건**입니다. 없으면 Application 집계도, 트레이싱 식별도, 카나리 비교도 반쪽이 됩니다.
- 관측은 **어디를 팔지 정하는 것까지**입니다. 그 다음 삽은 덤프와 프로파일이고, 부록의 치트시트가 그 인계표입니다.
- 다음 장(9장)에서는 지금까지 "관찰"한 트래픽을 **보안**의 관점에서 다룹니다 — mTLS, 워크로드 신원, 인가 정책입니다.
