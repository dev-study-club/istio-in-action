이스티오가 존재하는 주요 이유는 무언가 잘못됐을 때 네트워크 통신을 조명하고 타임아웃, 재시도, 서킷 브레이커 같은 복원 기능을 배치함으로써 애플리케이션이 네트워크 문제에 자동으로 대응할 수 있도록 하기 위함이다.

프록시 자신이 예기치 못하게 작동하면 어떻게 될까?

# 데이터 플레인 문제 식별하기

첫 단계는 컨트롤 플레인과 데이터 플레인이 동기화된 상태인지 확인하는 것이다.

## 데이터 플레인이 최신 상태인지 확인하는 방법

데이터 플레인 설정은 설계상 궁극적으로 일관성을 가진다.

즉, 환경(서비스, 엔드포인트, 상태)이나 설정의 변화는 컨트롤 플레인과 적절히 동기화하기 전까지는 데이터 플레인에 즉시 반영되지 않는다.

![컨트롤 플레인과 데이터 플레인의 동기화 흐름](images/notes/istio-in-action/지민/10-2.png)

```bash
istioctl proxy-status
```

- SYNCED: istiod가 보낸 마지막 설정을 엔보이가 확인했다.
- NOT SENT: istiod가 아무것도 엔보이로 보내지 않았다. 보통은 istiod가 보낼 것이 없기 때문이다.
- STALE: istiod가 엔보이에 업데이트를 보냈지만 확인받지 못했다. istiod가 과부하됐거나, 엔보이와 istiod 사이의 커넥션 부족 또는 끊김이거나, 이스티오의 버그다.

키알리를 사용하면 설정을 빠르게 검증할 수 있다.

## 키알리로 잘못된 설정 발견하기

```bash
istioctl dashboard kiali
```

식별한 오류의 설명, 심각도, 해결책을 알려준다.

키알리 검증은 도움이 되므로, 워크로드가 예상대로 동작하지 않을 때 취하는 첫 조치 중 하나여야 한다.

## istioctl로 잘못된 설정 발견하기

잘못 설정된 워크로드를 자동으로 트러블슈팅하는 데 가장 유용한 istioctl 명령어 두 가지는 `istioctl analyze`와 `istioctl describe`이다.

### istioctl로 이스티오 설정 분석하기

`istioctl analyze` 명령어는 이스티오 설정을 분석하는 강력한 진단 도구다. 이미 문제가 발생한 클러스터에 실행하거나, 리소스를 잘못 구성하는 것을 방지하고자 클러스터에 적용하기 전에 설정이 유효한지 검사할 수 있다.

```bash
istioctl analyze -n istioinaction
```

### 워크로드별로 설정 오류 찾기

describe는 워크로드 하나에 직간접적으로 영향을 미치는 이스티오 설정을 분석해 요약 내용을 출력한다.

- 이 워크로드는 서비스 메시의 일부인가?
- 어떤 VirtualService와 DestinationRule이 적용되는가?
- 상호 인증 트래픽을 요구하는가?

```bash
istioctl x describe pod catalog-68666d4988-vqhmb
```

## istioctl로 프록시 설정 쿼리하기

`istioctl proxy-config` 명령어를 사용하면 엔보이 xDS API를 기반으로 워크로드의 프록시 설정을 가져오고 필터링할 수 있다.

### 요청을 라우팅하기 위한 엔보이 API의 상호작용

![리스너 → 루트 → 클러스터 → 엔드포인트로 이어지는 라우팅](images/notes/istio-in-action/지민/10-3.png)

- 리스너
    - 네트워크 설정(다운스트림 트래픽을 프록시로 허용하는 IP 주소 및 포트 등)을 정의
    - 허용된 커넥션에 HTTP 필터 체인이 만들어진다.
    - 체인에서 가장 중요한 필터는 라우터 필터로, 고급 라우팅 작업을 수행
- 루트
    - 가상 호스트를 클러스터에 일치시키는 규칙 집합
    - 순서대로 처리됨
- 클러스터
    - 각 클러스터에는 유사한 워크로드에 대한 엔드포인트 그룹이 있다. 부분집합은 클러스터 내에서 워크로드를 더 분할하는 데 사용하며 덕분에 정밀한 트래픽 관리가 가능해진다.
- 엔드포인트
    - 요청을 처리하는 워크로드의 IP 주소
