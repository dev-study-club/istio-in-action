# 7장. 관찰 가능성: 서비스의 동작 이해하기

애플리케이션을 수십, 수백개 혹은 그 이상의 서비스로 배포하기 시작하면 움직이는 부분의 수, 네트워크에 대한 의존도, 잘못될 수 있고 또 실제로 잘못되는 것들의 개수가 모두 늘어난다.

애플리케이션을 좀 더 안정적이고 복원력 있게 구축해야 할 뿐 아니라, 애플리케이션이 실행 중일 때 실제로 어떤 일이 일어나고 있는지 이해할 수 있도록 도구와 계측 기법도 개선해야 한다.

런타임에 서비스와 인프라에 어떤 일이 일어나고 있는지 자신 있게 이해할 수 있다면 예상치 못한 것을 봤을 때 장애를 감지하고 디버깅에 깊이 파고들 수 있다.

# 관찰 가능성이란 무엇인가?

관찰 가능성은 시스템의 특성 중 하나로, 외부 신호와 특성만 보고도 시스템의 내부 상태를 이해하고 추론할 수 있는 수준을 나타낸다.

언제 시스템이 잘 동작하는지 이해해야 시스템에 문제가 생겼을 때 이를 판단할 수 있고 상술한 역동성을 유지할 수 있는 적절한 수준의 자동 및 수동 제어를 구현할 수 있다.

이스티오는 트래픽 전환, 복원력, 정책 강제 등 제어를 구현하는 데 도움이 될 수 있다.

## 관찰 가능성 vs 모니터링

모니터링이란 메트릭, 로그, 트레이스 등을 수집 및 집계하고 신중하게 지켜봐야 하는 시스템 상태를 미리 정의한 기준과 비교하는 관행을 말한다.

모니터링은 관찰 가능성의 부분집합이다.

모니터링에서는 바람직하지 않다고 알려진 상태를 감시하고 경고하고자, 특히 메트릭을 수집하고 집계하고 있다. 반면에 관찰 가능성은 시스템을 예측하기 매우 어려운 것으로 보기에 일어날 수 있는 모든 고장을 사전에 알수는 없다고 가정한다.

## 이스티오는 어떻게 관찰 가능성을 돕는가?

관찰 가능한 시스템을 구축하는 데 도움을 줄 수 있는 독특한 위치에 있다.

이스티오의 데이터 플레인 프록시, 엔보이가 서비스 간 네트워크 요청 경로에 자리하고 있기 떄문이다.

이스티오에는 프로메테우스, 그라파나, 키알리 등과 같은 기본 샘플 도구가 포함돼 있어 서비스 메시와 서비스 메시가 알고 있는 서비스의 상태를 시각화하고 탐색하는 데 도움이 된다.

```jsx
cd istio-1.13.0
kubectl delete -f samples/addons/
```

# 이스티오 메트릭 살펴보기

이스티로의 데이터 플레인은 요청을 처리하고, 컨트롤 플레인은 데이터 플레인이 요청을 처리하도록 설정한다.

## 데이터 플레인의 메트릭

엔보이는 커넥션, 요청, 런타임 메트릭을 다양하게 갖추고 있으며, 이들을 사용해 서비스의 네트워크 및 통신 상태를 파악할 수 있다. 

이전 장에서 사용했던 것들 정리

```jsx
kubectl config set-context $(kubectl config current-context) --namespace=istioinaction
```

```jsx
kubectl delete virtualservice,deployment,service,destinationrule,gateway --all
```

```jsx
kubectl apply -f services/catalog/kubernetes/catalog.yaml
```

```jsx
kubectl apply -f services/webapp/kubernetes/webapp.yaml
```

```jsx
kubectl apply -f services/webapp/istio/webapp-catalog-gw-vs.yaml
```

```jsx
curl -H "Host: webapp.istioinaction.io" http://localhost/api/catalog
```

```jsx
kubectl get pod
```

```jsx
kubectl exec -it deploy/webapp -c istio-proxy -- curl localhost:15000/stats
```

사이드카 프록시가 보관하는 정보가 엄청나게 많다. 

### 프록시가 엔보이 통계를 더 많이 보고하도록 설정하기

네트워크 동작을 트러블슈팅하려면 표준 이스티오 메트릭보다 더 많은 정보를 확인해야 할 때가 있다.

애플리케이션의 호출이 자신의 클라이언트 측 프록시를 거쳐갈 때, 프록시는 라우팅 결정을 내리고 업스트림 클러스터로 라우팅한다.

메시 전체에서 수집하는 메트릭을 늘리면 메트릭 수집 시스템을 과부하 상태로 만들 수 있으므로 아주 신중하게 적용해야 한다. 더 나은 방법은 워크로드별로 애노테이션으로 포함할 메트릭을 지정하는 것이다.

```jsx
kubectl apply -f ch7/webapp-deployment-stats-inclusion.yaml
```

```jsx
curl -H "Host: webapp.istioinaction.io" http://localhost/api/catalog
```

```jsx
kubectl exec -it deploy/webapp -c istio-proxy -- curl localhost:15000/stats | grep catalog
```

```jsx
kubectl exec -it deploy/webapp -c istio-proxy -- curl localhost:15000/clusters
```

```jsx
kubectl exec -it deploy/webapp -c istio-proxy -- curl localhost:15000/clusters | grep catalog
```

프록시는 메트릭을 잘 수집하고 있지만, 이것을 보자고 각 서비스 인스턴스와 프록시로 가고 싶지는 않다. 이스티오 서비스 프록시는 프로메테우스나 데이터독 같은 메트릭 수집 시스템으로 긁어갈 수 있다. 

## 컨트롤 플레인의 메트릭

컨트롤 플레인 메트릭을 보자

```jsx
kubectl exec -it -n istio-system deploy/istiod -- curl localhost:15014/metrics
```

지금까지 데이터 플레인과 컨트롤 플레인이 내부에서 일어나는 일을 얼마나 자세히 보고하는지를 설명했다. 이런 세부 사항을 노출하는 것은 관찰 가능한 시스템을 구축하는 데 중요하다.

이 메트릭을 어떻게 활용할지를 고민해봐야 한다. 이 메트릭들을 얻자고 데이터 플레인이나 컨트롤 플레인의 각 구성 요소에 일일이 접근하는 것은 비현실적이다.

# 프로메테우스로 이스티오 메트릭 긁어오기

프로메테우스는 사운드클라우드에서 시작된 메트릭 수집 엔진이자 관련 모니터링 및 alert 도구 집합이며, 구글의 내부 모니터링 시스템 Borgmon에 어느 정도 기반을 두고 있다.

에이전트가 메트릭을 ‘밀어넣기’를 기대하기보다 목표에서 메트릭을 ‘당겨오기’ 때문이다.

프로메테우스를 사용하면, 우리의 애플리케이션 또는 이스티오 서비스 프록시가 최신 메트릭을 포함하는 엔드포인트를 제공하고 프로메테우스가 그 정보를 끌어오거나 긁어올 수 있도록 한다.

!image.png

프로메테우스를 사용하는 이점 중 하나는 단순 HTTP 클라이언트나 웹 브라우저를 사용해 메트릭 엔드포인트를 살펴볼 수 있다는 것이다.

```jsx
kubectl get pod
```

```jsx
kubectl exec -it deploy/webapp -c istio-proxy -- curl localhost:15090/stats/prometheus
```

# 이스티오 표준 메트릭 커스터마이징하기

1. 메트릭
    
    서비스 호출간 텔레메트리의 카운터나 게이지, 히스토그램/분포
    
2. 디멘션
3. 속성
